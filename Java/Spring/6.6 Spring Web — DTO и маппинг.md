## О чём эта статья

Возвращать JPA-сущность напрямую из контроллера — путь к утечке паролей, поломке API и `LazyInitializationException`. # Часть 1. Проблема

## 1. Введение и проблема Entity в API

**[Уровень: Intern/Junior]**

В статье 6.5 мы построили полный CRUD и уже использовали простой DTO с ручным маппингом — это был шаг в правильном направлении. Но чтобы понять **почему** DTO обязателен, посмотрим, что произойдёт без него.

Наша сущность — `User`. Обратите внимание на поле `passwordHash` — оно присутствует намеренно, чтобы наглядно показать главную проблему:

```java
package com.example.model;

import jakarta.persistence.*;
import java.time.LocalDateTime;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String firstName;

    @Column(nullable = false)
    private String lastName;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(nullable = false)
    private String passwordHash; // ← Это поле НИКОГДА не должно попасть в API

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private Role role;

    private LocalDateTime createdAt;
    private LocalDateTime updatedAt;

    // Конструкторы, геттеры, сеттеры опущены для краткости

    public enum Role { USER, ADMIN, MODERATOR }
}
```

Теперь представим «наивный» контроллер, возвращающий Entity напрямую:

Java

```
package com.example.controller;

import com.example.model.User;
import com.example.repository.UserRepository;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/api/users")
public class UserController {

    private final UserRepository userRepository;

    public UserController(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    // ❌ ОПАСНО: возвращаем Entity напрямую из контроллера
    @GetMapping("/{id}")
    public User getUser(@PathVariable Long id) {
        return userRepository.findById(id).orElseThrow();
    }
}
```

Код компилируется. Тесты проходят. Но теперь откройте DevTools в браузере, перейдите на вкладку Network и кликните на любой GET-запрос к вашему API — вот что увидит **каждый** пользователь приложения:

JSON

```
{
    "id": 1,
    "firstName": "Иван",
    "lastName": "Петров",
    "email": "ivan@example.com",
    "passwordHash": "$2a$10$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy",
    "role": "USER",
    "createdAt": "2024-01-15T10:30:00",
    "updatedAt": "2024-06-20T14:22:00"
}
```

> ⚠️ **Антипаттерн: возврат Entity из контроллера**
> 
> Хеш пароля виден любому, кто откроет DevTools. Злоумышленник может использовать его для offline-атаки методом перебора (brute-force) или по rainbow tables. Кроме того, утекли `updatedAt` и `role` — поля, раскрывающие внутреннюю структуру системы.

Это не единственная проблема. Вот пять причин, по которым Entity нельзя возвращать из API:

### 1.1. Утечка чувствительных данных

Jackson сериализует **все** поля Entity. Каждое новое поле, добавленное разработчиком в сущность, автоматически попадает в API — без ревью, без осознанного решения.

### 1.2. Mass Assignment — атака через десериализацию

При приёме Entity как `@RequestBody` злоумышленник добавляет в JSON произвольные поля:

Java

```
// ❌ ОПАСНО: принимаем Entity как RequestBody
@PostMapping
public User create(@RequestBody User user) {
    return userRepository.save(user);
}
```

Атакующий отправляет:

JSON

```
{
    "firstName": "Хакер",
    "email": "hacker@evil.com",
    "role": "ADMIN",
    "passwordHash": "my_controlled_hash"
}
```

Jackson послушно десериализует `role: "ADMIN"` и `passwordHash` прямо в Entity. Мы сохраняем в базу — злоумышленник стал администратором с контролируемым паролем.

### 1.3. LazyInitializationException и N+1

Если `User` имеет связь `@OneToMany(fetch = FetchType.LAZY) List<Order> orders`, Jackson при сериализации вызовет `getOrders()`. Hibernate попытается загрузить данные, но транзакция уже закрыта — получим `LazyInitializationException`. Либо, при включённом OSIV (Open Session In View), получим N+1 SELECT: один запрос на список пользователей + N запросов на связанные сущности каждого из них.

### 1.4. API привязан к схеме БД

Переименовали колонку в базе — сломали API-контракт для всех клиентов. DTO создаёт буферный слой: внутренние изменения схемы не затрагивают внешний контракт.

### 1.5. Невозможность версионирования и кастомизации

Entity не может одновременно вернуть `name: "Иван Петров"` для API v1 и `firstName: "Иван"`, `lastName: "Петров"` для API v2. Также Entity не содержит вычисляемых полей (`fullName`, `orderCount`), которые часто нужны фронтенду.

> 💡 **Важно знать**
> 
> Все пять проблем решаются одним архитектурным решением — **паттерном DTO**. Entity остаётся внутренним объектом слоя данных. Наружу уходит только то, что мы осознанно включили в DTO.

# Часть 2. DTO как решение

## 2. Что такое DTO: определение и виды

**[Уровень: Intern/Junior]**

### 2.1. Определение

**DTO (Data Transfer Object)** — паттерн из книги Мартина Фаулера _«Patterns of Enterprise Application Architecture»_ (2002):

> DTO — объект, который переносит данные между слоями. Не содержит бизнес-логики — только данные и аксессоры.

Ключевая идея: DTO **изолирует** внутреннее представление данных от внешнего. Мы контролируем, какие поля видит клиент, в каком формате и под какими именами.

### 2.2. Поток данных в слоистой архитектуре

text

```
 POST /api/users
 Body: {"firstName":"Иван", "email":"ivan@example.com", "password":"secret"}
       │
       ▼
┌─────────────────────────────────────────────────────────────────────┐
│                         Controller Layer                            │
│  @Valid @RequestBody UserCreateRequest request                      │
│  Jackson: JSON → UserCreateRequest (десериализация)                 │
│  Bean Validation: проверка @NotBlank, @Email, @Size                 │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ UserCreateRequest (Request DTO)
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│                          Service Layer                              │
│  User entity = mapper.toEntity(request)    // Request DTO → Entity  │
│  entity.setPasswordHash(encode(password))  // Сервис добавляет хеш  │
│  entity.setRole(Role.USER)                 // Сервис задаёт роль    │
│  entity.setCreatedAt(LocalDateTime.now())  // Сервис задаёт дату    │
│  User saved = repository.save(entity)      // Сохраняем в БД        │
│  return mapper.toResponse(saved)           // Entity → Response DTO  │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ UserResponse (Response DTO)
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│                         Controller Layer                            │
│  return UserResponse                                                │
│  Jackson: UserResponse → JSON (сериализация)                        │
└──────────────────────────────┬──────────────────────────────────────┘
                               │
                               ▼
 {"id":1,"firstName":"Иван","email":"ivan@example.com","role":"USER"}
 ✅ Нет passwordHash!  ✅ Нет password!  ✅ Только нужные поля.
```

**Request DTO** — данные от клиента. Содержит аннотации валидации (`@NotBlank`, `@Email`, `@Size`). Только те поля, которые клиент имеет право передать.

**Response DTO** — данные для клиента. Без `passwordHash`, без внутренних полей. Может содержать вычисляемые поля.

### 2.3. Сводная таблица всех DTO статьи

|DTO-класс|Назначение|HTTP-операция|Поля|
|---|---|---|---|
|`UserCreateRequest`|Создание пользователя|`POST /api/users`|`firstName`, `lastName`, `email`, `password`|
|`UserUpdateRequest`|Частичное обновление|`PATCH /api/users/{id}`|`firstName`, `lastName`|
|`UserResponse`|Полная информация|`GET /api/users/{id}`|`id`, `firstName`, `lastName`, `email`, `role`, `createdAt`|
|`UserSummaryResponse`|Краткая информация для списка|`GET /api/users`|`id`, `firstName`, `lastName`|

> ⚠️ **Антипаттерн: один DTO на все операции**
> 
> Один `UserDto` с 20 полями для создания, обновления и ответа — антипаттерн. Поле `id` бессмысленно при создании, `password` опасен в ответе, `createdAt` не нужен при обновлении. Каждая операция заслуживает своего DTO с минимально необходимым набором полей.

### 2.4. DTO vs Entity vs Value Object vs POJO

|Критерий|DTO|Entity|Value Object|POJO|
|---|---|---|---|---|
|**Идентичность**|Нет|Есть (ID/PK)|Нет|Нет|
|**Бизнес-логика**|Нет|Да|Да|Возможна|
|**Мутабельность**|Предпочтительно immutable|Mutable|Immutable|Любая|
|**Жизненный цикл**|Транзитный (один запрос)|Персистентный|Транзитный|Любой|
|**Слой**|Транспортный|Persistence|Domain|Любой|
|**Пример**|`UserResponse`|`User`|`Money`, `Email`|Любой бин|

## 3. Java Records как идеальный DTO

**[Уровень: Junior/Middle]**

### 3.1. Record vs обычный класс

Java Records (JEP 395, Java 16+) — встроенный механизм языка для создания иммутабельных классов данных. Сравним:

text

```
┌──────────────────────────────────────┬────────────────────────────────────┐
│   Обычный класс — 50+ строк          │   Record — 7 строк                 │
│                                      │                                    │
│   public class UserResponse {        │   public record UserResponse(      │
│       private final Long id;         │       Long id,                     │
│       private final String firstName;│       String firstName,            │
│       private final String lastName; │       String lastName,             │
│       private final String email;    │       String email,                │
│       private final String role;     │       String role,                 │
│       private final LocalDateTime    │       LocalDateTime createdAt      │
│           createdAt;                 │   ) {}                             │
│                                      │                                    │
│       // Конструктор — 8 строк       │   Компилятор генерирует:           │
│       // 6 геттеров  — 18 строк      │   ✅ Конструктор со всеми полями   │
│       // equals()    — 10 строк      │   ✅ Геттеры без get-префикса:     │
│       // hashCode()  — 6 строк       │      id(), firstName(), email()    │
│       // toString()  — 5 строк       │   ✅ equals() по всем полям        │
│   }                                  │   ✅ hashCode() по всем полям      │
│                                      │   ✅ toString() с именами полей    │
│   Итого: ~50 строк                   │   Итого: 7 строк                   │
└──────────────────────────────────────┴────────────────────────────────────┘
```

### 3.2. Создание Response DTO через Record

Java

```
package com.example.dto;

import java.time.LocalDateTime;

// Record — идеальный Response DTO: иммутабельный, компактный, без boilerplate
public record UserResponse(
        Long id,
        String firstName,
        String lastName,
        String email,
        String role,
        LocalDateTime createdAt
) {}
```

Использование:

Java

```
// Создание — через канонический конструктор
UserResponse response = new UserResponse(
        1L, "Иван", "Петров", "ivan@example.com", "USER", LocalDateTime.now()
);

// Геттеры — без get-префикса
response.id();        // 1L
response.firstName(); // "Иван"
response.email();     // "ivan@example.com"

// Нет сеттеров — объект неизменяем после создания
// response.setFirstName("Другое"); // ❌ не скомпилируется
```

### 3.3. Compact constructor для валидации

Record поддерживает компактный конструктор — форму каноничного конструктора без явного перечисления параметров. Используется для валидации и нормализации входных данных:

Java

```
package com.example.dto;

import java.util.Objects;

public record UserSummaryResponse(
        Long id,
        String firstName,
        String lastName
) {
    // Компактный конструктор: параметры доступны без объявления
    public UserSummaryResponse {
        Objects.requireNonNull(id, "id не может быть null");
        // Нормализация: убираем лишние пробелы
        firstName = firstName != null ? firstName.trim() : "";
        lastName  = lastName  != null ? lastName.trim()  : "";
    }
}
```

### 3.4. Ограничения Records

Records **не могут** использоваться как JPA Entity по следующим причинам:

- Все поля `final` — Hibernate требует мутабельность для управления состоянием proxy-объектов
- Нет no-arg конструктора — JPA-спецификация требует его наличия
- Нельзя наследоваться от класса — Records неявно наследуют `java.lang.Record`
- Нет Builder-паттерна из коробки — неудобно при 10+ полях

> 💡 **Важно знать**
> 
> В Hibernate 6+ (поставляется со Spring Boot 3) Records допустимы как `@Embeddable`-компоненты — встраиваемые объекты без собственного идентификатора. Однако корневой `@Entity` Record быть не может.
> 
> **Рекомендация:** используйте Records для **Response DTO** в Java 17+ проектах — это наиболее идиоматичный и безопасный подход.

## 4. Lombok в DTO: что и когда использовать

**[Уровень: Junior/Middle]**

Для Request DTO нужны: no-arg конструктор (Jackson десериализация) и Builder (удобство в тестах). Records это не обеспечивают. Здесь на помощь приходит Lombok.

### 4.1. UserCreateRequest с Lombok

Java

```
package com.example.dto;

import jakarta.validation.constraints.*;
import lombok.*;

@Getter                        // Генерирует геттеры для всех полей
@NoArgsConstructor             // Нужен для Jackson десериализации
@AllArgsConstructor            // Нужен для работы @Builder
@Builder                       // Паттерн Builder — удобен в тестах
public class UserCreateRequest {

    @NotBlank(message = "Имя обязательно")
    @Size(min = 2, max = 50, message = "Имя: от 2 до 50 символов")
    private String firstName;

    @NotBlank(message = "Фамилия обязательна")
    @Size(min = 2, max = 50)
    private String lastName;

    @NotBlank(message = "Email обязателен")
    @Email(message = "Некорректный формат email")
    private String email;

    @NotBlank(message = "Пароль обязателен")
    @Size(min = 8, max = 100, message = "Пароль: от 8 до 100 символов")
    private String password;
}
```

### 4.2. UserUpdateRequest с Lombok

Java

```
package com.example.dto;

import jakarta.validation.constraints.Size;
import lombok.*;

@Getter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class UserUpdateRequest {

    @Size(min = 2, max = 50)
    private String firstName; // null означает "не обновлять"

    @Size(min = 2, max = 50)
    private String lastName;  // null означает "не обновлять"
}
```

### 4.3. Альтернативный Response DTO с @Value (Java < 16)

Если проект использует Java ниже 16 и Records недоступны:

Java

```
package com.example.dto;

import lombok.Value;
import java.time.LocalDateTime;

@Value // Все поля private final, только геттеры, equals/hashCode/toString
public class UserResponseLombok {
    Long id;
    String firstName;
    String lastName;
    String email;
    String role;
    LocalDateTime createdAt;
}
// response.setFirstName("...") — ❌ не скомпилируется, нет сеттеров
```

### 4.4. Какой Lombok для какого DTO

|DTO|Аннотации Lombok|Почему|
|---|---|---|
|**Request DTO**|`@Getter` + `@NoArgsConstructor` + `@AllArgsConstructor` + `@Builder`|Jackson десериализация + Builder для тестов|
|**Response DTO (Java < 16)**|`@Value`|Иммутабельность, нет сеттеров|
|**Response DTO (Java 17+)**|**Record** (без Lombok)|Встроенная иммутабельность, нет лишних зависимостей|

> 💡 **Важно знать**
> 
> Не используйте `@Data` для Response DTO — он генерирует сеттеры, нарушая иммутабельность. Не используйте `@Value` для Request DTO — без no-arg конструктора Jackson не сможет десериализовать объект при использовании стандартных настроек.

# Часть 3. Маппинг

## 5. Ручной маппинг

**[Уровень: Junior]**

В статье 6.5 мы уже писали ручной маппинг. Разберём два способа его организации и определим, когда каждый из них оправдан.

### 5.1. Mapper как класс со статическими методами

Java

```
package com.example.mapper;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import com.example.dto.UserSummaryResponse;
import com.example.model.User;

import java.util.List;

public final class UserManualMapper {

    // Утилитный класс — экземпляры не нужны
    private UserManualMapper() {}

    public static UserResponse toResponse(User user) {
        if (user == null) {
            return null;
        }
        return new UserResponse(
                user.getId(),
                user.getFirstName(),
                user.getLastName(),
                user.getEmail(),
                user.getRole().name(),   // Enum → String
                user.getCreatedAt()
        );
    }

    public static UserSummaryResponse toSummaryResponse(User user) {
        if (user == null) {
            return null;
        }
        return new UserSummaryResponse(
                user.getId(),
                user.getFirstName(),
                user.getLastName()
        );
    }

    public static List<UserResponse> toResponseList(List<User> users) {
        if (users == null) {
            return List.of();
        }
        return users.stream()
                .map(UserManualMapper::toResponse)
                .toList();
    }

    public static User toEntity(UserCreateRequest request) {
        if (request == null) {
            return null;
        }
        User user = new User();
        user.setFirstName(request.getFirstName());
        user.setLastName(request.getLastName());
        user.setEmail(request.getEmail());
        // passwordHash — устанавливается в сервисе после хеширования
        // role        — устанавливается в сервисе (дефолт USER)
        // id          — генерируется базой данных
        // createdAt   — устанавливается в сервисе
        return user;
    }
}
```

### 5.2. Когда ручной маппинг оправдан

**Подходит:**

- Маленький проект (до 5 Entity)
- Очень специфичная логика (обращение к внешнему сервису, сложные вычисления)
- Нет желания добавлять зависимость от MapStruct

**Не подходит:**

- 10+ Entity с множеством полей — рутина и высокий риск ошибок
- Часто меняющаяся модель — при каждом новом поле нужно обновлять маппер вручную
- Командная разработка — стиль маппинга у разных авторов будет отличаться

Представьте: в проекте 15 Entity, каждая с 12 полями. Это 15 × 3 метода × 12 строк = **~540 строк** рутинного кода. Добавили поле в Entity — нужно вспомнить обновить маппер. Забыли — баг на продакшне. MapStruct решает эту проблему кардинально.

## 6. MapStruct: подключение и базовый маппинг

**[Уровень: Middle]**

### 6.1. Что такое MapStruct и почему он быстрее

MapStruct — annotation processor, который генерирует обычный Java-код маппинга **во время компиляции**. В runtime выполняются те же вызовы геттеров и сеттеров, что вы бы написали вручную — никакой рефлексии, никаких proxy.

text

```
┌──────────────────────────────────┬──────────────────────────────────┐
│  MapStruct (compile-time)        │  ModelMapper (runtime)           │
├──────────────────────────────────┼──────────────────────────────────┤
│  @Mapper interface               │  modelMapper.map(src, Dst.class) │
│       │                          │       │                          │
│       │ annotation processor     │       │ каждый вызов map()       │
│       ▼                          │       ▼                          │
│  XxxMapperImpl.java              │  Java Reflection API             │
│  (обычный Java-код)              │  Анализ полей через getFields()  │
│       │                          │  Matching по именам              │
│       │ JIT-оптимизация          │  Создание экземпляра             │
│       ▼                          │       │                          │
│  user.getFirstName() вызовы      │       ▼                          │
│  = как ручной маппинг            │  ~25x медленнее MapStruct        │
│  ~22 млн ops/сек                 │  ~830 тыс ops/сек                │
└──────────────────────────────────┴──────────────────────────────────┘
```

### 6.2. Подключение MapStruct к Spring Boot 3.x

    </plugins>
</build>

### 6.3. Первый MapStruct-маппер

Java

```
package com.example.mapper;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import com.example.dto.UserSummaryResponse;
import com.example.model.User;
import org.mapstruct.Mapper;
import org.mapstruct.Mapping;
import org.mapstruct.MappingConstants;
import org.mapstruct.ReportingPolicy;

import java.util.List;

@Mapper(
    // MappingConstants.ComponentModel.SPRING — добавляет @Component к impl-классу
    // Маппер становится Spring Bean: можно инжектировать через конструктор
    componentModel = MappingConstants.ComponentModel.SPRING,

    // ReportingPolicy.ERROR — если поле Target не имеет маппинга и нет ignore=true,
    // компиляция УПАДЁТ с ошибкой. Защита от забытых полей.
    unmappedTargetPolicy = ReportingPolicy.ERROR
)
public interface UserMapper {

    // ===== Entity → Response DTO =====

    // Поля с одинаковыми именами маппятся автоматически:
    // id, firstName, lastName, email, createdAt
    @Mapping(target = "role", expression = "java(user.getRole().name())")
    UserResponse toResponse(User user);

    // Для Summary — MapStruct берёт только id, firstName, lastName
    UserSummaryResponse toSummaryResponse(User user);

    // Коллекции — MapStruct генерирует цикл автоматически
    // на основе метода toResponse(User)
    List<UserResponse> toResponseList(List<User> users);
    List<UserSummaryResponse> toSummaryResponseList(List<User> users);

    // ===== Request DTO → Entity =====

    @Mapping(target = "id",           ignore = true) // БД генерирует
    @Mapping(target = "passwordHash", ignore = true) // Устанавливается в сервисе
    @Mapping(target = "role",         ignore = true) // Роль задаётся в сервисе
    @Mapping(target = "createdAt",    ignore = true) // Устанавливается в сервисе
    @Mapping(target = "updatedAt",    ignore = true) // Устанавливается в сервисе
    User toEntity(UserCreateRequest request);
}
```

**Ключевые аннотации:**

- **`componentModel = MappingConstants.ComponentModel.SPRING`** — MapStruct добавит `@Component` к сгенерированному классу, и он станет Spring Bean. Не используйте устаревшую строковую форму `"spring"`.
- **`unmappedTargetPolicy = ReportingPolicy.ERROR`** — если в целевом объекте есть поле без маппинга и без `ignore = true`, компиляция **не пройдёт**.
- **`expression = "java(...)"`** — произвольное Java-выражение для маппинга поля.
- **`ignore = true`** — явно исключает поле из маппинга.

### 6.4. Использование маппера в сервисе

Java

```
package com.example.service;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import com.example.dto.UserSummaryResponse;
import com.example.mapper.UserMapper;
import com.example.model.User;
import com.example.repository.UserRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.time.LocalDateTime;
import java.util.List;

@Service
public class UserService {

    private final UserRepository userRepository;
    private final UserMapper userMapper; // Spring @Autowired через конструктор

    public UserService(UserRepository userRepository, UserMapper userMapper) {
        this.userRepository = userRepository;
        this.userMapper = userMapper;
    }

    // Маппинг Entity → DTO происходит ВНУТРИ сервиса, пока транзакция активна
    @Transactional(readOnly = true)
    public UserResponse findById(Long id) {
        User user = userRepository.findById(id)
                .orElseThrow(() -> new RuntimeException("User not found: " + id));
        return userMapper.toResponse(user); // Entity → Response DTO
    }

    @Transactional(readOnly = true)
    public List<UserSummaryResponse> findAll() {
        return userMapper.toSummaryResponseList(userRepository.findAll());
    }

    @Transactional
    public UserResponse create(UserCreateRequest request) {
        User user = userMapper.toEntity(request);           // DTO → Entity
        user.setPasswordHash(hashPassword(request.getPassword())); // Хеш в сервисе
        user.setRole(User.Role.USER);                        // Роль в сервисе
        user.setCreatedAt(LocalDateTime.now());

        User saved = userRepository.save(user);
        return userMapper.toResponse(saved);                 // Entity → DTO
    }

    private String hashPassword(String rawPassword) {
        // В реальном проекте — BCryptPasswordEncoder из Spring Security
        return "$2a$10$hashed_" + rawPassword;
    }
}
```

> 🔬 **Под капотом: что генерирует MapStruct**
> 
> После `mvn compile` MapStruct создаёт файл `target/generated-sources/annotations/com/example/mapper/UserMapperImpl.java`. Откройте его и убедитесь — это обычный Java-код:

Java

```
package com.example.mapper;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import com.example.dto.UserSummaryResponse;
import com.example.model.User;
import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;
import javax.annotation.processing.Generated;
import org.springframework.stereotype.Component;

// ← MapStruct добавил @Generated для трассировки
@Generated(value = "org.mapstruct.ap.MappingProcessor", date = "2024-01-15")
// ← @Component: маппер теперь Spring Bean, доступен для @Autowired
@Component
public class UserMapperImpl implements UserMapper {

    @Override
    public UserResponse toResponse(User user) {
        // ← null-safety: всегда проверяет входящий объект первым делом
        if (user == null) {
            return null;
        }

        // ← Обычные вызовы геттеров — никакой рефлексии в runtime
        Long id = user.getId();
        String firstName = user.getFirstName();
        String lastName = user.getLastName();
        String email = user.getEmail();
        LocalDateTime createdAt = user.getCreatedAt();

        // ← expression = "java(user.getRole().name())" из @Mapping
        String role = user.getRole().name();

        // ← Вызов канонического конструктора Record
        // passwordHash НЕ передаётся — @Mapping(ignore = true)
        return new UserResponse(id, firstName, lastName, email, role, createdAt);
    }

    @Override
    public UserSummaryResponse toSummaryResponse(User user) {
        // ← null-safety для каждого метода
        if (user == null) {
            return null;
        }
        // ← Маппит только поля, присутствующие в UserSummaryResponse
        return new UserSummaryResponse(
            user.getId(),
            user.getFirstName(),
            user.getLastName()
        );
    }

    @Override
    public List<UserResponse> toResponseList(List<User> users) {
        if (users == null) {
            return null;
        }
        // ← MapStruct сгенерировал цикл, переиспользуя метод toResponse()
        // initial capacity оптимизирует выделение памяти
        List<UserResponse> list = new ArrayList<>(users.size());
        for (User user : users) {
            list.add(toResponse(user)); // ← Переиспользует toResponse
        }
        return list;
    }

    @Override
    public List<UserSummaryResponse> toSummaryResponseList(List<User> users) {
        if (users == null) {
            return null;
        }
        List<UserSummaryResponse> list = new ArrayList<>(users.size());
        for (User user : users) {
            list.add(toSummaryResponse(user)); // ← Переиспользует toSummaryResponse
        }
        return list;
    }

    @Override
    public User toEntity(UserCreateRequest request) {
        if (request == null) {
            return null;
        }
        User user = new User();
        // ← Маппит только поля без ignore = true
        user.setFirstName(request.getFirstName());
        user.setLastName(request.getLastName());
        user.setEmail(request.getEmail());
        // ← id, passwordHash, role, createdAt, updatedAt — ignore = true,
        //   они отсутствуют в сгенерированном коде полностью
        return user;
    }
}
```

## 7. MapStruct: продвинутый маппинг

**[Уровень: Middle/Senior]**

### 7.1. @MappingTarget — обновление существующего объекта

При update-операции нельзя создавать новую Entity — нужно обновить существующую (JPA dirty checking отследит изменения):

Java

```
package com.example.mapper;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import com.example.dto.UserSummaryResponse;
import com.example.dto.UserUpdateRequest;
import com.example.model.User;
import org.mapstruct.*;

import java.util.List;

@Mapper(
    componentModel = MappingConstants.ComponentModel.SPRING,
    unmappedTargetPolicy = ReportingPolicy.ERROR
)
public interface UserMapper {

    @Mapping(target = "role", expression = "java(user.getRole().name())")
    UserResponse toResponse(User user);

    UserSummaryResponse toSummaryResponse(User user);

    List<UserResponse> toResponseList(List<User> users);
    List<UserSummaryResponse> toSummaryResponseList(List<User> users);

    @Mapping(target = "id",           ignore = true)
    @Mapping(target = "passwordHash", ignore = true)
    @Mapping(target = "role",         ignore = true)
    @Mapping(target = "createdAt",    ignore = true)
    @Mapping(target = "updatedAt",    ignore = true)
    User toEntity(UserCreateRequest request);

    // @MappingTarget: обновляет существующий объект, не создаёт новый
    // void — предпочтительный тип возврата для update-семантики:
    // явно выражает намерение "изменить переданный объект"
    // (MapStruct также поддерживает возврат User, но void — яснее)
    @BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)
    @Mapping(target = "id",           ignore = true)
    @Mapping(target = "passwordHash", ignore = true)
    @Mapping(target = "role",         ignore = true)
    @Mapping(target = "email",        ignore = true)
    @Mapping(target = "createdAt",    ignore = true)
    @Mapping(target = "updatedAt",    ignore = true)
    void updateUserFromRequest(UserUpdateRequest request, @MappingTarget User user);
}
```

Подробнее о `NullValuePropertyMappingStrategy.IGNORE` и проблеме null-полей — в [разделе 10](https://arena.ai/ru/c/019cacd5-04e3-7856-9c56-ae63031f7ef4#10-partial-update-%D0%BF%D1%80%D0%BE%D0%B1%D0%BB%D0%B5%D0%BC%D0%B0-null-%D0%BF%D0%BE%D0%BB%D0%B5%D0%B9-%D0%BF%D1%80%D0%B8-patch).

### 7.2. qualifiedByName — кастомная логика преобразования поля

Когда стандартного маппинга недостаточно и нужна своя логика для конкретного поля:

Java

```
@Mapper(
    componentModel = MappingConstants.ComponentModel.SPRING,
    unmappedTargetPolicy = ReportingPolicy.ERROR
)
public interface UserMapper {

    // qualifiedByName указывает использовать метод с @Named("roleToString")
    @Mapping(target = "role", qualifiedByName = "roleToString", source = "role")
    UserResponse toResponse(User user);

    // @Named помечает метод как именованный конвертер
    @Named("roleToString")
    default String roleToString(User.Role role) {
        if (role == null) {
            return "UNKNOWN";
        }
        // Например: ADMIN → "admin", MODERATOR → "moderator"
        return role.name().toLowerCase();
    }

    // ... остальные методы
}
```

### 7.3. @AfterMapping — пост-обработка результата

`@AfterMapping` вызывается после завершения основного маппинга. Полезен для установки полей, требующих дополнительной логики:

Java

```
@Mapper(
    componentModel = MappingConstants.ComponentModel.SPRING,
    unmappedTargetPolicy = ReportingPolicy.ERROR
)
public interface UserMapper {

    // ... методы маппинга ...

    // Вызывается после updateUserFromRequest
    @AfterMapping
    default void setUpdatedTimestamp(@MappingTarget User user) {
        user.setUpdatedAt(java.time.LocalDateTime.now());
    }
}
```

> 💡 **Важно знать**
> 
> `@AfterMapping` вызывается для **всех** методов, принимающих через `@MappingTarget` подходящий тип. В данном случае — только для `updateUserFromRequest`, потому что это единственный метод с `@MappingTarget User`. Если будет несколько методов с `@MappingTarget User` — `@AfterMapping` вызовется для всех.

# Часть 4. Jackson

## 8. Jackson: базовые аннотации

**[Уровень: Middle]**

Jackson — библиотека сериализации/десериализации JSON. Spring Boot использует её для всех `@RestController`. Разберём три аннотации, которые нужны в каждом проекте.

### 8.1. @JsonProperty — переименование поля

Если API возвращает `snake_case`, а Java-поля написаны в `camelCase`:

Java

```
package com.example.dto;

import com.fasterxml.jackson.annotation.JsonProperty;
import java.time.LocalDateTime;

public record UserResponse(
        Long id,

        @JsonProperty("first_name")   // В JSON будет "first_name"
        String firstName,

        @JsonProperty("last_name")    // В JSON будет "last_name"
        String lastName,

        String email,
        String role,

        @JsonProperty("created_at")   // В JSON будет "created_at"
        LocalDateTime createdAt
) {}
```

Результирующий JSON:

JSON

```
{
    "id": 1,
    "first_name": "Иван",
    "last_name": "Петров",
    "email": "ivan@example.com",
    "role": "USER",
    "created_at": "2024-01-15T10:30:00"
}
```

### 8.2. @JsonNaming — стратегия именования для всего класса

Вместо `@JsonProperty` на каждом поле — одна аннотация на класс. Класс `PropertyNamingStrategies.SnakeCaseStrategy` корректен для Jackson 2.12+ (Jackson 2.15+ поставляется со Spring Boot 3):

Java

```
package com.example.dto;

import com.fasterxml.jackson.annotation.JsonFormat;
import com.fasterxml.jackson.annotation.JsonNaming;
import com.fasterxml.jackson.databind.PropertyNamingStrategies;
import java.time.LocalDateTime;

// Автоматически конвертирует camelCase → snake_case для всех полей класса
@JsonNaming(PropertyNamingStrategies.SnakeCaseStrategy.class)
public record UserResponse(
        Long id,
        String firstName,    // → "first_name"
        String lastName,     // → "last_name"
        String email,        // → "email" (одно слово, не меняется)
        String role,
        LocalDateTime createdAt  // → "created_at"
) {}
```

Глобальная альтернатива для всего приложения — настройка в `application.yml`:

YAML

```
spring:
  jackson:
    property-naming-strategy: SNAKE_CASE
```

### 8.3. @JsonFormat — форматирование дат

Без `@JsonFormat` Jackson сериализует `LocalDateTime` как массив `[2024,1,15,10,30,0]` — нечитаемо для клиентов:

Java

```
package com.example.dto;

import com.fasterxml.jackson.annotation.JsonFormat;
import java.time.LocalDateTime;

public record UserResponse(
        Long id,
        String firstName,
        String lastName,
        String email,
        String role,

        @JsonFormat(
            shape = JsonFormat.Shape.STRING,
            pattern = "yyyy-MM-dd HH:mm:ss"
        )
        LocalDateTime createdAt  // → "2024-01-15 10:30:00" вместо [2024,1,15,10,30,0]
) {}
```

Глобальная настройка в `application.yml` (рекомендуется):

YAML

```
spring:
  jackson:
    serialization:
      write-dates-as-timestamps: false  # Все даты как строки ISO-8601
```

> 💡 **Важно знать**
> 
> `LocalDateTime` **не содержит** информации о часовом поясе — это концептуальное ограничение типа. Добавлять `timezone` в `@JsonFormat` для `LocalDateTime` семантически некорректно.
> 
> Если ваши пользователи находятся в разных часовых поясах, используйте `Instant` для хранения времени. Тогда `@JsonFormat` вернёт ISO-8601 строку с явным указанием UTC: `"2024-01-15T10:30:00Z"`.

## 9. Jackson: продвинутые аннотации

**[Уровень: Senior]**

### 9.1. @JsonIgnore — исключение поля из JSON

Дополнительная страховка на случай, если чувствительное поле попало в DTO:

Java

```
import com.fasterxml.jackson.annotation.JsonIgnore;

public record UserInternalDto(
        Long id,
        String firstName,
        String email,

        @JsonIgnore  // Никогда не попадёт в JSON — дополнительный барьер безопасности
        String sensitiveData
) {}
```

### 9.2. @JsonInclude — управление null-полями

По умолчанию Jackson включает в JSON поля с `null`. Это увеличивает размер ответа:

Java

```
import com.fasterxml.jackson.annotation.JsonInclude;

// Применяется на весь класс — все null-поля исключаются
@JsonInclude(JsonInclude.Include.NON_NULL)
public record UserResponse(
        Long id,
        String firstName,
        String lastName,
        String email,
        String role,
        LocalDateTime createdAt,
        String middleName  // Если null → поле отсутствует в JSON полностью
) {}
```

Результат при `middleName = null`:

JSON

```
{
    "id": 1,
    "firstName": "Иван",
    "lastName": "Петров",
    "email": "ivan@example.com",
    "role": "USER",
    "createdAt": "2024-01-15T10:30:00"
}
```

Поле `middleName` **полностью отсутствует**, а не `"middleName": null`.

### 9.3. @JsonAlias — псевдонимы при десериализации

Принимает одно поле под несколькими именами. Полезно для обратной совместимости при интеграции с разными клиентами:

Java

```
import com.fasterxml.jackson.annotation.JsonAlias;
import jakarta.validation.constraints.*;
import lombok.*;

@Getter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class UserCreateRequest {

    // Jackson примет все три варианта при десериализации
    @JsonAlias({"first_name", "firstName", "name"})
    @NotBlank
    private String firstName;

    @JsonAlias({"last_name", "lastName", "surname"})
    @NotBlank
    private String lastName;

    @Email
    private String email;

    @Size(min = 8)
    private String password;
}
```

### 9.4. Полный пример Response DTO с Jackson-аннотациями

Java

```
package com.example.dto;

import com.fasterxml.jackson.annotation.JsonInclude;

        String firstName,         // → "first_name"
        String lastName,          // → "last_name"
        String email,
        String role,

        @JsonFormat(shape = JsonFormat.Shape.STRING, pattern = "yyyy-MM-dd HH:mm:ss")
        LocalDateTime createdAt   // → "created_at", формат строки
) {}
```

# Часть 5. Продвинутые темы

## 10. Partial Update: проблема null-полей при PATCH

**[Уровень: Middle/Senior]**

### 10.1. В чём проблема

При PATCH-запросе клиент присылает **только изменяемые поля**:

JSON

```
{ "firstName": "Николай" }
```

Поле `lastName` не прислано → Jackson десериализует его в `null`. Без специальной настройки маппер перенесёт `null` в Entity и **уничтожит** существующее значение:

text

```
┌────────────────────────────────────────────────────────┐
│              Проблема partial update                   │
├────────────────────────────────────────────────────────┤
│ Запрос: { "firstName": "Николай" }                     │
│                                                        │
│             firstName      lastName                    │
│ DTO:        "Николай"      null (не прислано)          │
│ Entity ДО:  "Иван"         "Петров"                    │
│                                                        │
│ ❌ Без IGNORE:                                         │
│ Entity После: "Николай"    null   ← ДАННЫЕ ПОТЕРЯНЫ!   │
│                                                        │
│ ✅ С IGNORE:                                           │
│ Entity После: "Николай"    "Петров" ← Данные сохранены │
└────────────────────────────────────────────────────────┘
```

### 10.2. Решение: NullValuePropertyMappingStrategy.IGNORE

Java

```
// В интерфейсе UserMapper:
// @BeanMapping + IGNORE: null-поля из DTO не перезаписывают поля Entity
@BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)
@Mapping(target = "id",           ignore = true)
@Mapping(target = "passwordHash", ignore = true)
@Mapping(target = "role",         ignore = true)
@Mapping(target = "email",        ignore = true)
@Mapping(target = "createdAt",    ignore = true)
@Mapping(target = "updatedAt",    ignore = true)
void updateUserFromRequest(UserUpdateRequest request, @MappingTarget User user);
```

MapStruct сгенерирует:

Java

```
@Override
public void updateUserFromRequest(UserUpdateRequest request, User user) {
    if (request == null) {
        return;
    }
    // Проверка null ПЕРЕД каждым setter — это и есть IGNORE-стратегия
    if (request.getFirstName() != null) {
        user.setFirstName(request.getFirstName()); // Обновляем только если не null
    }
    if (request.getLastName() != null) {
        user.setLastName(request.getLastName());
    }
    // updatedAt, passwordHash, role, email — не трогаем (ignore = true)
}
```

### 10.3. Полный PATCH в сервисе

Java

```
@Transactional
public UserResponse update(Long id, UserUpdateRequest request) {
    User user = userRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("User not found: " + id));

    // null-поля из request не затирают значения в user
    userMapper.updateUserFromRequest(request, user);
    user.setUpdatedAt(LocalDateTime.now()); // Метка времени обновления

    User saved = userRepository.save(user);
    return userMapper.toResponse(saved);
}
```

Контроллер:

Java

```
@PatchMapping("/{id}")
public UserResponse update(
        @PathVariable Long id,
        @Valid @RequestBody UserUpdateRequest request) {
    return userService.update(id, request);
}
```

## 11. Циклические ссылки при сериализации

**[Уровень: Senior]**

### 11.1. Демонстрация проблемы

Представим двунаправленную связь между `User` и `Order`:

Java

```
@Entity
public class User {
    @Id private Long id;
    private String firstName;

    @OneToMany(mappedBy = "user")
    private List<Order> orders;  // User → Order
}

@Entity
public class Order {
    @Id private Long id;
    private String description;

    @ManyToOne
    private User user;           // Order → User → Order → User → ...
}
```

При сериализации `User` Jackson рекурсивно обходит граф объектов:

text

```
Jackson сериализует User:
  User {
    id: 1,
    firstName: "Иван",
    orders: [
      Order {
        id: 10,
        description: "Заказ #10",
        user: User {                    ← тот же User!
          id: 1,
          firstName: "Иван",
          orders: [
            Order {
              id: 10,
              description: "Заказ #10",
              user: User {              ← снова!
                id: 1,
                orders: [
                  Order {
                    user: User {        ← бесконечно...
                      ...
                    }                  💥 StackOverflowError
```

### 11.2. Паллиативные решения на Entity

Применяйте эти подходы только если использование DTO временно невозможно:

**@JsonManagedReference / @JsonBackReference:**

Java

```
@Entity
public class User {
    @OneToMany(mappedBy = "user")
    @JsonManagedReference    // "Прямая" сторона — сериализуется
    private List<Order> orders;
}

@Entity
public class Order {
    @ManyToOne
    @JsonBackReference       // "Обратная" сторона — НЕ сериализуется
    private User user;
}
// Ограничение: поле user внутри Order НИКОГДА не попадёт в JSON
```

**@JsonIgnoreProperties:**

Java

```
@Entity
public class User {
    @OneToMany(mappedBy = "user")
    @JsonIgnoreProperties("user")  // Сериализуя Order, игнорировать его поле "user"
    private List<Order> orders;
}
```

Оба подхода — паллиативные меры: они подавляют симптом, но не устраняют причину.

### 11.3. Правильное решение: DTO без циклов

Java

```
// UserResponse — содержит краткое представление заказов
public record UserResponse(
        Long id,
        String firstName,
        String lastName,
        String email,
        String role,
        LocalDateTime createdAt,
        List<OrderBriefResponse> orders  // ← Краткий DTO заказа
) {}

// OrderBriefResponse НЕ содержит UserResponse — цикл разорван по конструкции
public record OrderBriefResponse(
        Long id,
        String description
) {}
```

> 💡 **Важно знать**
> 
> DTO решает проблему циклических ссылок **архитектурно**: вы проектируете граф данных без циклов заранее. Entity остаётся чистой — без Jackson-аннотаций. Проблема `StackOverflowError` становится невозможной по конструкции — это принципиально лучше, чем подавлять её аннотацией.

## 12. Тестирование маппинга

**[Уровень: Middle/Senior]**

Маппер — такой же код, как и любой другой. Он должен быть покрыт тестами. Хорошая новость: тестировать его можно без Spring-контекста.

### 12.1. Unit-тест без Spring-контекста

Java

```
package com.example.mapper;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import com.example.dto.UserSummaryResponse;
import com.example.dto.UserUpdateRequest;
import com.example.model.User;
import org.junit.jupiter.api.Test;
import org.mapstruct.factory.Mappers;

import java.time.LocalDateTime;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

class UserMapperTest {

    // Mappers.getMapper() находит UserMapperImpl и создаёт экземпляр через new UserMapperImpl()
    // Работает даже при componentModel=SPRING: @Component не мешает прямому созданию
    // Тест запускается за миллисекунды — Spring-контекст не поднимается
    private final UserMapper mapper = Mappers.getMapper(UserMapper.class);

    @Test
    void shouldMapUserToResponse() {
        // Given
        User user = new User();
        user.setId(1L);
        user.setFirstName("Иван");
        user.setLastName("Петров");
        user.setEmail("ivan@example.com");
        user.setRole(User.Role.USER);
        user.setCreatedAt(LocalDateTime.of(2024, 1, 15, 10, 30, 0));

        // When
        UserResponse response = mapper.toResponse(user);

        // Then: проверяем каждое поле явно
        assertThat(response).isNotNull();
        assertThat(response.id()).isEqualTo(1L);
        assertThat(response.firstName()).isEqualTo("Иван");
        assertThat(response.lastName()).isEqualTo("Петров");
        assertThat(response.email()).isEqualTo("ivan@example.com");
        assertThat(response.role()).isEqualTo("USER");
        assertThat(response.createdAt()).isEqualTo(LocalDateTime.of(2024, 1, 15, 10, 30, 0));
    }

    @Test
    void shouldMapUserToSummaryResponse() {
        User user = new User();
        user.setId(2L);
        user.setFirstName("Мария");
        user.setLastName("Сидорова");

        UserSummaryResponse summary = mapper.toSummaryResponse(user);

        assertThat(summary).isNotNull();
        assertThat(summary.id()).isEqualTo(2L);
        assertThat(summary.firstName()).isEqualTo("Мария");
        assertThat(summary.lastName()).isEqualTo("Сидорова");
    }

    @Test
    void shouldMapCollectionOfUsers() {
        User user1 = new User();
        user1.setId(1L);
        user1.setFirstName("Иван");
        user1.setLastName("Петров");
        user1.setEmail("ivan@example.com");
        user1.setRole(User.Role.USER);
        user1.setCreatedAt(LocalDateTime.now());

        User user2 = new User();
        user2.setId(2L);
        user2.setFirstName("Мария");
        user2.setLastName("Сидорова");
        user2.setEmail("maria@example.com");
        user2.setRole(User.Role.ADMIN);
        user2.setCreatedAt(LocalDateTime.now());

        List<UserResponse> responses = mapper.toResponseList(List.of(user1, user2));

        assertThat(responses).hasSize(2);
        assertThat(responses.get(0).firstName()).isEqualTo("Иван");
        assertThat(responses.get(1).firstName()).isEqualTo("Мария");
        assertThat(responses.get(1).role()).isEqualTo("ADMIN");
    }

    @Test
    void shouldMapCreateRequestToEntity() {
        UserCreateRequest request = UserCreateRequest.builder()
                .firstName("Иван")
                .lastName("Петров")
                .email("ivan@example.com")
                .password("password123")
                .build();

        User entity = mapper.toEntity(request);

        assertThat(entity).isNotNull();
        assertThat(entity.getId()).isNull();           // ignore = true
        assertThat(entity.getFirstName()).isEqualTo("Иван");
        assertThat(entity.getLastName()).isEqualTo("Петров");
        assertThat(entity.getEmail()).isEqualTo("ivan@example.com");
        assertThat(entity.getPasswordHash()).isNull(); // ignore = true
        assertThat(entity.getRole()).isNull();          // ignore = true
    }

    @Test
    void shouldNotOverwriteNullFieldsOnPartialUpdate() {
        // Given: существующий пользователь в БД
        User existing = new User();
        existing.setId(1L);
        existing.setFirstName("Иван");
        existing.setLastName("Петров");
        existing.setEmail("ivan@example.com");
        existing.setRole(User.Role.USER);

        // Клиент прислал только firstName: { "firstName": "Николай" }
        UserUpdateRequest request = UserUpdateRequest.builder()
                .firstName("Николай")
                // lastName не установлен → null
                .build();

        // When
        mapper.updateUserFromRequest(request, existing);

        // Then
        assertThat(existing.getFirstName()).isEqualTo("Николай");     // ← Обновлено ✅
        assertThat(existing.getLastName()).isEqualTo("Петров");        // ← Сохранено ✅
        assertThat(existing.getEmail()).isEqualTo("ivan@example.com"); // ← Не тронуто ✅
        assertThat(existing.getRole()).isEqualTo(User.Role.USER);      // ← Не тронуто ✅
    }

    @Test
    void shouldReturnNullForNullInput() {
        // Проверяем null-safety всех методов
        assertThat(mapper.toResponse(null)).isNull();
        assertThat(mapper.toSummaryResponse(null)).isNull();
        assertThat(mapper.toResponseList(null)).isNull();
        assertThat(mapper.toSummaryResponseList(null)).isNull();
        assertThat(mapper.toEntity(null)).isNull();
    }
}
```

> 💡 **Важно знать**
> 
> `Mappers.getMapper(UserMapper.class)` создаёт экземпляр `UserMapperImpl` напрямую через `new UserMapperImpl()` — Spring-контекст не нужен. Тест запускается за ~10-50ms вместо ~3-10 секунд при `@SpringBootTest`.
> 
> **Ограничение:** если ваш маппер использует `uses = {AnotherMapper.class}`, зависимые мапперы нужно инжектировать вручную (через `ReflectionTestUtils`) или переходить к `@SpringBootTest`. Добавляйте `uses` только когда это действительно необходимо.

## 14. Типичные ошибки и антипаттерны

**[Уровень: Middle]**

### 14.1. Один DTO на все операции

Java

```
// ❌ АНТИПАТТЕРН: один класс для создания, обновления и ответа
public class UserDto {
    private Long id;            // Бессмысленно при создании — БД генерирует
    private String password;    // Опасно в ответе — утечка данных!
    private String passwordHash;// Зачем клиенту хеш?
    private String role;        // Mass Assignment: клиент сам назначает роль
    private LocalDateTime createdAt; // Клиент не должен устанавливать дату
}
```

**Правило:** отдельный DTO для каждой операции. Каждый класс — минимально необходимый набор полей.

### 14.2. Маппинг Entity вне транзакции

Java

```
// ❌ АНТИПАТТЕРН: маппинг в контроллере, транзакция уже закрыта
@GetMapping("/{id}")
public UserResponse getUser(@PathVariable Long id) {
    User user = userService.findEntityById(id);  // Сервис возвращает Entity
    return userMapper.toResponse(user);           // Lazy-поля → LazyInitializationException!
}

// ✅ ПРАВИЛЬНО: маппинг внутри сервиса, транзакция активна
@Service
public class UserService {
    @Transactional(readOnly = true)
    public UserResponse findById(Long id) {
        User user = userRepository.findById(id).orElseThrow();
        return userMapper.toResponse(user); // Маппинг внутри @Transactional
    }
}
```

### 14.3. Неправильный порядок annotation processors

XML

```
<!-- ❌ MapStruct ДО Lombok — не видит Lombok-геттеры -->
<annotationProcessorPaths>
    <path><!-- mapstruct-processor --></path>
    <path><!-- lombok --></path>
</annotationProcessorPaths>
<!-- Результат: маппер компилируется, но возвращает null во всех полях -->

<!-- ✅ Lombok → Binding → MapStruct -->
<annotationProcessorPaths>
    <path><!-- lombok --></path>
    <path><!-- lombok-mapstruct-binding --></path>
    <path><!-- mapstruct-processor --></path>
</annotationProcessorPaths>
```

### 14.4. Отсутствие unmappedTargetPolicy

Java

```
// ❌ Без ERROR: добавили поле в Entity → маппер молча вернёт null
@Mapper(componentModel = MappingConstants.ComponentModel.SPRING)
public interface UserMapper { ... }

// ✅ С ERROR: добавили поле → ошибка компиляции → вспомнили обновить маппер
@Mapper(
    componentModel = MappingConstants.ComponentModel.SPRING,
    unmappedTargetPolicy = ReportingPolicy.ERROR
)
public interface UserMapper { ... }
```

### 14.5. Partial update без стратегии IGNORE

Java

```
// ❌ Без IGNORE: PATCH { "firstName": "Николай" } обнуляет все остальные поля
void updateUserFromRequest(UserUpdateRequest request, @MappingTarget User user);

// ✅ С IGNORE: null-поля из DTO не трогают Entity
@BeanMapping(nullValuePropertyMappingStrategy = NullValuePropertyMappingStrategy.IGNORE)
void updateUserFromRequest(UserUpdateRequest request, @MappingTarget User user);
```

## 15. Итоги: когда что использовать

**[Уровень: все]**

### Таблица решений

|Ситуация|Рекомендуемый подход|
|---|---|
|Маленький проект (≤ 5 Entity)|Ручной маппинг|
|Средний/большой проект (5+ Entity)|**MapStruct**|
|Прототип, PoC|ModelMapper|
|Response DTO (Java 17+)|**Java Record**|
|Response DTO (Java < 16)|Lombok `@Value`|
|Request DTO с валидацией|Lombok `@Getter` + `@NoArgsConstructor` + `@AllArgsConstructor` + `@Builder`|
|Partial update (PATCH)|MapStruct + `NullValuePropertyMappingStrategy.IGNORE`|
|Кастомный JSON-формат|Jackson-аннотации на DTO (не на Entity!)|
|Циклические ссылки|DTO без циклических ссылок (архитектурное решение)|
|Версионирование API|Отдельные DTO v1/v2 + отдельные маппинги|

### Ключевые правила

1. **Entity никогда не возвращается из контроллера** — только DTO
2. **Отдельный DTO для каждой операции** — Create, Update, Response, Summary
3. **Response DTO — иммутабельный** — Record (Java 17+) или `@Value` (Lombok)
4. **Маппинг — внутри сервисного слоя** — там, где активна транзакция
5. **`unmappedTargetPolicy = ReportingPolicy.ERROR`** — забытые поля ловятся при компиляции
6. **Jackson-аннотации — на DTO, не на Entity** — Entity не должна знать о формате JSON
7. **Partial update — с `IGNORE`-стратегией** — null из запроса не перезаписывает данные
8. **Тестируйте маппинг** — `Mappers.getMapper()` без Spring-контекста, быстро и надёжно

## Что дальше

В следующей статье **6.7 «Валидация и обработка ошибок»** мы разберём:

- **`@Valid`** и **`@Validated`** — как Spring автоматически проверяет Request DTO перед обработкой
- **`BindingResult`** — получение деталей ошибок валидации из `@Valid`
- **`@ExceptionHandler`** — обработка конкретных исключений в контроллере
- **`@ControllerAdvice`** — глобальный обработчик всех исключений приложения
- **`ErrorResponse` DTO** — структурированный JSON-ответ при ошибках: `{"code": "VALIDATION_ERROR", "message": "...", "fields": [...]}`

Знание DTO из этой статьи — прямой фундамент для следующего шага: ошибки тоже возвращаются как DTO, и их нужно правильно маппировать из исключений.
