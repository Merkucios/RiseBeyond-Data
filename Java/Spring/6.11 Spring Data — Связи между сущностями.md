## О статье

В реальных приложениях данные не живут изолированно: пользователь делает заказы, заказ содержит товары, у пользователя есть профиль. JPA позволяет выразить эти отношения прямо в Java-коде — и Hibernate автоматически транслирует их в FK, JOIN и каскадные операции в БД. В этой статье мы разберём все четыре типа связей (`@ManyToOne`, `@OneToMany`, `@OneToOne`, `@ManyToMany`), научимся правильно настраивать FetchType и каскадирование, избегать классических ловушек вроде N+1 и `LazyInitializationException`. Результат — полная доменная модель интернет-магазина: `User`, `Order`, `Product`, `OrderItem`, `UserProfile` — с правильными связями, helper-методами и тестами.

## 1. Введение

> 🎯 **Уровень: Intern** — этот раздел для всех

В статье **6.9** мы научились создавать JPA Entity. В статье **6.10** — делать CRUD через Repository. Но до сих пор каждая Entity жила сама по себе.

**Было (изолированные Entity):**

Java

```
// Чтобы узнать имя автора заказа — два ручных запроса
Order order = orderRepository.findById(orderId).orElseThrow();
User user = userRepository.findById(order.getUserId()).orElseThrow(); // ручной поиск
String name = user.getName();
```

**Стало (связанные Entity):**

Java

```
// Hibernate сам выполняет JOIN — навигация по объектному графу
Order order = orderRepository.findById(orderId).orElseThrow();
String name = order.getUser().getName(); // одна строка вместо двух запросов
```

**Что даёт связывание Entity:**

- **Навигация** — `order.getUser()`, `user.getOrders()`
- **Автоматические JOIN** — Hibernate генерирует SQL сам
- **Каскадные операции** — сохранил `User` → сохранились его `Order`
- **Целостность** — FK-constraints создаются автоматически

**Доменная модель, которую мы построим:**

text

```
User ──(1:1)──▶ UserProfile    (профиль пользователя)
User ──(1:N)──▶ Order          (заказы пользователя)
Order ──(1:N)──▶ OrderItem     (позиции заказа)
OrderItem ──(N:1)──▶ Product   (продукт в позиции)
```

## 3. Владеющая сторона и mappedBy

> 🎯 **Уровень: Junior**

### Аналогия: кто хранит ключ

Представьте Алису и Боба — они соседи по квартире. Оба знают адрес. Но **ключ хранит только Алиса** — именно она открывает замок.

- Боб может говорить "я живу с Алисой" сколько угодно — в замке ничего не изменится.
- Только Алиса физически управляет доступом.

В JPA точно так же:

text

```
━━━ КТО ЗАПИСЫВАЕТ FK В БД ━━━

  ВЛАДЕЮЩАЯ СТОРОНА              ОБРАТНАЯ СТОРОНА
  (Алиса — хранит ключ)          (Боб — только знает об Алисе)

  orders                         users
  ┌────┬─────────┬─────────┐     ┌────┬───────────┐
  │ id │ status  │ user_id │     │ id │ email     │
  └────┴─────────┴────┬────┘     └────┴───────────┘
                      │
                      FK — Hibernate пишет сюда
                      ТОЛЬКО через владеющую сторону

  class Order {                  class User {
      @ManyToOne                     @OneToMany(
      @JoinColumn("user_id")             mappedBy = "user") ← "Боб"
      User user; ← "Алиса"           List<Order> orders;
  }                              }
                                 Hibernate ИГНОРИРУЕТ при записи FK
```

### Критическая ошибка — установка связи только на обратной стороне

Java

```
// ❌ БАГ: FK не запишется! user_id = NULL в БД
User user = userRepository.findById(1L).orElseThrow();
Order order = new Order();
order.setStatus("PENDING");
user.getOrders().add(order); // обратная сторона — Hibernate игнорирует
orderRepository.save(order); // user_id = NULL 💥

// ✅ ПРАВИЛЬНО: устанавливаем на владеющей стороне
order.setUser(user);         // владеющая сторона — FK запишется
orderRepository.save(order); // user_id = 1 ✅

// ✅ ЕЩЁ ЛУЧШЕ: helper-метод (детали в разделе о @OneToMany)
user.addOrder(order);        // синхронизирует обе стороны сразу
```

> **🔬 Под капотом:** Hibernate отслеживает изменения через **Persistence Context** (dirty checking). При `flush()` он сканирует **только владеющую сторону** каждой связи, чтобы сгенерировать SQL с FK. Обратная сторона (`mappedBy`) существует исключительно для навигации в Java-коде.

## 4. @ManyToOne — самая важная связь

> 🎯 **Уровень: Junior**

`@ManyToOne` — самая частая связь. Она напрямую маппит FK-колонку в текущей таблице и всегда является владеющей стороной.

### Три шага к правильному маппингу

Java

```
// Шаг 1: минимальный рабочий вариант (работает, но не оптимально)
@ManyToOne
private User user;

// Шаг 2: добавляем рекомендуемые настройки
@ManyToOne(fetch = FetchType.LAZY)  // НИКОГДА не оставляй EAGER!
@JoinColumn(name = "user_id")       // явное имя FK-колонки
private User user;

// Шаг 3: production-вариант
@ManyToOne(fetch = FetchType.LAZY, optional = false) // optional=false → INNER JOIN
@JoinColumn(
    name = "user_id",
    nullable = false,                                // DDL: NOT NULL
    foreignKey = @ForeignKey(name = "fk_order_user") // читаемое имя FK в БД
)
private User user;
```

### Полный пример: Order с @ManyToOne

Java

```
package com.example.shop.entity;

import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.LocalDateTime;

@Entity
@Table(name = "orders")
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false)
    private String status;

    @Column(name = "total_amount", precision = 10, scale = 2)
    private BigDecimal totalAmount;

    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    // ✅ Владеющая сторона: FK user_id живёт в таблице orders
    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(
        name = "user_id",
        nullable = false,
        foreignKey = @ForeignKey(name = "fk_order_user")
        // Именованный FK полезен: в логах БД "fk_order_user" понятнее чем "orders_user_id_fkey"
    )
    private User user;

    @PrePersist
    protected void onCreate() {
        this.createdAt = LocalDateTime.now();
    }

    protected Order() {} // обязателен для JPA

    public Order(String status, User user) {
        this.status = status;
        this.user = user;
    }

    public Long getId() { return id; }
    public String getStatus() { return status; }
    public void setStatus(String status) { this.status = status; }
    public User getUser() { return user; }
    public void setUser(User user) { this.user = user; }
    public BigDecimal getTotalAmount() { return totalAmount; }
    public void setTotalAmount(BigDecimal totalAmount) { this.totalAmount = totalAmount; }
    public LocalDateTime getCreatedAt() { return createdAt; }
}
```

SQL, который Hibernate генерирует:

SQL

```
CREATE TABLE orders (
    id           BIGSERIAL PRIMARY KEY,
    status       VARCHAR(255) NOT NULL,
    total_amount DECIMAL(10, 2),
    created_at   TIMESTAMP NOT NULL,
    user_id      BIGINT NOT NULL,
    CONSTRAINT fk_order_user FOREIGN KEY (user_id) REFERENCES users(id)
);
```

### Однонаправленная vs двунаправленная

**Однонаправленная** (только `Order → User`) — проще, достаточна в большинстве случаев:

Java

```
// Только в Order.java — User.java не знает об Orders
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "user_id", nullable = false)
private User user;
```

**Двунаправленная** (нужна, когда часто навигируем `User → Orders`):

Java

```
// В User.java добавляем обратную сторону
@OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Order> orders = new ArrayList<>();

// + helper-методы (см. раздел 5)
```

> **💡 Совет:** начинай с однонаправленной. Добавляй обратную сторону только когда реально нужна навигация от родителя к детям.

### ✅ Чеклист @ManyToOne

text

```
□ fetch = FetchType.LAZY — явно, всегда
□ @JoinColumn(name = "...") — явное имя FK-колонки
□ nullable = false — если связь обязательна
□ foreignKey = @ForeignKey(name = "...") — именованный constraint
□ optional = false — если User всегда должен быть
□ Без CascadeType — Order не управляет жизнью User
```

## 5. @OneToMany — коллекция на стороне «один»

> 🎯 **Уровень: Junior/Middle**

### Три варианта — от худшего к лучшему

text

```
━━━ СРАВНЕНИЕ ПОДХОДОВ @OneToMany ━━━

❌ Вариант 1: без mappedBy и без @JoinColumn (худший)
   → Hibernate создаёт ЛИШНЮЮ промежуточную таблицу users_orders
   SQL: INSERT INTO users_orders (user_id, orders_id) VALUES (1, 42)

⚠️ Вариант 2: с @JoinColumn без mappedBy (лучше, но есть проблема)
   → Нет лишней таблицы, но два запроса вместо одного:
   SQL: INSERT INTO orders (status) VALUES ('PENDING')   ← user_id = NULL!
   SQL: UPDATE orders SET user_id = 1 WHERE id = 42     ← лишний UPDATE
   ⚠️ Если user_id NOT NULL — INSERT упадёт с ошибкой FK!

✅ Вариант 3: двунаправленная с mappedBy (рекомендуемый)
   → FK управляется через @ManyToOne на стороне Order
   SQL: INSERT INTO orders (status, user_id) VALUES ('PENDING', 1)
   Один INSERT, FK установлен сразу
```

### Правильная реализация: User с @OneToMany

Java

```
package com.example.shop.entity;

import jakarta.persistence.*;
import java.util.ArrayList;
import java.util.List;
import java.util.Objects;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(nullable = false)
    private String name;

    // ✅ Обратная сторона — не управляет FK, только навигация
    // mappedBy = "user" → поле user в классе Order
    @OneToMany(
        mappedBy = "user",
        cascade = CascadeType.ALL,    // сохранение/удаление User каскадирует на Orders
        orphanRemoval = true          // удаление из коллекции = DELETE из БД
    )
    private List<Order> orders = new ArrayList<>(); // инициализация обязательна

    // ✅ @OneToOne с профилем (детали в разделе 6)
    @OneToOne(
        mappedBy = "user",
        cascade = CascadeType.ALL,
        orphanRemoval = true,
        fetch = FetchType.LAZY
    )
    private UserProfile profile;

    protected User() {}

    public User(String email, String name) {
        this.email = email;
        this.name = name;
    }

    // ━━━ Helper-методы для синхронизации обеих сторон ━━━

    /**
     * Добавляет заказ пользователю.
     * Синхронизирует обе стороны двунаправленной связи.
     * Без этого метода есть риск установить связь только на обратной стороне.
     */
    public void addOrder(Order order) {
        orders.add(order);
        order.setUser(this); // ← устанавливаем владеющую сторону — FK запишется в БД
    }

    /**
     * Удаляет заказ. orphanRemoval = true обеспечит DELETE из БД.
     */
    public void removeOrder(Order order) {
        orders.remove(order);
        order.setUser(null);
    }

    /**
     * Устанавливает профиль. Корректно обрабатывает замену старого профиля.
     */
    public void setProfile(UserProfile newProfile) {
        if (this.profile != null) {
            this.profile.setUser(null); // detach старый профиль
        }
        this.profile = newProfile;
        if (newProfile != null) {
            newProfile.setUser(this); // синхронизируем владеющую сторону
        }
    }

    // Getters
    public Long getId() { return id; }
    public String getEmail() { return email; }
    public String getName() { return name; }
    public List<Order> getOrders() { return orders; }
    public UserProfile getProfile() { return profile; }

    // equals/hashCode по бизнес-ключу (email уникален)
    // ⚠️ НЕ включаем коллекции — LazyInitializationException + N+1!
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User user)) return false;
        return Objects.equals(email, user.email);
    }

    @Override
    public int hashCode() {
        return Objects.hash(email);
    }

    // ⚠️ toString БЕЗ LAZY-полей — иначе LazyInitializationException при логировании
    @Override
    public String toString() {
        return "User{id=" + id + ", email='" + email + "'}";
    }
}
```

### ✅ Чеклист @OneToMany

text

```
□ mappedBy = "fieldName" — всегда! Иначе лишняя таблица
□ FetchType.LAZY — по умолчанию, не менять на EAGER
□ Инициализировать коллекцию: = new ArrayList<>()
□ Helper-методы addXxx() / removeXxx() — синхронизация обеих сторон
□ CascadeType.ALL + orphanRemoval только для strict parent-child
□ equals()/hashCode() — НЕ включать коллекции (N+1 + StackOverflow)
□ toString() — НЕ включать LAZY-поля
```

## 6. @OneToOne — связь один к одному

> 🎯 **Уровень: Middle**

### Стандартный подход (рабочий, но не оптимальный)

Java

```
// Отдельная FK-колонка + UNIQUE constraint
@OneToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id", unique = true, nullable = false)
private User user;
// Таблица: id | bio | user_id (FK+UNIQUE) — избыточно!
```

### Оптимальный подход: @MapsId

Java

```
package com.example.shop.entity;

import jakarta.persistence.*;

@Entity
@Table(name = "user_profiles")
public class UserProfile {

    // PK = FK к users.id (без @GeneratedValue — значение берётся из User)
    @Id
    private Long id;

    private String bio;

    @Column(name = "avatar_url")
    private String avatarUrl;

    // ✅ @MapsId: id этой Entity = id связанного User
    @OneToOne(fetch = FetchType.LAZY)
    @MapsId                    // говорим Hibernate: id = FK к User
    @JoinColumn(name = "id")   // одна колонка и PK, и FK одновременно
    private User user;

    protected UserProfile() {}

    public UserProfile(User user, String bio) {
        this.user = user;
        this.bio = bio;
    }

    public Long getId() { return id; }
    public String getBio() { return bio; }
    public void setBio(String bio) { this.bio = bio; }
    public String getAvatarUrl() { return avatarUrl; }
    public void setAvatarUrl(String avatarUrl) { this.avatarUrl = avatarUrl; }
    public User getUser() { return user; }
    public void setUser(User user) { this.user = user; }
}
```

SQL

```
-- @MapsId: одна колонка вместо двух!
CREATE TABLE user_profiles (
    id         BIGINT PRIMARY KEY,  -- PK = FK к users.id
    bio        TEXT,
    avatar_url VARCHAR(500),
    FOREIGN KEY (id) REFERENCES users(id)
);
-- Нет отдельного user_id, нет лишнего UNIQUE index
```

### Почему @MapsId лучше и для LAZY

text

```
━━━ ПРОБЛЕМА LAZY В @OneToOne БЕЗ @MapsId ━━━

Для @ManyToOne LAZY работает всегда:
  Order.user = proxy(id=5)
  Hibernate знает user_id = 5 → создаёт proxy
  При обращении → SELECT WHERE id = 5 ✅

Для @OneToOne БЕЗ @MapsId (обратная сторона, mappedBy):
  User.profile = ???
  Hibernate НЕ знает: есть ли запись в user_profiles для user.id=5?
  NULL или объект — неизвестно без запроса в БД
  → Hibernate делает SELECT чтобы проверить ← LAZY нарушен! ❌

Для @OneToOne С @MapsId:
  User.profile = proxy(id=user.id=5)
  Hibernate знает: profile.id = user.id = 5
  → Можно создать lazy proxy без дополнительного SELECT ✅
  + Можно найти профиль: entityManager.find(UserProfile.class, userId) — без JOIN!
```

### ✅ Чеклист @OneToOne

text

```
□ @MapsId — используй всегда когда возможно
□ fetch = FetchType.LAZY — явно на обеих сторонах
□ @Id без @GeneratedValue на стороне с @MapsId
□ CascadeType.ALL + orphanRemoval — если profile зависит от User
□ Helper-метод setProfile() в родительской Entity
```

## 7. @ManyToMany и промежуточная Entity

> 🎯 **Уровень: Middle**

### Почему прямая @ManyToMany недостаточна

Java

```
// ⚠️ Прямая @ManyToMany — ограниченный вариант
// Нет места для quantity, price на момент покупки
@ManyToMany(cascade = {CascadeType.PERSIST, CascadeType.MERGE})
@JoinTable(
    name = "order_product",
    joinColumns = @JoinColumn(name = "order_id"),
    inverseJoinColumns = @JoinColumn(name = "product_id")
)
private Set<Product> products = new HashSet<>(); // ← Set, НЕ List!
```

**Проблема List vs Set** — критическая разница:

text

```
━━━ LIST vs SET при удалении одного продукта из заказа ━━━

С LIST (Bag):
  DELETE FROM order_product WHERE order_id = 10      ← ВСЕ строки!
  INSERT INTO order_product (order_id, product_id) VALUES (10, 1)
  INSERT INTO order_product (order_id, product_id) VALUES (10, 3)
  ⛔ Удаляем 1 — переписываем все

С SET:
  DELETE FROM order_product WHERE order_id=10 AND product_id=2
  ✅ Удаляем только нужную строку
```

### Промежуточная Entity: правильное решение для production

В нашей модели нужны `quantity` и `unitPrice` — прямой `@ManyToMany` не подойдёт.

**Составной ключ:**

Java

```

import jakarta.persistence.Embeddable;

import java.util.Objects;

@Embeddable
public class OrderItemId implements Serializable {

        this.orderId = orderId;
        this.productId = productId;

    // equals и hashCode ОБЯЗАТЕЛЬНЫ для @Embeddable PK
    @Override

        if (this == o) return true;
        if (!(o instanceof OrderItemId that)) return false;
        return Objects.equals(orderId, that.orderId) &&

    }

    @Override
    public int hashCode() {

    }
```

**Промежуточная Entity:**

Java

```
package com.example.shop.entity;

import jakarta.persistence.*;
import java.math.BigDecimal;
import java.util.Objects;

@Entity
@Table(name = "order_items")
public class OrderItem {

    @EmbeddedId
    private OrderItemId id;

    // @MapsId связывает часть составного ключа с @ManyToOne
    @ManyToOne(fetch = FetchType.LAZY)
    @MapsId("orderId")             // id.orderId = FK к orders
    @JoinColumn(name = "order_id")
    private Order order;

    @ManyToOne(fetch = FetchType.LAZY)
    @MapsId("productId")           // id.productId = FK к products
    @JoinColumn(name = "product_id")
    private Product product;

    // Дополнительные поля — ГЛАВНАЯ причина использовать промежуточную Entity
    @Column(nullable = false)
    private Integer quantity;

    // Цена фиксируется на момент заказа (может отличаться от текущей цены товара)
    @Column(name = "unit_price", nullable = false, precision = 10, scale = 2)
    private BigDecimal unitPrice;

    protected OrderItem() {}

    public OrderItem(Order order, Product product, Integer quantity, BigDecimal unitPrice) {
        this.id = new OrderItemId(order.getId(), product.getId());
        this.order = order;
        this.product = product;
        this.quantity = quantity;
        this.unitPrice = unitPrice;
    }

    // Вычисляемое поле — не хранится в БД
    public BigDecimal getTotalPrice() {
        return unitPrice.multiply(BigDecimal.valueOf(quantity));
    }

    public OrderItemId getId() { return id; }
    public Order getOrder() { return order; }
    public Product getProduct() { return product; }
    public Integer getQuantity() { return quantity; }
    public void setQuantity(Integer quantity) { this.quantity = quantity; }
    public BigDecimal getUnitPrice() { return unitPrice; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof OrderItem that)) return false;
        return Objects.equals(id, that.id);
    }

    @Override
    public int hashCode() {
        return Objects.hash(id);
    }
}
```

## 9. FetchType: LAZY vs EAGER

> 🎯 **Уровень: Middle**

FetchType определяет **когда** Hibernate загружает связанные данные.

text

```
╔══════════════╦══════════════════╦══════════════════════════════════════════════╗
║ Аннотация    ║ Default по JPA   ║ Рекомендация                                ║
╠══════════════╬══════════════════╬══════════════════════════════════════════════╣
║ @ManyToOne   ║ EAGER ⚠️         ║ Всегда явно LAZY                            ║
║ @OneToOne    ║ EAGER ⚠️         ║ Всегда явно LAZY + @MapsId                  ║
║ @OneToMany   ║ LAZY ✅          ║ Оставить LAZY (по умолчанию)                ║
║ @ManyToMany  ║ LAZY ✅          ║ Оставить LAZY (по умолчанию)                ║
╚══════════════╩══════════════════╩══════════════════════════════════════════════╝
```

> **🔬 Под капотом — изменение в Hibernate 6.x:**  
> Исторически Hibernate следовал JPA-спецификации: `@ManyToOne` — `EAGER` по умолчанию. Это решение было принято ещё в ранних версиях Hibernate (2.x), когда считалось, что загрузка родительской Entity вместе с дочерней — удобное поведение. Со временем стало очевидно, что это антипаттерн: каждый `findAll()` автоматически тянет все связанные объекты.
> 
> **В Hibernate 6.x** дефолт для `@ManyToOne` всё ещё `EAGER` (спецификация JPA требует этого), но команда Hibernate настоятельно рекомендует явно указывать `LAZY`. Если вы мигрируете проект с Hibernate 5.x, проверьте: если в коде нет явного `fetch = FetchType.LAZY` на `@ManyToOne`, поведение не изменилось — но добавить `LAZY` стоит при рефакторинге.

### Как работает LAZY

Java

```
// Hibernate создаёт proxy-объект — "обёртку-обещание"
Order order = orderRepository.findById(1L).orElseThrow();
// SQL: SELECT * FROM orders WHERE id = 1
// order.user — это PROXY, реальных данных User ещё нет в памяти

// При первом обращении к данным proxy — Hibernate выполняет SELECT
String userName = order.getUser().getName();
// SQL: SELECT * FROM users WHERE id = ?

// Проверить состояние proxy:
boolean isLoaded = org.hibernate.Hibernate.isInitialized(order.getUser()); // false/true
```

### @EntityGraph — точечная подгрузка

Java

```
package com.example.shop.repository;

import com.example.shop.entity.Order;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;

import java.util.List;
import java.util.Optional;

public interface OrderRepository extends JpaRepository<Order, Long> {

    // Загрузить заказ вместе с пользователем одним JOIN запросом
    @EntityGraph(attributePaths = {"user"})
    Optional<Order> findWithUserById(Long id);

    // Загрузить полный граф: заказ + пользователь + позиции + продукты
    @EntityGraph(attributePaths = {"user", "orderItems", "orderItems.product"})
    Optional<Order> findWithFullDetailsById(Long id);

    // JOIN FETCH через JPQL — альтернатива @EntityGraph
    @Query("""
        SELECT o FROM Order o
        JOIN FETCH o.user
        LEFT JOIN FETCH o.orderItems oi
        LEFT JOIN FETCH oi.product
        WHERE o.id = :id
        """)
    Optional<Order> findWithAllDetails(@Param("id") Long id);

    // Для отчётов — только нужные данные через DTO
    // (DTO Projection — см. раздел про circular reference и статью 6.6)
    @EntityGraph(attributePaths = {"user"})
    List<Order> findByStatus(String status);
}
```

> **⚠️ Антипаттерн:** `FetchType.EAGER` на коллекциях — гарантированные проблемы. `findAll()` с `@OneToMany(fetch = EAGER)` при 100 пользователях × 1000 заказов = 100 000 строк за один запрос. Правило: **всегда LAZY, нужное — через `@EntityGraph` или `JOIN FETCH`**.

## 10. CascadeType — каскадные операции

> 🎯 **Уровень: Middle**

### Аналогия: директор и команда

- `CascadeType.PERSIST` — принять директора → его команда тоже оформлена
- `CascadeType.MERGE` — обновить директора → обновления применяются к команде
- `CascadeType.REMOVE` — уволить директора → его команда тоже уволена
- `CascadeType.REMOVE` на `@ManyToMany` — уволить одного директора → уволить всех **shared**-сотрудников, которые работают в других командах тоже ← вот почему это опасно

text

```

╠════════════════╬═══════════════════════════╬═════════════════════════╬════════════════════════╣
║ PERSIST        ║ persist(parent) →         ║ @OneToMany parent-child ║ @ManyToMany (риск      ║
║                ║ persist children          ║                         ║ создать лишние Entity) ║
╠════════════════╬═══════════════════════════╬═════════════════════════╬════════════════════════╣
║ MERGE          ║ merge(parent) →           ║ @OneToMany parent-child ║ Если дети независимы   ║
║                ║ merge children            ║ @ManyToMany (PERSIST+   ║                        ║
║                ║                           ║ MERGE — безопасно)      ║                        ║
╠════════════════╬═══════════════════════════╬═════════════════════════╬════════════════════════╣
║ REMOVE         ║ remove(parent) →          ║ @OneToMany parent-child ║ @ManyToMany — удалит   ║
║                ║ remove children           ║ @OneToOne с @MapsId     ║ независимые Product!   ║
║                ║                           ║                         ║ @ManyToOne — удалит    ║
║                ║                           ║                         ║ родителя при удалении  ║
║                ║                           ║                         ║ ребёнка                ║

║                ║                           ║ (User → Orders)         ║ @ManyToOne,            ║
║                ║                           ║                         ║ везде без понимания    ║
╚════════════════╩═══════════════════════════╩═════════════════════════╩════════════════════════╝
```

### Правильное применение

Java

```
// ✅ User → Orders: строгий parent-child
@OneToMany(mappedBy = "user", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Order> orders = new ArrayList<>();
// Сохранение User → автоматически сохраняются Orders
// Удаление User → автоматически удаляются Orders

// ✅ Если бы был прямой @ManyToMany (напр. Order → Tag)
@ManyToMany(cascade = {CascadeType.PERSIST, CascadeType.MERGE})
private Set<Tag> tags = new HashSet<>();
// PERSIST и MERGE — безопасно. REMOVE — опасно!

// ✅ Order → User: без каскада
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private User user;  // Order не управляет жизнью User
```

Java

```
// Демонстрация каскадного сохранения:
@Transactional
public User createUserWithOrders() {
    User user = new User("alice@example.com", "Alice");
    user.addOrder(new Order("PENDING", user));
    user.addOrder(new Order("SHIPPED", user));

    return userRepository.save(user);
    // SQL: INSERT INTO users ...
    // SQL: INSERT INTO orders (status, user_id) VALUES ('PENDING', 1)  ← каскад!
    // SQL: INSERT INTO orders (status, user_id) VALUES ('SHIPPED', 1)  ← каскад!
}
```

> **⚠️ Антипаттерн:** `CascadeType.ALL` везде — классическая ошибка. Особенно опасен `CascadeType.REMOVE` на `@ManyToMany`: удаление `Order` удалит `Product`, который используется в других заказах. Думайте о каскадах как о правиле: **от Aggregate Root к его внутренним Entity, никогда наоборот**.

## 11. orphanRemoval — удаление сирот

> 🎯 **Уровень: Middle**

### Аналогия: корзина покупок

- `CascadeType.REMOVE` — выбросить всю корзину → все товары исчезли
- `orphanRemoval = true` — убрать товар из корзины → товар удалён из базы (его больше нет нигде)
- Без `orphanRemoval` — убрать товар из корзины → в Java список пустой, но строка в БД осталась с `user_id = NULL`

text

```
━━━ РАЗНИЦА: CascadeType.REMOVE vs orphanRemoval ━━━

CascadeType.REMOVE (срабатывает при удалении РОДИТЕЛЯ):
  userRepository.delete(user)
  → DELETE FROM orders WHERE user_id = 1   ← каскад
  → DELETE FROM users WHERE id = 1

orphanRemoval = true (срабатывает при удалении из КОЛЛЕКЦИИ):
  user.getOrders().remove(order)           ← убираем из коллекции
  userRepository.save(user)
  → DELETE FROM orders WHERE id = 10      ← orphanRemoval!

Без orphanRemoval:
  user.getOrders().remove(order)
  userRepository.save(user)
  → UPDATE orders SET user_id = NULL WHERE id = 10
  ⚠️ Строка осталась в БД, просто без владельца!
```

Java

```
@Service
@Transactional
public class OrderService {

    public void cancelOrder(Long userId, Long orderId) {
        User user = userRepository.findById(userId).orElseThrow();

        // orphanRemoval = true обеспечит DELETE автоматически
        user.getOrders().removeIf(o -> o.getId().equals(orderId));
        // Не нужно вызывать orderRepository.delete() — Hibernate сделает сам
    }
}
```

> **💡 Важно:** `orphanRemoval = true` неявно включает поведение `CascadeType.REMOVE` (удаление родителя удаляет детей). Но `CascadeType.REMOVE` **не** включает `orphanRemoval`. `orphanRemoval` работает только для `@OneToOne` и `@OneToMany`.

## 12. LazyInitializationException

> 🎯 **Уровень: Senior**

### Воспроизведение проблемы

Java

```
// Service: транзакция открывается и закрывается здесь
@Service
public class OrderService {
    @Transactional(readOnly = true)
    public Order getOrder(Long id) {
        return orderRepository.findById(id).orElseThrow();
        // ← Session закрывается здесь! order.user — это proxy без Session
    }
}

// Controller: Session уже закрыта
@RestController
public class OrderController {
    @GetMapping("/orders/{id}")
    public String getInfo(@PathVariable Long id) {
        Order order = orderService.getOrder(id);
        return order.getUser().getName(); // 💥 LazyInitializationException!
        // proxy пытается выполнить SELECT, но Session уже закрыта
    }
}
```

### Open Session in View — замаскированная проблема

YAML

```
# Spring Boot по умолчанию:
spring:
  jpa:
    open-in-view: true  # ⚠️ ВКЛЮЧЕНО ПО УМОЛЧАНИЮ!
```

text

```
━━━ ЧТО ДЕЛАЕТ OSIV И ПОЧЕМУ ЭТО АНТИПАТТЕРН ━━━

С OSIV = true (по умолчанию):
  HTTP Request → [Session открыта] → Controller → Service (@Transactional)
                      ↑_____________________________________↑
                          Session живёт весь HTTP-запрос!

  Проблемы:
  1. Соединение с БД занято весь HTTP-запрос (утечки при медленных клиентах)
  2. Неявные SELECT в Controller/View-слое — скрытая N+1 проблема
  3. Ложная безопасность: LazyInitializationException не возникает в dev,
     но появляется в prod при отключении OSIV
  4. Нарушение разделения ответственности: JPA-код "утекает" в View-слой

С OSIV = false (рекомендуется):
  HTTP Request → Controller → Service (@Transactional начало)
                              ↕ Session открыта только здесь ↕
                              Service (@Transactional конец) → Response
  LazyInitializationException явно указывает на проблему → решаешь правильно
```

**Отключите OSIV:**

properties

```
# application.properties — рекомендуется добавить в любой Spring Boot проект
spring.jpa.open-in-view=false
```

### Три правильных решения

**Решение 1: JOIN FETCH в `@Query`**

Java

```
public interface OrderRepository extends JpaRepository<Order, Long> {

    @Query("SELECT o FROM Order o JOIN FETCH o.user WHERE o.id = :id")
    Optional<Order> findByIdWithUser(@Param("id") Long id);
}

// В Service:
@Transactional(readOnly = true)
public Order getOrderWithUser(Long id) {
    return orderRepository.findByIdWithUser(id).orElseThrow();
    // User уже загружен — нет LazyInitializationException
}
```

**Решение 2: `@EntityGraph`**

Java

```
public interface OrderRepository extends JpaRepository<Order, Long> {

    @EntityGraph(attributePaths = {"user"})
    Optional<Order> findById(Long id);
}
```

**Решение 3: DTO Projection (лучшее — см. также статью [6.6](https://arena.ai/c/019cbbb0-eea4-7129-8324-13de82856284))**

Java

```
// DTO без двунаправленных ссылок — нет LazyInitializationException,
// нет circular reference, только нужные данные
public record OrderSummaryDto(Long orderId, String status, String userName) {}

public interface OrderRepository extends JpaRepository<Order, Long> {
    @Query("""
        SELECT new com.example.shop.dto.OrderSummaryDto(o.id, o.status, o.user.name)
        FROM Order o
        WHERE o.id = :id
        """)
    Optional<OrderSummaryDto> findOrderSummaryById(@Param("id") Long id);
    // ⚠️ Имя класса в JPQL — если измените пакет DTO, запрос сломается!
    // Альтернатива: Interface-based Projection (не требует полного имени класса)
}
```

> **💡 Важно:** `LazyInitializationException` — это не баг, а сигнал. Он говорит: "ты обратился к данным, которые не загрузил". Правильная реакция — не включать OSIV, а загружать данные явно там, где они нужны. Подробнее об обработке JPA-исключений — в статье [6.8](https://arena.ai/c/019cbbb0-eea4-7129-8324-13de82856284).

## 13. N+1 проблема и решения

> 🎯 **Уровень: Senior**

### Как возникает N+1

Java

```
@Transactional(readOnly = true)
public void generateReport() {
    List<Order> orders = orderRepository.findAll(); // 1 запрос

    for (Order order : orders) {
        // Каждое обращение к LAZY-полю = отдельный SELECT!
        System.out.println(order.getUser().getName()); // +1 запрос
    }
    // Итого: 1 + N запросов
}
```

text

```
━━━ N+1 VS РЕШЕНИЯ (пример: 100 заказов) ━━━

❌ БЕЗ ОПТИМИЗАЦИИ:
  Запрос   1: SELECT * FROM orders                     ← 1
  Запрос   2: SELECT * FROM users WHERE id = 1         ← +1
  Запрос   3: SELECT * FROM users WHERE id = 2         ← +1
  Запрос   4: SELECT * FROM users WHERE id = 1         ← +1 (дубликат!)
  ...
  Запрос 101: SELECT * FROM users WHERE id = 87        ← +1
  ИТОГО: 101 запрос 🔴

✅ @EntityGraph / JOIN FETCH:
  Запрос   1: SELECT o.*, u.* FROM orders o
              LEFT JOIN users u ON o.user_id = u.id    ← 1 запрос с JOIN
  ИТОГО: 1 запрос 🟢

✅ @BatchSize(size = 25):
  Запрос   1: SELECT * FROM orders                     ← 1
  Запрос   2: SELECT * FROM users WHERE id IN (1..25)  ← пачка 1
  Запрос   3: SELECT * FROM users WHERE id IN (26..50) ← пачка 2
  Запрос   4: SELECT * FROM users WHERE id IN (51..75) ← пачка 3
  Запрос   5: SELECT * FROM users WHERE id IN (76..100)← пачка 4
  ИТОГО: 5 запросов 🟡
```

### Решения

**@EntityGraph и JOIN FETCH — уже показаны в разделе 9**

**@BatchSize — для случаев, когда JOIN нежелателен:**

Java

```
import org.hibernate.annotations.BatchSize;

@Entity
public class Order {

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "user_id")
    // Hibernate загрузит users пачками через IN-clause
    // вместо N отдельных SELECT
    @BatchSize(size = 25)
    private User user;
}
```

Или глобально для всего приложения:

YAML

```
# application.yml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 25
        # Рекомендуемые значения: 10–30
        # @BatchSize на конкретном поле переопределяет глобальный
```

**Decision Matrix: когда что использовать:**

text

```
Сценарий                                    → Решение
──────────────────────────────────────────────────────────
Одна Entity + 1-2 связи                    → JOIN FETCH или @EntityGraph
Список Entity + ToOne связь                → @EntityGraph на findAll()
Список Entity + ToMany коллекция           → @BatchSize глобально
Только чтение, конкретные поля             → DTO Projection (лучший вариант)
Пагинация + связи                          → DTO Projection или 2 запроса
Срочная оптимизация без рефакторинга       → @BatchSize глобально
```

## 14. Circular Reference при сериализации

> 🎯 **Уровень: Senior**

### Проблема

Java

```
// Controller возвращает Entity — Jackson видит бесконечный граф:
// User → orders → Order → user → User → orders → ...
@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    return userService.findById(id); // 💥 StackOverflowError или бесконечный JSON
}
```

### Три решения (от худшего к лучшему)

Java

```
// ⚠️ Вариант 1: @JsonManagedReference / @JsonBackReference (костыль)
// Связывает Entity с деталями сериализации — нарушение SRP
@JsonManagedReference
private List<Order> orders;  // сериализуется

@JsonBackReference
private User user;  // НЕ сериализуется (нет поля "user" в JSON)

// ⚠️ Вариант 2: @JsonIgnoreProperties (чуть лучше, но тоже костыль)
@JsonIgnoreProperties("user")
private List<Order> orders;

// ✅ Вариант 3: DTO (единственное правильное решение — убирает проблему на корню)
// DTO не имеет двунаправленных ссылок — нет рекурсии
```

Java

```
// ✅ Правильный подход: DTO-слой полностью контролирует JSON
public record UserResponse(
    Long id,
    String email,
    String name,
    List<OrderBrief> orders  // нет обратной ссылки на User!
) {
    public record OrderBrief(Long id, String status) {}
}

@Service
@Transactional(readOnly = true)
public class UserService {

    public UserResponse getUserWithOrders(Long id) {
        User user = userRepository.findById(id).orElseThrow();

        List<UserResponse.OrderBrief> briefs = user.getOrders().stream()
            .map(o -> new UserResponse.OrderBrief(o.getId(), o.getStatus()))
            .toList();

        return new UserResponse(user.getId(), user.getEmail(), user.getName(), briefs);
    }
}

// Controller возвращает DTO — никакой рекурсии
@RestController
public class UserController {
    @GetMapping("/users/{id}")
    public UserResponse getUser(@PathVariable Long id) {
        return userService.getUserWithOrders(id); // ✅ DTO, не Entity
    }
}
```

> **💡 Важно:** DTO решает circular reference на корню, а не маскирует его. Подробнее о DTO-паттерне и маппинге — в статье [6.6 DTO и маппинг](https://arena.ai/c/019cbbb0-eea4-7129-8324-13de82856284). Никогда не возвращайте Entity напрямую из Controller.

## 15. Тестирование связей

> 🎯 **Уровень: Senior**

### Ключевой паттерн: flush + clear

text

```
┌─────────────────────────────────────────────────────────────┐
│               PERSISTENCE CONTEXT                           │
│  user (managed) → order1 (managed) → order2 (managed)      │
└──────────────────────────┬──────────────────────────────────┘
                           │ em.flush()
                           ▼  (записывает изменения в БД, в рамках транзакции)
                      ┌─────────┐
                      │   БД    │
                      │ INSERT  │ users, orders
                      └────┬────┘
                           │ em.clear()
                           ▼  (очищает кеш Persistence Context)
┌─────────────────────────────────────────────────────────────┐
│               PERSISTENCE CONTEXT (пустой)                  │
│  следующий findById() → честный SELECT из БД ✅             │
└─────────────────────────────────────────────────────────────┘
```

### Тесты

Java

```
package com.example.shop.repository;

import com.example.shop.entity.*;
import org.hibernate.Hibernate;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;

import java.math.BigDecimal;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest
// По умолчанию использует встроенную H2. Для реальной БД:
// @AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
class EntityRelationshipTest {

    @Autowired
    private TestEntityManager em;

    @Autowired
    private UserRepository userRepository;

    // ━━━ Тест 1: каскадное сохранение ━━━
    @Test
    void cascadePersist_savingUser_shouldAutomaticallySaveOrders() {
        // Arrange
        User user = new User("cascade@test.com", "Cascade Test");
        user.addOrder(new Order("PENDING", user));
        user.addOrder(new Order("SHIPPED", user));

        // Act: сохраняем ТОЛЬКО User — CascadeType.ALL сохранит Orders
        userRepository.save(user);
        em.flush();
        em.clear(); // очищаем кеш — следующий запрос пойдёт в БД, не в кеш

        // Assert
        User found = userRepository.findById(user.getId()).orElseThrow();
        // Инициализируем LAZY коллекцию внутри транзакции теста
        assertThat(found.getOrders()).hasSize(2);
        assertThat(found.getOrders())
            .extracting(Order::getStatus)
            .containsExactlyInAnyOrder("PENDING", "SHIPPED");
    }

    // ━━━ Тест 2: orphanRemoval ━━━
    @Test
    void orphanRemoval_removingFromCollection_shouldDeleteFromDb() {
        // Arrange
        User user = new User("orphan@test.com", "Orphan Test");
        Order order = new Order("PENDING", user);
        user.addOrder(order);
        em.persistAndFlush(user);
        Long orderId = order.getId();
        em.clear();

        // Act: убираем Order из коллекции
        User found = userRepository.findById(user.getId()).orElseThrow();
        Order toRemove = found.getOrders().get(0);
        found.removeOrder(toRemove); // helper-метод
        em.flush();
        em.clear();

        // Assert: Order удалён из БД (не просто из коллекции в памяти)
        assertThat(em.find(Order.class, orderId)).isNull();
    }

    // ━━━ Тест 3: LAZY загрузка ━━━
    @Test
    void lazyCollection_shouldNotLoadUntilAccessed() {
        // Arrange
        User user = new User("lazy@test.com", "Lazy Test");
        user.addOrder(new Order("PENDING", user));
        em.persistAndFlush(user);
        em.clear();

        // Act: загружаем User — orders ещё не загружены
        User found = userRepository.findById(user.getId()).orElseThrow();

        // Assert: proxy не инициализирован
        assertThat(Hibernate.isInitialized(found.getOrders())).isFalse();

        // Act: обращаемся к коллекции внутри транзакции — OK, Session активна
        int size = found.getOrders().size();

        // Assert: теперь загружена
        assertThat(Hibernate.isInitialized(found.getOrders())).isTrue();
        assertThat(size).isEqualTo(1);
    }

    // ━━━ Тест 4: @MapsId для @OneToOne ━━━
    @Test
    void mapsId_profile_shouldSharePrimaryKeyWithUser() {
        // Arrange
        User user = new User("profile@test.com", "Profile Test");
        em.persistAndFlush(user); // User получает id из БД

        UserProfile profile = new UserProfile(user, "Java developer");
        user.setProfile(profile); // через helper-метод
        em.flush();
        em.clear();

        // Assert: PK профиля = PK пользователя (общий PK)
        UserProfile foundProfile = em.find(UserProfile.class, user.getId());
        assertThat(foundProfile).isNotNull();
        assertThat(foundProfile.getId()).isEqualTo(user.getId());
        assertThat(foundProfile.getBio()).isEqualTo("Java developer");
    }

    // ━━━ Тест 5: промежуточная Entity с доп. полями ━━━
    @Test
    void orderItem_shouldPersistQuantityAndPrice() {
        // Arrange
        User user = new User("items@test.com", "Items Test");
        em.persist(user);
        Product product = new Product("Ноутбук", new BigDecimal("99999.00"));
        em.persist(product);
        Order order = new Order("PENDING", user);
        user.addOrder(order);
        em.persist(order);
        em.flush(); // нужно получить ID для создания OrderItemId

        // Act
        order.addItem(product, 2, new BigDecimal("99999.00"));
        em.flush();
        em.clear();

        // Assert
        Order foundOrder = em.find(Order.class, order.getId());
        assertThat(foundOrder.getOrderItems()).hasSize(1);
        OrderItem item = foundOrder.getOrderItems().get(0);
        assertThat(item.getQuantity()).isEqualTo(2);
        assertThat(item.getTotalPrice()).isEqualByComparingTo("199998.00");
    }
}
```
