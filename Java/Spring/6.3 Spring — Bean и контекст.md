## 1. Что такое Spring Bean

`[Уровень: Intern]`

> **Связь с 6.1:** В статье 6.1 мы говорили что IoC-контейнер «берёт управление на себя». Bean — это именно тот объект, которым контейнер управляет. Теперь познакомимся с ним лично.

### Аналогия: ресторан и шеф-повар

Представьте ресторан. Когда вы хотите поесть, вы не идёте на кухню и не готовите сами — вы делаете заказ. **Шеф-повар** знает рецепт, ингредиенты и порядок приготовления. Вы получаете готовое блюдо.

В мире Spring:

- **Вы** (клиентский код) — посетитель, который делает заказ
- **Spring-контейнер** — шеф-повар, который всё готовит
- **Bean** — готовое блюдо, которое вы получаете

Вы не вызываете `new OrderService()` вручную. Вы объявляете потребность, а Spring создаёт и предоставляет нужный объект.

### Техническое определение

**Spring Bean** — это объект, зарегистрированный в IoC-контейнере Spring, управляемый контейнером на протяжении всего жизненного цикла: от создания до уничтожения, независимо от способа создания (конструктор, фабричный метод, `FactoryBean`).

text

```
┌─────────────────────────────┐    ┌──────────────────────────────────┐
│    Обычный Java-объект      │    │          Spring Bean              │
├─────────────────────────────┤    ├──────────────────────────────────┤
│ Создан: new MyService()     │    │ Создан: IoC-контейнером          │
│ Управляется: Garbage Coll.  │    │ Управляется: ApplicationContext  │
│ Зависимости: вручную        │    │ Зависимости: автоматически (DI)  │
│ Lifecycle: нет контроля     │    │ Lifecycle: init/destroy хуки     │
│ Тестируемость: сложно       │    │ Тестируемость: легко (DI)        │
└─────────────────────────────┘    └──────────────────────────────────┘
```

### Код: без Spring и со Spring

Java

```
// ❌ БЕЗ SPRING: жёсткая связанность, ручное управление
package com.example.demo;

public class OrderService {
    // Создаём зависимости сами — сложно тестировать и менять реализацию
    private final PaymentService paymentService = new PaymentService();
    private final NotificationService notificationService = new NotificationService();

    public void placeOrder(String orderId) {
        paymentService.charge(orderId);
        notificationService.notify("Заказ оформлен: " + orderId);
    }
}
```

Java

```
// ✅ СО SPRING: Spring создаёт и внедряет зависимости
package com.example.demo.service;

import org.springframework.stereotype.Service;

@Service // ← говорим Spring: "этот класс — бин, управляй им"
public class OrderService {

    private final PaymentService paymentService;
    private final NotificationService notificationService;

    // Spring видит конструктор и сам передаёт нужные бины
    public OrderService(PaymentService paymentService,
                        NotificationService notificationService) {
        this.paymentService = paymentService;
        this.notificationService = notificationService;
    }

    public void placeOrder(String orderId) {
        paymentService.charge(orderId);
        notificationService.notify("Заказ оформлен: " + orderId);
    }
}
```

Java

```
// Демонстрация: бин живёт в контейнере и всегда singleton по умолчанию
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.ConfigurableApplicationContext;
import com.example.demo.service.OrderService;

@SpringBootApplication
public class DemoApplication {
    public static void main(String[] args) {
        ConfigurableApplicationContext ctx =
            SpringApplication.run(DemoApplication.class, args);

        OrderService s1 = ctx.getBean(OrderService.class);
        OrderService s2 = ctx.getBean(OrderService.class);

        // true — один и тот же объект (singleton по умолчанию)
        System.out.println("Один объект? " + (s1 == s2));
        // Количество зарегистрированных бинов
        System.out.println("Бинов в контексте: " + ctx.getBeanDefinitionCount());
    }
}
```

📌 **Запомни:** Bean — не просто объект в памяти. Это объект с именем, скоупом, зависимостями и методами инициализации/уничтожения. Контейнер знает о нём всё.

## 2. ApplicationContext — контейнер бинов

`[Уровень: Intern/Junior]`

### Аналогия: городской реестр

Представьте городской реестр жителей. В нём записаны все жители (бины): их имена, адреса (зависимости), профессии (тип), статус (scope). Когда кому-то нужен врач — он не ищет врача сам по всему городу, а обращается в реестр: «дайте мне врача». Реестр знает всех врачей и предоставляет нужного.

**ApplicationContext** — это и есть такой реестр. Он знает о каждом бине всё: как создать, чем занимается, кто от него зависит, когда уничтожить.

### Что умеет ApplicationContext

ApplicationContext — центральный интерфейс IoC-контейнера Spring. Он расширяет семь интерфейсов одновременно:

text

```
ApplicationContext расширяет:
  ├── ListableBeanFactory    → перечисление всех бинов
  ├── HierarchicalBeanFactory → иерархия контейнеров
  ├── MessageSource           → интернационализация (i18n)
  ├── ApplicationEventPublisher → публикация событий
  ├── EnvironmentCapable      → доступ к Environment и @Value
  ├── ResourcePatternResolver → загрузка ресурсов (classpath:, file:)
  └── BeanFactory             → базовый DI
```

### Виды ApplicationContext

text

```
BeanFactory (interface) — базовый контейнер
  └── ApplicationContext (interface) — расширенный контейнер
        ├── AnnotationConfigApplicationContext    ← standalone / тесты
        ├── ClassPathXmlApplicationContext        ← legacy XML
        ├── GenericApplicationContext             ← программная регистрация
        └── WebApplicationContext (interface)
              ├── GenericWebApplicationContext    ← Spring MVC (современный)
              └── AnnotationConfigWebApplicationContext
```

Java

```
// Вариант 1: AnnotationConfigApplicationContext — для standalone и тестов
package com.example.demo;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import com.example.demo.service.OrderService;

@Configuration
@ComponentScan("com.example.demo.service")
class AppConfig {}

public class StandaloneDemo {
    public static void main(String[] args) {
        // try-with-resources: контекст закроется автоматически
        // @PreDestroy методы будут вызваны при закрытии
        try (var ctx = new AnnotationConfigApplicationContext(AppConfig.class)) {

            OrderService service = ctx.getBean(OrderService.class);
            service.placeOrder("ORDER-001");

            // Метаинформация о контексте
            System.out.println("Всего бинов: " + ctx.getBeanDefinitionCount());
            System.out.println("Есть OrderService? " +
                ctx.containsBean("orderService"));
        }
        // Здесь контекст закрыт, @PreDestroy вызваны
    }
}
```

Java

```
// Вариант 2: GenericApplicationContext — программная регистрация (Spring 5+)
// Используется в тестах и при динамической конфигурации
import org.springframework.context.support.GenericApplicationContext;

var ctx = new GenericApplicationContext();
// Регистрируем бин программно с лямбдой-поставщиком
ctx.registerBean("orderService", OrderService.class,
    () -> new OrderService(new PaymentService(), new NotificationService()));
ctx.refresh(); // обязательно: обрабатывает все определения
ctx.close();
```

Java

```
// Вариант 3: Spring Boot создаёт контекст автоматически
// В зависимости от classpath выбирается нужная реализация:
// - Есть spring-webmvc → AnnotationConfigServletWebServerApplicationContext
// - Нет web-зависимостей → AnnotationConfigApplicationContext
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.context.ConfigurableApplicationContext;

@SpringBootApplication
public class App {
    public static void main(String[] args) {
        // run() создаёт, настраивает и запускает контекст
        ConfigurableApplicationContext ctx =
            SpringApplication.run(App.class, args);
        // ctx уже содержит все зарегистрированные бины
    }
}
```

💡 **Важно знать:** В Spring Boot вы почти никогда не создаёте контекст вручную. Но понимание его видов помогает в тестах (`@SpringBootTest`, `@ContextConfiguration`) и при отладке проблем старта.

## 3. BeanFactory vs ApplicationContext

`[Уровень: Junior]`

`BeanFactory` — исторически первый контейнер Spring: минималистичный, ленивый. `ApplicationContext` расширяет его, добавляя всё необходимое для enterprise-разработки. Практическое правило: **всегда используйте ApplicationContext**.

|Возможность|BeanFactory|ApplicationContext|
|---|---|---|
|Базовый DI (`getBean()`)|✅|✅|
|Eager-инициализация singleton|❌ (lazy)|✅ (при старте)|
|`@Autowired` без настройки|❌|✅|
|`@PostConstruct` / `@PreDestroy`|❌|✅|
|`BeanPostProcessor` авторегистрация|❌ (вручную)|✅|
|`ApplicationEvent` / `@EventListener`|❌|✅|
|`MessageSource` (i18n)|❌|✅|
|`@Transactional` / `@Cacheable`|❌|✅|
|AOP-прокси из коробки|❌|✅|
|`@Value("${...}")`|❌|✅|
|**Когда использовать**|Embedded / IoT|**Всё остальное**|

⚠️ **Частая ошибка:** Некоторые пытаются использовать `BeanFactory` для «оптимизации». На практике выигрыш по памяти минимален (~несколько КБ), а потеря функциональности огромна. Если вы не пишете прошивку для микроконтроллера — используйте `ApplicationContext`.

## 4. Как Spring находит бины

`[Уровень: Junior]`

> **Связь с 6.2:** В нашем первом Spring Boot проекте мы добавили `@SpringBootApplication`. Эта аннотация включает Component Scanning — механизм, который мы сейчас разберём.

### Аналогия: HR-агентство с базой резюме

Представьте HR-агентство, которое ищет кандидатов. Чтобы вас нашли — нужно подать резюме с указанием специализации: «Я разработчик», «Я дизайнер». Spring делает то же самое: вы помечаете класс аннотацией (`@Service`, `@Repository`...) — это и есть «резюме». Spring сканирует пакеты и находит всех «кандидатов».

### Механизм Component Scanning

Java

```
// @SpringBootApplication включает ComponentScan автоматически
// для текущего пакета и ВСЕХ его подпакетов
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.SpringApplication;

@SpringBootApplication
// Эквивалентно:
// @SpringBootConfiguration
// @EnableAutoConfiguration
// @ComponentScan(basePackages = "com.example.demo") ← текущий пакет!
public class DemoApplication {
    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

⚠️ **Частая ошибка: класс вне scan-пакета**

Java

```
// Структура проекта:
// com.example.demo          ← @SpringBootApplication здесь
// com.example.demo.service  ← ✅ сканируется
// com.other.service         ← ❌ НЕ сканируется!

package com.other.service; // другой корневой пакет!

import org.springframework.stereotype.Service;

@Service // аннотация есть, но Spring её не увидит!
public class ExternalService {
    // При @Autowired ExternalService:
    // NoSuchBeanDefinitionException: No qualifying bean of type 'ExternalService'
}

// ✅ Решения:
// 1. Перенести класс в com.example.demo.service
// 2. Добавить @ComponentScan(basePackages = "com.other")
// 3. Зарегистрировать через @Bean в конфиг-классе
```

### Стереотипные аннотации — семантика и различия

Все четыре аннотации являются специализациями `@Component`. Разница — семантическая и, в случае `@Repository`, функциональная.

|Аннотация|Слой|Мета-аннотация|Техническое отличие|
|---|---|---|---|
|`@Component`|Любой|—|Базовая; регистрирует бин|
|`@Service`|Бизнес-логика|`@Component`|Только семантика|
|`@Repository`|Слой данных|`@Component`|**+** Трансляция DB-исключений в `DataAccessException`|
|`@Controller`|Web MVC|`@Component`|**+** Обработка HTTP через `@RequestMapping`|
|`@RestController`|Web REST|`@Controller`|**+** `@ResponseBody` на всех методах|
|`@Configuration`|Конфигурация|`@Component`|**+** CGLIB-проксирование (гарантия singleton для `@Bean`)|

Java

```
// @Repository: трансляция исключений БД — реальное функциональное отличие
package com.example.demo.repository;

import org.springframework.dao.EmptyResultDataAccessException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Repository;
import java.util.Optional;

@Repository // включает PersistenceExceptionTranslationPostProcessor
public class UserRepository {

    private final JdbcTemplate jdbcTemplate;

    public UserRepository(JdbcTemplate jdbcTemplate) {
        this.jdbcTemplate = jdbcTemplate;
    }

    public Optional<String> findNameById(Long id) {
        try {
            String name = jdbcTemplate.queryForObject(
                "SELECT name FROM users WHERE id = ?",
                String.class, id
            );
            return Optional.ofNullable(name);
        } catch (EmptyResultDataAccessException e) {
            return Optional.empty();
        }
        // JPA PersistenceException → DataAccessException происходит автоматически
        // Цепочка: @Repository → PersistenceExceptionTranslationPostProcessor
        //   → PersistenceExceptionTranslationInterceptor
        //   → HibernateExceptionTranslator / JpaDialect
        //   → DataAccessException
    }
}
```

🔬 **Под капотом:** Трансляция исключений в `@Repository` работает через `PersistenceExceptionTranslationPostProcessor` — специальный `BeanPostProcessor`, который оборачивает методы `@Repository`-бинов в прокси. Прокси перехватывает исключения и конвертирует их через `PersistenceExceptionTranslator`. Для JDBC с `JdbcTemplate` трансляция встроена в сам `JdbcTemplate`, поэтому `@Repository` там несёт только семантическую роль.

🛠️ **Сделай сам:**

## 5. @Bean vs @Component

`[Уровень: Junior/Middle]`

text

```
Q: Это мой класс (есть доступ к исходнику)?
   ├── Да → @Component / @Service / @Repository
   └── Нет (сторонняя библиотека) → @Bean (единственный вариант!)

Q: Нужна нестандартная логика создания?
   ├── Да → @Bean
   └── Нет → @Component

Q: Нужен Component Scan?
   └── Да → @Component | Нет → @Bean в @Configuration
```

Java

```
// ✅ @Bean для стороннего класса (ObjectMapper из Jackson)
package com.example.demo.config;

import com.fasterxml.jackson.databind.DeserializationFeature;
import com.fasterxml.jackson.databind.ObjectMapper;
import com.fasterxml.jackson.databind.PropertyNamingStrategies;
import com.fasterxml.jackson.databind.SerializationFeature;
import com.fasterxml.jackson.datatype.jsr310.JavaTimeModule;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class JacksonConfig {

    // ObjectMapper — чужой класс, нельзя добавить @Component
    // @Bean — единственный способ зарегистрировать его с нашей конфигурацией
    @Bean
    public ObjectMapper objectMapper() {
        ObjectMapper mapper = new ObjectMapper();
        // Нестандартная настройка — невозможно через @Component
        mapper.configure(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES, false);
        mapper.configure(SerializationFeature.WRITE_DATES_AS_TIMESTAMPS, false);
        mapper.registerModule(new JavaTimeModule());
        mapper.setPropertyNamingStrategy(PropertyNamingStrategies.SNAKE_CASE);
        return mapper;
    }
}
```

⚠️ **Частая ошибка: `@Component` вместо `@Configuration`**

Java

```
// ❌ НЕПРАВИЛЬНО: @Component не создаёт CGLIB-прокси
// serviceB() вызывается напрямую как обычный Java-метод!
// Результат: два разных объекта ServiceB — singleton нарушен
import org.springframework.stereotype.Component;
import org.springframework.context.annotation.Bean;

@Component // ← должно быть @Configuration!
public class WrongConfig {

    @Bean
    public ServiceA serviceA() {
        return new ServiceA(serviceB()); // прямой Java-вызов → новый объект!
    }

    @Bean
    public ServiceB serviceB() {
        return new ServiceB(); // вызывается дважды!
    }
}

// ✅ ПРАВИЛЬНО: @Configuration + CGLIB-прокси
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration // CGLIB создаёт подкласс, перехватывает @Bean вызовы
public class CorrectConfig {

    @Bean
    public ServiceA serviceA() {
        return new ServiceA(serviceB()); // через прокси → один и тот же ServiceB
    }

    @Bean
    public ServiceB serviceB() {
        return new ServiceB(); // создаётся строго один раз
    }
}
```

🔬 **Под капотом:** Когда Spring видит `@Configuration`, он создаёт CGLIB-подкласс. Все `@Bean`-методы в подклассе переопределяются: при вызове `serviceB()` изнутри `serviceA()` CGLIB перехватывает вызов и возвращает уже существующий бин из контейнера. Именно поэтому `@Configuration`-классы не могут быть `final` — CGLIB не наследует финальные классы. Начиная с Spring 5.2 есть `@Configuration(proxyBeanMethods = false)` — «lite mode» без CGLIB, когда `@Bean`-методы не вызывают друг друга.

## 6. Управление бинами

`[Уровень: Middle]`

### @Lazy — создание по требованию

По умолчанию Spring создаёт все singleton-бины **при старте** (eager). `@Lazy` откладывает создание до первого обращения.

Java

```
package com.example.demo.service;

import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Component;

@Component
@Lazy // создастся только при первом ctx.getBean() или @Autowired-вызове
public class HeavyReportGenerator {

    public HeavyReportGenerator() {
        // Тяжёлая инициализация: загрузка ML-модели, подключение к S3
        System.out.println("HeavyReportGenerator создан");
    }

    public byte[] generate(String type) {
        return new byte[0]; // логика генерации
    }
}
```

Java

```
// @Lazy при инжекции: прокси создаётся сразу, реальный объект — при первом вызове
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;

@Service
public class ReportService {

    @Lazy
    @Autowired
    private HeavyReportGenerator generator; // это прокси до первого вызова

    public byte[] getReport(String type) {
        // Только здесь создастся реальный HeavyReportGenerator
        return generator.generate(type);
    }
}
```

💡 **Важно знать:** `spring.main.lazy-initialization=true` делает все бины ленивыми глобально. Удобно в dev для быстрого старта, но опасно в prod: ошибки конфигурации (опечатка в `@Value`) проявятся не при старте, а при первом запросе пользователя.

## 7. Bean Scopes

`[Уровень: Middle]`

### Аналогия: парковочные места

text

```
Singleton  → место с именем «Директор». Всегда одна машина, один владелец.
Prototype  → обычные анонимные места. Каждый запрос → новое место.
Request    → место на время встречи. Встреча закончилась → место свободно.
Session    → место на весь рабочий день. Ушёл вечером → место свободно.
```

### Сравнительная таблица

|Scope|Аннотация|Создаётся|Уничтожается|`@PreDestroy`|Контекст|
|---|---|---|---|---|---|
|**singleton**|по умолчанию|При старте|При закрытии контейнера|✅|Любой|
|**prototype**|`@Scope("prototype")`|На каждый `getBean()`|GC (Spring не управляет!)|❌|Любой|
|**request**|`@RequestScope`|На каждый HTTP-запрос|Конец запроса|✅|Web|
|**session**|`@SessionScope`|На HTTP-сессию|Окончание сессии|✅|Web|
|**application**|`@ApplicationScope`|При старте ServletContext|Завершение приложения|✅|Web|
|**websocket**|`@Scope("websocket")`|На WebSocket-сессию|Закрытие WS|✅|WebSocket|

### Singleton — один на контейнер

Java

```
package com.example.demo.service;
```

## 8. Жизненный цикл бина

`[Уровень: Middle/Senior]`

> **Связь с 6.1:** В статье 6.1 мы видели что Spring «создаёт объекты и внедряет зависимости». Lifecycle — это детальный ответ на вопрос «как именно» и «в каком порядке» он это делает.

### Аналогия: жизнь сотрудника в компании

text

```
1. Найм (конструктор)           — человек приходит в компанию
2. Инструктаж (DI)              — получает рабочие инструменты
3. Знакомство с офисом (Aware)  — узнаёт где что находится
4. Испытательный срок (init)    — проверяет что всё настроено
5. Работа (бин готов)           — выполняет задачи
6. Увольнение (destroy)         — сдаёт дела и оборудование
```

### 8.1 Базовый уровень: три главные фазы `[Middle]`

Для повседневной работы достаточно знать три фазы:

text

```
РОЖДЕНИЕ                  ЖИЗНЬ                   СМЕРТЬ
─────────────────────    ──────────────────────   ────────────────────
Конструктор              Бин готов к работе       ctx.close()
@Autowired (DI)          Используется             или shutdown hook
@PostConstruct ←──────── другими бинами           @PreDestroy ←──────
                                                  Ресурсы освобождены
```

Java

```
// Самый практичный способ управлять lifecycle — @PostConstruct и @PreDestroy
package com.example.demo.service;

import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Service;
import java.util.Map;
import java.util.stream.Collectors;

@Service
public class CountryCacheService {

    @Autowired
    private CountryRepository countryRepository;

    private Map<String, Country> cache;

    // ❌ Нельзя в конструкторе: countryRepository ещё null!
    // public CountryCacheService() {
    //     this.cache = countryRepository.findAll()... // NPE!
    // }

    @PostConstruct // ✅ Здесь все @Autowired поля уже внедрены
    public void loadCache() {
        this.cache = countryRepository.findAll()
            .stream()
            .collect(Collectors.toMap(Country::getCode, c -> c));
        System.out.println("Кэш загружен: " + cache.size() + " стран");
    }

    @PreDestroy // Вызывается при ctx.close() или JVM shutdown
    public void clearCache() {
        cache.clear();
        System.out.println("Кэш очищен");
    }

    public Country findByCode(String code) {
        return cache.get(code);
    }
}
```

```
║  ║     БИН УНИЧТОЖЕН  ❌                      ║                      ║
║  ╚════════════════════════════════════════════╝                      ║
║                                                                      ║
║  ⚠️  Prototype бины: Spring НЕ вызывает фазу 7!                     ║
║  ⚠️  @PostConstruct — это часть фазы 4 (BPP.before), не после неё! ║
╚══════════════════════════════════════════════════════════════════════╝
```

🔬 **Под капотом:** Посмотрим на реальный код Spring (`AbstractAutowireCapableBeanFactory`):

Java

```
// Упрощённый исходник Spring — initializeBean()
// Именно здесь происходит вся магия инициализации
protected Object initializeBean(String beanName, Object bean,
                                 @Nullable RootBeanDefinition mbd) {
    // Шаг 1: Aware группа 1 (BeanNameAware, BeanFactoryAware...)
    invokeAwareMethods(beanName, bean);

    Object wrappedBean = bean;
    // Шаг 2: BPP.postProcessBeforeInitialization()
    // Внутри: ApplicationContextAwareProcessor (все Aware группы 2)
    // Внутри: CommonAnnotationBPP → вызывает @PostConstruct!
    wrappedBean = applyBeanPostProcessorsBeforeInitialization(wrappedBean, beanName);

    // Шаг 3: afterPropertiesSet() + custom init-method
    invokeInitMethods(beanName, wrappedBean, mbd);

    // Шаг 4: BPP.postProcessAfterInitialization()
    // Внутри: AnnotationAwareAspectJAutoProxyCreator → AOP-прокси!
    wrappedBean = applyBeanPostProcessorsAfterInitialization(wrappedBean, beanName);

    return wrappedBean;
}
```

**Ключевой вывод:** `@PostConstruct` — это НЕ отдельная фаза после `BPP.postProcessBeforeInitialization()`. Это часть этой фазы, реализованная через `CommonAnnotationBeanPostProcessor`.

### Сравнение методов lifecycle

|Подход|Привязка к Spring|Для сторонних классов|Рекомендуется|
|---|---|---|---|
|`@PostConstruct`|❌ (Jakarta EE)|❌|✅ **Да**|
|`InitializingBean.afterPropertiesSet()`|✅ Spring API|❌|⚠️ Устарело|
|`@Bean(initMethod = "...")`|❌|✅|✅ Для сторонних|
|`@PreDestroy`|❌ (Jakarta EE)|❌|✅ **Да**|
|`DisposableBean.destroy()`|✅ Spring API|❌|⚠️ Устарело|
|`@Bean(destroyMethod = "...")`|❌|✅|✅ Для сторонних|

💡 **Важно знать:** `@Bean` без явного `destroyMethod` по умолчанию ищет методы `close()` или `shutdown()` и вызывает их автоматически (`INFER_METHOD`). Чтобы отключить: `@Bean(destroyMethod = "")`.

## 9. BeanPostProcessor

`[Уровень: Senior]`

> **Переход:** Мы научились использовать готовые точки lifecycle (`@PostConstruct`, `@PreDestroy`). Теперь вопрос глубже: а что если нужно обработать не один конкретный бин, а **все бины определённого типа**? Именно для этого существует `BeanPostProcessor`.

### Аналогия: служба безопасности при входе

Представьте здание с охраной на входе и выходе. Каждый сотрудник при входе проходит через рамку металлодетектора — охрана проверяет документы (`postProcessBeforeInitialization`). При выходе — ставит отметку (`postProcessAfterInitialization`). Иногда охрана выдаёт сотруднику специальный бейдж — прокси.

`BeanPostProcessor` — это такая служба безопасности. **Каждый** бин проходит через неё при создании.

### Встроенные BPP в Spring

|BPP класс|Что обрабатывает|
|---|---|
|`AutowiredAnnotationBeanPostProcessor`|`@Autowired`, `@Value`, `@Inject`|
|`CommonAnnotationBeanPostProcessor`|`@PostConstruct`, `@PreDestroy`, `@Resource`|
|`PersistenceAnnotationBeanPostProcessor`|`@PersistenceContext`, `@PersistenceUnit`|
|`AsyncAnnotationBeanPostProcessor`|`@Async`|
|`ScheduledAnnotationBeanPostProcessor`|`@Scheduled`|
|`AnnotationAwareAspectJAutoProxyCreator`|`@Transactional`, `@Cacheable`, `@Aspect`|

Java

```
// Пример: кастомный BPP для логирования времени инициализации
package com.example.demo.infra;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.BeansException;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.stereotype.Component;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

@Component
public class InitTimingBeanPostProcessor implements BeanPostProcessor {

    private static final Logger log =
        LoggerFactory.getLogger(InitTimingBeanPostProcessor.class);

    // ConcurrentHashMap: BPP вызывается из нескольких потоков при параллельной инициализации
    private final Map<String, Long> startTimes = new ConcurrentHashMap<>();

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName)
            throws BeansException {
        // Вызывается ДО @PostConstruct / afterPropertiesSet
        startTimes.put(beanName, System.currentTimeMillis());
        return bean; // ОБЯЗАТЕЛЬНО вернуть бин! null — поломает контейнер
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName)
            throws BeansException {
        // Вызывается ПОСЛЕ @PostConstruct / afterPropertiesSet
        Long start = startTimes.remove(beanName);
        if (start != null) {
            long elapsed = System.currentTimeMillis() - start;
            if (elapsed > 100) {
                log.warn("🐢 Медленный бин '{}': инициализация заняла {}мс",
                    beanName, elapsed);
            }
        }
        // Можно вернуть ДРУГОЙ объект (прокси)!
        // Именно так работает AOP: здесь возвращается прокси вместо оригинала
        return bean;
    }
}
```

⚠️ **Важно про порядок BPP:** Когда несколько BPP зарегистрированы — порядок важен. Используйте `PriorityOrdered` или `Ordered`:

Java

```
import org.springframework.core.PriorityOrdered;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.beans.BeansException;
import org.springframework.stereotype.Component;
import org.springframework.core.Ordered;

@Component
public class FirstBeanPostProcessor implements BeanPostProcessor, PriorityOrdered {

    @Override
    public int getOrder() {
        return Ordered.HIGHEST_PRECEDENCE; // вызывается первым среди BPP
    }

    @Override
    public Object postProcessBeforeInitialization(Object bean, String beanName)
            throws BeansException {
        return bean;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName)
            throws BeansException {
        return bean;
    }
}
// Порядок вызова: PriorityOrdered BPP → Ordered BPP → остальные BPP
```

🔬 **Под капотом:** BPP-бины создаются **раньше всех остальных бинов** — это гарантирует Spring при инициализации контекста. Именно поэтому в BPP нельзя инжектировать обычные `@Autowired` бины через поля — они ещё не созданы. Используйте конструкторное внедрение или `@Lazy`.

## 10. BeanFactoryPostProcessor

`[Уровень: Senior]`

Если BPP работает с **экземплярами** бинов, то `BeanFactoryPostProcessor` (BFPP) работает с **метаданными** (`BeanDefinition`) — **до создания каких-либо бинов**.

text

```
ВРЕМЕННАЯ ШКАЛА ИНИЦИАЛИЗАЦИИ:

СТАРТ
  │
  ▼
[Загрузка BeanDefinitions] ← @Config, @Component, XML
  │
  ▼
[★ BFPP.postProcessBeanFactory()] ← Меняем BeanDefinition ЗДЕСЬ
  │   PropertySourcesPlaceholderConfigurer → обрабатывает ${...}
  │   ConfigurationClassPostProcessor → обрабатывает @Configuration
  ▼
[Создание bean instances] ← конструкторы
  │
  ▼
[★ BPP.postProcessBeforeInitialization()] ← до @PostConstruct
  │
  ▼
[@PostConstruct, afterPropertiesSet, initMethod]
  │
  ▼
[★ BPP.postProcessAfterInitialization()] ← AOP прокси
  │
  ▼
[БИНЫ ГОТОВЫ ✅]
```

Java

```
// Пример BFPP: изменяем BeanDefinition для всех бинов из пакета "service"
// ⚠️ ВАЖНО: не используйте @Autowired в BFPP! Реализуйте EnvironmentAware.
package com.example.demo.infra;

import org.springframework.beans.BeansException;
import org.springframework.beans.factory.config.BeanDefinition;
import org.springframework.beans.factory.config.BeanFactoryPostProcessor;
import org.springframework.beans.factory.config.ConfigurableListableBeanFactory;
import org.springframework.context.EnvironmentAware;
import org.springframework.core.env.Environment;
import org.springframework.core.env.Profiles;
import org.springframework.stereotype.Component;

@Component
public class DevLazyInitBFPP implements BeanFactoryPostProcessor, EnvironmentAware {

    private Environment environment;

    // ✅ EnvironmentAware вместо @Autowired Environment
    // BeanFactoryPostProcessor создаётся очень рано — @Autowired не работает!
    @Override
    public void setEnvironment(Environment environment) {
        this.environment = environment;
    }

    @Override
    public void postProcessBeanFactory(ConfigurableListableBeanFactory factory)
            throws BeansException {

        if (!environment.acceptsProfiles(Profiles.of("dev"))) {
            return; // только в dev-профиле
        }

        int modified = 0;
        for (String beanName : factory.getBeanDefinitionNames()) {
            BeanDefinition bd = factory.getBeanDefinition(beanName);

            // Пропускаем инфраструктурные бины Spring
            if (bd.getRole() == BeanDefinition.ROLE_INFRASTRUCTURE) {
                continue;
            }

            String className = bd.getBeanClassName();
            if (className != null && className.contains(".service.")) {
                bd.setLazyInit(true); // изменяем BeanDefinition до создания бинов!
                modified++;
            }
        }
        System.out.printf("[BFPP] Dev-профиль: %d service-бинов помечены lazy%n", modified);
    }
}
```

## 11. Circular Dependency

`[Уровень: Senior]`

### Аналогия: замкнутый круг рекомендаций

Вы ищете работу. Компания А говорит: «Возьмём вас только с рекомендацией от компании Б». Компания Б говорит: «Только с рекомендацией от А». Вы не можете получить ни одну — потому что ни одна не возьмёт вас первой.

Circular dependency — то же самое. Bean A не может быть создан без Bean B, Bean B — без Bean A. Кто первый? Никто.

### Демонстрация проблемы

Java

```
// ❌ BeanCurrentlyInCreationException при старте!
package com.example.demo.bad;

import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final PaymentService paymentService;

    // Spring начинает создавать OrderService → нужен PaymentService
    // Spring начинает создавать PaymentService → нужен OrderService
    // OrderService ещё создаётся! → DEADLOCK
    public OrderService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}

@Service
public class PaymentService {
    private final OrderService orderService; // ← замыкает кольцо

    public PaymentService(OrderService orderService) {
        this.orderService = orderService;
    }
}
```

text

```
Сообщение об ошибке Spring Boot 3.x:
The dependencies of some of the beans in the application context form a cycle:

orderService → paymentService
     ↑               ↓
     └───────────────┘

Action: Update your application to remove the dependency cycle.
```

### Как Spring обнаруживает: Three-Level Cache `[Senior]`

Spring использует трёхуровневый кэш для разрешения circular dependency у **singleton с field/setter injection**:

Java

```
// Три Map в DefaultSingletonBeanRegistry:

// Уровень 1: готовые бины
private final Map<String, Object> singletonObjects = new ConcurrentHashMap<>(256);

// Уровень 2: «ранние» ссылки (объект создан, но НЕ инициализирован)
private final Map<String, Object> earlySingletonObjects = new ConcurrentHashMap<>(16);

// Уровень 3: фабрики для создания early references
private final Map<String, ObjectFactory<?>> singletonFactories = new HashMap<>(16);
```

text

```
КАК РАБОТАЕТ ПРИ FIELD INJECTION (circular dep частично разрешается):

1. Создаём ServiceA → помещаем ObjectFactory в Level 3
2. ServiceA нуждается в ServiceB → начинаем создавать ServiceB
3. ServiceB нуждается в ServiceA
4. Проверяем: Level1? Нет. Level2? Нет. Level3? ДА!
5. Получаем early reference ServiceA (создан, но @PostConstruct не вызван!)
6. Early reference → Level 2
7. ServiceB получает early ServiceA, инициализируется полностью
8. ServiceA получает готовый ServiceB, завершает инициализацию
9. Готовый ServiceA → Level 1

⚠️ ВАЖНО: early reference — это объект ДО @PostConstruct!
Если @PostConstruct меняет состояние объекта — ServiceB может
получить «полусырой» ServiceA.

ПРИ CONSTRUCTOR INJECTION (circular dep НЕ разрешается):
Чтобы вызвать конструктор ServiceA → нужен готовый ServiceB.
Чтобы вызвать конструктор ServiceB → нужен готовый ServiceA.
Объект не создан → нечего помещать в Level 3 → DEADLOCK.

ДЛЯ PROTOTYPE:
Prototype не кэшируется в singletonObjects.
Spring обнаруживает кольцо через Set<String> prototypesCurrentlyInCreation
и немедленно бросает BeanCurrentlyInCreationException.
```

### Решения

**Решение 1: Рефакторинг** ✅ Лучший вариант — всегда начинайте с него

Java

```
// Причина circular dep: A знает о B, B знает об A.
// Решение: выделить общую зависимость в третий класс.
package com.example.demo.good;

import org.springframework.context.ApplicationEventPublisher;
import org.springframework.stereotype.Service;

// Общая зависимость без кольца
@Service
public class OrderEventPublisher {
    private final ApplicationEventPublisher publisher;

    public OrderEventPublisher(ApplicationEventPublisher publisher) {
        this.publisher = publisher;
    }

    public void publishOrderCreated(String orderId) {
        System.out.println("Событие: заказ создан " + orderId);
    }
}

@Service
public class OrderService {
    private final OrderEventPublisher events; // нет зависимости от PaymentService

    public OrderService(OrderEventPublisher events) {
        this.events = events;
    }
}

@Service
public class PaymentService {
    private final OrderEventPublisher events; // нет зависимости от OrderService

    public PaymentService(OrderEventPublisher events) {
        this.events = events;
    }
}
```

**Решение 2: `@Lazy`** ✅ Когда рефакторинг невозможен

Java

```
import org.springframework.context.annotation.Lazy;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private final PaymentService paymentService;

    // Spring передаст прокси PaymentService.
    // Реальный объект создастся при первом вызове метода.
    public OrderService(@Lazy PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

**Решение 3: Setter injection** ✅ Допустимо для некритичных случаев

Java

```
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

@Service
public class OrderService {
    private PaymentService paymentService;

    // Spring создаст объект с null, затем вызовет setter
    @Autowired
    public void setPaymentService(PaymentService paymentService) {
        this.paymentService = paymentService;
    }
}
```

properties

```
# Spring Boot 3.x: circular dependencies запрещены по умолчанию
# Явное разрешение (не рекомендуется — это обход проблемы, не решение):
spring.main.allow-circular-references=true
```

💡 **Важно знать:** Circular dependency — это всегда признак архитектурной проблемы. Первый вопрос при её возникновении: «Почему A знает о B, который знает об A?» Рефакторинг с выделением общей зависимости или событийной модели — правильный ответ в 90% случаев.

🛠️ **Сделай сам:**  
Создайте два сервиса с circular dependency через конструктор — убедитесь в ошибке при старте. Затем примените каждое из трёх решений по очереди и убедитесь что приложение запускается.

## 12. Prototype в Singleton

`[Уровень: Senior+]`

### Аналогия: дизайнер по требованию

Вместо того чтобы держать в офисе постоянного дизайнера (prototype в singleton = проблема), вы звоните в агентство (ObjectProvider) и говорите: «Пришлите дизайнера». Каждый раз агентство присылает нового специалиста. ObjectProvider — это агентство временного персонала.

### Демонстрация проблемы

Java

```
// Prototype-бин: каждый экземпляр должен быть уникальным
package com.example.demo.scope;

import org.springframework.beans.factory.config.ConfigurableBeanFactory;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;
import java.util.UUID;

@Component
@Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE)
public class PrototypeCounter {
    // Уникальный ID для демонстрации: разные ID = разные объекты
    private final String instanceId = UUID.randomUUID().toString().substring(0, 8);
    private int count = 0;

    public int increment() { return ++count; }
    public String getInstanceId() { return instanceId; }
}
```

Java

```
// ❌ ПРОБЛЕМА: prototype инжектируется в singleton ОДИН РАЗ
package com.example.demo.scope;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;

@Service // singleton: создаётся ОДИН раз
public class BrokenCounterService {

    @Autowired
    private PrototypeCounter counter; // инжектируется при создании singleton — один раз!

    public String increment() {
        // ВСЕГДА один и тот же экземпляр — prototype не работает!
        return "id=" + counter.getInstanceId() + ", count=" + counter.increment();
    }
    // Результат трёх вызовов:
    // id=abc12345, count=1
    // id=abc12345, count=2  ← тот же id! тот же объект!
    // id=abc12345, count=3  ← снова тот же!
}
```

**Почему это происходит?** Singleton создаётся один раз. При его создании Spring выполняет DI — и инжектирует prototype-бин. Один раз. После этого singleton держит ссылку на **конкретный экземпляр** — и никогда не запрашивает новый.

### Решение 1: ObjectProvider — рекомендуется ✅

Java

```
package com.example.demo.scope;

import org.springframework.beans.factory.ObjectProvider;
import org.springframework.stereotype.Service;

@Service
public class CorrectServiceV1 {

    // ObjectProvider — ленивый поставщик бинов из контейнера
    private final ObjectProvider<PrototypeCounter> counterProvider;

    public CorrectServiceV1(ObjectProvider<PrototypeCounter> counterProvider) {
        this.counterProvider = counterProvider;
    }

    public String increment() {
        // getObject() → НОВЫЙ экземпляр каждый раз!
        PrototypeCounter counter = counterProvider.getObject();
        return "id=" + counter.getInstanceId() + ", count=" + counter.increment();
    }
    // Результат:
    // id=abc12345, count=1
    // id=def67890, count=1  ← новый id! новый объект!
    // id=ghi11121, count=1  ← снова новый!
}
```

### Решение 2: @Lookup — Spring-way ✅

Java

```
package com.example.demo.scope;

import org.springframework.beans.factory.annotation.Lookup;
import org.springframework.stereotype.Service;

// Класс должен быть non-final: Spring создаёт CGLIB-подкласс
// ⚠️ НЕ работает с final классами и final методами
// ⚠️ НЕ работает если объект создан через new (вне контейнера)
@Service
public abstract class CorrectServiceV2 {

    // Spring переопределит этот метод через CGLIB:
    // каждый вызов = ctx.getBean(PrototypeCounter.class)
    @Lookup
    protected abstract PrototypeCounter getCounter();

    public String increment() {
        PrototypeCounter counter = getCounter(); // новый экземпляр каждый раз
        return "id=" + counter.getInstanceId() + ", count=" + counter.increment();
    }
}
```

### Решение 3: ApplicationContext.getBean() — Service Locator ⚠️

Java

```
package com.example.demo.scope;

import org.springframework.context.ApplicationContext;
import org.springframework.stereotype.Service;

@Service
public class CorrectServiceV3 {

    private final ApplicationContext ctx;

    public CorrectServiceV3(ApplicationContext ctx) {
        this.ctx = ctx;
    }

    public String increment() {
        // Явный запрос нового бина из контейнера
        PrototypeCounter counter = ctx.getBean(PrototypeCounter.class);
        return "id=" + counter.getInstanceId() + ", count=" + counter.increment();
    }
    // Минус: прямая зависимость от Spring API
    // Нарушает IoC — мы «тянем» зависимость сами
    // Используйте как крайний вариант
}
```

💡 **Важно знать:** Помимо Spring-специфичного `ObjectProvider`, существует стандартный JSR-330 `jakarta.inject.Provider<T>` — он работает так же, но не привязывает код к Spring API. Выбирайте `ObjectProvider` если нужны его дополнительные методы: `getIfAvailable()`, `getIfUnique()`, `stream()`.

5. Вы инжектируете prototype-бин в singleton через `@Autowired`. Приложение работает, ошибок нет, но поведение неправильное. Что происходит и как это исправить тремя способами?

<details> <summary>Ответы</summary>

**1.** `new OrderService()` — объект создан вами, Spring о нём не знает, DI не работает, lifecycle не управляется. `ctx.getBean()` — объект создан Spring, все зависимости внедрены, lifecycle управляется, по умолчанию singleton.

**2.** На `EmailSender` добавить `@Primary`, на `SmsSender` добавить `@Qualifier("smsSender")`. В месте где нужен SMS использовать `@Autowired @Qualifier("smsSender")`.

**3.** Нет, не вызывается. Spring создаёт prototype-бин и передаёт его вызывающему коду, но **не управляет его уничтожением**. `@PreDestroy` — это callback контейнера при уничтожении бина, но контейнер не отслеживает prototype после передачи.

**4.** Нет, неверно. `@PostConstruct` является **частью** фазы `BPP.postProcessBeforeInitialization()`. Он обрабатывается внутри `CommonAnnotationBeanPostProcessor`, который является BPP. Порядок: `BPP.before()` (→ внутри: `@PostConstruct`) → `afterPropertiesSet()` → `initMethod` → `BPP.after()`.

**5.** Происходит: при создании singleton Spring инжектирует prototype один раз. Все последующие вызовы используют тот же экземпляр. Три решения: (1) `ObjectProvider<T>` — вызывать `provider.getObject()` при каждом обращении; (2) `@Lookup` — метод-инъекция через CGLIB; (3) `ApplicationContext.getBean()` — напрямую, но нарушает IoC.

</details>

```
package com.example.demo.infra;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.beans.BeansException;
import org.springframework.beans.factory.SmartInitializingSingleton;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.stereotype.Component;
import java.util.concurrent.atomic.AtomicInteger;

@Component
public class BeanCreationLogger implements BeanPostProcessor, SmartInitializingSingleton {

    private static final Logger log = LoggerFactory.getLogger(BeanCreationLogger.class);
    private final AtomicInteger appBeanCount = new AtomicInteger(0);

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName)
            throws BeansException {

        boolean isSpringInfra = beanName.startsWith("org.springframework")
            || beanName.startsWith("spring")
            || bean.getClass().getName().startsWith("org.springframework");

        if (!isSpringInfra) {
            log.info("✅ Бин создан: '{}' ({})",
                beanName, bean.getClass().getSimpleName());
            appBeanCount.incrementAndGet();
        }

        return bean; // всегда возвращаем бин!
    }

    // SmartInitializingSingleton: вызывается ПОСЛЕ создания всех singleton-бинов
    @Override
    public void afterSingletonsInstantiated() {
        log.info("🎉 Контекст готов. Бинов приложения создано: {}", appBeanCount.get());
    }
}
```

## 14. Итоги и глоссарий

### Главные выводы

1. **Bean** — объект под управлением Spring. Не вызывайте `new` для бинов — позвольте Spring управлять их созданием и зависимостями.
2. **Scope по умолчанию** — singleton (один на контейнер). Думайте о thread-safety для stateful singleton-бинов.
3. **`@PostConstruct`** — лучшее место для инициализации (все зависимости уже внедрены). **`@PreDestroy`** — для освобождения ресурсов. Оба не работают для prototype.
4. **Circular dependency** — всегда архитектурная проблема. Начинайте с рефакторинга, не с `@Lazy`.
5. **Prototype в singleton** — тихий баг. Используйте `ObjectProvider`, `@Lookup` или event-driven подход.

### Глоссарий

#### Базовые понятия `[Intern/Junior]`

|Понятие|Определение|
|---|---|
|**Spring Bean**|Объект, созданный и управляемый IoC-контейнером Spring|
|**ApplicationContext**|Центральный IoC-контейнер с enterprise-функциями|
|**BeanFactory**|Базовый контейнер (используйте ApplicationContext)|
|**BeanDefinition**|Метаданные бина внутри контейнера (класс, scope, зависимости)|
|**@Component**|Базовая аннотация регистрации бина через Component Scan|
|**@Service**|`@Component` для бизнес-логики (только семантика)|
|**@Repository**|`@Component` + трансляция DB-исключений в `DataAccessException`|
|**@Controller**|`@Component` + обработка HTTP-запросов|
|**@Configuration**|`@Component` + CGLIB-проксирование для `@Bean`-методов|

#### Конфигурация и управление `[Middle]`

|Понятие|Определение|
|---|---|
|**@Bean**|Явное создание бина в методе `@Configuration`-класса|
|**Singleton scope**|1 экземпляр на контейнер (по умолчанию)|
|**Prototype scope**|Новый экземпляр на каждый `getBean()`|
|**Request scope**|1 экземпляр на HTTP-запрос (только web)|
|**Session scope**|1 экземпляр на HTTP-сессию (только web)|
|**Scoped Proxy**|Прокси для web-scoped бина в singleton-контексте|
|**@PostConstruct**|Инициализация после DI (Jakarta EE, не Spring API)|
|**@PreDestroy**|Очистка перед уничтожением (не вызывается для prototype)|
|**@Lazy**|Откладывает создание бина до первого обращения|
|**@Primary**|Приоритетный кандидат при неоднозначности DI|
|**@Qualifier**|Точное указание бина по имени|
|**@DependsOn**|Явный порядок создания бинов|

#### Продвинутые механизмы `[Senior/Senior+]`

|Понятие|Определение|
|---|---|
|**BeanPostProcessor**|Хук до/после инициализации каждого бина (экземпляры)|
|**BeanFactoryPostProcessor**|Модификация `BeanDefinition` до создания бинов|
|**Three-level Cache**|Механизм Spring для частичного разрешения circular dep у singleton|
|**Circular Dependency**|Кольцевые зависимости — признак архитектурной проблемы|
|**ObjectProvider**|Ленивый поставщик бинов; решение prototype-in-singleton|
|**@Lookup**|Метод-инъекция через CGLIB; решение prototype-in-singleton|
|**SmartInitializingSingleton**|Callback после создания **всех** singleton-бинов|
|**FactoryBean**|Специальный бин-фабрика; `&beanName` возвращает саму фабрику|
