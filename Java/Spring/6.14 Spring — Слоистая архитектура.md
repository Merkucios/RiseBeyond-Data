Когда проект только начинается, весь код умещается в паре файлов — и это кажется разумным. Но через несколько месяцев контроллеры пухнут, логика расползается по всему коду, и написать тест становится задачей на полдня. Принцип разделения ответственности (Separation of Concerns) даёт ответ: каждый класс отвечает ровно за один вопрос, а Spring Boot предоставляет три готовых «этажа» для распределения кода. В результате вы получаете приложение, где бизнес-логику можно протестировать за миллисекунды, а смена базы данных не затрагивает HTTP-слой.

## 1. Когда всё начинается «нормально»

> 🟢 **Уровень: Intern**

Типичная картина: стартап, первый спринт, задача — зарегистрировать пользователя. Разработчик открывает `UserController.java` и думает: _«Здесь же один метод, много кода не будет»_. Добавляет проверку email, хэширует пароль, сохраняет в БД, отправляет приветственное письмо — всё в одном методе. Работает. Дедлайн соблюдён.

Через месяц: нужна регистрация через OAuth. Копируем часть логики. Ещё через месяц: batch-импорт пользователей из CSV. Копируем снова. Потом меняется алгоритм хэширования — и нужно найти все три места...

**Симптомы деградации**, которые знакомы каждому:

- Баг в одном месте ломает другое — логика переплетена
- Невозможно написать тест без запуска всего сервера
- Новый разработчик открывает контроллер и видит 300 строк
- Любое изменение затрагивает 5 файлов сразу

Эту проблему решает **слоистая архитектура**. Давайте разберёмся, как именно.

## 2. Ресторанная аналогия: три роли, три слоя

> 🟢 **Уровень: Intern**

Прежде чем перейти к коду, посмотрим на хорошо знакомую систему — ресторан. В хорошем ресторане у каждого сотрудника своя роль. И именно поэтому ресторан работает эффективно.

text

```
╔══════════════════════════════════════════════════════════════╗
║                    РЕСТОРАН  🍽️                              ║
╠══════════════════════════════════════════════════════════════╣
║                                                              ║
║  ОФИЦИАНТ 🧑‍💼        ПОВАР 👨‍🍳          КЛАДОВЩИК 📦          ║
║                                                              ║
║  Принимает заказ   Готовит по рецепту   Выдаёт продукты     ║
║  от гостя          Применяет правила    со склада            ║
║  Возвращает блюдо  (аллергии, порции)   Ничего не готовит   ║
║                                                              ║
║  НЕ готовит еду    НЕ общается с        НЕ знает рецептов   ║
║  НЕ ходит на склад гостем напрямую      НЕ видит гостей     ║
║                                                              ║
╠══════════════════════════════════════════════════════════════╣
║                                                              ║
║                    SPRING BOOT  ☕                            ║
╠══════════════════════════════════════════════════════════════╣
║                                                              ║
║  @RestController   @Service             @Repository          ║
║                                                              ║
║  Принимает HTTP-   Выполняет            Читает/пишет         ║
║  запрос (DTO)      бизнес-логику        в базу данных        ║
║  Возвращает ответ  Применяет правила    Работает с Entity    ║
║  (DTO)             Управляет            Выполняет запросы    ║
║                    транзакцией                               ║
╚══════════════════════════════════════════════════════════════╝
```

Теперь — явная таблица соответствий:

|Ресторан|Spring Boot|Принимает / возвращает|Что делает|
|---|---|---|---|
|🧑‍💼 Официант|`@RestController`|Принимает Request DTO, возвращает Response DTO|HTTP: десериализация, валидация, делегирование|
|📋 Бланк заказа|`DTO`|Передаётся между официантом и поваром|Стандартизированная форма данных|
|👨‍🍳 Повар|`@Service`|Принимает DTO, работает с Entity внутри|Бизнес-логика, правила, транзакции|
|📦 Кладовщик|`@Repository`|Принимает/возвращает Entity|CRUD-операции, SQL/JPQL-запросы|
|🏪 Склад|Database|—|Хранит данные|

**Ключевое правило ресторана:** официант не готовит еду, повар не ходит на склад сам, кладовщик не общается с гостями. Если один человек делает всё — при первом же больничном ресторан встаёт. В коде — то же самое.

## 3. Separation of Concerns — принцип, который всё объясняет

> 🟢 **Уровень: Intern**

**Separation of Concerns (SoC)** — каждая единица кода отвечает ровно на _один_ вопрос:

- **Controller** → _«Как принять запрос и как ответить клиенту?»_
- **Service** → _«Что нужно сделать и какие правила применить?»_
- **Repository** → _«Где взять данные и как их сохранить?»_

Три практических следствия:

**Тестируемость.** Если бизнес-логика живёт в сервисе и не знает о HTTP, её можно проверить обычным Java-тестом — без MockMvc, без базы данных, за миллисекунды.

**Заменяемость.** Решили сменить PostgreSQL на MongoDB? Переписываете только Repository — Controller и Service не подозревают об изменении.

**Читаемость.** Новый разработчик смотрит на `UserService` и сразу понимает: здесь бизнес-правила. На `UserController` — здесь HTTP. На `UserRepository` — здесь запросы к БД.

text

```
┌──────────────────────────────────────────────────────────┐
│           HTTP-запрос: POST /api/users                   │
│           Body: {"email": "...", "password": "..."}      │
└────────────────────────┬─────────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│                 PRESENTATION LAYER                        │
│                  @RestController                          │
│                                                          │
│  Вопрос: КАК принять и КАК ответить?                    │
│  Принимает:  CreateUserRequest (DTO)                     │
│  Делает:     @Valid валидация → вызов сервиса            │
│  Возвращает: UserResponse (DTO) + HTTP 201               │
└────────────────────────┬─────────────────────────────────┘
                         │ CreateUserRequest (DTO)
                         ▼
┌──────────────────────────────────────────────────────────┐
│                  BUSINESS LAYER                           │
│                    @Service                               │
│                                                          │
│  Вопрос: ЧТО делать и КАКИЕ правила применить?          │
│  Принимает:  CreateUserRequest (DTO)                     │
│  Делает:     бизнес-правила, маппинг, @Transactional    │
│  Возвращает: UserResponse (DTO)                          │
└────────────────────────┬─────────────────────────────────┘
                         │ User (Entity) — только внутри слоя
                         ▼
┌──────────────────────────────────────────────────────────┐
│                 PERSISTENCE LAYER                         │

│                                                          │

## 4. Три кита Spring Boot: зоны ответственности

> 🔵 **Уровень: Junior**

### 4.1 Controller — официант на границе системы

|✅ Должен|❌ Не должен|
|---|---|
|Принимать HTTP-запрос, десериализовать тело|Содержать бизнес-if-условия|
|Запускать валидацию формата (`@Valid`)|Обращаться к Repository напрямую|
|Вызывать один метод сервиса|Возвращать JPA Entity|
|Возвращать DTO с нужным HTTP-статусом|Управлять транзакциями|
|Обрабатывать HTTP-ошибки (`@RestControllerAdvice`)|Отправлять письма / пуши|

### 4.2 Service — повар с рецептами

Мартин Фаулер (PEAA, 2002): _«Service Layer defines an application's boundary with a layer of services that establishes a set of available operations and coordinates the application's response in each operation»_.

|✅ Должен|❌ Не должен|
|---|---|
|Содержать бизнес-правила и бизнес-валидацию|Принимать `HttpServletRequest`|
|Управлять транзакциями (`@Transactional`)|Возвращать `ResponseEntity`|
|Координировать несколько репозиториев|Знать о JSON-сериализации|
|Бросать доменные исключения|Зависеть от `@RestController`|

### 4.3 Repository — кладовщик со складом

|✅ Должен|❌ Не должен|
|---|---|
|Выполнять CRUD-операции|Содержать бизнес-логику|
|Писать JPQL/SQL-запросы|Знать об HTTP или UI|
|Работать с JPA Entity|Возвращать DTO (кроме проекций)|

│       └── TaskServiceImpl.java
│
├── repository/                      ← Persistence Layer
│   ├── UserRepository.java
│   └── TaskRepository.java
│
├── entity/                          ← JPA-сущности
│   ├── User.java
│   └── Task.java
│
├── dto/                             ← Data Transfer Objects
│   ├── request/
│   │   ├── CreateUserRequest.java
│   │   └── CreateTaskRequest.java
│   └── response/
│       ├── UserResponse.java
│       └── TaskResponse.java
│
└── exception/                       ← Доменные исключения
    ├── UserNotFoundException.java
    └── EmailAlreadyTakenException.java
```

> 💡 **Почему `@Service` vs `@Component` vs `@Repository`?**
> 
> Все три — синонимы `@Component` для Spring IoC-контейнера. Разница семантическая:  
> `@Repository` дополнительно активирует перевод JPA-исключений в Spring `DataAccessException`.  
> `@Service` — сигнал команде: здесь бизнес-логика.  
> Используйте правильную аннотацию — это документация в коде.

## 6. Правило направленных зависимостей

> 🔵 **Уровень: Junior**

### 6.1 Железное правило: только сверху вниз

Представьте армейскую цепочку командования: солдат выполняет приказы сержанта, сержант — лейтенанта. Солдат не командует лейтенантом. Если каждый мог бы командовать каждым — армия превратилась бы в хаос. С зависимостями в коде — то же самое.

text

```
✅ ПРАВИЛЬНО                      ❌ ЗАПРЕЩЕНО

Controller                        Controller ─────────────→ Repository
    │                             (перескок: нет транзакций,
    │ зависит от                   нет бизнес-логики,
    ▼                              Entity утекает в JSON)
  Service
    │                             Controller A ──→ Controller B
    │ зависит от                  (горизонталь: HTTP вызывает HTTP,
    ▼                              скрытая связность между фичами)
Repository
    │                             Repository ──→ Service
    │                             (инверсия: нижний слой знает
    ▼                              о верхнем, невозможно
  Database                        переиспользовать Repository)
```

### 6.2 Конкретный пример нарушения и исправления

Java

```

import com.example.app.entity.User;               // Entity в контроллере

        // 1. Нет транзакции → LazyInitializationException при сериализации
        // 2. Entity в JSON → поле password видно всем
        // 3. Нет бизнес-валидации
        // 4. Логику findUser() нельзя переиспользовать
        return userRepository.findById(id).orElseThrow();
    }
}

## 7. Антипаттерн: Pass-through Service

> 🟡 **Уровень: Middle**

Разобравшись с Fat Controller, разработчики иногда впадают в противоположную крайность. Сделали три слоя — но сервис ничего не делает:

Java

```
// ❌ АНТИПАТТЕРН: Pass-through Service — бессмысленный слой

import com.example.app.entity.Task;              // возвращает Entity!
import com.example.app.repository.TaskRepository;
import org.springframework.stereotype.Service;
import lombok.RequiredArgsConstructor;
import java.util.List;

@Service
@RequiredArgsConstructor
public class TaskService {

    private final TaskRepository taskRepository;

    // Каждый метод — просто делегирование. Зачем этот класс?
    public List<Task> findAll() {
        return taskRepository.findAll();   // транзит
    }

    public Task save(Task task) {          // принимает Entity!
        return taskRepository.save(task); // транзит
    }

    public void deleteById(Long id) {
        taskRepository.deleteById(id);    // транзит
    }
}
```

**Проблемы:** контроллер вынужден самостоятельно маппить DTO → Entity, Entity утекает в HTTP-слой, нет ни одного бизнес-правила, нет транзакционных гарантий для сложных операций.

**Когда тонкий сервис оправдан?** Для простых справочников — нормально. Но даже «пустой» сервис должен добавлять ценность:

Java

```
// ✅ Тонкий сервис с реальной ценностью

import com.example.app.dto.request.CreateTaskRequest;
import com.example.app.dto.response.TaskResponse;
import com.example.app.entity.Task;
import com.example.app.entity.TaskStatus;
import com.example.app.exception.TaskNotFoundException;
import com.example.app.repository.TaskRepository;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.util.List;

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true) // оптимизация: Hibernate отключает dirty checking
public class TaskServiceImpl implements TaskService {

    private final TaskRepository taskRepository;

    @Override
    public List<TaskResponse> findAll() {
        return taskRepository.findAll().stream()
            .map(this::toResponse)  // маппинг DTO здесь, Entity не утекает
            .toList();
    }

    @Override
    @Transactional                  // read-write для операций записи
    public TaskResponse create(CreateTaskRequest request) {
        Task task = new Task();
        task.setTitle(request.title());
        task.setStatus(TaskStatus.OPEN);
        return toResponse(taskRepository.save(task));
    }

    private TaskResponse toResponse(Task task) {
        return new TaskResponse(task.getId(), task.getTitle(), task.getStatus());
    }
}
```

**Правило большого пальца:** если задаёте себе вопрос «зачем нужен этот сервис?» — проверьте:

1. Есть ли `@Transactional`? → Уже ценность
2. Есть ли маппинг Entity → DTO? → Уже ценность
3. Есть ли хоть одно бизнес-правило? → Тем более нужен
4. Если ответы «нет» на всё — возможно, для совсем простого CRUD контроллер _может_ обратиться к репозиторию напрямую. Но будьте честны: такие случаи редки и проект вырастает быстро.

## 8. Рефакторинг Fat Controller: шаг за шагом

> 🔵 **Уровень: Junior / Middle**

Посмотрим на код, в котором каждый тег означает отдельную зону ответственности.

### 8.1 Исходный Fat Controller — диагностика

> ⚠️ **Антипаттерн ниже.** Читайте теги в комментариях: `[HTTP]` — работа с запросом/ответом, `[BUSINESS]` — бизнес-правила, `[DB]` — доступ к данным, `[INFRA]` — инфраструктура (почта, логи), `[TX]` — управление транзакцией.

Java

```
// ❌ АНТИПАТТЕРН: Fat Controller — пять зон ответственности в одном методе

import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import lombok.extern.slf4j.Slf4j;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.http.ResponseEntity;
import org.springframework.mail.SimpleMailMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.bind.annotation.*;
import java.time.LocalDateTime;
import java.util.HashMap;
import java.util.Map;

@RestController
@RequestMapping("/api/users")
public class UserController {

    @PersistenceContext
    private EntityManager entityManager;     // [DB] прямой доступ к Hibernate!

    @Autowired
    private JavaMailSender mailSender;       // [INFRA] инфраструктура в контроллере

    @Autowired
    private PasswordEncoder passwordEncoder; // [BUSINESS] в контроллере

    @PostMapping
    @Transactional                           // [TX] транзакция на контроллере!
    public ResponseEntity<?> registerUser(@RequestBody Map<String, String> body) {

        // [HTTP] ручная работа с сырым Map вместо DTO
        String email = body.get("email");

        // [BUSINESS] бизнес-валидация прямо здесь
        if (email == null || !email.contains("@")) {
            return ResponseEntity.badRequest().body("Invalid email");
        }

        // [DB] + [BUSINESS] JPQL-запрос строкой прямо в контроллере!
        Long count = (Long) entityManager
            .createQuery(
                "SELECT COUNT(u) FROM User u WHERE u.email = :email")
            .setParameter("email", email)
            .getSingleResult();
        if (count > 0) {
            return ResponseEntity.status(409).body("Email already taken");
        }

        // [BUSINESS] хэширование пароля в контроллере
        String rawPassword = body.get("password");
        if (rawPassword == null || rawPassword.length() < 8) {
            return ResponseEntity.badRequest().body("Password too short");
        }
        String hashedPassword = passwordEncoder.encode(rawPassword);

        // [DB] создание Entity и persist через EntityManager
        User user = new User();
        user.setEmail(email);
        user.setPassword(hashedPassword);
        user.setCreatedAt(LocalDateTime.now());
        user.setRole("USER");
        entityManager.persist(user);

        // [INFRA] отправка письма прямо в контроллере
        SimpleMailMessage message = new SimpleMailMessage();
        message.setTo(email);
        message.setSubject("Welcome!");
        message.setText("Hello, " + email + "!");
        mailSender.send(message);

        // [HTTP] ручное формирование JSON
        Map<String, Object> response = new HashMap<>();
        response.put("id", user.getId());
        response.put("email", user.getEmail());

        // [INFRA] логирование через System.out вместо Logger
        System.out.println("User registered: " + email);

        return ResponseEntity.status(201).body(response);
    }
}
```

Пять тегов в одном методе. Задайте себе три вопроса:

1. Как написать unit-тест для правила «пароль < 8 символов» без запуска сервера?
2. Как переиспользовать логику регистрации в batch-скрипте?
3. Как изменить хранилище с PostgreSQL на Mongo, не трогая HTTP-логику?

Если ни один ответ не очевиден — перед нами именно та проблема, которую решает рефакторинг.

### 8.2 Шаг 0: Методика аудита

Возьмите любой подозрительный метод. Пометьте каждую строку тегом: `[HTTP]`, `[BUSINESS]`, `[DB]`, `[INFRA]`. Если тегов три и больше — метод делает слишком много. **Цель рефакторинга:** в контроллере остаётся только `[HTTP]`.

### 8.3 Шаг 1: Вводим DTO и декларативную валидацию

Заменяем `Map<String, String>` на типизированный DTO. Валидация становится декларативной — `@Valid` делает всё за нас:

Java

```

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

public record CreateUserRequest(

    @NotBlank(message = "Email is required")
    @Email(message = "Invalid email format")
    String email,

    @NotBlank(message = "Password is required")
    @Size(min = 8, message = "Password must be at least 8 characters")
    String password

) {}

// dto/response/UserResponse.java
import com.example.app.entity.UserRole;
import java.time.LocalDateTime;

public record UserResponse(
    Long id,
    String email,
    UserRole role,
    LocalDateTime createdAt
) {}
```

> ✅ **После шага 1:** убраны ручные проверки формата и сырой `Map`. В контроллере осталось: `[HTTP]`, `[BUSINESS]`, `[DB]`, `[INFRA]` — прогресс есть, продолжаем.

### 8.5 Шаг 3: Выносим бизнес-логику в Service

Java

```
// service/UserService.java — интерфейс (контракт слоя)
import com.example.app.dto.request.CreateUserRequest;
import com.example.app.dto.response.UserResponse;

public interface UserService {
    UserResponse register(CreateUserRequest request);
    UserResponse findById(Long id);
}

// service/impl/UserServiceImpl.java — реализация
import com.example.app.dto.request.CreateUserRequest;
import com.example.app.dto.response.UserResponse;
import com.example.app.entity.User;
import com.example.app.entity.UserRole;
import com.example.app.exception.EmailAlreadyTakenException;
import com.example.app.exception.UserNotFoundException;
import com.example.app.repository.UserRepository;
import com.example.app.service.EmailService;
import com.example.app.service.UserService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
@Slf4j
public class UserServiceImpl implements UserService {

    private final UserRepository userRepository;
    private final PasswordEncoder passwordEncoder;
    private final EmailService emailService;

    @Override
    @Transactional
    public UserResponse register(CreateUserRequest request) {
        // [BUSINESS] проверка уникальности email
        if (userRepository.existsByEmail(request.email())) {
            throw new EmailAlreadyTakenException(request.email());
        }

        // [BUSINESS] хэширование — в правильном слое
        User user = new User();
        user.setEmail(request.email());
        user.setPassword(passwordEncoder.encode(request.password()));
        user.setRole(UserRole.USER);

        User saved = userRepository.save(user); // [DB]

        emailService.sendWelcome(saved.getEmail()); // [INFRA]

        log.info("User registered: {}", saved.getEmail()); // правильный логгер
        return toResponse(saved);
    }

    @Override
    public UserResponse findById(Long id) {
        return userRepository.findById(id)
            .map(this::toResponse)
            .orElseThrow(() -> new UserNotFoundException(id));
    }

    private UserResponse toResponse(User user) {
        return new UserResponse(
            user.getId(),
            user.getEmail(),
            user.getRole(),
            user.getCreatedAt()
        );
    }
}
```

> ✅ **После шага 3:** вся бизнес-логика и инфраструктура переехали в сервис. В контроллере осталось только: `[HTTP]`.

### 8.6 Шаг 4: Контроллер становится тонким

Java

```

## 9. Поток данных: DTO ↔ Entity — где делать маппинг?

> 🟡 **Уровень: Middle**

Теперь, когда базовые правила разобраны, перейдём к вопросу, который вызывает споры даже среди опытных разработчиков. Вы уже знаете (из статьи 6.6), зачем нужны DTO: Entity — контракт с БД, DTO — контракт с клиентом. Они меняются по разным причинам. Но кто именно отвечает за преобразование одного в другое?

text

```
HTTP-запрос (JSON)
      │
      ▼  [Jackson десериализует]
CreateUserRequest (DTO)
      │
      ▼  ★ СПОРНАЯ ТОЧКА: кто делает маппинг DTO → Entity?
User (JPA Entity)
      │
      ▼  [Hibernate — SQL INSERT]
Database
      │
      ▲  [Hibernate — SQL SELECT]
User (JPA Entity)
      │
      ▲  ★ СПОРНАЯ ТОЧКА: кто делает маппинг Entity → DTO?
UserResponse (DTO)
      │
      ▲  [Jackson сериализует]
HTTP-ответ (JSON)
```

В индустрии нет единого стандарта — есть два подхода с разными компромиссами.

### Подход A: маппинг в Controller

Controller сам преобразует DTO → Entity и Entity → DTO. Сервис работает только с Entity.

Java

```
// Подход A: Controller делает маппинг
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public UserResponse register(@Valid @RequestBody CreateUserRequest request) {
    User user = new User();
    user.setEmail(request.email());
    // Внимание: пароль ещё не хэширован — хэширование оказалось в контроллере!
    user.setPassword(request.password());

    User saved = userService.register(user); // сервис принимает Entity

    return new UserResponse(saved.getId(), saved.getEmail(),
        saved.getRole(), saved.getCreatedAt());
}
```

|✅ Плюсы|❌ Минусы|
|---|---|
|Сервис работает с Entity — нет зависимости от DTO|Entity «утекает» в Web Layer|
|Один сервис — несколько форматов DTO|Lazy-загрузка ломается вне транзакции|
||Бизнес-операции (хэширование) оказываются в контроллере|
||Контроллер знает структуру Entity|

### Подход B: маппинг в Service (рекомендуется для большинства проектов)

Java

```
// Подход B: Service делает маппинг

// Контроллер — максимально тонкий:
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public UserResponse register(@Valid @RequestBody CreateUserRequest request) {
    return userService.register(request); // не знает об Entity
}

// В сервисе — маппинг внутри @Transactional:
@Transactional
public UserResponse register(CreateUserRequest request) {
    User user = new User();
    user.setEmail(request.email());
    user.setPassword(passwordEncoder.encode(request.password())); // правильное место
    user.setRole(UserRole.USER);

    User saved = userRepository.save(user);
    emailService.sendWelcome(saved.getEmail());

    // Маппинг внутри транзакции → Lazy-коллекции доступны
    return toResponse(saved);
}
```

|✅ Плюсы|❌ Минусы|
|---|---|
|Entity не покидает сервисный слой|Сервис привязан к конкретным DTO|
|Маппинг внутри транзакции (Lazy работает)|При множестве форматов ответа — дублирование|
|Бизнес-операции (хэширование) в правильном месте|DTO из Web Layer используется в Service|
|Контроллер максимально тонкий||

> 💡 **Важно знать: это компромисс, не догма**
> 
> **Подход B** — выбор большинства Spring Boot проектов из-за безопасности с Lazy-загрузкой и правильной локализации бизнес-операций. Но если у вас один сервис обслуживает REST, gRPC и WebSocket — Подход A с отдельным `UserMapper`-компонентом может оказаться удобнее.
> 
> **Главное правило, которое не обсуждается:** Entity никогда не должна появляться в JSON-ответе напрямую. Это утечка схемы БД в API-контракт: добавили колонку `internal_notes` → она автоматически в JSON. Переименовали поле в Entity → сломали всех клиентов.
> 
> Для автоматизации маппинга используйте **MapStruct** — compile-time генерация, без reflection, type-safe:
> 
> Java
> 
> ```
> // build.gradle:
> // annotationProcessor 'org.mapstruct:mapstruct-processor:1.5.5.Final'
> // implementation 'org.mapstruct:mapstruct:1.5.5.Final'
> 
> import org.mapstruct.Mapper;
> import org.mapstruct.Mapping;
> 
> @Mapper(componentModel = "spring")
> public interface UserMapper {
> 
>     @Mapping(target = "id", ignore = true)
>     @Mapping(target = "role", constant = "USER")
>     @Mapping(target = "createdAt", ignore = true)
>     @Mapping(target = "password", ignore = true) // хэшируется отдельно

## 10. Границы транзакций: почему @Transactional живёт в Service

> 🟡 **Уровень: Middle**

**Аналогия:** банковский перевод — снять деньги со счёта А и положить на счёт Б. Это одна операция: либо оба действия происходят, либо ни одно. Граница транзакции — «конверт», в котором оба действия атомарны. Кто определяет границы этого конверта? Только тот, кто знает бизнес-операцию — сервис.

### Почему @Transactional на Controller — плохо

Java

```
// ❌ АНТИПАТТЕРН: транзакция на контроллере

import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.bind.annotation.*;

@PostMapping("/users")
@Transactional // транзакция открывается здесь — соединение с БД занято
public ResponseEntity<UserResponse> register(
        @Valid @RequestBody CreateUserRequest request) {

    UserResponse response = userService.register(request);

    // Транзакция ещё открыта!
    // Jackson сериализует JSON — CPU работает, соединение с БД занято.
    // При 100 одновременных запросах и пуле в 10 соединений — пул исчерпан.

    return ResponseEntity.status(201).body(response);
    // Только здесь COMMIT — соединение держалось всё время сериализации
}
```

### Почему только @Transactional на Repository — недостаточно

Java

```
// ❌ НЕДОСТАТОЧНО: атомарность бизнес-операции не гарантирована

@Service
@RequiredArgsConstructor
public class UserServiceImpl implements UserService {

    // Нет @Transactional на методе сервиса:
    public UserResponse register(CreateUserRequest request) {
        User saved = userRepository.save(toEntity(request));
        // Транзакция 1: COMMIT. Пользователь сохранён.

        // Если здесь RuntimeException — пользователь уже в БД,
        // а задача не создана. Данные рассинхронизированы.
        taskRepository.save(createWelcomeTask(saved));
        // Транзакция 2: отдельный COMMIT

        return toResponse(saved);
    }
}
```

### Правильное решение: @Transactional на методе Service

Java

```
// ✅ ПРАВИЛЬНО: транзакция охватывает всю бизнес-операцию

import com.example.app.dto.request.CreateUserRequest;
import com.example.app.dto.response.UserResponse;
import com.example.app.entity.Task;
import com.example.app.entity.TaskStatus;
import com.example.app.entity.User;
import com.example.app.entity.UserRole;
import com.example.app.exception.EmailAlreadyTakenException;
import com.example.app.repository.TaskRepository;
import com.example.app.repository.UserRepository;
import com.example.app.service.EmailService;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true) // оптимизация для всего класса
@Slf4j
public class UserServiceImpl implements UserService {

    private final UserRepository userRepository;
    private final TaskRepository taskRepository;
    private final PasswordEncoder passwordEncoder;
    private final EmailService emailService;

    @Override
    @Transactional // read-write: переопределяем для операций записи
    public UserResponse register(CreateUserRequest request) {
        if (userRepository.existsByEmail(request.email())) {
            throw new EmailAlreadyTakenException(request.email());
        }

        User user = new User();
        user.setEmail(request.email());
        user.setPassword(passwordEncoder.encode(request.password()));
        user.setRole(UserRole.USER);

        User saved = userRepository.save(user);

        // Если эта строка упадёт — saved тоже откатится. Атомарно!
        taskRepository.save(createWelcomeTask(saved));

        emailService.sendWelcome(saved.getEmail());
        return toResponse(saved);
        // COMMIT только здесь. Или ROLLBACK при любом RuntimeException.
    }

    @Override
    // readOnly = true: Hibernate отключает dirty checking → быстрее на 10-30%
    public UserResponse findById(Long id) {
        return userRepository.findById(id)
            .map(this::toResponse)
            .orElseThrow(() -> new UserNotFoundException(id));
    }

    private Task createWelcomeTask(User user) {
        Task task = new Task();
        task.setTitle("Complete your profile");
        task.setUser(user);
        task.setStatus(TaskStatus.OPEN);
        return task;
    }

    private UserResponse toResponse(User user) {
        return new UserResponse(
            user.getId(), user.getEmail(),
            user.getRole(), user.getCreatedAt()
        );
    }
}
```

> ⚠️ **Антипаттерн: self-invocation ловушка**
> 
> Вызов `@Transactional`-метода из того же класса через `this.` не создаёт новую транзакцию — Spring AOP-прокси не задействуется:
> 
> Java
> 
> ```
> @Service
> public class UserServiceImpl {
> 
>     @Transactional
>     public void register(CreateUserRequest request) {
>         // ...
>         this.notifyAdmins(); // ПРОКСИ ОБХОДИТСЯ! Транзакция не создаётся.
>     }
> 
>     @Transactional(propagation = Propagation.REQUIRES_NEW)
>     public void notifyAdmins() {
>         // Эта аннотация не работает при вызове через this.
>     }
> }
> ```
> 
> **Решение:** вынести `notifyAdmins()` в отдельный Spring-бин.

> 🔬 **Под капотом: как Spring применяет @Transactional**
> 
> Spring создаёт CGLIB-прокси вокруг вашего сервиса. Когда контроллер вызывает `userService.register()`, он обращается к **прокси**, который:
> 
> 1. Открывает транзакцию (берёт соединение из пула)
> 2. Вызывает реальный метод `UserServiceImpl.register()`
> 3. Если метод завершился нормально — делает `COMMIT` и возвращает соединение в пул
> 4. Если метод бросил `RuntimeException` — делает `ROLLBACK`
> 
> При `this.method()` внутри класса вы обращаетесь к **реальному объекту**, минуя прокси — транзакция не создаётся.

## 12. Утечка абстракций: когда слои «просачиваются» друг в друга

> 🔴 **Уровень: Senior**

Утечка абстракций — нарушение SoC, которое сложнее заметить, чем Fat Controller: три слоя формально есть, но детали одного слоя проникают в другой.

**Аналогия:** представьте повара, которому перед приготовлением пасты нужно знать, приехал гость на машине или пришёл пешком. Абсурдно — способ доставки клиента не влияет на рецепт. Точно так же сервис не должен знать, пришёл запрос через HTTP, gRPC или из командной строки.

### 13.2 @WebMvcTest: тестируем только Controller

`@WebMvcTest` загружает только Web Layer: MockMvc, Jackson, валидацию, `@RestControllerAdvice`. Сервисы — моки. Реальной БД нет.

            .andExpect(status().isCreated())
            .andExpect(jsonPath("$.id").value(1))
            .andExpect(jsonPath("$.email").value("alice@example.com"));
    }

    @Test
    @DisplayName("POST /users: возвращает 400 при невалидном email")
    void register_invalidEmail_returns400() throws Exception {
        var request = new CreateUserRequest("not-an-email", "password123");

        mockMvc.perform(post("/api/v1/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content(objectMapper.writeValueAsString(request)))
            .andExpect(status().isBadRequest());

        verify(userService, never()).register(any()); // сервис не вызывается
    }

    @Test
    @DisplayName("POST /users: возвращает 409 если email занят")
    void register_emailTaken_returns409() throws Exception {
        var request = new CreateUserRequest("bob@example.com", "password123");
        when(userService.register(any()))
            .thenThrow(new EmailAlreadyTakenException("bob@example.com"));

        mockMvc.perform(post("/api/v1/users")
                .contentType(MediaType.APPLICATION_JSON)

### 13.3 Сигналы архитектурных проблем в тестах

|Симптом в тесте|Диагноз|
|---|---|
|Тест сервиса требует `@SpringBootTest`|Сервис зависит от Spring-контекста — утечка|
|Тест контроллера требует реальный Repository|Controller обходит Service Layer|
|Тест занимает >30 секунд для «unit-логики»|Слишком много интеграции, нужно изолировать|
|Для теста одного метода — 7+ моков|God Service: сервис делает слишком много|
|Нельзя протестировать без `MockHttpServletRequest`|`HttpServletRequest` в сервисе — утечка|

## 14. Под капотом: Dependency Rule и путь к Hexagonal

> 🔴 **Уровень: Senior+**

### 14.1 Dependency Rule из Clean Architecture

Роберт Мартин («Дядя Боб») в книге _Clean Architecture_ (2017) формулирует **Dependency Rule**: _«Зависимости исходного кода должны указывать только внутрь, к высокоуровневой политике»_. Иными словами, бизнес-логика не должна зависеть от деталей реализации — HTTP, SQL, фреймворков.

В слоистой архитектуре Spring Boot это правило _частично_ соблюдается: Controller зависит от Service, Service зависит от Repository. Но есть скрытая проблема.

### 14.2 Скрытая проблема: Service зависит от инфраструктуры

text

```
КЛАССИЧЕСКАЯ СЛОИСТАЯ АРХИТЕКТУРА:

  UserController
       │ зависит от
       ▼
  UserService (бизнес-логика)
       │ зависит от
       ▼
  UserRepository extends JpaRepository  ← Spring Data JPA
       │ зависит от
       ▼
  Hibernate / PostgreSQL

ПРОБЛЕМА: бизнес-логика (Service) зависит от деталей инфраструктуры (JPA).
Хотите сменить PostgreSQL на Cassandra?
UserRepository нужно переписать — и это может затронуть вызывающий код.
Хотите протестировать Service без Hibernate?
Придётся мокать интерфейс JpaRepository со всеми его методами.
```

### 14.3 Инверсия зависимостей: шаг к Hexagonal

Решение — **Dependency Inversion Principle** (D из SOLID): зависеть не от конкретной реализации, а от абстракции, определённой в том месте, которое её использует, — в домене.

> 💡 **Если этот код пока незнаком — не переживайте.** Гексагональную архитектуру мы разберём подробно в статье 6.15. Здесь лишь краткий обзор направления движения.

Java

```
// ГЕКСАГОНАЛЬНАЯ АРХИТЕКТУРА: домен определяет порт (интерфейс)
// domain/port/out/UserRepositoryPort.java
//
// Обратите внимание: НЕ extends JpaRepository!
// Это чистый Java-интерфейс без зависимостей на Spring Data.
public interface UserRepositoryPort {
    Optional<User> findByEmail(String email);
    boolean existsByEmail(String email);
    User save(User user);
    Optional<User> findById(Long id);
}

// domain/service/UserDomainService.java
// Зависит от ПОРТА, не от JpaRepository
import com.example.app.domain.port.out.UserRepositoryPort;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import lombok.RequiredArgsConstructor;

@Service
@RequiredArgsConstructor
public class UserDomainService {

    private final UserRepositoryPort userRepository; // абстракция, не JpaRepository
    // ...
}

// adapter/out/persistence/JpaUserRepositoryAdapter.java
// Адаптер реализует порт домена.
// БД — деталь, которая знает о домене, а не наоборот.
import com.example.app.domain.port.out.UserRepositoryPort;
import org.springframework.stereotype.Repository;
import lombok.RequiredArgsConstructor;

@Repository
@RequiredArgsConstructor
public class JpaUserRepositoryAdapter implements UserRepositoryPort {

    private final SpringDataUserRepository jpaRepo; // Spring Data внутри адаптера

    @Override
    public Optional<User> findByEmail(String email) {
        return jpaRepo.findByEmail(email);
    }

    @Override
    public User save(User user) {
        return jpaRepo.save(user);
    }
}
```

Теперь направление зависимостей инвертировано:

text

```
ГЕКСАГОНАЛЬНАЯ АРХИТЕКТУРА:

  REST Adapter (Controller)
       │ вызывает через входной порт
       ▼
  UserDomainService (бизнес-логика)
       │ зависит от выходного ПОРТА (интерфейс в домене)
       ▲
  JpaUserRepositoryAdapter     ← реализует порт, зависит от домена
       │ использует
       ▼
  Spring Data JPA / PostgreSQL

Теперь: Infrastructure зависит от Domain.
Domain НЕ зависит от Infrastructure.
```

### 14.4 Когда что выбирать

|Ситуация|Слоистая|Гексагональная|
|---|---|---|
|CRUD-приложение, MVP|✅ Оптимальна|Overhead не оправдан|
|Сложный домен, DDD|Начинает «скрипеть»|✅ Хорошо масштабируется|
|Частая смена БД или инфраструктуры|Болезненно|✅ Только адаптер|
|Тест домена без Hibernate|Сложно (моки JPA)|✅ Простые unit-тесты|

> 🔗 **В статье 6.15** мы разберём гексагональную архитектуру подробно: порты, адаптеры, пошаговая миграция.

```

Назовите как минимум две проблемы с этой сигнатурой.

**4.** Коллега предлагает поставить `@Transactional` на метод контроллера «чтобы не забыть». Какие конкретные проблемы это вызовет?

**🟡 Middle:**

**5.** В каком случае маппинг DTO → Entity в контроллере (Подход A) может быть оправдан? Приведите пример сценария.

<details> <summary>💡 Посмотреть ответы</summary>

**1.** Нет, это нарушение правила направленных зависимостей. Controller может зависеть только от Service. Прямое обращение к Repository из контроллера означает: нет транзакционной обёртки, нет бизнес-логики, Entity утекает в JSON, логику нельзя переиспользовать.

**2.** Сервис. Отправка письма — часть бизнес-операции «регистрация пользователя». Контроллер не знает о деталях операции, репозиторий занимается только данными. Сервис оркестрирует всю операцию, включая уведомления.

**3.** Первая: возвращает `User` (Entity), а не DTO — Entity может утечь в JSON или вызвать `LazyInitializationException`. Вторая: `orElseThrow()` без аргумента бросает `NoSuchElementException` вместо доменного `UserNotFoundException` — контроллер не сможет сформировать корректный 404-ответ.

**4.** Конкретные проблемы: (а) транзакция держит соединение с БД всё время сериализации JSON — при нагрузке исчерпывается пул соединений; (б) если сервис вызывает два репозитория, они будут в разных транзакциях — нет атомарности бизнес-операции; (в) нарушается SoC — контроллер не должен знать о транзакционных деталях.

**5.** Когда один сервисный метод обслуживает несколько форматов входных данных (REST, gRPC, GraphQL) и каждый формат имеет свой DTO. Контроллер делает маппинг своего DTO в единый доменный объект Command, который понимает сервис. Это позволяет сервису не зависеть от конкретного транспортного формата.

</details>

### Практическое задание

Возьмите следующий «монолитный» метод и разбейте его на слои:

Java

```
// Стартовый код для рефакторинга (намеренно плохой)
import jakarta.servlet.http.HttpServletRequest;
import lombok.RequiredArgsConstructor;
import org.springframework.http.ResponseEntity;
import org.springframework.mail.SimpleMailMessage;
import org.springframework.mail.javamail.JavaMailSender;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.bind.annotation.*;
import java.time.LocalDateTime;
import java.util.HashMap;
import java.util.Map;

@RestController
@RequiredArgsConstructor
public class TaskController {

    private final TaskRepository taskRepository;
    private final UserRepository userRepository;
    private final JavaMailSender mailSender;

    @PostMapping("/api/tasks")
    @Transactional
    public ResponseEntity<?> createTask(
            @RequestBody Map<String, Object> body,
            HttpServletRequest request) {

        String title = (String) body.get("title");
        if (title == null || title.isBlank()) {
            return ResponseEntity.badRequest().body("Title required");
        }

        Long assigneeId = ((Number) body.get("assigneeId")).longValue();
        User assignee = userRepository.findById(assigneeId).orElse(null);
        if (assignee == null) {
            return ResponseEntity.notFound().build();
        }

        String createdBy = request.getHeader("X-User-Email");

        Task task = new Task();
        task.setTitle(title);
        task.setAssignee(assignee);
        task.setStatus("OPEN");
        task.setCreatedBy(createdBy);
        task.setCreatedAt(LocalDateTime.now());
        taskRepository.save(task);

        SimpleMailMessage message = new SimpleMailMessage();
        message.setTo(assignee.getEmail());
        message.setSubject("New task: " + title);
        message.setText("You have a new task: " + title);
        mailSender.send(message);

        System.out.println("Task created: " + title + " by " + createdBy);

        Map<String, Object> response = new HashMap<>();
        response.put("id", task.getId());
        response.put("title", task.getTitle());
        response.put("status", task.getStatus());
        return ResponseEntity.status(201).body(response);
    }
}
```

**Требования к решению:**

1. Создайте `CreateTaskRequest` DTO с валидацией (`@NotBlank title`, `@NotNull assigneeId`)
2. Создайте `TaskResponse` DTO
3. Создайте `TaskService` с методом `createTask(CreateTaskRequest request, String createdBy)`
4. Разместите `@Transactional` в правильном месте
5. Контроллер не должен содержать бизнес-логику
6. Напишите unit-тест для `TaskService` (без Spring): кейс «исполнитель не найден»

Используйте при self-ревью или code review. Каждый вопрос — конкретная проверка, а не абстрактный принцип.

text

```
КОНТРОЛЛЕР
  [ ] Импортируется ли jakarta.servlet.* или org.springframework.web.*
      внутри моего @Service?
      (Если да — утечка HTTP в бизнес-слой)

  [ ] Возвращает ли мой @RestController JPA Entity напрямую?
      (User, Task без суффикса Response/DTO — красный флаг)

  [ ] Есть ли в методе контроллера бизнес-if-условия?
      (if (user.getBalance() < 0) — этому здесь не место)

  [ ] Есть ли @Transactional на методе контроллера?
      (Должно быть в Service)

СЕРВИС
  [ ] Могу ли я вызвать этот метод сервиса из @Scheduled
      без создания MockHttpServletRequest?
      (Если нет — HttpServletRequest или MultipartFile в сигнатуре)

  [ ] Возвращает ли мой @Service ResponseEntity<...>?
      (Не должен — это HTTP-концепция)

  [ ] Написан ли unit-тест для сервиса без @SpringBootTest?
      (Если невозможно — сервис зависит от Spring-контекста)

РЕПОЗИТОРИЙ
  [ ] Есть ли бизнес-if-условия в методах репозитория?
      (SQL/JPQL — да, бизнес-логика — нет)

  [ ] Вызывает ли репозиторий методы сервиса?
      (Нарушение правила направленных зависимостей)

ОБЩЕЕ
  [ ] Могу ли я за 10 секунд назвать, за что отвечает каждый класс?
      (Если нет — класс делает слишком много)

  [ ] При добавлении нового поля в таблицу — появляется ли оно
      автоматически в JSON-ответе API?
      (Если да — Entity утекает в API-контракт, нужен DTO)
