## 2. Паттерн Repository — зачем нужен

`[Junior]`

> _Представь библиотеку. **DAO** — это библиотекарь, который знает, в каком стеллаже стоит книга, и работает с физическим расположением. **Repository** — это поисковая система: ты говоришь «найди книги по Java», и тебя не касается, на каком стеллаже они стоят._

Паттерн Repository описал Эрик Эванс в книге «Domain-Driven Design» (2003). Главная идея: **Repository моделирует in-memory коллекцию доменных объектов**, полностью скрывая механизм хранения от вызывающего кода.

Java

```
// ❌ DAO-подход — привязан к SQL и конкретной таблице
public class UserDao {

    private final DataSource dataSource;

    // Знает про таблицы, столбцы, JDBC — инфраструктурная деталь
    public User findById(Long id) {
        String sql = "SELECT id, first_name, email FROM users WHERE id = ?";
        // ... JDBC boilerplate: Connection, PreparedStatement, ResultSet ...
        return null; // упрощено
    }
}

// ✅ Repository-подход — работает с доменом, скрывает хранилище
public interface UserRepository {
    Optional<User> findById(Long id);
    User save(User user);
    // Бизнес-ориентированные методы:
    List<User> findAllActiveInDepartment(String department);
    boolean existsByEmail(String email);
}
// Вызывающий код не знает ничего о SQL, JDBC или структуре таблиц
```

**Чем Repository отличается от DAO:**

|Критерий|DAO|Repository|
|---|---|---|
|Происхождение|Core J2EE Patterns|DDD (Eric Evans, 2003)|
|Уровень абстракции|Таблица / хранилище|Агрегатный корень|
|Гранулярность|1 DAO = 1 таблица|1 Repository = 1 агрегат|
|Ориентация API|Техническая: save/update/delete|Доменная: findAllActive/deactivate|
|Знание о БД|Присутствует|Полностью скрыто|

**Практическая ценность:**

- **Тестируемость** — подменяем реализацию на in-memory стаб без изменения бизнес-логики
- **Единое место запросов** — вся логика работы с данными сосредоточена в одном месте
- **Замена хранилища** — смена PostgreSQL на MongoDB не затрагивает сервисный слой

## 3. Иерархия интерфейсов Spring Data

`[Junior]`

Spring Data JPA строит иерархию интерфейсов по принципу **наименьшей привилегии** (Interface Segregation Principle): каждый уровень добавляет только то, что нужно. Микросервис для чтения данных не должен иметь доступ к `deleteAllInBatch()`.

text

```
Repository<T, ID>                              ← маркер, без методов
  │
  ├── CrudRepository<T, ID>                   ← базовый CRUD (Iterable)
  │     │
  │     └── ListCrudRepository<T, ID>         ← CRUD с возвратом List
  │                                             ✨ Новый в Spring Data 3.0+
  │
  ├── PagingAndSortingRepository<T, ID>       ← пагинация и сортировка
  │     │   ⚠️ Spring Data 3.0+: НЕ наследует CrudRepository!
  │     │
  │     └── ListPagingAndSortingRepository<T, ID>
  │                                             ✨ Новый в Spring Data 3.0+
  │
  └── JpaRepository<T, ID>                   ← JPA-специфичные операции
        наследует: ListCrudRepository
                 + ListPagingAndSortingRepository
                 + QueryByExampleExecutor
```

> **⚠️ Breaking change в Spring Data 3.0 (Spring Boot 3.0+):**  
> `PagingAndSortingRepository` больше **не наследует** `CrudRepository`. Это было изменено намеренно для чёткого разделения ответственности. Если тебе нужны оба набора методов — используй `JpaRepository`, который объединяет всё.

> **✨ Зачем появился `ListCrudRepository`?**  
> До Spring Data 3.0 метод `findAll()` возвращал `Iterable<T>`. Работать с ним в эпоху Stream API неудобно — приходилось писать `StreamSupport.stream(iterable.spliterator(), false).collect(toList())`. `ListCrudRepository` решает эту проблему, возвращая `List<T>` напрямую.

**Что добавляет каждый уровень:**

|Интерфейс|Ключевые методы|Тип возврата|
|---|---|---|
|`Repository`|— (только маркер)|—|
|`CrudRepository`|save, findById, findAll, deleteById, count|`Iterable<T>`|
|`ListCrudRepository`|Те же методы|**`List<T>`**|
|`PagingAndSortingRepository`|findAll(Sort), findAll(Pageable)|`Page<T>`|
|`JpaRepository`|flush, saveAndFlush, deleteAllInBatch, getReferenceById|`List<T>`, `void`|

**Когда какой интерфейс выбрать:**

|Ситуация|Рекомендация|
|---|---|
|Нужны только несколько специфических методов|`Repository` — объявляй только нужные вручную|
|Базовый CRUD, пагинация не нужна|`ListCrudRepository`|
|Нужна пагинация, JPA-специфика не нужна|`PagingAndSortingRepository`|
|**Типичный Spring JPA проект**|**`JpaRepository` ← рекомендуется по умолчанию**|
|Read-only репозиторий (принцип наименьшей привилегии)|`Repository` + явные `findBy*` методы|

### 🔬 Под капотом: как Spring создаёт реализацию

Ты не написал ни строки реализации — откуда берётся работающий репозиторий?

При старте приложения Spring Data:

1. Сканирует все интерфейсы, наследующие `Repository`
2. Для каждого создаёт **реализацию на основе `SimpleJpaRepository`**
3. Оборачивает её в **JDK Dynamic Proxy** и регистрирует как Spring Bean

Java

```
// SimpleJpaRepository — настоящая реализация всех методов JpaRepository.
// Писать самому НЕ нужно — Spring Data делает это за тебя.
// Код ниже — упрощённый показ того, что происходит внутри библиотеки.

import jakarta.persistence.EntityManager;
import org.springframework.data.jpa.repository.support.JpaEntityInformation;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Transactional;
import java.util.Optional;

@Repository
@Transactional(readOnly = true) // все методы чтения — read-only по умолчанию
public class SimpleJpaRepository<T, ID> implements JpaRepository<T, ID> {

    // EntityManager — точка входа в JPA / Hibernate
    private final EntityManager em;
    private final JpaEntityInformation<T, ?> entityInformation;

    // save() — определяет: новая сущность (persist) или существующая (merge)
    @Transactional
    public <S extends T> S save(S entity) {
        if (entityInformation.isNew(entity)) {
            em.persist(entity);  // INSERT: entity.id == null или @Version == null
            return entity;
        } else {
            return em.merge(entity); // UPDATE: entity.id уже задан
        }
    }

    // findById() — немедленный SELECT по первичному ключу
    public Optional<T> findById(ID id) {
        return Optional.ofNullable(
            em.find(entityInformation.getJavaType(), id)
        );
    }

    // ... остальные ~30 методов реализованы аналогично через EntityManager
}

// Spring создаёт JDK Dynamic Proxy примерно так (упрощённо):
// UserRepository proxy = (UserRepository) Proxy.newProxyInstance(
//     UserRepository.class.getClassLoader(),
//     new Class[]{ UserRepository.class },
//     new RepositoryFactorySupport.QueryExecutorMethodInterceptor(
//         new SimpleJpaRepository<>(User.class, entityManager)
//     )
// );
// Этот proxy и внедряется в твой @Service через @Autowired / конструктор.
```

### Все доступные методы из коробки

|Метод|SQL-операция|Особенность|
|---|---|---|
|`save(entity)`|INSERT / UPDATE|Определяет новизну по `id == null` или наличию `@Version`|
|`saveAll(entities)`|N × INSERT/UPDATE|Batch при правильной настройке Hibernate|
|`findById(id)`|`SELECT WHERE id=?`|Возвращает `Optional<T>` — никогда не `null`|
|`findAll()`|`SELECT *`|⚠️ Опасно на больших таблицах — используй с пагинацией|
|`findAllById(ids)`|`SELECT WHERE id IN(...)`|—|
|`existsById(id)`|`SELECT 1 WHERE id=?`|Эффективнее `findById` для простой проверки|
|`count()`|`SELECT COUNT(*)`|—|
|`deleteById(id)`|`DELETE WHERE id=?`|Сначала проверяет существование|
|`deleteAllInBatch()`|`DELETE FROM users`|Один запрос, без cascade и lifecycle callbacks|
|`flush()`|sync к БД|Синхронизирует без commit|
|`saveAndFlush(entity)`|INSERT/UPDATE + sync|Немедленное выполнение SQL|
|`getReferenceById(id)`|_нет SQL_|Lazy proxy — разберём в разделе 13|

`[Junior/Middle]`

Самая «магическая» возможность Spring Data: **Spring генерирует SQL-запрос автоматически**, анализируя имя метода в интерфейсе репозитория.

### Как Spring разбирает имя метода

text

```

│    │   │         │         └─ ORDER BY created_at DESC
│    │   │         └─ AND active = ?

│    └─ LIMIT 5

> 
> text

> ```
> 
> Это **fail-fast** поведение — ошибка обнаруживается сразу при деплое, а не в runtime под нагрузкой.

## 6. @Query — кастомные JPQL-запросы

`[Middle]`

Query Methods удобны для простых условий, но становятся нечитаемы при 4+ условиях или когда нужны `GROUP BY`, сложные `JOIN`, подзапросы. Здесь на помощь приходит `@Query` с JPQL.

**JPQL vs Native SQL — ключевое отличие:**

|Аспект|JPQL|Native SQL|
|---|---|---|
|Работает с|**Сущностями** (`User`, `firstName`)|**Таблицами** (`users`, `first_name`)|
|Портируемость|Любая JPA-совместимая БД|Зависит от диалекта БД|
|JOIN|По связям сущностей (`u.department.name`)|По внешним ключам (`JOIN departments d ON ...`)|
|Поддержка Hibernate|Полная|Ограниченная (нет automatic mapping)|

Java

```
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;
import java.time.LocalDateTime;
import java.util.Collection;
import java.util.List;
import java.util.Optional;

public interface UserRepository extends JpaRepository<User, Long> {

    // === Именованные параметры (рекомендуется) ===
    // В JPQL: "User" — имя класса-сущности, "u" — алиас, "u.email" — поле Java-класса
    // @Param("email") — обязательная привязка параметра метода к :email в запросе
    @Query("SELECT u FROM User u WHERE u.email = :email AND u.active = true")
    Optional<User> findActiveByEmail(@Param("email") String email);

    // === Поиск с LIKE (автоматические %) ===
    @Query("SELECT u FROM User u WHERE u.firstName LIKE %:name%")
    List<User> searchByName(@Param("name") String name);

    // === IN с коллекцией ===
    @Query("SELECT u FROM User u WHERE u.status IN :statuses ORDER BY u.createdAt DESC")
    List<User> findByStatuses(@Param("statuses") Collection<UserStatus> statuses);

    // === JOIN по связи (User → Department) ===
    @Query("SELECT u FROM User u WHERE u.department.name = :deptName AND u.active = true")
    List<User> findActiveByDepartment(@Param("deptName") String departmentName);

    // === JPQL с пагинацией ===
    @Query("SELECT u FROM User u WHERE u.active = true")
    Page<User> findAllActive(Pageable pageable);

    // === Явный COUNT-запрос (когда автоматический неэффективен) ===
    // При сложных JOIN Spring Data генерирует неоптимальный COUNT.
    // Для JPQL Spring обычно умеет сам, но при JOIN с коллекциями лучше явно:
    @Query(
        value      = "SELECT u FROM User u JOIN u.roles r WHERE r.name = :roleName",
        countQuery = "SELECT COUNT(DISTINCT u.id) FROM User u JOIN u.roles r WHERE r.name = :roleName"
    )
    Page<User> findByRoleName(@Param("roleName") String roleName, Pageable pageable);

    // === JOIN FETCH — предварительная загрузка связей (решение N+1, см. раздел 10) ===
    @Query("SELECT DISTINCT u FROM User u LEFT JOIN FETCH u.roles WHERE u.active = true")
    List<User> findAllActiveWithRoles();
}
```

> **💡 Зачем явный `@Param`, если Java может определить имя сам?**  
> С Java 8+ и флагом компилятора `-parameters` Spring Data умеет определять имена параметров автоматически. Но `@Param` — это явная документация и защита от ошибок при рефакторинге (переименовании параметра). **Рекомендуем всегда использовать `@Param` явно.**

### ⚠️ Антипаттерн: nativeQuery = true без крайней необходимости

Java

```
// ❌ ПЛОХО — привязывает приложение к конкретной СУБД
@Query(value = "SELECT * FROM users WHERE ROWNUM <= 10", nativeQuery = true)
List<User> findFirst10();
// ROWNUM — специфика Oracle! Не работает на PostgreSQL (там LIMIT) или MySQL

// ❌ ПЛОХО — дублирует то, что JPQL делает лучше и портативнее
@Query(value = "SELECT * FROM users WHERE email = :email", nativeQuery = true)
Optional<User> findByEmailNative(@Param("email") String email);
// Лучше просто: Optional<User> findByEmail(String email);

// ✅ Native SQL оправдан ТОЛЬКО когда:
// 1. Нужны специфичные для БД возможности (window functions, JSONB в PostgreSQL)
// 2. Критическая производительность, и JPQL генерирует неоптимальный план запроса
// 3. Работа с нативными типами или расширениями конкретной СУБД
@Query(
    value = """
        SELECT u.*,
               RANK() OVER (PARTITION BY u.department_id ORDER BY u.created_at) AS rnk
        FROM users u
        WHERE u.active = true
        """,
    nativeQuery = true
)
List<Object[]> findUsersWithRank(); // Window function — нет аналога в стандартном JPQL
```

## 7. @Modifying + @Transactional для UPDATE и DELETE

`[Middle]`

Для запросов, изменяющих данные (UPDATE, DELETE), обязательны обе аннотации:

- `@Modifying` — сигнализирует Spring Data, что это DML-запрос, а не SELECT
- `@Transactional` — без активной транзакции JPA не может изменять данные

Java

```
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Modifying;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;
import org.springframework.transaction.annotation.Transactional;
import java.time.LocalDateTime;

public interface UserRepository extends JpaRepository<User, Long> {

    // === Базовый UPDATE ===
    @Modifying                  // обязательно для UPDATE/DELETE
    @Transactional              // обязательно — без транзакции выброшен TransactionRequiredException
    @Query("UPDATE User u SET u.status = :status WHERE u.id = :id")
    int updateStatus(@Param("id") Long id, @Param("status") UserStatus status);
    // Возвращает количество затронутых строк (0 если не найден)

    // === DELETE через JPQL ===
    @Modifying
    @Transactional
    @Query("DELETE FROM User u WHERE u.status = :status AND u.createdAt < :before")
    int purgeOldUsers(@Param("status") UserStatus status,
                      @Param("before") LocalDateTime before);

    // === clearAutomatically = true — КРИТИЧЕСКИ ВАЖНО для корректности данных ===
    @Modifying(
        clearAutomatically = true,  // очищает 1st level cache после DML-операции
        flushAutomatically = true   // выполняет flush перед DML (синхронизирует незакрытые изменения)
    )
    @Transactional
    @Query("UPDATE User u SET u.active = false WHERE u.createdAt < :threshold")
    int deactivateOldUsers(@Param("threshold") LocalDateTime threshold);
}
```

**Зачем нужен `clearAutomatically = true`? Демонстрация проблемы:**

Java

```
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import lombok.RequiredArgsConstructor;

@Service
@RequiredArgsConstructor
public class UserService {

    private final UserRepository userRepository;

    @Transactional
    public void demonstrateStaleData(Long userId) {

        // 1. Загружаем пользователя — он попадает в 1st level cache (persistence context)
        User user = userRepository.findById(userId).get();
        System.out.println(user.getStatus()); // → "ACTIVE"

        // 2. Bulk UPDATE через @Modifying (БЕЗ clearAutomatically)
        userRepository.updateStatus(userId, UserStatus.INACTIVE);
        // SQL выполнен: UPDATE users SET status='INACTIVE' WHERE id=?

        // 3. ❌ ПРОБЛЕМА: findById возвращает объект из кэша, не из БД!
        User staleUser = userRepository.findById(userId).get();
        System.out.println(staleUser.getStatus()); // → "ACTIVE" (устаревшие данные!)
    }

    @Transactional
    public void correctVersion(Long userId) {

        User user = userRepository.findById(userId).get();
        System.out.println(user.getStatus()); // → "ACTIVE"

        // clearAutomatically = true очистит кэш после UPDATE
        userRepository.deactivateOldUsers(LocalDateTime.now().minusDays(90));

        // ✅ Теперь Spring делает свежий SELECT из БД
        User freshUser = userRepository.findById(userId).get();
        System.out.println(freshUser.getStatus()); // → "INACTIVE"
    }
}
```

**Матрица обязательных аннотаций:**

|Тип запроса|@Query|@Modifying|@Transactional|
|---|---|---|---|
|SELECT|✅|❌|Не обязательно|
|UPDATE|✅|✅|✅|
|DELETE|✅|✅|✅|
|INSERT (nativeQuery)|✅|✅|✅|

## 8. Пагинация и сортировка

`[Middle]`

> **❌ Без пагинации:**  
> `GET /api/users` → загрузка 2 000 000 записей → OutOfMemoryError на сервере, 30-секундный ответ, браузер зависает.
> 
> **✅ С пагинацией:**  
> `GET /api/users?page=0&size=20` → загрузка 20 записей → ответ за 50 мс.

### Page vs Slice vs List

|Характеристика|`Page<T>`|`Slice<T>`|`List<T>` + Pageable|
|---|---|---|---|
|COUNT-запрос к БД|✅ Да|❌ Нет|❌ Нет|
|`getTotalElements()`|✅ Да|❌ Нет|❌ Нет|
|`getTotalPages()`|✅ Да|❌ Нет|❌ Нет|
|`hasNext()`|✅ Да|✅ Да (size+1 трюк)|❌ Нет|
|SQL-запросов на вызов|**2** (data + count)|**1**|**1**|
|Когда использовать|UI с номерами страниц|Бесконечная прокрутка|Просто ограничить выборку|

Java

```
import org.springframework.data.domain.Page;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Slice;
import org.springframework.data.jpa.repository.JpaRepository;
import java.util.List;

public interface UserRepository extends JpaRepository<User, Long> {

    // Page — с COUNT-запросом (для нумерации страниц)
    Page<User> findByStatus(UserStatus status, Pageable pageable);

    // Slice — без COUNT (для "загрузить ещё" / бесконечной прокрутки)
    Slice<User> findByActive(boolean active, Pageable pageable);

    // List — просто ограничить выборку, метаданные не нужны
    List<User> findByDepartmentId(Long deptId, Pageable pageable);
}

## 9. Projection — загружаем только нужные данные

`[Middle/Senior]`

Зачем загружать все 15 полей `User` из БД, если API возвращает только три? Projection позволяет загружать **только нужные столбцы**, снижая нагрузку на БД и сеть.

Java

```
import org.springframework.beans.factory.annotation.Value;

// === 1. Interface Projection (Closed) — максимальная эффективность ===
// Spring генерирует SELECT только указанных полей
public interface UserSummary {
    Long   getId();
    String getFirstName();
    String getEmail();
    // SQL: SELECT id, first_name, email FROM users WHERE ...
    // Остальные поля (status, active, version, created_at) НЕ загружаются!
}

// Open Projection — вычисляемые поля (⚠️ загружает ВСЮ сущность через target!)
public interface UserFullName {
    @Value("#{target.firstName + ' ' + target.lastName}")
    String getFullName();
    String getEmail();
    // ⚠️ Несмотря на два поля, загружается ВЕСЬ User из-за обращения к target
}

// === 2. Вложенная проекция ===
public interface UserWithDepartment {
    String getFirstName();
    DepartmentInfo getDepartment();

    interface DepartmentInfo {
        String getName();
    }
}
```

Java

```
// === 3. Class-based Projection (DTO Record) ===
// Явный контроль через JPQL constructor expression
public record UserDto(String firstName, String email) {}
```

Java

```
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import java.util.List;

public interface UserRepository extends JpaRepository<User, Long> {

    // Interface Projection — Spring подбирает поля по именам геттеров
    List<UserSummary> findByStatus(UserStatus status);

    // Class-based через constructor expression в JPQL
    @Query("SELECT new com.example.dto.UserDto(u.firstName, u.email) " +
           "FROM User u WHERE u.active = true")
    List<UserDto> findAllActiveAsDto();

    // Dynamic Projection — один метод для разных типов возврата
    <T> List<T> findByActive(boolean active, Class<T> type);
}
```

Java

```

**Сравнение типов проекций:**

|Тип|SQL-оптимизация|Вычисляемые поля|Когда использовать|
|---|---|---|---|
|Interface Closed|✅ Только нужные|❌ Нет|API-списки, сводные данные|
|Interface Open (`@Value`)|❌ Все поля|✅ Да|Вычисляемые поля (`fullName`)|
|Class-based DTO|✅ Только нужные|Через @Query|Явный контроль над JPQL|
|Dynamic|Зависит от типа|Зависит|Один метод для разных нужд|

## 10. N+1 проблема — диагностика и решения

`[Senior]`

N+1 — **самая распространённая проблема производительности** в JPA-проектах. Суть: 1 запрос для загрузки N сущностей плюс N дополнительных запросов для каждой связанной сущности.

### Конкретные числа — почему это важно

> Если у вас **100 пользователей** и у каждого есть `Department` (загружается `LAZY`), то при обращении к `user.getDepartment().getName()` в цикле выполнится **101 SQL-запрос** вместо 1.  
> При **1000 пользователях** — **1001 запрос**.  
> При **10 000 пользователях** — **10 001 запрос**.

text

```
БЕЗ решения (N+1), 100 пользователей:

  SQL #1:    SELECT * FROM users                         → 50 мс
  SQL #2:    SELECT * FROM departments WHERE id = 1     →  2 мс
  SQL #3:    SELECT * FROM departments WHERE id = 2     →  2 мс
  SQL #4:    SELECT * FROM departments WHERE id = 3     →  2 мс
  ...
  SQL #101:  SELECT * FROM departments WHERE id = 100   →  2 мс
  ──────────────────────────────────────────────────────────────
  ИТОГО: 101 запрос, ~250 мс

С @EntityGraph (1 запрос):

  SQL #1: SELECT u.id, u.first_name, u.email, d.id, d.name
          FROM users u
          LEFT JOIN departments d ON u.department_id = d.id  → 55 мс
  ──────────────────────────────────────────────────────────────
  ИТОГО: 1 запрос, ~55 мс  (в ~4.5 раза быстрее!)

С @BatchSize(25), 100 пользователей:

  SQL #1: SELECT * FROM users                                → 50 мс
  SQL #2: SELECT * FROM departments WHERE id IN (1..25)     →  5 мс
  SQL #3: SELECT * FROM departments WHERE id IN (26..50)    →  5 мс
  SQL #4: SELECT * FROM departments WHERE id IN (51..75)    →  5 мс
  SQL #5: SELECT * FROM departments WHERE id IN (76..100)   →  5 мс
  ──────────────────────────────────────────────────────────────
  ИТОГО: 5 запросов, ~70 мс  (в ~3.5 раза быстрее!)
```

### Как обнаружить N+1 в своём проекте

Добавь в `application.properties`:

properties

```
# Показывает все SQL-запросы
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true

# Показывает параметры запросов
logging.level.org.hibernate.orm.jdbc.bind=TRACE

# Статистика Hibernate — количество запросов на операцию
spring.jpa.properties.hibernate.generate_statistics=true
logging.level.org.hibernate.stat=DEBUG
```

**Признак N+1 в логах:** десятки одинаковых `SELECT * FROM departments WHERE id = ?` с разными параметрами, следующих подряд.

    List<User> findByActiveTrue();

import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageImpl;
import org.springframework.data.domain.Pageable;
import org.springframework.data.jpa.repository.EntityGraph;
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.Query;
import org.springframework.data.repository.query.Param;
import java.util.List;

public interface UserRepository extends JpaRepository<User, Long> {

    // Шаг 1: только ID с пагинацией (лёгкий запрос без JOIN)
    @Query("SELECT u.id FROM User u WHERE u.active = true")
    Page<Long> findActiveUserIds(Pageable pageable);

    // Шаг 2: полные данные по ID с JOIN FETCH
    @EntityGraph(attributePaths = {"department", "roles"})
    @Query("SELECT u FROM User u WHERE u.id IN :ids")
    List<User> findByIdsWithDetails(@Param("ids") List<Long> ids);
}
```

Java

```
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageImpl;
import org.springframework.data.domain.Pageable;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import lombok.RequiredArgsConstructor;
import java.util.List;

@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class UserService {

    private final UserRepository userRepository;

    public Page<User> getActiveUsersWithDetails(Pageable pageable) {
        // Шаг 1: пагинированный список ID (2 SQL: SELECT ids + SELECT COUNT)
        Page<Long> idPage = userRepository.findActiveUserIds(pageable);

        // Шаг 2: данные по ID с JOIN (1 SQL с LEFT JOIN)
        List<User> users = userRepository.findByIdsWithDetails(idPage.getContent());

        // Собираем Page из двух результатов
        return new PageImpl<>(users, pageable, idPage.getTotalElements());
        // Итого: 3 SQL-запроса вместо 1 + N — и корректная пагинация!
    }
}

## 11. Specification API — динамические запросы

`[Senior]`

**Задача:** форма поиска пользователей с 8 необязательными фильтрами (имя, статус, отдел, возраст, дата). Пользователь может выбрать любую комбинацию. Query Methods потребовали бы 256 методов. Один `@Query` не справится с динамическими условиями. **Specification решает это элегантно.**

Java

```
import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.JpaSpecificationExecutor;

// Добавляем JpaSpecificationExecutor — он даёт findAll(Specification), count(Specification) и др.
public interface UserRepository extends JpaRepository<User, Long>,
                                        JpaSpecificationExecutor<User> {
}
```

Java

```
import jakarta.persistence.criteria.CriteriaBuilder;
import jakarta.persistence.criteria.CriteriaQuery;
import jakarta.persistence.criteria.Root;
import org.springframework.data.jpa.domain.Specification;
import java.time.LocalDateTime;

// Статический класс со спецификациями — один метод = одно условие фильтрации
public final class UserSpecs {

    private UserSpecs() {} // утилитный класс, не инстанциировать

    // null-safe: если параметр null — возвращаем null (условие игнорируется)
    public static Specification<User> hasFirstName(String name) {
        return (Root<User> root, CriteriaQuery<?> query, CriteriaBuilder cb) ->
            name == null ? null
                : cb.like(cb.lower(root.get("firstName")),
                          "%" + name.toLowerCase() + "%");
    }

    public static Specification<User> hasStatus(UserStatus status) {
        return (root, query, cb) ->
            status == null ? null : cb.equal(root.get("status"), status);
    }

    public static Specification<User> isActive() {
        return (root, query, cb) -> cb.isTrue(root.get("active"));
    }

    public static Specification<User> createdAfter(LocalDateTime date) {
        return (root, query, cb) ->
            date == null ? null
                : cb.greaterThanOrEqualTo(root.get("createdAt"), date);
    }
}
```

Java

```
import org.springframework.data.jpa.domain.Specification;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import lombok.RequiredArgsConstructor;
import java.time.LocalDateTime;

// DTO для критериев поиска
public record UserSearchCriteria(
    String        firstName,     // null = не фильтровать
    UserStatus    status,        // null = не фильтровать
    LocalDateTime createdAfter   // null = не фильтровать
) {}
```

Java

```
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class UserSearchService {

    private final UserRepository userRepository;

    public Page<User> search(UserSearchCriteria criteria, Pageable pageable) {
        // Specification.where(null) — начальная точка, всегда истина
        Specification<User> spec = Specification
            .where(UserSpecs.hasFirstName(criteria.firstName()))  // null → игнорируется
            .and(UserSpecs.hasStatus(criteria.status()))          // null → игнорируется
            .and(UserSpecs.createdAfter(criteria.createdAfter())); // null → игнорируется

        // При пустых критериях вернёт всех пользователей с пагинацией
        return userRepository.findAll(spec, pageable);
    }
}
```

> **💡 Важно знать:** Specification — обёртка над JPA Criteria API. Код работает, но при большом количестве условий становится громоздким. Для типобезопасных динамических запросов с отличной читаемостью рассмотри **QueryDSL** — он генерирует Q-классы (например, `QUser`) из Entity и позволяет писать запросы как `QUser.user.firstName.containsIgnoreCase("John").and(...)`. Подробный разбор QueryDSL — в отдельной статье.

## 12. Custom Repository

`[Senior]`

**Используй Custom Repository когда:**

- ☑️ Нужен прямой доступ к `EntityManager` (сложный Criteria API, нет аналога в JPQL)
- ☑️ Нужны bulk-операции через JDBC/`JdbcTemplate` для максимальной скорости
- ☑️ Нужна GROUP BY с агрегатами — Query Methods не поддерживают
- ☑️ Нужно вызвать хранимую процедуру или native function
- ☑️ Логика запроса слишком сложна даже для Specification

Java

```
// Шаг 1: Объявляем кастомный интерфейс с нужными методами
public interface UserRepositoryCustom {
    List<User> findByComplexFilter(UserFilter filter);
    List<UserStatDto> getStatsByDepartment();
}
```

Java

```
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import jakarta.persistence.criteria.CriteriaBuilder;
import jakarta.persistence.criteria.CriteriaQuery;
import jakarta.persistence.criteria.JoinType;
import jakarta.persistence.criteria.Predicate;
import jakarta.persistence.criteria.Root;
import org.springframework.stereotype.Repository;
import java.util.ArrayList;
import java.util.List;

// Шаг 2: Реализация — имя ОБЯЗАТЕЛЬНО: <ИмяОсновногоРепозитория> + "Impl"
// Spring Data найдёт класс по этой конвенции автоматически
@Repository
public class UserRepositoryImpl implements UserRepositoryCustom {

    @PersistenceContext
    private EntityManager em; // EntityManager — прямой доступ к JPA

    @Override
    public List<User> findByComplexFilter(UserFilter filter) {
        CriteriaBuilder cb = em.getCriteriaBuilder();
        CriteriaQuery<User> cq = cb.createQuery(User.class);
        Root<User> root = cq.from(User.class);

        // Жадная загрузка через fetch — решаем N+1 прямо в запросе
        root.fetch("department", JoinType.LEFT);

        // Динамические предикаты — добавляем только непустые условия
        List<Predicate> predicates = new ArrayList<>();

        if (filter.getName() != null) {
            predicates.add(cb.like(
                cb.lower(root.get("firstName")),
                "%" + filter.getName().toLowerCase() + "%"
            ));
        }
        if (filter.getStatus() != null) {
            predicates.add(cb.equal(root.get("status"), filter.getStatus()));
        }
        if (filter.getMinAge() != null) {
            predicates.add(cb.ge(root.get("age"), filter.getMinAge()));
        }

        cq.where(predicates.toArray(new Predicate[0]));
        cq.orderBy(cb.desc(root.get("createdAt")));

        return em.createQuery(cq)
            .setMaxResults(filter.getLimit())
            .getResultList();
    }

    @Override
    public List<UserStatDto> getStatsByDepartment() {
        // GROUP BY — недоступно через Query Methods, возможно через @Query или EntityManager
        return em.createQuery(
            "SELECT new com.example.dto.UserStatDto(" +
            "    d.name, COUNT(u), AVG(u.age)" +
            ") " +
            "FROM User u JOIN u.department d " +
            "GROUP BY d.name " +
            "ORDER BY COUNT(u) DESC",
            UserStatDto.class
        ).getResultList();
    }

## 13. save() vs saveAndFlush() vs getReferenceById()

`[Middle/Senior]`

Эти методы выглядят похоже, но работают принципиально по-разному. Неправильный выбор приводит к лишним SQL-запросам или неожиданному поведению.

Java

```
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
@RequiredArgsConstructor
@Transactional
public class OrderService {

    private final UserRepository  userRepository;
    private final OrderRepository orderRepository;

    // === save() — откладывает SQL до flush ===
    public User saveUser(User user) {
        User saved = userRepository.save(user);
        // SQL может не выполниться прямо сейчас:
        // Hibernate накапливает изменения и отправляет в БД при flush или commit транзакции.
        // Но для GenerationType.IDENTITY: INSERT выполняется сразу (для получения ID).
        return saved;
    }

    // === saveAndFlush() — немедленный SQL + синхронизация кэша ===
    public User saveUserImmediately(User user) {
        User saved = userRepository.saveAndFlush(user);
        // INSERT выполнен ПРЯМО СЕЙЧАС, persistence context синхронизирован с БД.
        // Нужно когда: последующий nativeQuery в той же транзакции должен видеть новые данные.
        return saved;
    }

    // === getReferenceById() — lazy proxy БЕЗ SELECT ===
    public Order createOrder(Long userId, OrderRequest request) {
        // Нам нужен только user_id для внешнего ключа — данные пользователя не нужны
        User userProxy = userRepository.getReferenceById(userId);
        // SQL НЕ выполняется! Hibernate создаёт proxy-объект только с заполненным id.

        Order order = new Order();
        order.setUser(userProxy);       // устанавливаем FK
        order.setTotal(request.total());

        // При save() — INSERT INTO orders (user_id, total) VALUES (?, ?)
        // Лишнего SELECT users НЕТ — экономим один запрос к БД!
        return orderRepository.save(order);
    }

    // ⚠️ ОПАСНОСТЬ getReferenceById() — используй осознанно
    public void dangerousUsage(Long userId) {
        User proxy = userRepository.getReferenceById(userId);
        // Пока не обращаемся к полям — всё OK, SQL нет

        String name = proxy.getFirstName();
        // ← ЗДЕСЬ выполняется SELECT * FROM users WHERE id = ?
        // Если пользователя с userId НЕ существует → EntityNotFoundException!
        // В отличие от findById(), которая вернула бы Optional.empty()
    }
}

### Оптимистичная блокировка через @Version

text

```
Concurrent update без блокировки — проблема "lost update":

Транзакция A:  READ (version=5)      →  UPDATE (version=5→6) ✅
Транзакция B:  READ (version=5)      →  UPDATE (version=5??)
                                             ↑ version уже 6!
                                         → OptimisticLockException ❌
```

Java

```
import org.springframework.dao.OptimisticLockingFailureException;
import org.springframework.retry.annotation.Backoff;
import org.springframework.retry.annotation.Recover;
import org.springframework.retry.annotation.Retryable;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import lombok.RequiredArgsConstructor;

@Service
@RequiredArgsConstructor
public class UserUpdateService {

    private final UserRepository userRepository;

    // Автоматический retry при конфликте версий (требует spring-retry)
    @Retryable(
        retryFor   = OptimisticLockingFailureException.class,
        maxAttempts = 3,
        backoff    = @Backoff(delay = 100, multiplier = 2) // 100ms, 200ms, 400ms
    )
    @Transactional
    public User updateUser(Long id, String newFirstName) {
        User user = userRepository.findById(id)
            .orElseThrow(() -> new RuntimeException("User not found: " + id));

        user.setFirstName(newFirstName);

        // При save():
        // UPDATE users SET first_name=?, version=6 WHERE id=? AND version=5
        // Если version уже изменилась (другая транзакция обновила) → OptimisticLockingFailureException
        return userRepository.save(user);
    }

    // Вызывается если все 3 попытки неудачны
    @Recover
    public User recoverFromLock(OptimisticLockingFailureException ex, Long id, String name) {
        throw new RuntimeException(
            "Не удалось обновить User " + id + " после 3 попыток. " +
            "Данные изменяются слишком часто.", ex
        );
    }
}
```

**Сводная таблица методов:**

|Метод|SQL|Возврат|Если не найден|Когда использовать|
|---|---|---|---|---|
|`findById(id)`|SELECT сразу|`Optional<T>`|`Optional.empty()`|Нужны поля сущности|
|`getReferenceById(id)`|Нет SQL|`T` (proxy)|`EntityNotFoundException` при обращении к полям|Установка FK без чтения данных|
|`getById(id)`|**DEPRECATED**|—|—|**Не использовать!**|
|`save(entity)`|INSERT/UPDATE (отложен)|`S`|—|Стандартное сохранение|
|`saveAndFlush(entity)`|INSERT/UPDATE сразу|`S`|—|Нужен немедленный SQL в транзакции|
|`flush()`|Sync к БД|`void`|—|Перед nativeQuery в той же транзакции|

## 14. Тестирование — @DataJpaTest

`[Senior]`

`@DataJpaTest` — специализированный slice-тест для JPA-слоя:

- Загружает только JPA-контекст (без `@Service`, `@Controller`, `@Component`)

### ❌ Антипаттерн 6: Batch Insert с GenerationType.IDENTITY

Java

```
// ❌ МЕДЛЕННО: каждый save() — отдельный INSERT (N запросов)
for (User user : thousandUsers) {
    userRepository.save(user); // 1000 отдельных INSERT
}

// ❌ saveAll() без настройки Hibernate тоже даёт N INSERT!
// Причина: GenerationType.IDENTITY требует немедленного INSERT для получения ID,
// что делает невозможным батчирование на уровне JDBC.
userRepository.saveAll(thousandUsers); // всё ещё 1000 INSERT

// ✅ Используй SEQUENCE + настройку Hibernate:
// application.properties:
// spring.jpa.properties.hibernate.jdbc.batch_size=50
// spring.jpa.properties.hibernate.order_inserts=true
// spring.jpa.properties.hibernate.order_updates=true

// Entity с SEQUENCE (поддерживает батчирование):
// @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
// @SequenceGenerator(name = "user_seq", allocationSize = 50)
// private Long id;

// Тогда saveAll() будет выполнять пачки INSERT по 50 за раз
userRepository.saveAll(thousandUsers); // ~20 batch INSERT вместо 1000
```

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;
import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;

import java.time.LocalDateTime;
import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest
class TaskRepositoryTest {

    @Autowired
    private TestEntityManager entityManager;

    @Autowired
    private TaskRepository taskRepository;

    // Вспомогательный метод
    private Task buildTask(String title, boolean done, LocalDateTime createdAt) {
        Task task = new Task();
        task.setTitle(title);
        task.setDone(done);
        task.setCreatedAt(createdAt);
        return task;
    }

    // Тест 1: findByDoneFalse() — только незавершённые задачи
    @Test
    void findByDoneFalse_shouldReturnOnlyPendingTasks() {
        // given — 2 незавершённые и 1 завершённая
        entityManager.persist(buildTask("Task A", false, LocalDateTime.now()));
        entityManager.persist(buildTask("Task B", false, LocalDateTime.now()));
        entityManager.persist(buildTask("Task C", true,  LocalDateTime.now()));
        entityManager.flush();
        entityManager.clear();

        // when
        List<Task> pending = taskRepository.findByDoneFalse();

        // then
        assertThat(pending).hasSize(2)
            .extracting(Task::getTitle)
            .containsExactlyInAnyOrder("Task A", "Task B");
    }

    // Тест 2: findByTitleContaining() с пагинацией
    @Test
    void findByTitleContainingIgnoreCase_shouldReturnMatchingTasksPaged() {
        // given — 3 задачи, 2 содержат "spring" (разный регистр)
        entityManager.persist(buildTask("Spring Boot tutorial", false, LocalDateTime.now()));
        entityManager.persist(buildTask("Learn SPRING Data",    false, LocalDateTime.now()));
        entityManager.persist(buildTask("Java basics",          false, LocalDateTime.now()));
        entityManager.flush();
        entityManager.clear();

        // when — ищем "spring", страница 0, размер 10
        Page<Task> result = taskRepository.findByTitleContainingIgnoreCase(
            "spring", PageRequest.of(0, 10));

        // then
        assertThat(result.getContent()).hasSize(2);
        assertThat(result.getTotalElements()).isEqualTo(2);
        assertThat(result.getContent())
            .extracting(Task::getTitle)
            .containsExactlyInAnyOrder("Spring Boot tutorial", "Learn SPRING Data");
    }

    // Тест 3: findRecentTasks() — только задачи за последние 7 дней
    @Test
    void findRecentTasks_shouldReturnOnlyTasksCreatedAfterGivenDate() {
        // given — задача 10 дней назад и задача сегодня
        LocalDateTime tenDaysAgo = LocalDateTime.now().minusDays(10);
        LocalDateTime now        = LocalDateTime.now();

        entityManager.persist(buildTask("Old task",    false, tenDaysAgo));
        entityManager.persist(buildTask("Recent task", false, now));
        entityManager.flush();
        entityManager.clear();

        // when — ищем задачи созданные после 7 дней назад
        LocalDateTime since = LocalDateTime.now().minusDays(7);
        List<Task> recent = taskRepository.findRecentTasks(since);

        // then — только "Recent task" попадает в период
        assertThat(recent).hasSize(1);
        assertThat(recent.get(0).getTitle()).isEqualTo("Recent task");
    }
}

Мы умеем работать с данными через Repository. Но как управлять **самой схемой базы данных** при каждом деплое?

В статье 6.11 разберём:

- **Flyway** — версионные SQL-миграции (`V1__init.sql`, `V2__add_index.sql`, `V3__rename_column.sql`)

- Автоматический запуск миграций при старте Spring Boot
- Тестирование с миграциями — `@DataJpaTest` + Flyway + Testcontainers
- Rollback-стратегии и работа в команде с ветками
- **Liquibase** как альтернатива (XML/YAML/JSON формат миграций)
