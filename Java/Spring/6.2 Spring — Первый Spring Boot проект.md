## 1. От контейнера к приложению

> 🎯 **Этот раздел для:** Intern

В статье 6.1 мы разобрались с IoC-контейнером и Dependency Injection. Ты уже знаешь, что Spring умеет создавать объекты-бины и внедрять зависимости между ними. Это мощно — но давай честно: чтобы запустить даже простейшее веб-приложение на "чистом" Spring Framework, нужно сделать немало шагов вручную.

Нужно настроить `DispatcherServlet`, подключить Jackson для сериализации JSON, прописать ViewResolver, собрать WAR-архив, задеплоить его во внешний Tomcat... И это ещё до того, как ты напишешь первую строчку бизнес-логики.

**Spring Boot решает именно эту проблему.** Это не новый фреймворк — это надстройка над Spring Framework, которая берёт на себя всю рутинную конфигурацию. Ты описываешь _что_ хочешь сделать (создать веб-приложение), а Spring Boot сам решает _как_ это настроить.

> 💡 **Аналогия:** Если Spring Framework — это двигатель внутреннего сгорания, то Spring Boot — это уже собранный автомобиль, в который этот двигатель установлен, заправлен и готов к поездке. Ты садишься и едешь — не собираешь машину с нуля.

## 2. Зачем нам Spring Boot: Pain vs Gain

> 🎯 **Этот раздел для:** Junior → Middle

### Боль классического Spring

Представь, что тебе нужно создать REST-эндпоинт на классическом Spring MVC. Вот минимум того, что потребуется настроить вручную:

XML

```
<!-- web.xml — регистрация DispatcherServlet вручную -->
<web-app>
    <servlet>
        <servlet-name>dispatcher</servlet-name>
        <servlet-class>
            org.springframework.web.servlet.DispatcherServlet
        </servlet-class>
        <load-on-startup>1</load-on-startup>
    </servlet>
    <servlet-mapping>
        <servlet-name>dispatcher</servlet-name>
        <url-pattern>/</url-pattern>
    </servlet-mapping>
</web-app>
```

Java

```
// WebMvcConfig.java — настройка MVC вручную (~30 строк только для старта)
@Configuration
@EnableWebMvc
@ComponentScan("com.example")
public class WebMvcConfig implements WebMvcConfigurer {

    @Bean
    public MappingJackson2HttpMessageConverter jacksonConverter() {
        return new MappingJackson2HttpMessageConverter();
    }
    // И ещё десяток бинов: DataSource, TransactionManager, EntityManagerFactory...
}
```

И это только начало. К этому добавляются конфигурации DataSource, TransactionManager, EntityManagerFactory — каждая по 20–30 строк. Плюс сборка WAR и деплой во внешний Tomcat. Итого: **~240 строк конфигурации** до первой строки бизнес-логики.

### Как это решает Spring Boot

Ключевая философия Spring Boot: **Convention over Configuration** — "Соглашение важнее конфигурации". Фреймворк предоставляет разумные настройки по умолчанию, которые подходят для 80% случаев. Нестандартное поведение — явно переопределяешь. Мы будем встречать этот принцип в каждом разделе статьи.

**Главные отличия (запомни эти три):**

||Классический Spring|Spring Boot|
|---|---|---|
|⭐ Конфигурация|XML + Java Config (~240 строк)|`.properties` (~10 строк)|
|⭐ Сервер|Внешний Tomcat|Встроенный Tomcat|
|⭐ Запуск|Деплой WAR-архива|`java -jar app.jar`|

<details> <summary>📋 Показать полное сравнение →</summary>

|Аспект|Классический Spring|Spring Boot|
|---|---|---|
|Конфигурация|XML + Java Config (~240 строк)|`application.properties` (~10 строк)|
|Управление зависимостями|Версии каждой библиотеки вручную|BOM через `parent` POM|
|Сервер приложений|Внешний Tomcat, WildFly, Jetty|Встроенный Tomcat|
|Формат деплоя|WAR-архив|Исполняемый JAR (Fat JAR)|
|Время до первого эндпоинта|30–60 минут настройки|5 минут|
|DataSource|Явный `@Bean` + XML|3 строки в `.properties`|
|Запуск|Деплой в сервер|`java -jar app.jar`|
|Мониторинг|Сторонние решения|Spring Boot Actuator из коробки|

</details>

> 💡 **Важно знать:** Spring Boot не скрывает сложность Spring — он устраняет её там, где она не нужна. Ты всегда можешь переопределить любую автоматическую настройку своей собственной.

## 3. Spring Initializr: создаём проект

> 🎯 **Этот раздел для:** Intern → Senior

Хватит теории — создадим проект. Spring Initializr — это официальный генератор проектов от команды Spring. Он создаёт корректную структуру, подключает зависимости и настраивает систему сборки.

### Способ 1: Через браузер (рекомендуется для начала)

**1.** Открой [start.spring.io](https://start.spring.io/)

**2.** Заполни параметры:

|Поле|Значение|
|---|---|
|Project|Maven|
|Language|Java|
|Spring Boot|3.2.x _(выбирай последний стабильный — без SNAPSHOT и RC)_|
|Group|`com.example`|
|Artifact|`demo`|
|Packaging|Jar|
|Java|17|

**3.** В секции **Dependencies** нажми **ADD DEPENDENCIES** и добавь:

- `Spring Web` — для REST API (подтянет Tomcat, Spring MVC, Jackson)
- `Spring Boot DevTools` — для горячей перезагрузки кода при разработке

**4.** Нажми **GENERATE** — браузер скачает архив `demo.zip`

**5.** Распакуй архив

**6.** Открой проект в IntelliJ IDEA:

- **Рекомендуемый способ:** `File → Open` → выбери файл `pom.xml` → нажми **Open as Project**
- **Альтернатива:** `File → Open` → выбери папку `demo` → IntelliJ предложит "Maven build script found" → нажми **Load**

> ⏳ **После открытия проекта:** IntelliJ автоматически скачает все зависимости из интернета (~50–100 МБ при первом запуске). Следи за индикатором в правом нижнем углу IDE. **Не начинай писать код пока индикатор не исчезнет** — автодополнение и проверка ошибок не будут работать корректно до завершения загрузки.

### Способ 2: Через curl (для тех, кто любит терминал)

> 🎯 **Этот способ для:** Senior

Bash

```
# Генерация проекта одной командой
curl https://start.spring.io/starter.zip \
  -d type=maven-project \
  -d language=java \
  -d bootVersion=3.2.0 \
  -d baseDir=demo \
  -d groupId=com.example \
  -d artifactId=demo \
  -d packageName=com.example.demo \
  -d packaging=jar \
  -d javaVersion=17 \
  -d dependencies=web,devtools \
  -o demo.zip

# Распаковка и переход в папку проекта
unzip demo.zip && cd demo

# Открыть в IntelliJ (если установлена CLI-утилита)
idea .
```

🛠️ **Сделай сам:** Создай проект через UI. После открытия в IDE найди в `pom.xml` зависимость `spring-boot-devtools` и убедись, что она присутствует с флагами `<scope>runtime</scope>` и `<optional>true</optional>`.

## 4. Анатомия проекта: что мы получили

> 🎯 **Этот раздел для:** Junior

Открой проект. Перед тобой стандартная структура Maven-проекта с дополнениями от Spring Boot. Разберём каждый файл — начинающие разработчики часто пропускают этот шаг и потом сталкиваются с непонятными ошибками.

text

```
demo/
├── .mvn/
│   └── wrapper/
│       └── maven-wrapper.properties    # ① Версия Maven для Wrapper
├── src/
│   ├── main/
│   │   ├── java/
│   │   │   └── com/example/demo/
│   │   │       └── DemoApplication.java    # ② Точка входа в приложение
│   │   └── resources/
│   │       ├── static/                 # ③ Статические файлы (HTML, CSS, JS)
│   │       ├── templates/              # ④ Шаблоны (Thymeleaf и др.)
│   │       └── application.properties # ⑤ Конфигурация приложения
│   └── test/
│       └── java/com/example/demo/
│           └── DemoApplicationTests.java   # ⑥ Интеграционный тест
├── .gitignore                          # ⑦ Исключения для Git
├── mvnw                                # ⑧ Maven Wrapper (Linux/Mac)
├── mvnw.cmd                            # ⑧ Maven Wrapper (Windows)
└── pom.xml                             # ⑨ Конфигурация Maven-проекта
```

### ⑨ pom.xml — сердце проекта Maven

XML

```
<?xml version="1.0" encoding="UTF-8"?>
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0
         https://maven.apache.org/xsd/maven-4.0.0.xsd">
    <modelVersion>4.0.0</modelVersion>

    <!--
        ① spring-boot-starter-parent — самое важное место в файле.
        Это BOM (Bill of Materials — "список материалов"):
        управляет версиями ВСЕХ Spring-зависимостей.
        Ты никогда не указываешь версии вручную — они всегда совместимы.
    -->
    <parent>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-parent</artifactId>
        <version>3.2.0</version>
        <relativePath/>
    </parent>

    <!-- Координаты нашего проекта -->
    <groupId>com.example</groupId>
    <artifactId>demo</artifactId>
    <version>0.0.1-SNAPSHOT</version>
    <name>demo</name>

    <properties>
        <!-- Версия Java — меняй только здесь -->
        <java.version>17</java.version>
    </properties>

    <dependencies>
        <!--
            spring-boot-starter-web — один starter вместо 10+ зависимостей.
            Включает: Spring MVC, встроенный Tomcat, Jackson (JSON), Servlet API.
            Версия не указана — берётся из parent BOM.
        -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-web</artifactId>
        </dependency>

        <!--
            DevTools: автоматический перезапуск при изменении классов.
            optional=true гарантирует что DevTools НЕ попадёт в Fat JAR.
            В продакшене DevTools автоматически отключается.
        -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-devtools</artifactId>
            <scope>runtime</scope>
            <optional>true</optional>
        </dependency>

        <!--
            spring-boot-starter-test — всё для тестирования:
            JUnit 5, Mockito, MockMvc, AssertJ.
            scope=test — эта зависимость НЕ попадёт в финальный JAR.
        -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-test</artifactId>
            <scope>test</scope>
        </dependency>
    </dependencies>

    <build>
        <plugins>
            <!--
                spring-boot-maven-plugin — создаёт Fat JAR.
                Без этого плагина mvn package создаст обычный JAR
                без зависимостей, который нельзя запустить через java -jar.
            -->
            <plugin>
                <groupId>org.springframework.boot</groupId>
                <artifactId>spring-boot-maven-plugin</artifactId>
            </plugin>
        </plugins>
    </build>

</project>
```

### ⑧ mvnw и mvnw.cmd — Maven Wrapper

**Зачем это нужно:** У тебя Maven 3.8, у коллеги Maven 3.6 — билд может вести себя по-разному. Maven Wrapper решает эту проблему: он скачивает точную нужную версию Maven автоматически. Вся команда использует одну версию.

Bash

```
# Используй mvnw вместо mvn — это правило хорошего тона в командной разработке
./mvnw spring-boot:run    # Linux/Mac
mvnw.cmd spring-boot:run  # Windows
```

**Для CI/CD это особенно важно:** В GitHub Actions, Jenkins или GitLab CI не нужно устанавливать Maven — Wrapper скачает нужную версию сам. Версия зафиксирована в файле:

Bash

```
cat .mvn/wrapper/maven-wrapper.properties
# distributionUrl=...apache-maven-3.9.5-bin.zip
```

### ⑥ DemoApplicationTests.java — базовый тест

Java

```
package com.example.demo;

import org.junit.jupiter.api.Test;
import org.springframework.boot.test.context.SpringBootTest;

// @SpringBootTest загружает полный Spring ApplicationContext.
// Если что-то настроено неправильно — тест упадёт при старте.
@SpringBootTest
class DemoApplicationTests {

    @Test

```

## 5. @SpringBootApplication под капотом

> 🎯 **Этот раздел для:** Junior → Senior+

Открой `DemoApplication.java`. Это главный класс — с него начинается жизнь приложения.

Java

```
package com.example.demo;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;

@SpringBootApplication  // Одна аннотация — три роли
public class DemoApplication {

    public static void main(String[] args) {
        // Запускает Spring Application Context + встроенный Tomcat
        SpringApplication.run(DemoApplication.class, args);
    }
}
```

### Что скрывается за @SpringBootApplication

`@SpringBootApplication` — составная аннотация. Под ней скрываются три аннотации:

Java

```
// Исходный код Spring Boot (упрощённо):
@SpringBootConfiguration   // 1. Объявляет источник бинов
@EnableAutoConfiguration   // 2. Включает механизм автоконфигурации
@ComponentScan             // 3. Включает сканирование компонентов
public @interface SpringBootApplication { ... }
```

#### 1️⃣ @SpringBootConfiguration

Это специализация `@Configuration` с важным отличием: Spring Boot Test-инфраструктура использует именно `@SpringBootConfiguration` для автоматического поиска конфигурации при `@SpringBootTest`. Благодаря этому тест "знает" с чего начать загрузку контекста.

> ⚠️ **Важно:** Не заменяй `@SpringBootConfiguration` на `@Configuration` в main-классе — тесты с `@SpringBootTest` перестанут корректно находить конфигурацию.

Java

```
// Можно добавлять @Bean прямо в главный класс
@SpringBootApplication
public class DemoApplication {

    public static void main(String[] args) {
        SpringApplication.run(DemoApplication.class, args);
    }

    // Пример определения бина (для небольших приложений — допустимо)
    @Bean
    public String appName() {
        return "My First Spring Boot App";
    }
}
```

#### 2️⃣ @EnableAutoConfiguration

Включает механизм автоконфигурации — подробно разберём его в разделе 8, после того как запустим первое приложение. Сейчас важно знать одно: именно благодаря этой аннотации Spring Boot "видит" `spring-boot-starter-web` в classpath и автоматически настраивает Tomcat, DispatcherServlet и Jackson.

Java

```
// Если конкретная автоконфигурация мешает — можно исключить
@SpringBootApplication(exclude = {DataSourceAutoConfiguration.class})
public class DemoApplication { ... }
```

#### 3️⃣ @ComponentScan — и почему структура пакетов критична

Говорит Spring: "Сканируй пакет, где находится этот класс, и все его подпакеты в поисках компонентов (`@Component`, `@Service`, `@Repository`, `@Controller`, `@RestController`)".

Это и есть **Convention over Configuration** в действии: по соглашению, компоненты ищутся в пакете main-класса и ниже. Хочешь другое поведение — явно переопредели через `basePackages`.

text

```
Если DemoApplication находится в com.example.demo:

  Spring НАЙДЁТ компоненты в:          Spring НЕ НАЙДЁТ в:
  ✅ com.example.demo                   ❌ com.example (родительский)
  ✅ com.example.demo.controller        ❌ com.other.package
  ✅ com.example.demo.service
  ✅ com.example.demo.repository
```

> ⚠️ **Частая ошибка — Неверное расположение главного класса:**

### Шаг 2: Создай модель данных

package com.example.demo.model;

// Java Record (Java 16+) — компактная запись для неизменяемых данных.
// Автоматически генерирует: конструктор, getters, equals, hashCode, toString.
// Jackson умеет сериализовать Record в JSON из коробки — никаких аннотаций не нужно.

### Шаг 3: Создай контроллер

Java

```
// src/main/java/com/example/demo/controller/HelloController.java
package com.example.demo.controller;

import com.example.demo.model.Greeting;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;

import java.util.concurrent.atomic.AtomicLong;

// @RestController = @Controller + @ResponseBody.
// Все методы возвращают данные напрямую в тело HTTP-ответа.
// Jackson автоматически превращает объект Java в JSON.
//
// Без @RestController (только @Controller) Spring попытался бы
// найти HTML-шаблон с именем возвращаемой строки — и упал бы с ошибкой.
@RestController
public class HelloController {

    // AtomicLong — потокобезопасный счётчик для генерации уникальных ID.
    // Используем его чтобы каждый запрос получал свой ID.
    // Обычный long counter++ небезопасен при одновременных запросах.
    private final AtomicLong counter = new AtomicLong();

    // @GetMapping("/greeting") — обрабатывает GET-запросы на /greeting.
    @GetMapping("/greeting")
    public Greeting greeting(
            // @RequestParam читает параметр из URL (?name=Alice).
            // defaultValue — значение если параметр не передан.
            // required = false — параметр необязателен.
            @RequestParam(value = "name", defaultValue = "World",
                          required = false) String name) {

        // Создаём и возвращаем Greeting — Spring сам превратит его в JSON.
        return new Greeting(counter.incrementAndGet(), "Hello, " + name + "!");
    }
}
```

> ✅ **Чекпоинт:** После создания `HelloController.java` убедись что:
> 
> - Первая строка: `package com.example.demo.controller;`
> - Все импорты добавлены (IntelliJ подсветит красным если нет — Alt+Enter для исправления)
> - Нет красных подчёркиваний в редакторе

### Как это работает: Flow запроса

#### 🔄 Что происходит когда ты открываешь браузер:

text

```
[Клиент: браузер / curl]
         │
         │  HTTP GET /greeting?name=Alice
         ▼
[Встроенный Tomcat]
         │  Принимает TCP-соединение, парсит HTTP-запрос
         ▼
[DispatcherServlet]  ← настроен автоматически Spring Boot
         │  Находит подходящий @GetMapping("/greeting")
         ▼
[HelloController.greeting("Alice")]
         │  Создаёт: new Greeting(1, "Hello, Alice!")
         ▼
[Jackson ObjectMapper]  ← настроен автоматически Spring Boot
         │  Greeting → {"id":1,"content":"Hello, Alice!"}
         ▼
[HTTP Response 200 OK]
         │  Content-Type: application/json
         ▼
[Клиент получает JSON]
```

> 💡 **Узнаёшь?** Это то самое **Dependency Injection** из статьи 6.1! `HelloController` не создаёт ничего через `new` — он просто объявляет что ему нужно, а Spring IoC-контейнер сам создаёт все объекты. Разница с 6.1: теперь ты не настраиваешь контейнер вручную через XML или `@Configuration` — Spring Boot делает это сам через Auto-Configuration.

🛠️ **Сделай сам:** Добавь второй эндпоинт в `HelloController`:

```

    return "Hello, Spring Boot 3!";
}
```

## 8. Под капотом: Starters и Auto-Configuration

> 🎯 **Этот раздел для:** Middle → Senior

Твоё приложение работает. Но ты нигде не настраивал Tomcat, не регистрировал `DispatcherServlet` и не создавал `ObjectMapper`. Как Spring Boot это всё сделал? Пора разобраться.

### Starter Dependencies — умные зависимости

**Зачем это нужно:** Раньше, чтобы добавить поддержку веба, нужно было вручную находить совместимые версии 10+ библиотек. Одна несовместимая версия — часы на отладку.

**Что такое starter:** Это Maven-артефакт, который сам не содержит кода — только список транзитивных зависимостей с согласованными версиями.

XML

```
<!-- Одна зависимость вместо десяти -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
    <!-- Версия не указывается — управляется BOM из parent POM -->
</dependency>
```

Хочешь увидеть что реально подтягивается? Используй `dependency:tree`:

Bash

```
./mvnw dependency:tree -Dincludes=org.springframework*,org.apache.tomcat*,com.fasterxml*

# Фрагмент вывода:
[INFO] com.example:demo:jar:0.0.1-SNAPSHOT
[INFO] +- org.springframework.boot:spring-boot-starter-web:jar:3.2.0
[INFO] |  +- org.springframework.boot:spring-boot-starter-tomcat:jar:3.2.0
[INFO] |  |  +- org.apache.tomcat.embed:tomcat-embed-core:jar:10.1.16
[INFO] |  +- org.springframework:spring-webmvc:jar:6.1.0
[INFO] |  +- com.fasterxml.jackson.core:jackson-databind:jar:2.15.3
```

Наглядно видно: одна строка в `pom.xml` = целое дерево согласованных зависимостей.

### Auto-Configuration — умная конфигурация

**Как Spring Boot понимает что настраивать:** При запуске он читает специальный файл регистрации автоконфигураций.

> 🔍 **Под капотом — важно для Spring Boot 3.x:**
> 
> - Spring Boot **2.x**: `META-INF/spring.factories` (устаревший формат)
> - Spring Boot **3.x**: `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` (актуальный формат)
> 
> Если ты ищешь автоконфигурации в `spring.factories` в Spring Boot 3.x — ты смотришь не туда.

Этот файл содержит список классов-конфигураций. Каждый кандидат применяется только при выполнении условий:

text

```
Запуск приложения
       │
       ▼
Чтение META-INF/spring/
org.springframework.boot.autoconfigure.AutoConfiguration.imports
       │
       ▼
Для каждого AutoConfiguration-класса проверяются условия:
  ┌─────────────────────────────────────────────────────────┐
  │ @ConditionalOnClass(DispatcherServlet.class)            │
  │   → Класс есть в classpath? (добавили starter-web?)    │
  │                                                         │
  │ @ConditionalOnMissingBean(DispatcherServlet.class)      │
  │   → Пользователь ещё не определил свой бин?            │
  │                                                         │
  │ @ConditionalOnProperty("spring.mvc.enabled")            │
  │   → Свойство имеет нужное значение?                     │
  └─────────────────────────────────────────────────────────┘
       │ ВСЕ условия выполнены
       ▼
  Конфигурация применяется, бины создаются
       │
       ▼
  Spring Context готов к работе
```

**Ключевое условие `@ConditionalOnMissingBean`** означает: "Применить эту автоконфигурацию только если пользователь ещё не определил свой аналогичный бин". Именно это позволяет переопределить любое поведение — просто объяви свой `@Bean`, и автоконфигурация отступит.

> 💎 **Совет профи:** Хочешь увидеть что применилось при запуске и почему?
> 
> properties
> 
> ```
> # application.properties
> debug=true
> ```
> 
> В консоли появится подробный отчёт: "CONDITIONS EVALUATION REPORT" — что применилось, что было отклонено и по какой причине.

### Кастомизация Auto-Configuration

> 🎯 **Этот блок для:** Senior+

Если ты пишешь библиотеку или платформенный компонент — ты можешь создать собственную автоконфигурацию:

Java

```
// Своя автоконфигурация — применяется только при нужных условиях
@AutoConfiguration
@ConditionalOnClass(MyService.class)          // класс есть в classpath
@ConditionalOnMissingBean(MyService.class)    // пользователь не определил свой
public class MyServiceAutoConfiguration {

    @Bean
    @ConditionalOnProperty(
        name = "my.service.enabled",
        havingValue = "true",
        matchIfMissing = true  // применять если свойство не задано
    )
    public MyService myService() {
        return new MyService();
    }
}
```

text

```
# Регистрация в Spring Boot 3.x:
# src/main/resources/META-INF/spring/
# org.springframework.boot.autoconfigure.AutoConfiguration.imports

com.example.autoconfigure.MyServiceAutoConfiguration
```

- [Список всех AutoConfiguration классов Spring Boot 3.x](https://docs.spring.io/spring-boot/docs/current/reference/html/auto-configuration-classes.html)
- [Создание собственной AutoConfiguration](https://docs.spring.io/spring-boot/docs/current/reference/html/features.html#features.developing-auto-configuration)

## 9. application.properties: конфигурация без перекомпиляции

> 🎯 **Этот раздел для:** Junior

Ключевое следствие принципа **Convention over Configuration**: порт 8080, путь `/`, уровень логов INFO — это соглашения по умолчанию. Хочешь 9090 и `/api` — одна строка в `.properties`. Без изменения кода, без перекомпиляции.

properties

```
# src/main/resources/application.properties

# === Настройки сервера ===

# Порт встроенного Tomcat (по умолчанию 8080)
server.port=8080

# Контекстный путь (по умолчанию "/")
# Раскомментируй — и все эндпоинты переедут на /api/v1/...
# server.servlet.context-path=/api/v1


# === Настройки приложения ===

# Имя приложения (видно в логах и Spring Boot Actuator)
spring.application.name=demo


# === Логирование ===

# Подробные логи для нашего кода (полезно при разработке)
logging.level.com.example.demo=DEBUG

# Только важные события от Spring Web
logging.level.org.springframework.web=INFO

# Включить отчёт об автоконфигурации (раскомментируй для изучения)
# debug=true
```

### application.yml — альтернативный формат

Те же настройки в YAML (многие команды предпочитают его за читаемость при большом количестве настроек):

YAML

```
server:
  port: 8080

spring:
  application:
    name: demo

logging:
  level:
    com.example.demo: DEBUG
    org.springframework.web: INFO
```

> 💡 **Важно знать:** Если в проекте существуют оба файла одновременно (`application.properties` и `application.yml`), Spring Boot загружает **оба**. При наличии одинаковых ключей в обоих файлах — значение из `.properties` переопределяет значение из `.yml`. Чтобы избежать путаницы: **используй только один формат** в проекте.

### Профили: разные настройки для разных окружений

> 🎯 **Этот блок для:** Middle

Профили — один из фундаментальных механизмов Spring Boot для разделения конфигурации по окружениям (dev/staging/prod):

properties

```
# application.properties — общее для всех окружений

```

properties

```

```

properties

```

```

## 10. Сборка и запуск: Fat JAR

> 🎯 **Этот раздел для:** Middle

При разработке удобен `spring-boot:run`. Но для деплоя на сервер нужен артефакт, который можно передать и запустить без Maven и IDE. Это Fat JAR (он же Uber JAR, он же Executable JAR).

### Что такое Fat JAR

Обычный JAR (Java ARchive) содержит только скомпилированный код твоего приложения. **Fat JAR** содержит всё необходимое: и твой код, и все зависимости, и встроенный Tomcat.

text

```
demo-0.0.1-SNAPSHOT.jar  (~18 МБ — "жирный" потому что всё внутри)
├── BOOT-INF/
│   ├── classes/              ← твой скомпилированный код
│   │   └── com/example/demo/
│   │       ├── DemoApplication.class
│   │       ├── controller/HelloController.class
│   │       └── model/Greeting.class
│   └── lib/                  ← ВСЕ зависимости как отдельные JAR-файлы
│       ├── spring-boot-3.2.0.jar
│       ├── spring-webmvc-6.1.0.jar
│       ├── tomcat-embed-core-10.1.16.jar  ← встроенный Tomcat!
│       └── jackson-databind-2.15.3.jar
├── META-INF/
│   └── MANIFEST.MF           ← точка входа: Main-Class
└── org/springframework/boot/loader/    ← Spring Boot Launcher
    └── ...                             (умеет загружать вложенные JAR)
```

Именно `spring-boot-maven-plugin` в `pom.xml` создаёт такую структуру. Без него `mvn package` создаст обычный "тонкий" JAR без зависимостей, который не запустится через `java -jar`.

### Сборка

Bash

```
# Собрать JAR (перед сборкой выполнит все тесты)
./mvnw clean package

# Собрать без тестов (быстрее, используй в CI/CD когда тесты уже прошли)
./mvnw clean package -DskipTests

# Посмотреть что получилось
ls -lh target/*.jar
# -rw-r--r-- demo-0.0.1-SNAPSHOT.jar  18M
```

### Запуск

Bash

```
# Базовый запуск
java -jar target/demo-0.0.1-SNAPSHOT.jar

# Переопределить порт без изменения application.properties
java -jar target/demo-0.0.1-SNAPSHOT.jar --server.port=9090

# Активировать продакшн-профиль
java -jar target/demo-0.0.1-SNAPSHOT.jar --spring.profiles.active=prod

# Ограничить память (важно для контейнеров)
java -Xmx512m -jar target/demo-0.0.1-SNAPSHOT.jar
```

> 💡 **Важно знать:** Любое свойство из `application.properties` можно переопределить аргументом командной строки. Аргумент `--server.port=9090` при запуске имеет **приоритет** над `server.port=8080` в файле свойств. Это позволяет использовать один и тот же JAR в разных окружениях.

### Spring Boot Actuator — production-ready из коробки

> 🎯 **Этот блок для:** Middle

Добавь в `pom.xml` и получи мониторинг бесплатно:

XML

```
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
```

Bash

### Ошибка 1: Неверная структура пакетов

**Симптом:**

text

```

Field helloService in com.example.demo.controller.HelloController
required a bean of type 'com.example.demo.service.HelloService'
that could not be found.
```

**Причина:** Main-класс находится не в корневом пакете — `@ComponentScan` не видит компоненты.

**Решение:**

text

```
❌ НЕПРАВИЛЬНО:                    ✅ ПРАВИЛЬНО:
src/main/java/                     src/main/java/
├── DemoApplication.java           └── com/example/demo/
└── com/example/demo/                  ├── DemoApplication.java
    └── controller/                    └── controller/
        └── HelloController.java           └── HelloController.java
```

### Ошибка 3: Ручное указание версий зависимостей

**Симптом:** `NoSuchMethodError`, `ClassNotFoundException`, странные ошибки при старте.

**Причина:** Ручная версия конфликтует с версией из Spring Boot BOM.

XML

```
<!-- ❌ НЕПРАВИЛЬНО: указываем версию вручную -->
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <version>2.13.0</version>  <!-- может конфликтовать! -->
</dependency>

<!-- ✅ ПРАВИЛЬНО: доверяем parent POM -->
<dependency>
    <groupId>com.fasterxml.jackson.core</groupId>
    <artifactId>jackson-databind</artifactId>
    <!-- версия берётся из spring-boot-starter-parent -->
</dependency>
```

### Ошибка 4: @Controller вместо @RestController

**Симптом:** Браузер показывает `Whitelabel Error Page` вместо JSON, или Spring ищет HTML-шаблон.

Java

```
// ❌ НЕПРАВИЛЬНО для REST API
@Controller
public class HelloController {
    @GetMapping("/greeting")
    public Greeting greeting() {
        return new Greeting(1, "Hello");
        // Spring ищет HTML-шаблон с именем "Greeting" — и не находит!
    }
}

// ✅ ПРАВИЛЬНО
@RestController  // = @Controller + @ResponseBody
public class HelloController {
    @GetMapping("/greeting")
    public Greeting greeting() {
        return new Greeting(1, "Hello");
        // Возвращается как JSON — Jackson сериализует автоматически
    }
}
```

### Ошибка 5: Циклические зависимости

**Симптом:**

text

```
The dependencies of some of the beans in the application context form a cycle:
serviceA → serviceB → serviceA
```

**Важно для Spring Boot 2.6+:** Циклические зависимости **запрещены по умолчанию** и приводят к ошибке при старте. Это не баг — это защита от архитектурных проблем.

Java

```
// ❌ ПРОБЛЕМА: циклическая зависимость
@Service
public class ServiceA {
    public ServiceA(ServiceB b) { ... } // A зависит от B
}
@Service
public class ServiceB {
    public ServiceB(ServiceA a) { ... } // B зависит от A — цикл!
}

// ✅ РЕШЕНИЕ: выделить общую логику в третий сервис
@Service
public class CommonService { /* общая логика */ }

@Service
public class ServiceA {
    public ServiceA(CommonService c) { ... }
}
@Service
public class ServiceB {
    public ServiceB(CommonService c) { ... }
}
```

Если нужно **временно** разрешить циклические зависимости (например, при миграции легаси-кода):

properties

```
# application.properties
# ⚠️ Только как временная мера! Это не решение проблемы.
spring.main.allow-circular-references=true
```

### Ошибка 6: javax.* вместо jakarta.* (Spring Boot 3.x)

**Симптом:** `ClassNotFoundException: javax.servlet.http.HttpServletRequest`

**Причина:** Spring Boot 3.x перешёл на Jakarta EE 9+. Все пакеты переименованы.

Java

```
// ❌ Старый код (Spring Boot 2.x)
import javax.servlet.http.HttpServletRequest;
import javax.persistence.Entity;
import javax.validation.Valid;

// ✅ Spring Boot 3.x
import jakarta.servlet.http.HttpServletRequest;
import jakarta.persistence.Entity;
import jakarta.validation.Valid;
```

> 💡 **Быстрое исправление в IntelliJ IDEA:** Edit → Find → Replace in Files → найди `javax.` → замени на `jakarta.` (только для пакетов Spring/JPA/Validation — не для `java.` пакетов!).

### Таблица ключевых понятий

**🏗️ Архитектура и философия**

|Понятие|Определение|
|---|---|
|**Convention over Configuration**|"Соглашение важнее конфигурации" — фреймворк предоставляет разумные настройки по умолчанию, нестандартное — явно переопределяется|
|**Auto-Configuration**|Механизм автоматической настройки бинов на основе classpath и условных аннотаций (`@Conditional*`)|
|**BOM (Bill of Materials)**|Список зависимостей с согласованными версиями; Spring Boot предоставляет BOM через `spring-boot-starter-parent`|

**📦 Инструменты и зависимости**

|Понятие|Определение|
|---|---|
|**Spring Initializr**|Веб-инструмент (`start.spring.io`) для генерации скелета Spring Boot проекта|
|**Starter Dependency**|Maven-зависимость с предопределённым набором транзитивных зависимостей для конкретной функциональности|
|**Fat JAR**|Исполняемый JAR-архив, содержащий код приложения, все зависимости и встроенный сервер|
|**Embedded Server**|Встроенный сервер (Tomcat по умолчанию), входящий в Fat JAR; внешний сервер не нужен|
|**Maven Wrapper**|Скрипт (`mvnw`), обеспечивающий использование точной версии Maven независимо от системы|

**💻 Аннотации**

|Понятие|Определение|
|---|---|
|**@SpringBootApplication**|Составная аннотация = `@SpringBootConfiguration` + `@EnableAutoConfiguration` + `@ComponentScan`|
|**@SpringBootConfiguration**|Специализация `@Configuration`; используется Test-инфраструктурой для поиска конфигурации при `@SpringBootTest`|
|**@EnableAutoConfiguration**|Активирует механизм автоконфигурации Spring Boot|
|**@ComponentScan**|Сканирует пакет и подпакеты в поисках компонентов (`@Service`, `@Controller` и др.)|
|**@RestController**|`@Controller` + `@ResponseBody`; все методы возвращают данные напрямую в HTTP-ответ|

> 💬 **Вопрос для самопроверки:** Что произойдёт, если ты создашь свой `@Bean ObjectMapper` в конфигурационном классе? Применится ли автоконфигурация Jackson?
> 
> _Ответ: Нет. `JacksonAutoConfiguration` содержит `@ConditionalOnMissingBean(ObjectMapper.class)`. Когда Spring Boot увидит, что ObjectMapper уже определён пользователем — автоконфигурация пропустится. Твой бин будет использован вместо стандартного. Это и есть механизм переопределения автоконфигурации._
