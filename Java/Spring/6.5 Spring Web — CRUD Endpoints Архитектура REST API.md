## 1. Что было в 6.4 и что мы улучшим

**[Уровень: Intern]**

В статье 6.4 мы написали первый контроллер. Он выглядел примерно так:

Java

```
// ❌ Контроллер из статьи 6.4 — рабочий, но с архитектурными проблемами
@RestController
@RequestMapping("/tasks")
public class TaskController {

    // Хранилище прямо в контроллере — нарушение принципа единой ответственности
    private final List<Task> tasks = new ArrayList<>();
    private long nextId = 1;

    @GetMapping
    public List<Task> getAll() {
        return tasks; // Возвращаем внутренний объект напрямую
    }

    @PostMapping
    public Task create(@RequestBody Task task) { // Принимаем Entity — опасно
        task.setId(nextId++);
        tasks.add(task);
        return task; // 200 OK вместо 201 Created — нарушение HTTP-семантики
    }
}
```

Код работает, но содержит проблемы, которые в реальном проекте станут источником боли:

|Проблема|Последствие|
|---|---|
|Хранилище в контроллере|Невозможно тестировать слои изолированно|
|Entity в запросе/ответе|Клиент видит внутренние поля, риск mass assignment|
|Нет валидации|Можно создать задачу с пустым названием|
|Всегда `200 OK`|Нарушение HTTP-стандарта, клиенты не могут правильно обработать ответ|
|Нет обработки `404`|При запросе несуществующей задачи — `NullPointerException`|

В этой статье мы исправим каждую из этих проблем, обосновав каждое решение.

> **💡 Справка: Richardson Maturity Model.** Существует шкала "зрелости" REST API из четырёх уровней (0–3). Большинство production API работает на **Level 2**: используют правильные HTTP-методы (`GET`, `POST`, `PUT`, `DELETE`) и корректные статус-коды. Именно такой API мы и построим. Level 3 (HATEOAS — ссылки в каждом ответе) применяется редко и выходит за рамки этой статьи.

## 2. Слоистая архитектура

**[Уровень: Junior]**

### Аналогия с рестораном

Прежде чем смотреть на код — представьте ресторан.

text

```
                    🧑 Гость (HTTP-клиент)
                         │
                         │ заказывает блюдо
                         ▼
              👨‍💼 Официант (Controller)
          • принимает заказ (HTTP Request)
          • проверяет, что заказ осмыслен (валидация)
          • передаёт заказ на кухню
          • НЕ готовит еду сам
                         │
                         │ передаёт заказ
                         ▼
              👨‍🍳 Шеф-повар (Service)
          • знает рецепты (бизнес-логика)
          • решает: достаточно ли ингредиентов
          • НЕ общается с гостем напрямую
          • НЕ ходит сам в кладовую
                         │
                         │ запрашивает продукты
                         ▼
              🏪 Кладовщик (Repository)
          • выдаёт и хранит продукты (Entity)
          • НЕ знает, что из них приготовят
          • НЕ знает, кто и зачем заказал
```

Теперь та же схема — в терминах Spring:

text

```
┌─────────────────────────────────────────────────────┐
│              Controller (@RestController)            │
│  ✓ Принимает HTTP-запросы, извлекает данные         │
│  ✓ Валидирует входные DTO (@Valid)                  │
│  ✓ Вызывает Service, формирует ResponseEntity       │
│  ✗ НЕ содержит бизнес-логику                        │
│  ✗ НЕ обращается к Repository напрямую              │
└──────────────────────┬──────────────────────────────┘
                       │ DTO / Domain objects
┌──────────────────────▼──────────────────────────────┐
│                Service (@Service)                    │
│  ✓ Содержит бизнес-логику и правила                 │
│  ✓ Управляет транзакциями (@Transactional)          │
│  ✓ Бросает доменные исключения                      │
│  ✗ НЕ знает об HTTP (статусы, заголовки)            │
└──────────────────────┬──────────────────────────────┘
                       │ Entity objects
┌──────────────────────▼──────────────────────────────┐
│              Repository (@Repository)                │
│  ✓ CRUD-операции с хранилищем данных                │
│  ✓ Абстракция: смена БД не затрагивает слои выше    │
│  ✗ НЕ содержит бизнес-логику                        │
└─────────────────────────────────────────────────────┘
```

**Почему это важно?** В статье 6.6 мы заменим in-memory хранилище на PostgreSQL через Spring Data JPA. Изменится только `Repository`. Контроллер и сервис не тронем ни строчки — и это ценность правильной архитектуры.

## 3. DTO паттерн: зачем скрывать кухню от гостя

**[Уровень: Middle]**

Гость в ресторане видит красиво оформленное меню — не список сырых ингредиентов с ценами закупки. DTO (Data Transfer Object) — это именно такое "меню": мы контролируем, что клиент видит и что может передать.

### Почему нельзя использовать Entity напрямую

Java

```
// ⚠️ Антипаттерн: Entity в контроллере
@PostMapping
public Task create(@RequestBody Task task) {
    // Проблема 1: клиент может передать id, createdAt — сервер должен их генерировать
    // Проблема 2: поля пароля или внутреннего статуса попадут в ответ
    // Проблема 3: добавили поле в Entity → изменился API контракт (без вашего ведома)
    // Проблема 4: JPA lazy-loading вызовет ошибки сериализации
    return taskRepository.save(task);
}
```

### Наши DTO и их назначение

text

```
dto/request/
  TaskCreateRequest  → что клиент присылает при создании (POST)
  TaskUpdateRequest  → что клиент присылает при полном обновлении (PUT)
  TaskPatchRequest   → что клиент присылает при частичном обновлении (PATCH)

dto/response/
  TaskResponse       → что сервер возвращает клиенту (всегда)

exception/
  ErrorResponse      → единый формат ошибки (4xx, 5xx)
```

> **💡 Важно знать.** Мы используем ручной маппинг (`TaskResponse.from(task)`). В реальных проектах с десятками сущностей применяют **MapStruct** — он генерирует маппинг-код во время компиляции без overhead в runtime. **ModelMapper** работает через рефлексию в runtime — гибче, но медленнее. Для нашего учебного проекта ручной маппинг прозрачнее и понятнее.

### DTO для запросов

Java

```
// dto/request/TaskCreateRequest.java
package ru.example.taskapi.dto.request;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Size;

/**
 * DTO для создания задачи (POST /api/v1/tasks).
 * Клиент передаёт только title, description и done.
 * id и createdAt — генерирует сервер, клиент их не передаёт.
 */
public class TaskCreateRequest {

    @NotBlank(message = "Название задачи не может быть пустым")
    @Size(max = 255, message = "Название не должно превышать 255 символов")
    private String title;

    @Size(max = 1000, message = "Описание не должно превышать 1000 символов")
    private String description; // опционально — @NotBlank намеренно не ставим

    private boolean done = false;

    public TaskCreateRequest() {}

    public TaskCreateRequest(String title, String description, boolean done) {
        this.title = title;
        this.description = description;
        this.done = done;
    }

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getDescription() { return description; }
    public void setDescription(String description) { this.description = description; }
    public boolean isDone() { return done; }
    public void setDone(boolean done) { this.done = done; }
}
```

Java

```
// dto/request/TaskUpdateRequest.java
package ru.example.taskapi.dto.request;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Size;

/**
 * DTO для полного обновления задачи (PUT /api/v1/tasks/{id}).
 * При PUT клиент ОБЯЗАН передать все поля — поэтому все они помечены
 * как обязательные. Отсутствующее поле означает "установить в null/default".
 */
public class TaskUpdateRequest {

    @NotBlank(message = "Название задачи не может быть пустым")
    @Size(max = 255, message = "Название не должно превышать 255 символов")
    private String title;

    @Size(max = 1000, message = "Описание не должно превышать 1000 символов")
    private String description;

    // Boolean (wrapper), не boolean (primitive) — чтобы @NotNull мог поймать null
    @NotNull(message = "Статус выполнения обязателен")
    private Boolean done;

    public TaskUpdateRequest() {}

    public TaskUpdateRequest(String title, String description, Boolean done) {
        this.title = title;
        this.description = description;
        this.done = done;
    }

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getDescription() { return description; }
    public void setDescription(String description) { this.description = description; }
    public Boolean getDone() { return done; }
    public void setDone(Boolean done) { this.done = done; }
}
```

// dto/request/TaskPatchRequest.java
package ru.example.taskapi.dto.request;

import jakarta.validation.constraints.Size;

/**
 * DTO для частичного обновления задачи (PATCH /api/v1/tasks/{id}).
 *
 * Ключевая задача PATCH: отличить "поле не передано" (не трогать)
 * от "поле передано" (обновить, даже если значение null).
 *
 * Решение: флаги *Present, которые Jackson устанавливает через сеттеры.
 * Если Jackson вызвал setTitle() — значит "title" был в JSON.
 * Если не вызвал — поле отсутствовало в JSON.
 */
public class TaskPatchRequest {

    @Size(max = 255, message = "Название не должно превышать 255 символов")
    private String title;

    @Size(max = 1000, message = "Описание не должно превышать 1000 символов")
    private String description;

    private Boolean done;

    // Флаги присутствия полей — Jackson вызывает сеттер только для полей из JSON
    private boolean titlePresent;
    private boolean descriptionPresent;
    private boolean donePresent;

    public TaskPatchRequest() {}

    public String getTitle() { return title; }
    public void setTitle(String title) {
        this.title = title;
        this.titlePresent = true; // ← Jackson вызвал этот сеттер = поле было в JSON
    }

    public String getDescription() { return description; }
    public void setDescription(String description) {
        this.description = description;
        this.descriptionPresent = true;
    }

    public Boolean getDone() { return done; }
    public void setDone(Boolean done) {
        this.done = done;
        this.donePresent = true;
    }

    public boolean isTitlePresent() { return titlePresent; }
    public boolean isDescriptionPresent() { return descriptionPresent; }
    public boolean isDonePresent() { return donePresent; }
}
```

### DTO для ответов

Java

```
// dto/response/TaskResponse.java
package ru.example.taskapi.dto.response;

import ru.example.taskapi.model.Task;

import java.time.LocalDateTime;

/**
 * DTO ответа — то, что видит клиент.
 * Мы контролируем состав ответа: можно скрыть поля,
 * добавить вычисляемые значения или переименовать поля
 * не трогая доменный объект Task.
 */
public class TaskResponse {

    private Long id;
    private String title;
    private String description;
    private boolean done;
    private LocalDateTime createdAt;

    public TaskResponse() {}

    public TaskResponse(Long id, String title, String description,
                        boolean done, LocalDateTime createdAt) {
        this.id = id;
        this.title = title;
        this.description = description;
        this.done = done;

// repository/InMemoryTaskRepository.java
package ru.example.taskapi.repository;

import org.springframework.stereotype.Repository;
import ru.example.taskapi.model.Task;

import java.time.LocalDateTime;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

/**
 * In-memory реализация репозитория.
 *
 * ConcurrentHashMap — потокобезопасная Map.
 * Spring Boot использует пул потоков Tomcat: несколько запросов
 * могут выполняться одновременно. Обычный HashMap дал бы race condition.
 *
 * AtomicLong — атомарный счётчик для генерации уникальных id.
 * Без него два одновременных запроса могли бы получить одинаковый id.
 */
@Repository
public class InMemoryTaskRepository implements TaskRepository {

    private final Map<Long, Task> storage = new ConcurrentHashMap<>();

    // getAndIncrement(): возвращает ТЕКУЩЕЕ значение, затем увеличивает на 1.
    // При начальном значении 1: первый вызов → id=1, второй → id=2 и т.д.
    private final AtomicLong idSequence = new AtomicLong(1);

    @Override
    public Task save(Task task) {
        if (task.getId() == null) {
            // Новая задача: генерируем id и фиксируем время создания
            task.setId(idSequence.getAndIncrement());
            task.setCreatedAt(LocalDateTime.now());
            // 💡 В реальных проектах для тестируемости времени используют Clock:
            // task.setCreatedAt(LocalDateTime.now(clock));
        }
        // Сохраняем в Map; при повторном вызове — обновляем существующую запись
        // 💡 В production лучше хранить defensive copy (копию), а не ссылку на объект,
        // но для учебных целей in-memory хранилище допускает хранение ссылок.
        storage.put(task.getId(), task);
        return task;
    }

    @Override
    public Optional<Task> findById(Long id) {
        // Optional явно выражает возможность отсутствия значения —
        // это лучше чем возвращать null и проверять его везде
        return Optional.ofNullable(storage.get(id));
    }

    @Override
    public List<Task> findAll() {
        // Возвращаем копию — защищаем внутренний storage от изменений снаружи
        return new ArrayList<>(storage.values());
    }

    @Override
    public void deleteById(Long id) {
        storage.remove(id);
    }

    @Override
    public boolean existsById(Long id) {
        return storage.containsKey(id);
    }
}
```

> **🔬 Под капотом: AtomicLong.**  
> `getAndIncrement()` — атомарная операция: чтение и увеличение происходят неделимо.  
> Даже если два потока вызовут её одновременно — каждый получит уникальное значение.  
> `synchronized` или `volatile` здесь не нужны: `AtomicLong` сам гарантирует безопасность.

// service/impl/TaskServiceImpl.java
package ru.example.taskapi.service.impl;

import org.springframework.stereotype.Service;
import ru.example.taskapi.dto.request.TaskCreateRequest;
import ru.example.taskapi.dto.request.TaskPatchRequest;
import ru.example.taskapi.dto.request.TaskUpdateRequest;
import ru.example.taskapi.dto.response.TaskResponse;
import ru.example.taskapi.exception.TaskNotFoundException;
import ru.example.taskapi.model.Task;
import ru.example.taskapi.repository.TaskRepository;
import ru.example.taskapi.service.TaskService;

import java.util.List;
import java.util.stream.Collectors;

/**
 * Реализация бизнес-логики для управления задачами.
 *
 * Зависит от интерфейса TaskRepository, а не от конкретной реализации.
 * Spring внедрит InMemoryTaskRepository через конструктор (статья 6.1).
 */
@Service
public class TaskServiceImpl implements TaskService {

    private final TaskRepository taskRepository;

    // Constructor injection — явная зависимость, поле можно сделать final,
    // легко тестировать (передаём mock прямо в конструктор)
    public TaskServiceImpl(TaskRepository taskRepository) {
        this.taskRepository = taskRepository;
    }

    @Override
    public TaskResponse create(TaskCreateRequest request) {
        Task task = new Task(
            null,                    // id сгенерирует репозиторий
            request.getTitle(),
            request.getDescription(),
            request.isDone(),
            null                     // createdAt установит репозиторий
        );
        return TaskResponse.from(taskRepository.save(task));
    }

    @Override
    public List<TaskResponse> findAll(int page, int size) {
        List<Task> all = taskRepository.findAll();

        // Простая пагинация через Stream API
        // В статье 6.6 это заменит Spring Data Pageable + SQL LIMIT/OFFSET
        int fromIndex = Math.min((long) page * size >= all.size()
            ? all.size() : page * size, all.size());
        int toIndex   = Math.min(fromIndex + size, all.size());

        return all.subList(fromIndex, toIndex)
                  .stream()
                  .map(TaskResponse::from)
                  .collect(Collectors.toList());
    }

    @Override
    public TaskResponse findById(Long id) {
        // orElseThrow — стандартный паттерн: Optional → доменное исключение
        // GlobalExceptionHandler перехватит его и вернёт 404
        Task task = taskRepository.findById(id)
            .orElseThrow(() -> new TaskNotFoundException(id));
        return TaskResponse.from(task);
    }

    @Override
    public TaskResponse update(Long id, TaskUpdateRequest request) {
        Task task = taskRepository.findById(id)
            .orElseThrow(() -> new TaskNotFoundException(id));

        // PUT: заменяем ВСЕ поля — даже если description == null,
        // это корректно: клиент сказал "description должен быть null"
        task.setTitle(request.getTitle());
        task.setDescription(request.getDescription()); // может быть null — это OK
        task.setDone(request.getDone());               // Boolean wrapper, @NotNull в DTO
        // createdAt не трогаем — это неизменяемые метаданные

        return TaskResponse.from(taskRepository.save(task));
    }

    @Override
    public TaskResponse patch(Long id, TaskPatchRequest request) {
        Task task = taskRepository.findById(id)
            .orElseThrow(() -> new TaskNotFoundException(id));

        // PATCH: обновляем ТОЛЬКО поля, которые присутствовали в JSON-запросе
        // Флаги *Present установил Jackson через сеттеры
        if (request.isTitlePresent()) {
            task.setTitle(request.getTitle());
        }
        if (request.isDescriptionPresent()) {
            task.setDescription(request.getDescription());
        }
        if (request.isDonePresent()) {
            // done в Task — boolean (primitive), done в request — Boolean (wrapper)
            // @NotNull не стоит в PatchRequest (поле опционально),
            // но раз флаг установлен — значение точно пришло
            task.setDone(request.getDone() != null && request.getDone());
        }

        return TaskResponse.from(taskRepository.save(task));
    }

    @Override
    public void delete(Long id) {
        // Сначала проверяем существование: если не найдено — 404
        // Это осознанный выбор: клиент должен знать, что передал неверный id
        if (!taskRepository.existsById(id)) {
            throw new TaskNotFoundException(id);
        }
        taskRepository.deleteById(id);
    }
}

package ru.example.taskapi.controller;

import ru.example.taskapi.service.TaskService;

import java.util.List;

/**
 * REST-контроллер для управления задачами.
 *
 * @Validated — включает валидацию @PathVariable и @RequestParam через аннотации.
 * Без него @Min, @Max на параметрах метода будут проигнорированы.
 */
@RestController
@RequestMapping("/api/v1/tasks")
@Validated
public class TaskController {

    private final TaskService taskService;

    public TaskController(TaskService taskService) {
        this.taskService = taskService;
    }

    // ─────────────────────────────────────────────
    // CREATE — POST /api/v1/tasks
    // ─────────────────────────────────────────────

    /**
     * Создаёт новую задачу.
     *
     * @Valid активирует Bean Validation для TaskCreateRequest.
     * Если валидация не прошла — Spring бросает MethodArgumentNotValidException
     * до вызова тела метода. GlobalExceptionHandler вернёт 400.
     *
     * ResponseEntity.created(location) устанавливает:
     * - статус 201 Created
     * - заголовок Location: /api/v1/tasks/{id}
     */
    @PostMapping
    public ResponseEntity<TaskResponse> create(
            @Valid @RequestBody TaskCreateRequest request) {

        TaskResponse created = taskService.create(request);

        // Строим Location header: текущий URL + "/{id}"
        URI location = ServletUriComponentsBuilder
            .fromCurrentRequest()           // http://localhost:8080/api/v1/tasks
            .path("/{id}")
            .buildAndExpand(created.getId())
            .toUri();                       // → .../api/v1/tasks/1

        return ResponseEntity
            .created(location)  // 201 Created + Location header
            .body(created);
    }

    // ─────────────────────────────────────────────
    // READ ALL — GET /api/v1/tasks?page=0&size=10
    // ─────────────────────────────────────────────

    /**
     * Возвращает список задач с пагинацией.
     * Параметры необязательны — при отсутствии используются defaults.
     *
     * @Min/@Max требуют @Validated на классе контроллера.
     */
    @GetMapping
    public ResponseEntity<List<TaskResponse>> findAll(
            @RequestParam(defaultValue = "0")
            @Min(value = 0, message = "Номер страницы не может быть отрицательным")
            int page,

            @RequestParam(defaultValue = "10")
            @Min(value = 1,   message = "Размер страницы должен быть не менее 1")
            @Max(value = 100, message = "Размер страницы не должен превышать 100")
            int size) {

        return ResponseEntity.ok(taskService.findAll(page, size));
    }

    // ─────────────────────────────────────────────
    // READ ONE — GET /api/v1/tasks/{id}
    // ─────────────────────────────────────────────

    /**
     * Возвращает задачу по id.
     * Если задача не найдена — TaskNotFoundException → GlobalExceptionHandler → 404.
     */
    @GetMapping("/{id}")
    public ResponseEntity<TaskResponse> findById(
            @PathVariable
            @Min(value = 1, message = "ID задачи должен быть положительным числом")
            Long id) {

        return ResponseEntity.ok(taskService.findById(id));
    }

    // ─────────────────────────────────────────────
    // UPDATE (full) — PUT /api/v1/tasks/{id}
    // ─────────────────────────────────────────────

    /**
     * Полностью заменяет задачу. Клиент обязан передать все поля.
     * Идемпотентен: повторный вызов с теми же данными даёт тот же результат.
     */
    @PutMapping("/{id}")
    public ResponseEntity<TaskResponse> update(

            @Valid @RequestBody TaskUpdateRequest request) {

        return ResponseEntity.ok(taskService.update(id, request));
    }

    // ─────────────────────────────────────────────
    // UPDATE (partial) — PATCH /api/v1/tasks/{id}
    // ─────────────────────────────────────────────

    /**
     * Частично обновляет задачу. Клиент передаёт только изменяемые поля.

     */
    @PatchMapping("/{id}")
    public ResponseEntity<TaskResponse> patch(
            @PathVariable @Min(1) Long id,
            @Valid @RequestBody TaskPatchRequest request) {

    }

    // ─────────────────────────────────────────────
    // DELETE — DELETE /api/v1/tasks/{id}
    // ─────────────────────────────────────────────

    /**
     * Удаляет задачу по id.

> Когда Bean Validation находит нарушения, Spring выбрасывает `MethodArgumentNotValidException`. ```
// advice/GlobalExceptionHandler.java
package ru.example.taskapi.advice;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.validation.ConstraintViolationException;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.http.converter.HttpMessageNotReadableException;
import org.springframework.validation.FieldError;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import ru.example.taskapi.dto.response.ErrorResponse;
import ru.example.taskapi.exception.TaskNotFoundException;

import java.util.List;
import java.util.stream.Collectors;

/**
 * Централизованный обработчик исключений.
 *
 * @RestControllerAdvice = @ControllerAdvice + @ResponseBody
 * Перехватывает исключения из ВСЕХ контроллеров приложения.
 *
 * Порядок обработчиков:
 * 1. Специфические исключения (TaskNotFoundException) — высокий приоритет
 * 2. Исключения валидации (MethodArgumentNotValidException)
 * 3. Общий обработчик (Exception) — низкий приоритет, последний рубеж
 *
 * Все методы возвращают ResponseEntity<ErrorResponse> —
 * единый тип для всех ошибок, единый формат JSON для клиента.
 */
@RestControllerAdvice
public class GlobalExceptionHandler {

    // ─────────────────────────────────────────────────────────
    // 404 Not Found: задача не найдена
    // ─────────────────────────────────────────────────────────

    @ExceptionHandler(TaskNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleTaskNotFound(
            TaskNotFoundException ex,
            HttpServletRequest request) {

        ErrorResponse body = ErrorResponse.of(
            HttpStatus.NOT_FOUND.value(),
            "Not Found",
            ex.getMessage(),        // "Задача с id=42 не найдена"
            request.getRequestURI() // "/api/v1/tasks/42"
        );
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(body);
    }

    // ─────────────────────────────────────────────────────────
    // 400 Bad Request: ошибки валидации @RequestBody (@Valid)
    // ─────────────────────────────────────────────────────────

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> handleValidation(
            MethodArgumentNotValidException ex,
            HttpServletRequest request) {

        // Собираем все нарушения в список строк "поле: сообщение"
        List<String> errors = ex.getBindingResult()
            .getFieldErrors()
            .stream()
            .map(FieldError::getDefaultMessage)
            .collect(Collectors.toList());

        ErrorResponse body = ErrorResponse.validation(
            request.getRequestURI(),
            errors
        );
        return ResponseEntity.badRequest().body(body);
    }

    // ─────────────────────────────────────────────────────────
    // 400 Bad Request: нарушения @Min/@Max на @PathVariable/@RequestParam
    // (срабатывает благодаря @Validated на контроллере)
    // ─────────────────────────────────────────────────────────

    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<ErrorResponse> handleConstraintViolation(
            ConstraintViolationException ex,
            HttpServletRequest request) {

        List<String> errors = ex.getConstraintViolations()
            .stream()
            .map(cv -> cv.getPropertyPath() + ": " + cv.getMessage())
            .collect(Collectors.toList());

        ErrorResponse body = ErrorResponse.validation(
            request.getRequestURI(),
            errors
        );
        return ResponseEntity.badRequest().body(body);
    }

    // ─────────────────────────────────────────────────────────
    // 400 Bad Request: невалидный JSON в теле запроса
    // ─────────────────────────────────────────────────────────

    @ExceptionHandler(HttpMessageNotReadableException.class)
    public ResponseEntity<ErrorResponse> handleMessageNotReadable(
            HttpMessageNotReadableException ex,
            HttpServletRequest request) {

        ErrorResponse body = ErrorResponse.of(
            HttpStatus.BAD_REQUEST.value(),
            "Bad Request",
            "Некорректный формат JSON в теле запроса",
            request.getRequestURI()
        );
        return ResponseEntity.badRequest().body(body);
    }

    // ─────────────────────────────────────────────────────────
    // 500 Internal Server Error: всё остальное
    // ─────────────────────────────────────────────────────────

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleAll(
            Exception ex,
            HttpServletRequest request) {

        // ВАЖНО: подробности — в лог (для разработчика), не клиенту (безопасность)
        // В production: log.error("Unexpected error", ex);
        System.err.println("Unexpected error: " + ex.getMessage());

        ErrorResponse body = ErrorResponse.of(
            HttpStatus.INTERNAL_SERVER_ERROR.value(),
            "Internal Server Error",
            "Произошла внутренняя ошибка. Попробуйте позже.", // без деталей!
            request.getRequestURI()
        );
        return ResponseEntity.internalServerError().body(body);
    }
}

## 11. PUT vs PATCH: в чём разница

**[Уровень: Middle]**

### Таблица сравнения

|Характеристика|PUT|PATCH|
|---|---|---|
|Семантика|Полная замена ресурса|Частичное изменение|
|Обязательность полей|Все поля обязательны|Только изменяемые|
|Отсутствующие поля|Затираются (null/default)|Не изменяются|
|Идемпотентность|✅ Да (RFC 7231)|⚠️ Зависит от реализации|
|Когда использовать|Замена всей задачи целиком|Смена только статуса, только названия|

> **💡 Альтернатива: Optional<T>.**  
> Вместо использования флагов `isTitlePresent` (как мы сделали в DTO), для реализации PATCH часто используют `Optional<T>` поля в DTO. Если поле `Optional.empty()` — оно не было передано. Если `Optional.of(value)` — было передано. Для работы этого подхода с Jackson требуется модуль `jackson-datatype-jdk8`.

### Визуализация: задача как ящик с ячейками

text

```
Исходное состояние задачи:
┌──────────────────┬──────────────────┬──────┐
│ title            │ description       │ done │
│ "Изучить Spring" │ "Читать статьи"   │false │
└──────────────────┴──────────────────┴──────┘

PUT { "title": "Новое название", "done": true }
→ description не передан → затирается!
┌──────────────────┬──────────────────┬──────┐
│ title            │ description       │ done │
│ "Новое название" │      null         │ true │
└──────────────────┴──────────────────┴──────┘

PATCH { "done": true }
→ title и description не переданы → не трогаем!
┌──────────────────┬──────────────────┬──────┐
│ title            │ description       │ done │
│ "Изучить Spring" │ "Читать статьи"   │ true │ ← изменился только done
└──────────────────┴──────────────────┴──────┘
```

### Демонстрация curl

Bash

```
# PUT — полная замена (description намеренно не передаём)
curl -X PUT http://localhost:8080/api/v1/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"title": "Новое название", "done": true}'
# → description станет null

# PATCH — только статус
curl -X PATCH http://localhost:8080/api/v1/tasks/1 \
  -H "Content-Type: application/json" \
  -d '{"done": true}'
# → title и description не изменятся
```

> **⚠️ Антипаттерн: "частичный PUT".**
> 
> Java
> 
> ```
> // ❌ Принимаем Map и обновляем только переданные поля в методе с @PutMapping
> @PutMapping("/{id}")
> public ResponseEntity<TaskResponse> update(@RequestBody Map<String, Object> fields) {
>     // Это поведение PATCH, а не PUT. Нарушает HTTP-семантику.
>     // Клиенты ожидают, что PUT = полная замена.
> }
> ```

## 12. Пагинация и сортировка

**[Уровень: Middle]**

Возвращать все записи сразу — плохая практика. Представьте список из миллиона задач. Пагинация ограничивает объём ответа.

Bash

```
# Первая страница, 10 задач (по умолчанию)
GET /api/v1/tasks

# Вторая страница, 5 задач
GET /api/v1/tasks?page=1&size=5

# Защита: size > 100 → ConstraintViolationException → 400 Bad Request
GET /api/v1/tasks?size=999
```

**Ответ с пагинацией:**

JSON

```
[
  {
    "id": 6,
    "title": "Задача шестая",
    "description": null,
    "done": false,
    "createdAt": "2024-01-15T11:00:00"
  }
]
```

> **💡 Важно знать: Spring Data Pageable.**  
> Наша реализация пагинации через `subList` — учебная заглушка без БД.  
> В реальном проекте с Spring Data JPA вы получаете пагинацию "из коробки":
> 
> Java
> 
> ```
> // Контроллер
> @GetMapping
> public Page<TaskResponse> findAll(Pageable pageable) { ... }
> 
> // Репозиторий
> public interface TaskRepository extends JpaRepository<Task, Long> {}
> // findAll(pageable) → SQL: SELECT * FROM tasks LIMIT ? OFFSET ?
> ```
> 
> Это принципиально важно: базе данных не нужно загружать миллион записей  
> в память — она отдаёт только нужную страницу. В статье 6.6 мы это реализуем.

## 13. Тестирование контроллера

**[Уровень: Senior]**

### Почему @WebMvcTest, а не @SpringBootTest

text

```
@SpringBootTest — загружает ВЕСЬ контекст:
✗ База данных, JPA, Flyway
✗ Все бины (@Service, @Repository, @Component)
✗ Медленно: 5–30 секунд на старт

@WebMvcTest — загружает ТОЛЬКО веб-слой:
✓ @RestController, @ControllerAdvice, фильтры
✓ MockMvc — HTTP запросы без реальной сети
✓ @Service мокируется через @MockBean
✓ Быстро: < 2 секунд
```

> **💡 Важно знать: @ControllerAdvice в @WebMvcTest.**  
> `@WebMvcTest` автоматически подхватывает все `@ControllerAdvice` в classpath.  
> Наш `GlobalExceptionHandler` будет загружен, поэтому тесты на `400` и `404`  
> проверяют реальную обработку ошибок, а не стандартный Spring Boot error response.

### Именование URL — правила

text

```
✅ Правильно                        ❌ Антипаттерн
/api/v1/tasks                       /api/v1/getTaskList
/api/v1/tasks/42                    /api/v1/task/42      (не множественное число)
/api/v1/tasks/42/subtasks           /api/v1/getSubtasksForTask?id=42

```

### Версионирование

text

```
# URL-версионирование (наш выбор — явно и просто)
/api/v1/tasks
/api/v2/tasks  ← новая версия с breaking changes

# Header-версионирование (менее наглядно)
Accept: application/vnd.myapi.v1+json
```

Версионирование позволяет выпускать новые версии API, не ломая клиентов, которые используют старую.

### Антипаттерны

> **⚠️ Антипаттерн #1: Entity в контроллере**
> 
> Java
> 
> ```
> @PostMapping
> public Task create(@RequestBody Task task) { ... } // ❌
> ```
> 
> Клиент видит структуру БД, может передать служебные поля, изменение схемы ломает API.

> **⚠️ Антипаттерн #2: 200 OK вместо 201 Created**
> 
> Java
> 
> ```
> return ResponseEntity.ok(created); // ❌ — нарушение HTTP-семантики
> return ResponseEntity.created(location).body(created); // ✅
> ```

> **⚠️ Антипаттерн #3: Бизнес-логика в контроллере**
> 
> Java
> 
> ```
> @PostMapping
> public ResponseEntity<?> create(@RequestBody TaskCreateRequest req) {
>     if (req.getTitle().contains("запрещённое слово")) { ... } // ❌ → в сервис
>     if (taskRepository.count() > 1000) { ... }               // ❌ → в сервис
> }
> ```

> **⚠️ Антипаттерн #4: Поглощение исключений с 200 OK**
> 
> Java
> 
> ```
> try {
>     return ResponseEntity.ok(taskService.findById(id));
> } catch (TaskNotFoundException e) {
>     return ResponseEntity.ok(null); // ❌ — 200 с null вместо 404
> }
> ```

## 15. Итоги: таблица всех endpoints

**[Уровень: все]**

|Метод|URL|Описание|Тело запроса|Статус успеха|Статусы ошибок|
|---|---|---|---|---|---|
|`POST`|`/api/v1/tasks`|Создать задачу|`TaskCreateRequest`|`201` + `Location`|`400`|
|`GET`|`/api/v1/tasks`|Список задач (с пагинацией)|—|`200`|`400` (невалидные params)|
|`GET`|`/api/v1/tasks/{id}`|Получить задачу|—|`200`|`404`|
|`PUT`|`/api/v1/tasks/{id}`|Полное обновление|`TaskUpdateRequest`|`200`|`400`, `404`|
|`PATCH`|`/api/v1/tasks/{id}`|Частичное обновление|`TaskPatchRequest`|`200`|`400`, `404`|
|`DELETE`|`/api/v1/tasks/{id}`|Удалить задачу|—|`204`|`404`|

### Что мы реализовали

- ✅ **Слоистая архитектура** Controller → Service → Repository
- ✅ **DTO паттерн**: разные DTO для создания, обновления и ответа
- ✅ **Правильные HTTP-статусы**: `201 + Location`, `204`, `404`, `400`
- ✅ **PUT vs PATCH**: полное и частичное обновление с корректной семантикой
- ✅ **Валидация**: `@Valid`, `jakarta.validation`, понятные сообщения об ошибках
- ✅ **Единый формат ошибок**: `ErrorResponse` с полем `errors` для списка нарушений
- ✅ **Централизованная обработка**: `@RestControllerAdvice` с тремя уровнями обработчиков
- ✅ **Тесты**: `@WebMvcTest` + `MockMvc` для всех операций и сценариев ошибок

4. Напиши 3 теста:
    - `GET /api/v1/tasks?categoryId=1` → `200` со списком задач нужной категории
    - `GET /api/v1/tasks?categoryId=1` → `200` с пустым списком если задач с такой категорией нет
    - `POST /api/v1/tasks` с `categoryId=999` (несуществующий) → `404`

> **Подсказка по URL для вложенных ресурсов.** Если категория — самостоятельная сущность, её CRUD располагается по пути `/api/v1/categories`. Задачи конкретной категории можно получить двумя путями: через фильтр (`/tasks?categoryId=1`) или через вложенный ресурс (`/categories/1/tasks`). Фильтр проще в реализации, вложенный ресурс — более "чистый" REST. Для этого задания используй фильтр.
