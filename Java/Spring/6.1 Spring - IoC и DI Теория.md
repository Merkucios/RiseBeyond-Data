
**Эта статья** — исчерпывающее руководство по **Spring IoC** (Inversion of Control) и **Dependency Injection в Java** для Spring Framework 6.x и Spring Boot 3.x. Мы пройдём путь от проблем жёсткой связанности (tight coupling) до внутренней архитектуры контейнера, AOT-компиляции и борьбы с циклическими зависимостями.

|Термин|Одной строкой|
|---|---|

|**BeanFactory**|Базовый интерфейс контейнера (минимальный функционал)|

<a name="tldr"></a>

## ⚡ TL;DR — для нетерпеливых

Если совсем нет времени на теорию — запомни три золотых правила:

1. **Всегда используй Constructor Injection** для обязательных зависимостей
2. **Зависись от интерфейсов**, а не от конкретных классов (принцип DIP из SOLID)
3. **Делай поля `final`** — это сигнал и компилятору, и читателю кода

Java

```
// ✅ Делай ТАК — Constructor Injection с final-полями
@Service
public class OrderService {

    // final: гарантия неизменности после создания
    private final OrderRepository repository;

    // Spring 4.3+: @Autowired не нужен, если конструктор один
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

Java

```
// ❌ НЕ делай ТАК — Field Injection
@Service
public class OrderService {

    // Нет final. Скрытая зависимость. Нельзя протестировать без Spring.
    @Autowired
    private MySqlOrderRepository repository; // плюс: зависимость от реализации, не интерфейса
}
```

_Почему именно так — читай дальше. Остальная статья объясняет **причины** этих правил._

## 1. Жизнь без IoC: история одной боли

`[Уровень: 🟢 Intern]`

<a name="section-11"></a>

### 1.1. Наивный подход: создаём всё сами

Представь: ты пишешь сервис для интернет-магазина. Нужно сохранить заказ в базу данных и отправить письмо покупателю. Самый очевидный подход — создать всё через `new`.

В Java 17+ для DTO (Data Transfer Object) используем `record` — лаконичный и неизменяемый тип данных:

Java

```
// DTO в виде record (Java 17+) — неизменяемый, без boilerplate
public record OrderRequest(List<String> items, String email) {}

// ❌ ПЛОХОЙ КОД: Tight Coupling (жёсткая связанность)
public class OrderService {

    // Мы сами создаём зависимости через new.
    // Конфигурация (адрес БД, SMTP) захардкожена прямо тут.
    private final MySqlOrderRepository repository =
            new MySqlOrderRepository("jdbc:mysql://localhost:3306/shop", "root", "password");

    private final EmailNotificationService notifier =
            new EmailNotificationService("smtp.gmail.com", 587);

    public void createOrder(OrderRequest request) {
        repository.save(request);
        notifier.send("Заказ создан", request.email());
    }
}
```

Код работает. Заказы создаются. Но попробуем написать тест — и начнётся боль.

<a name="section-12"></a>

### 1.2. Проблемы tight coupling

Java

```
// ❌ Попытка написать unit-тест для tight coupled кода
class OrderServiceTest {

    @Test
    void shouldCreateOrder() {
        // Чтобы создать OrderService, нужно:
        // 1. Поднятая MySQL на localhost:3306 с базой "shop"
        // 2. Доступный SMTP-сервер Google
        //
        // Это НЕ unit-тест. Это интеграционный тест поневоле.
        // Тест упадёт с "Connection refused" без реальной инфраструктуры.

        OrderService service = new OrderService(); // создаст ВСЕ зависимости
    }
}
```

Разберём проблемы системно:

|Проблема|Суть|Последствие|
|---|---|---|
|**Нетестируемость**|Нельзя создать сервис без реальной БД и SMTP|Тесты медленные, хрупкие, требуют инфраструктуры|
|**Жёсткая привязка**|`OrderService` знает о `MySqlOrderRepository`|Замена MySQL на PostgreSQL = правка кода сервиса|
|**Нарушение SRP**|Класс и бизнес-логикой занимается, и зависимости создаёт|Два повода для изменений|
|**Захардкоженная конфигурация**|Адрес БД и SMTP-порт — в исходном коде|Нельзя иметь разные настройки для dev/prod|
|**Нарушение OCP**|Добавить PayPal вместо Stripe = изменить сервис|Класс закрыт для расширения|

> 💡 **Что такое SOLID?**  
> SOLID — пять принципов объектно-ориентированного дизайна. В контексте IoC нас интересуют два:
> 
> - **S (SRP)** — класс должен иметь только одну причину для изменения
> - **D (DIP)** — зависеть от абстракций, а не от конкретных реализаций
> 
> Подробнее — в статье 3.1 нашей серии про принципы проектирования.

### 🤔 Проверь себя

Есть ли у тебя эти симптомы в проекте?

- [ ]  Чтобы запустить тест сервиса, нужно поднять Docker-контейнер с БД
- [ ]  В коде встречаются строки `"jdbc:mysql://..."` внутри конструкторов бизнес-классов
- [ ]  Нельзя заменить реализацию (например, SMS вместо Email) без правки кода сервиса

Если отметил хотя бы один пункт — IoC решает именно эти проблемы.

## 2. Inversion of Control: переворачиваем управление

`[Уровень: 🔵 Junior]`

### 2.1. Аналогия с IKEA и официантом

Есть два варианта получить стул:

**Без IoC (Tight Coupling):** Ты идёшь в лес, рубишь дерево, пилишь доски, шлифуешь, красишь, собираешь стул. Ты контролируешь **каждый шаг** создания зависимости.

**С IoC (Spring):** Ты приходишь в IKEA (Контейнер) и говоришь: _«Мне нужен стул»_. Ты не знаешь, на каком заводе его сделали и откуда привезли дерево. Ты просто **декларируешь потребность** — контейнер **предоставляет результат**.

Или ещё одна аналогия из ресторана:

- **Без IoC (шведский стол):** Ты сам берёшь блюда, сам несёшь, сам решаешь, сколько чего взять.
- **С IoC (ресторан с официантом):** Ты делаешь заказ (объявляешь зависимость). Официант (Spring) приносит блюдо (объект). Ты не знаешь и не должен знать, как оно приготовлено.

**Hollywood Principle:** «Don't call us, we'll call you» — не ты создаёшь зависимости, фреймворк управляет этим за тебя.

### 2.2. IoC — это принцип, а не паттерн

IoC — это **принцип проектирования** (как SOLID), а не конкретный инструмент. У него несколько форм реализации:

|Форма IoC|Суть|Пример|
|---|---|---|
|**Dependency Injection**|Зависимости передаются извне|Spring DI — фокус этой статьи|
|**Service Locator**|Объект сам запрашивает зависимости у реестра|JNDI — считается антипаттерном|
|**Template Method**|Базовый класс определяет алгоритм, подклассы — шаги|`JdbcTemplate`|
|**Strategy**|Поведение делегируется вставляемой стратегии|`Comparator`, `AuthenticationProvider`|

> 💡 **Важно знать:** IoC и DI — **не синонимы**. IoC — принцип («управление инвертировано»). DI — конкретный механизм реализации этого принципа. Так же, как SOLID — принцип, а конкретный рефакторинг — его воплощение.

## 3. Dependency Injection: теория

`[Уровень: 🔵 Junior]`

### 3.1. Три участника DI

**Аналогия с прорабом:**

- **Client (`OrderService`)** — строитель дома. Ему нужна электропроводка.
- **Service (`OrderRepository`)** — электрик. Делает нужную работу.
- **Injector (Spring Container)** — прораб. Находит электрика и приводит его к строителю.

Строитель не ищет электрика сам и не знает его имени. Прораб (Spring) всё решает.

Java

```
// Интерфейс — контракт (абстракция)
public interface OrderRepository {
    Order save(Order order);
    Optional<Order> findById(Long id);
}

// Реализация — конкретный электрик (клиент о нём НЕ знает)
@Repository
public class JpaOrderRepository implements OrderRepository {

    private final EntityManager em;

    // Spring инъецирует EntityManager через конструктор
    public JpaOrderRepository(EntityManager em) {
        this.em = em;
    }

    @Override
    public Order save(Order order) {
        em.persist(order);
        return order;
    }

    @Override
    public Optional<Order> findById(Long id) {
        return Optional.ofNullable(em.find(Order.class, id));
    }
}

// Клиент — зависит от интерфейса, не знает о JPA
@Service
public class OrderService {

    private final OrderRepository repository; // интерфейс!

    // Spring (Injector) найдёт реализацию и передаст сюда
    public OrderService(OrderRepository repository) {
        this.repository = repository;
    }

    public Order createOrder(OrderRequest request) {
        Order order = Order.from(request);
        return repository.save(order); // не знает: JPA это, JDBC или Redis
    }
}
```

**Ключевое правило DI:** клиент не знает **как** создаётся его зависимость — он знает только **что** ему нужно.

## 4. Виды DI: практика и рефакторинг

`[Уровень: 🔵 Junior → 🟡 Middle]`

<a name="section-41"></a>

### 4.1. Constructor Injection ✅ (Рекомендуемый)

Это **золотой стандарт** в современном Spring-коде.

Java

```
@Service
public class OrderService {

    // 1. Поля final — объект неизменяем после создания (Immutability)
    private final OrderRepository orderRepository;
    private final NotificationService notificationService;
    private final PaymentGateway paymentGateway;

    // 2. Один конструктор — @Autowired не нужен (Spring 4.3+)
    // Spring сам найдёт бины нужных типов и передаст их сюда
    public OrderService(
            OrderRepository orderRepository,
            NotificationService notificationService,
            PaymentGateway paymentGateway) {
        this.orderRepository = orderRepository;
        this.notificationService = notificationService;
        this.paymentGateway = paymentGateway;
    }

    public Order createOrder(OrderRequest request) {
        Payment payment = paymentGateway.charge(request.amount());
        Order order = Order.from(request, payment.id());
        Order saved = orderRepository.save(order);
        notificationService.send("Заказ создан: " + saved.id(), request.email());
        return saved;
    }
}
```

**Главное преимущество — тестируемость без Spring:**

Java

```
// JUnit 5 + Mockito — ни одной Spring-аннотации в тесте!
class OrderServiceTest {

    private OrderService orderService;
    private OrderRepository mockRepo;
    private NotificationService mockNotifier;
    private PaymentGateway mockGateway;

    @BeforeEach
    void setUp() {
        mockRepo = mock(OrderRepository.class);
        mockNotifier = mock(NotificationService.class);
        mockGateway = mock(PaymentGateway.class);

        // Создаём сервис напрямую — без Spring-контейнера!
        orderService = new OrderService(mockRepo, mockNotifier, mockGateway);
    }

    @Test
    void shouldCreateOrderAndSendNotification() {
        // Arrange
        var request = new OrderRequest(List.of("Book"), "user@test.com");
        when(mockGateway.charge(any())).thenReturn(new Payment("pay_123"));
        when(mockRepo.save(any())).thenReturn(new Order(1L, List.of("Book"), "pay_123"));

        // Act
        Order result = orderService.createOrder(request);

        // Assert
        assertThat(result.id()).isEqualTo(1L);
        verify(mockNotifier).send(contains("1"), eq("user@test.com"));
    }
}
```

**С Lombok — ещё лаконичнее:**

Java

```
@Service
@RequiredArgsConstructor // Lombok генерирует конструктор для всех final-полей
public class OrderService {

    private final OrderRepository orderRepository;
    private final NotificationService notificationService;
    private final PaymentGateway paymentGateway;

    // Конструктор не нужен — Lombok создаст его автоматически,
    // Spring увидит один конструктор и использует его для DI
}
```

**Преимущества Constructor Injection:**

|Преимущество|Пояснение|
|---|---|
|**Immutability**|Поля `final` — защита от случайного изменения|
|**Fail-fast**|Отсутствующая зависимость → исключение при старте, не NPE в runtime|
|**Явный контракт**|Все зависимости видны в API класса|
|**Тестируемость**|`new Service(mock1, mock2)` — без контейнера|
|**Circular deps**|Обнаруживаются немедленно при старте|
|**GraalVM / AOT**|Полная поддержка нативной компиляции в Spring 6.x|

<a name="section-42"></a>

### 4.2. Setter Injection ⚠️ (Для optional)

Используй только для **необязательных** зависимостей.

Java

```
@Component
public class ReportGenerator {

    // Обязательная зависимость — через конструктор (final)
    private final ReportDataService dataService;

    // Опциональная зависимость — через setter (не final)
    private MetricsCollector metricsCollector;

    public ReportGenerator(ReportDataService dataService) {
        this.dataService = dataService;
    }

    // required = false: если бина нет в контейнере — метод не вызовется
    @Autowired(required = false)
    public void setMetricsCollector(MetricsCollector metricsCollector) {
        this.metricsCollector = metricsCollector;
    }

    public Report generate(ReportRequest request) {
        Report report = dataService.fetchData(request);

        // Всегда проверяем optional-зависимость!
        if (metricsCollector != null) {
            metricsCollector.recordReportGenerated(report.type());
        }
        return report;
    }
}
```

**Современная альтернатива** — `Optional<T>` в конструкторе (Spring 4.3+):

Java

```
@Component
public class ReportGenerator {

    private final ReportDataService dataService;
    private final Optional<MetricsCollector> metricsCollector;

    public ReportGenerator(
            ReportDataService dataService,
            Optional<MetricsCollector> metricsCollector) {
        this.dataService = dataService;
        this.metricsCollector = metricsCollector;
    }

    public Report generate(ReportRequest request) {
        Report report = dataService.fetchData(request);
        // Никаких null-проверок — Optional сам всё обрабатывает
        metricsCollector.ifPresent(m -> m.recordReportGenerated(report.type()));
        return report;
    }
}
```

### 4.3. Field Injection ❌ (Антипаттерн)

Java

```
// ❌ АНТИПАТТЕРН — не делай так в production-коде

    @Autowired

**Почему это проблема — конкретные технические причины:**

**1. Тест требует рефлексии или поднятия Spring-контейнера:**

Java

```
// ❌ Вариант А: поднимаем ВЕСЬ контейнер ради одного unit-теста (медленно!)
@SpringBootTest
class BadOrderServiceTest { ... }

// ❌ Вариант Б: уродливый хак через рефлексию
class BadOrderServiceTest {
    @Test
    void test() {
        BadOrderService service = new BadOrderService();
        // orderRepository == null — NPE без рефлексии!
        ReflectionTestUtils.setField(service, "orderRepository", mockRepo);
        // 15 строк кода vs 3 строки при Constructor Injection
    }
}
```

**2. Нельзя сделать `final`** — поле изменяемо, защиты нет.

**3. Скрытые зависимости** — из конструктора не видно, что нужно классу. Можно добавить 15 `@Autowired`-полей, и никто не заметит сразу.

**4. Проблемы с GraalVM Native Image** — рефлексивный доступ к полям требует явной конфигурации `RuntimeHints`. Constructor Injection работает без дополнительных настроек.

> ⚠️ **Официальная позиция Spring Team:**  
> _«The Spring team generally advocates constructor injection»_  
> — Spring Framework Documentation 6.1
> 
> IntelliJ IDEA показывает предупреждение: _«Field injection is not recommended»_

### 🚫 Типичные ошибки новичков

**Ошибка:** Писать `@Autowired` над конструктором в Spring 6.

## 5. Spring IoC Container: архитектура изнутри

`[Уровень: 🟡 Middle]`

### 5.1. BeanFactory vs ApplicationContext

Spring IoC Container — это «директор завода». У него есть чертежи (`BeanDefinition`), конвейеры (`BeanPostProcessor`) и склад готовой продукции (singleton cache).

|Характеристика|BeanFactory|ApplicationContext|
|---|---|---|
|**Что это**|Базовый интерфейс (движок)|Полный контейнер (движок + функционал)|
|**Инициализация бинов**|Lazy — при первом `getBean()`|Eager — все singleton-бины при старте|
|**`@PostConstruct` / `@PreDestroy`**|Не обрабатывает|Обрабатывает автоматически|
|**AOP и `@Transactional`**|Нужна ручная настройка|Автоматически|
|**События (`ApplicationEvent`)**|Нет|Есть|
|**i18n (`MessageSource`)**|Нет|Есть|
|**Профили (`@Profile`)**|Нет|Есть|
|**Вердикт**|Только IoT / Embedded|**Стандарт для всех реальных проектов**|

> 💡 **Важно знать: FactoryBean != BeanFactory**
> 
> Это классический вопрос на собеседованиях, который путает многих:
> 
> - **`BeanFactory`** — это сам **контейнер** (интерфейс для управления бинами)
> - **`FactoryBean<T>`** — это специальный **бин**, который сам создаёт другие объекты
> 
> Если тебе нужно сложное создание объекта (например, настройка `DataSource` с кастомной логикой), ты реализуешь `FactoryBean`. Spring вызовет `getObject()` и положит результат в контейнер.
> 
> Java
> 
> ```
> // Пример FactoryBean
> @Component
> public class MyDataSourceFactory implements FactoryBean<DataSource> {
> 
>     @Override
>     public DataSource getObject() {
>         // сложная логика создания DataSource
>         HikariConfig config = new HikariConfig();
>         config.setJdbcUrl("jdbc:postgresql://localhost/mydb");
>         return new HikariDataSource(config);
>     }
> 
>     @Override
>     public Class<?> getObjectType() {
>         return DataSource.class;
>     }
> }
> ```

### 6.1. Кастомизация lifecycle

Используй стандартные аннотации Java (JSR-250) — они не привязывают код к Spring API:

Java

```
@Component
public class CacheService {

    private final ProductRepository productRepository;
    private Map<Long, Product> cache;

    public CacheService(ProductRepository productRepository) {
        this.productRepository = productRepository;
        // Здесь DI уже выполнен, но @PostConstruct ещё не вызван
    }

    // Вызывается ПОСЛЕ DI, перед тем как бин станет доступен
    @PostConstruct
    public void init() {
        // Инициализируем кеш данными из БД
        this.cache = productRepository.findAll().stream()
                .collect(Collectors.toMap(Product::id, product -> product));
        System.out.println("Кеш инициализирован: " + cache.size() + " записей");
    }

    // Вызывается при остановке приложения (ctx.close())
    @PreDestroy
    public void cleanup() {
        // Освобождаем ресурсы корректно
        cache.clear();
        System.out.println("Кеш очищен");
    }
}
```

> ⚡ **Внимание: уровень сложности повышается.**  
> Следующий абзац — для тех, кто хочет понять, КАК Spring реализует `@Transactional`, `@Async` и `@Cacheable` внутри. Если ты Junior/Middle — можешь пропустить и вернуться позже.

### 6.2. BeanPostProcessor: сердце Spring-магии

`[Уровень: 🔴 Senior]`

`BeanPostProcessor` — хук, позволяющий вклиниться в создание **каждого** бина. Именно здесь работает магия аспектов.

Java

```
// Spring делает примерно это для @Transactional-бинов:
@Component
public class TransactionProxyPostProcessor implements BeanPostProcessor {

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        // Если у бина есть @Transactional методы — создаём CGLIB-прокси
        if (hasTransactionalMethods(bean.getClass())) {
            // Вместо оригинального бина возвращаем прокси
            // Прокси оборачивает каждый @Transactional-метод в транзакцию
            return createTransactionalProxy(bean);
        }
        return bean; // без @Transactional — возвращаем оригинал
    }
}
```

Именно поэтому когда в дебаггере ты видишь `OrderService$$EnhancerBySpringCGLIB$$a1b2c3` — это прокси, созданный BPP, а не твой класс напрямую.

### 7.2. @Configuration vs @Component: критический момент

`[Уровень: 🟡 Middle]`

Это нюанс, который упускают большинство туториалов.

Java

```
// ✅ Правильно: @Configuration
// Spring оборачивает класс в CGLIB-прокси.
// Все вызовы @Bean-методов перехватываются — бин всегда singleton.
@Configuration
public class AppConfig {

    @Bean
    public DataSource dataSource() {
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl("jdbc:postgresql://localhost/mydb");
        config.setMaximumPoolSize(10);
        return new HikariDataSource(config);
    }

    @Bean
    public JdbcTemplate jdbcTemplate() {
        // dataSource() перехватывается CGLIB.
        // Возвращается ТОТ ЖЕ экземпляр DataSource — один пул соединений.
        return new JdbcTemplate(dataSource());
    }
}
```

Java

```
// ❌ Ловушка: @Component (Lite Mode)
// Нет CGLIB-прокси. Вызовы @Bean — обычные Java-вызовы.
@Component
public class LiteConfig {

    @Bean
    public DataSource dataSource() {
        return new HikariDataSource(...);
    }

    @Bean
    public JdbcTemplate jdbcTemplate() {
        // ❌ Это обычный вызов Java-метода!
        // Создаётся НОВЫЙ HikariDataSource.
        // В итоге: два пула соединений, утечка ресурсов.
        return new JdbcTemplate(dataSource());
    }
}
```

**Правило:** Если в классе с `@Bean` ты вызываешь другой `@Bean`-метод — используй `@Configuration`, не `@Component`.

### 7.3. Оптимизация старта: Context Indexer

`[Уровень: ⚫ Senior+]`

**Решение:** добавь зависимость `spring-context-indexer`. Она создаёт файл `META-INF/spring.components` при компиляции. Spring читает его вместо сканирования classpath.

XML

```
<!-- Maven -->
<dependency>
    <groupId>org.springframework</groupId>
    <artifactId>spring-context-indexer</artifactId>
    <optional>true</optional>
</dependency>
```

Никакого кода менять не нужно — только добавить зависимость. При компиляции файл создаётся автоматически.

`[Уровень: 🔴 Senior]`

### 8.1. Инъекция коллекций: паттерн Chain of Responsibility

Spring может внедрить **все** реализации интерфейса сразу в виде `List`. Это элегантная реализация паттернов Strategy и Chain of Responsibility.

Java

```
// Интерфейс для валидации заказа
public interface OrderValidator {
    void validate(Order order);
}

// Три реализации — каждая проверяет своё
@Component
@Order(1) // Порядок выполнения в цепочке
public class StockValidator implements OrderValidator {
    @Override
    public void validate(Order order) {
        // Проверяем наличие товаров на складе
        order.items().forEach(item -> {
            if (!stockService.isAvailable(item)) {
                throw new ValidationException("Товар недоступен: " + item);
            }
        });
    }
}

@Component
@Order(2)
public class PaymentValidator implements OrderValidator {
    @Override
    public void validate(Order order) {
        // Проверяем корректность платёжных данных
        if (!paymentService.isValid(order.paymentInfo())) {
            throw new ValidationException("Некорректные платёжные данные");
        }
    }
}

@Component
@Order(3)
public class FraudValidator implements OrderValidator {
    @Override
    public void validate(Order order) {
        // Проверяем на признаки мошенничества
        if (fraudDetector.isSuspicious(order)) {
            throw new ValidationException("Подозрительная активность");
        }
    }
}

// Spring инъецирует ВСЕ реализации в порядке @Order
@Service
public class OrderValidationService {

    private final List<OrderValidator> validators;

    // [StockValidator, PaymentValidator, FraudValidator] — в порядке @Order
    public OrderValidationService(List<OrderValidator> validators) {
        this.validators = validators;
    }

    public void validate(Order order) {
        validators.forEach(v -> v.validate(order));
    }
}
```

**Результат:** добавить новый шаг валидации = создать класс с `@Component` + `@Order`. Ни одна строка существующего кода не меняется — это Open/Closed Principle в действии.

### 8.2. Bean Scopes: ловушка Prototype в Singleton

**Scopes в Spring:**

|Scope|Жизнь экземпляра|Когда использовать|
|---|---|---|
|`singleton` (default)|Один на контейнер|Stateless-сервисы (большинство случаев)|
|`prototype`|Новый при каждом `getBean()`|Stateful-объекты (корзина покупок)|
|`request`|Один на HTTP-запрос|Веб-приложения|
|`session`|Один на HTTP-сессию|Веб-приложения|

**Главная ловушка: Prototype внутри Singleton**

Java

```
@Component
@Scope("prototype") // Должен быть новым для каждого пользователя
public class ShoppingCart {
    private final List<Item> items = new ArrayList<>();
    public void addItem(Item item) { items.add(item); }
    public List<Item> getItems() { return Collections.unmodifiableList(items); }
}

// ❌ ЛОВУШКА
@Service // Singleton — создаётся один раз
public class CheckoutService {

    private final ShoppingCart cart; // ← Prototype инъецируется ОДИН РАЗ!

    public CheckoutService(ShoppingCart cart) {
        // cart создан при создании CheckoutService.
        // Все пользователи делят ОДНУ корзину!
        this.cart = cart;
    }
}
```

**Решение 1: ObjectProvider** (рекомендуется)

Java

```
@Service
public class CheckoutService {

    // ObjectProvider — "фабрика" для получения новых экземпляров
    private final ObjectProvider<ShoppingCart> cartProvider;

    public CheckoutService(ObjectProvider<ShoppingCart> cartProvider) {
        this.cartProvider = cartProvider;
    }

    public Order checkout(String userId) {
        ShoppingCart cart = cartProvider.getObject(); // Каждый раз новый!
        // ... логика оформления заказа
        return createOrderFrom(cart);
    }
}
```

**Решение 2: @Lookup** (Spring переопределит метод через CGLIB)

Java

```
@Service
public abstract class CheckoutService {

    // Spring создаст CGLIB-подкласс и переопределит этот метод
    @Lookup
    public abstract ShoppingCart getShoppingCart();

    public Order checkout() {
        ShoppingCart cart = getShoppingCart(); // Каждый вызов = новый Prototype
        return createOrderFrom(cart);
    }
}
```

### 8.3. Circular Dependencies и нюансы Boot 3.x

Циклическая зависимость — когда `ServiceA` зависит от `ServiceB`, а `ServiceB` зависит от `ServiceA`.

> 🔴 **Критично для Spring Boot 3.x:**  
> Начиная с Spring Boot **2.6** (и во всех версиях 3.x), циклические зависимости **запрещены по умолчанию** — приложение падает при старте с явной ошибкой, независимо от типа инъекции (Constructor, Setter или Field).

YAML

```
# application.properties
# ❌ Костыль — только если нет времени на рефакторинг
spring.main.allow-circular-references=true
```

**Правильные решения:**

**1. Рефакторинг — лучший вариант**

Java

```
// Было: A → B → A (цикл)
// Стало: A → C ← B (нет цикла)

// ServiceC содержит общую логику, от которой зависят A и B
@Service
public class SharedLogicService {
    public Result computeSharedLogic(Input input) { ... }
}

@Service
public class ServiceA {
    private final SharedLogicService sharedLogic;
    public ServiceA(SharedLogicService sharedLogic) { ... }
}

@Service
public class ServiceB {
    private final SharedLogicService sharedLogic;
    public ServiceB(SharedLogicService sharedLogic) { ... }
}
```

**2. ApplicationEvent — декаплинг через события**

Java

```
@Service
public class ServiceA {
    private final ApplicationEventPublisher eventPublisher;

    public ServiceA(ApplicationEventPublisher eventPublisher) {
        this.eventPublisher = eventPublisher;
    }

    public void doWork() {
        // Вместо прямого вызова serviceB.process() — публикуем событие
        eventPublisher.publishEvent(new WorkCompletedEvent(this, result));
    }
}

@Service
public class ServiceB {

    // ServiceB реагирует на события — нет прямой зависимости от ServiceA
    @EventListener
    public void onWorkCompleted(WorkCompletedEvent event) {
        // обработка
    }
}
```

> ⚠️ **Важно о синхронности событий:**  
> По умолчанию `ApplicationEventMulticaster` работает **синхронно** в том же потоке. Если обработчик события бросит исключение — оно вернётся обратно к публикатору. Это **не** полный декаплинг.
> 
> Для полного разрыва потока выполнения используй:
> 
> - `@Async` на методе `@EventListener` (требует `@EnableAsync`)
> - `@TransactionalEventListener` для событий в рамках транзакции

**3. @Lazy — как временная мера**

Java

```
@Service
public class ServiceA {
    private final ServiceB serviceB;

    // @Lazy: Spring инъецирует прокси вместо реального объекта.
    // Реальный ServiceB создастся при первом обращении.
    public ServiceA(@Lazy ServiceB serviceB) {
        this.serviceB = serviceB;
    }
}
```

> 💡 **Важно понять:** Циклическая зависимость — это **архитектурная проблема**, а не техническая. Её обнаружение — сигнал пересмотреть дизайн. `@Lazy` и `allow-circular-references` — обезболивающее, а не лечение.

### 8.4. Spring 6.x: AOT и Native Image

`[Уровень: ⚫ Senior+]`

Spring 6 принёс поддержку **GraalVM Native Image** через AOT-компиляцию (Ahead-of-Time). Это позволяет компилировать Spring-приложение в нативный исполняемый файл: мгновенный старт, минимум памяти.

**Как DI влияет на AOT:**

GraalVM при компиляции анализирует весь граф вызовов и удаляет код, который не вызывается явно. Рефлексия (используемая в Field Injection) — «невидима» для анализатора.

|Тип DI|Поддержка AOT|Комментарий|
|---|---|---|
|**Constructor Injection**|Отличная|Анализатор видит явные вызовы конструктора|
|**Setter Injection**|Хорошая|Setter — обычный метод, анализируется|
|**Field Injection**|Проблемная|Требует явной конфигурации `RuntimeHints`|

**Что ломается с Field Injection в Native Image:**

Java

```
// ❌ Field Injection в Native Image
@Service
public class OrderService {
    @Autowired
    private OrderRepository repository; // Spring пишет в это поле через рефлексию
}

// При AOT-компиляции GraalVM "не видит" запись в поле через рефлексию
// и может удалить его. Нужна явная конфигурация:
```

Java

```
// Приходится регистрировать рефлексивный доступ вручную
@Component
public class OrderServiceHints implements RuntimeHintsRegistrar {

    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        // "GraalVM, не удаляй это поле — мы будем писать в него через рефлексию"
        hints.reflection()
             .registerType(OrderService.class, MemberCategory.DECLARED_FIELDS);
    }
}
```

С Constructor Injection ничего дополнительно делать не нужно — AOT-процессор Spring автоматически генерирует корректный нативный код.

### 🔍 Найди антипаттерны в коде

Сколько проблем видишь в этом классе?

Java

```
@Service
public class GodService {

    @Autowired
    private ApplicationContext context;

    @Autowired
    private RepoA repoA;

    @Autowired
    private RepoB repoB;

    @Autowired
    private ServiceC serviceC;

    @Autowired
    private ServiceD serviceD;

    @Autowired
    private ServiceE serviceE;

    public void businessLogic() {
        // Создаём объект вне контейнера — DI в нём не работает
        Report report = new ReportGenerator().create();

        // Получаем бин из контейнера прямо в бизнес-логике
        UserService users = context.getBean(UserService.class);
        users.process(report);
    }
}
```

<details> <summary>👁️ Посмотреть ответ</summary>

**Найдено 4 антипаттерна:**

1. **Field Injection** — все 6 зависимостей через `@Autowired` на полях.
2. **God Object** — 6 зависимостей = явное нарушение SRP. Класс делает слишком много.
3. **`new` внутри бина** — `new ReportGenerator()`. Объект создан вне контейнера, `@Autowired`-зависимости в нём не сработают.
4. **Service Locator** — `context.getBean(UserService.class)` в бизнес-логике. Сервис не должен знать о контейнере.

</details>

### 9.2. Топ-5 заблуждений

**Заблуждение 1: «Singleton Bean = Thread-Safe»**  
Singleton означает один экземпляр на контейнер. Если бин имеет изменяемое состояние — он **не** потокобезопасен. Singleton-бины должны быть stateless.

**Заблуждение 2: «`@Autowired` обязателен всегда»**  
С Spring 4.3+ при единственном конструкторе `@Autowired` не нужен. Spring автоматически использует единственный конструктор.

**Заблуждение 3: «Field Injection проще — значит лучше»**  
Меньше строк ≠ лучше. Field Injection скрывает сложность, затрудняет тестирование, нарушает инкапсуляцию и ломает AOT.

**Заблуждение 4: «`BeanFactory` = `ApplicationContext`»**  
`ApplicationContext` **расширяет** `BeanFactory`, добавляя i18n, события, AOP-автоматику, eager-инициализацию. Это надмножество, а не синоним.

**Заблуждение 5: «IoC и DI — одно и то же»**  
IoC — принцип (управление инвертировано). DI — один из способов реализовать этот принцип. Всякий DI — это IoC, но не всякий IoC — это DI.

## 🧠 Проверь себя

Ответы скрыты — попробуй ответить сам, прежде чем смотреть.

---

**Вопрос 1 (🟢 Intern):** Почему `@Repository` лучше `@Component` для классов доступа к данным?

<details> <summary>👁️ Ответ</summary>

`@Repository` делает всё то же, что `@Component` (регистрирует бин), **плюс** активирует автоматическую трансляцию исключений. Если репозиторий бросит `SQLException` или `JpaException`, Spring автоматически конвертирует их в соответствующий подтип `DataAccessException`. Это позволяет бизнес-логике работать с единой иерархией исключений независимо от технологии доступа к данным (JDBC, JPA, MongoDB).

</details>

---

**Вопрос 2 (🔵 Junior):** Почему для обязательных зависимостей лучше Constructor, а не Setter Injection?

<details> <summary>👁️ Ответ</summary>

Три ключевые причины:

1. **Fail-fast:** Если обязательная зависимость не найдена, приложение упадёт сразу при старте с понятной ошибкой. С Setter Injection — `NullPointerException` в runtime, когда метод реально вызовется.
2. **Immutability:** Constructor Injection позволяет сделать поле `final`. Объект неизменяем после создания — меньше риск случайно перезаписать зависимость.
3. **Явный контракт:** Конструктор показывает все зависимости явно. Посмотрев на сигнатуру конструктора, сразу видно, что нужно классу для работы.

</details>

---

**Вопрос 3 (🟡 Middle):** В каком порядке вызываются: конструктор, `@PostConstruct`, setter-методы с `@Autowired`?

<details> <summary>👁️ Ответ</summary>

Правильный порядок:

1. **Конструктор** — создание экземпляра
2. **Setter-методы** (`@Autowired`) — Dependency Injection через setter
3. **`@PostConstruct`** — вызывается после того, как все зависимости инъецированы

Именно поэтому `@PostConstruct`-метод может безопасно использовать все зависимости — они уже установлены к моменту его вызова. Если бы `@PostConstruct` вызывался до DI, зависимости были бы `null`.

</details>

---

**Вопрос 4 (🔴 Senior):** Как правильно внедрить Prototype-бин в Singleton-бин, чтобы каждый вызов метода получал новый экземпляр?

<details> <summary>👁️ Ответ</summary>

Простая инъекция через конструктор **не работает** — Prototype создаётся один раз при создании Singleton.

Два корректных решения:

**Вариант 1: `ObjectProvider`** (предпочтительный)

Java

```
@Service
public class CheckoutService {
    private final ObjectProvider<ShoppingCart> cartProvider;

    public CheckoutService(ObjectProvider<ShoppingCart> cartProvider) {
        this.cartProvider = cartProvider;
    }

    public Order checkout() {
        ShoppingCart cart = cartProvider.getObject(); // Новый экземпляр каждый раз
        return createOrderFrom(cart);
    }
}
```

**Вариант 2: `@Lookup`** (через CGLIB-переопределение метода)

Java

```
@Service
public abstract class CheckoutService {
    @Lookup
    public abstract ShoppingCart getShoppingCart();

    public Order checkout() {
        ShoppingCart cart = getShoppingCart(); // Spring переопределит этот метод
        return createOrderFrom(cart);
    }
}
```

</details>

**Вопрос 5 (⚫ Senior+):** Почему Field Injection создаёт проблемы при компиляции в GraalVM Native Image, и как это исправить?

<details> <summary>👁️ Ответ</summary>

**Проблема:**  
GraalVM при AOT-компиляции проводит статический анализ всего кода и удаляет «мёртвый код» (Dead Code Elimination). Рефлексивный доступ к `private`-полям (который Spring использует для Field Injection) **не виден** статическому анализатору. GraalVM может удалить поле или закрыть к нему рефлексивный доступ.

**Решение 1: Constructor Injection** — анализатор видит явный вызов конструктора, никакой дополнительной конфигурации не нужно.

**Решение 2: RuntimeHints** — если Field Injection неизбежен:

Java

```
@Component
@ImportRuntimeHints(OrderServiceHints.class)
public class OrderService {
    @Autowired
    private OrderRepository repository;
}

class OrderServiceHints implements RuntimeHintsRegistrar {
    @Override
    public void registerHints(RuntimeHints hints, ClassLoader classLoader) {
        hints.reflection()
             .registerType(OrderService.class, MemberCategory.DECLARED_FIELDS);
    }
}
```

Это явно говорит AOT-процессору: «Этот тип используется через рефлексию — не удаляй поля».

</details>
