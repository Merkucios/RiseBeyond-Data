**[Уровень: Intern]**

В статьях 6.5 и 6.6 мы построили CRUD-контроллер и научились работать с DTO. Мы уже использовали минимальную валидацию:

Java

Мы добавляли `@NotBlank` и `@Valid` без объяснений — просто чтобы работало. А что если отправить `{"name": " ", "age": -5, "email": "не-почта"}`? Давайте разберёмся, как Spring защищает наш API и как использовать эту защиту на полную мощность.

## 2. Зачем нужна валидация

**[Уровень: Intern]**

Ваш CRUD из 6.6 уже запущен. Откройте терминал и отправьте запрос:

Bash

```
curl -X POST http://localhost:8080/api/users \
  -H "Content-Type: application/json" \
  -d '{"name": "", "email": "не-email", "age": -5}'
```

Без валидации этот запрос **пройдёт**. В базе появится пользователь с пустым именем, сломанным email и возрастом минус пять. Три реальных последствия:

**Пример 1: Отрицательная цена → финансовые потери.** Злоумышленник отправляет `{"price": -99999}`. Система «продаёт» товар и начисляет ему деньги.

**Пример 2: Пустое имя → сломанный интерфейс.** В базе появляется пользователь без имени. На странице профиля — пустота. В email-уведомлениях: «Здравствуйте, !».

**Пример 3: Строка в 10 млн символов → падение сервера.** Если колонка в БД — `VARCHAR(255)`, произойдёт ошибка. Если `TEXT` — в базу запишутся 10 МБ мусора, и сервер может исчерпать память при выборке.

> **⚠️ Антипаттерн: «Фронтенд всё проверит»**
> 
> Фронтенд — это HTML и JavaScript в браузере пользователя. Любой может открыть DevTools, написать скрипт или использовать `curl` и отправить произвольный JSON прямо на ваш сервер. Фронтенд-валидация — удобство для пользователя. Серверная валидация — **защита системы**. Правило: **Never trust the client**.

Хорошая новость: Spring делает валидацию декларативной. Добавляете аннотацию на поле — и проблема решена.

## 3. Подключение

**[Уровень: Intern]**

Начиная с Spring Boot 2.3, валидация **не входит** в `spring-boot-starter-web`. Добавляем явно:

XML

```
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
</dependency>
<!-- Версия управляется spring-boot-starter-parent -->
```

Стартер транзитивно подтянет Jakarta Validation API, Hibernate Validator (эталонную реализацию) и Expression Language.

> **💡 Важно знать**
> 
> Без этого стартера все аннотации (`@NotBlank`, `@Valid`, `@Size`) **молча игнорируются** — никаких ошибок компиляции. Код запустится, но валидация не будет работать.

## 4. Архитектура

**[Уровень: Junior]**

Валидация в Spring — три уровня:

- **Jakarta Bean Validation 3.0** — спецификация (набор аннотаций и интерфейсов, как JDBC для баз данных)
- **Hibernate Validator 8.x** — эталонная реализация спецификации (как MySQL Connector для JDBC)
- **Spring Validation** — интеграционный слой, встраивающий Bean Validation в контроллеры и сервисы

На практике: аннотации импортируем из `jakarta.validation`, расширения Spring — из `org.springframework.validation`:

Java

```
import jakarta.validation.Valid;                    // спецификация
import jakarta.validation.constraints.NotBlank;     // спецификация
import org.springframework.validation.annotation.Validated; // Spring
```

> **⚠️ Антипаттерн: `javax.validation` в Spring Boot 3.x**
> 
> Spring Boot 3 перешёл на Jakarta EE. Пакет `javax.validation` **не скомпилируется**. Правильный пакет — `jakarta.validation`.

Вот как запрос проходит через слои валидации:

text

```
HTTP-запрос
    │
    ▼
DispatcherServlet
    │
    ▼
HandlerMethodArgumentResolver ──→ десериализация JSON в объект
    │
    ▼
Bean Validation (Hibernate Validator) ──→ проверка аннотаций
    │
    ├── Невалидно → MethodArgumentNotValidException → 400 Bad Request
    │
    └── Валидно ↓
        Controller Method
            │
            ▼
        Service [@Validated] ──→ бизнес-валидация
            │
            ├── Невалидно → ConstraintViolationException → 400
            │
            └── Валидно ↓
                Repository → БД
```

> **🔬 Под капотом**
> 
> Когда Spring MVC получает запрос, `RequestResponseBodyMethodProcessor` десериализует JSON в объект, затем вызывает валидатор. Если есть нарушения — `MethodArgumentNotValidException` бросается **до вызова метода контроллера**. Ваш код в контроллере даже не узнает о невалидном запросе.

## 5. Встроенные аннотации

**[Уровень: Junior]**

### 5.1. @NotNull, @NotEmpty, @NotBlank — ключевые различия

Эти три аннотации проверяют «непустоту», но по-разному:

|Значение|`@NotNull`|`@NotEmpty`|`@NotBlank`|
|---|---|---|---|
|`null`|❌|❌|❌|
|`""`|✅|❌|❌|
|`" "`|✅|✅|❌|
|`"text"`|✅|✅|✅|

- **`@NotNull`** — любой тип. Проверяет только `!= null`
- **`@NotEmpty`** — строки и коллекции. Не null и не пустая (`length > 0` или `size > 0`)
- **`@NotBlank`** — **только строки**. Не null, не пустая и не только пробелы

> **💡 Важно знать:** `@NotBlank` на `Integer` вызовет `UnexpectedTypeException` в рантайме — компилятор ошибку не покажет.

### 5.2. Полная таблица аннотаций по категориям

**Null-проверки:**

|Аннотация|Применимые типы|Что проверяет|
|---|---|---|
|`@NotNull`|Любой|`!= null`|
|`@Null`|Любой|`== null`|

**Строковые:**

|Аннотация|Что проверяет|Пример|
|---|---|---|
|`@NotEmpty`|Не null и не пустая|`@NotEmpty String name`|
|`@NotBlank`|Не null, не пустая, не из пробелов|`@NotBlank String name`|
|`@Size(min, max)`|Длина в диапазоне|`@Size(min=2, max=100) String name`|
|`@Email`|Формат email|`@Email String email`|
|`@Pattern(regexp)`|Соответствие регулярке|`@Pattern(regexp="^\\+7\\d{10}$")`|

**Числовые:**

|Аннотация|Что проверяет|Пример|
|---|---|---|
|`@Min(value)`|`>= value`|`@Min(0) int quantity`|
|`@Max(value)`|`<= value`|`@Max(150) int age`|
|`@Positive`|`> 0`|`@Positive BigDecimal price`|
|`@PositiveOrZero`|`>= 0`|`@PositiveOrZero int stock`|
|`@Negative` / `@NegativeOrZero`|`< 0` / `<= 0`|`@Negative int delta`|
|`@DecimalMin` / `@DecimalMax`|Для BigDecimal|`@DecimalMin("0.01")`|
|`@Digits(integer, fraction)`|Макс. цифр до/после запятой|`@Digits(integer=6, fraction=2)`|

**Дата и время:**

|Аннотация|Что проверяет|Пример|
|---|---|---|
|`@Past`|Строго в прошлом|`@Past LocalDate birthDate`|
|`@PastOrPresent`|В прошлом или сейчас|`@PastOrPresent LocalDate hireDate`|
|`@Future`|Строго в будущем|`@Future LocalDate expiration`|
|`@FutureOrPresent`|В будущем или сейчас|`@FutureOrPresent LocalDate delivery`|

**Логические:**

|Аннотация|Что проверяет|Пример|
|---|---|---|
|`@AssertTrue`|`== true`|`@AssertTrue boolean termsAccepted`|
|`@AssertFalse`|`== false`|`@AssertFalse boolean blocked`|

**Коллекции и массивы:**

|Аннотация|Что проверяет|Пример|
|---|---|---|
|`@NotEmpty`|Не null и `size > 0`|`@NotEmpty List<String> tags`|
|`@Size(min, max)`|Количество элементов в диапазоне|`@Size(min=1, max=10) List<Item> items`|

> **💡 Важно знать:** все аннотации (кроме `@NotNull`, `@NotEmpty`, `@NotBlank`) **пропускают null**. За проверку null отвечает `@NotNull` отдельно.

### 5.3. Практика — расширяем DTO из 6.6

Java

```
package com.example.dto;

import jakarta.validation.constraints.*;
import java.time.LocalDate;

public class UserCreateRequest {

    @NotBlank(message = "Имя обязательно")
    @Size(min = 2, max = 100, message = "Имя: от 2 до 100 символов")
    private String name;

    @NotBlank(message = "Email обязателен")
    @Email(message = "Невалидный формат email")
    private String email;

    @NotNull(message = "Возраст обязателен")
    @Min(value = 18, message = "Минимальный возраст — 18")
    @Max(value = 150, message = "Максимальный возраст — 150")
    private Integer age;

    @Past(message = "Дата рождения должна быть в прошлом")
    private LocalDate birthDate;

    @NotBlank(message = "Пароль обязателен")
    @Size(min = 8, max = 64, message = "Пароль: от 8 до 64 символов")
    private String password;

    @NotBlank(message = "Подтверждение пароля обязательно")
    private String confirmPassword;

    private String phone;

    // Геттеры и сеттеры
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
    public Integer getAge() { return age; }
    public void setAge(Integer age) { this.age = age; }
    public LocalDate getBirthDate() { return birthDate; }
    public void setBirthDate(LocalDate birthDate) { this.birthDate = birthDate; }
    public String getPassword() { return password; }
    public void setPassword(String password) { this.password = password; }
    public String getConfirmPassword() { return confirmPassword; }
    public void setConfirmPassword(String confirmPassword) { this.confirmPassword = confirmPassword; }
    public String getPhone() { return phone; }
    public void setPhone(String phone) { this.phone = phone; }
}
```

## 6. Где размещать валидацию

**[Уровень: Junior]**

Данные поступают в контроллер тремя путями. Каждый валидируется по-своему:

|Источник|Как валидировать|Исключение|
|---|---|---|
|`@RequestBody`|`@Valid` на параметре|`MethodArgumentNotValidException`|
|`@PathVariable`|Аннотации + `@Validated` на классе|`ConstraintViolationException`|
|`@RequestParam`|Аннотации + `@Validated` на классе|`ConstraintViolationException`|

Java

```
package com.example.controller;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import com.example.service.UserService;
import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import org.springframework.http.HttpStatus;
import org.springframework.validation.annotation.Validated;
import org.springframework.web.bind.annotation.*;

import java.util.List;

@RestController
@RequestMapping("/api/users")
@Validated // ← ОБЯЗАТЕЛЬНО для валидации @PathVariable и @RequestParam
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    // 1. @RequestBody + @Valid — валидирует тело запроса
    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    public UserResponse create(@RequestBody @Valid UserCreateRequest request) {
        return userService.create(request);
    }

    // 2. @PathVariable + аннотация — валидирует path-переменную
    @GetMapping("/{id}")
    public UserResponse getById(
            @PathVariable @Min(value = 1, message = "Id >= 1") Long id) {
        return userService.findById(id);
    }

    // 3. @RequestParam + аннотация — валидирует query-параметр
    @GetMapping
    public List<UserResponse> search(
            @RequestParam @NotBlank(message = "Запрос не пуст") String query,
            @RequestParam(defaultValue = "0") @Min(0) int page,
            @RequestParam(defaultValue = "20") @Min(1) @Max(100) int size) {
        return userService.search(query, page, size);
    }
}
```

> **💡 Важно знать:** без `@Validated` **на классе** контроллера аннотации `@Min`, `@NotBlank` на `@PathVariable` и `@RequestParam` **молча игнорируются**. Это неочевидно — `@Valid` на `@RequestBody` работает без `@Validated` на классе, а `@PathVariable` — нет.

## 7. @Valid vs @Validated

**[Уровень: Middle]**

|Критерий|`@Valid`|`@Validated`|
|---|---|---|
|**Пакет**|`jakarta.validation`|`org.springframework.validation.annotation`|
|**Стандарт**|Jakarta (стандарт)|Spring (расширение)|
|**Группы валидации**|❌ Не поддерживает|✅ `@Validated(OnCreate.class)`|
|**Каскадная валидация полей**|✅ `@Valid Address address`|❌ Не работает на полях|
|**На уровне класса**|❌ Нет эффекта|✅ Включает Method Validation|

**Правило:**

text

```
На полях DTO (каскадная валидация) → @Valid
На @RequestBody без групп          → @Valid
На @RequestBody с группами         → @Validated(Group.class)
На классе контроллера/сервиса      → @Validated
```

## 8. Каскадная валидация

**[Уровень: Middle]**

Если `UserCreateRequest` содержит вложенный объект, Spring **не валидирует** его поля автоматически. Нужен `@Valid` на поле:

Java

```
package com.example.dto;

import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Pattern;

public class AddressDto {

    @NotBlank(message = "Город обязателен")
    private String city;

    @NotBlank(message = "Улица обязательна")
    private String street;

    @Pattern(regexp = "\\d{6}", message = "Индекс: 6 цифр")
    private String zipCode;

    // Геттеры и сеттеры
    public String getCity() { return city; }
    public void setCity(String city) { this.city = city; }
    public String getStreet() { return street; }
    public void setStreet(String street) { this.street = street; }
    public String getZipCode() { return zipCode; }
    public void setZipCode(String zipCode) { this.zipCode = zipCode; }
}
```

В `UserCreateRequest` добавляем:

Java

```
import jakarta.validation.Valid;
import jakarta.validation.constraints.NotNull;

// Добавляем к существующим полям UserCreateRequest:
@Valid              // ← БЕЗ ЭТОГО поля AddressDto НЕ ВАЛИДИРУЮТСЯ!
@NotNull(message = "Адрес обязателен")
private AddressDto address;

// + геттер и сеттер
public AddressDto getAddress() { return address; }
public void setAddress(AddressDto address) { this.address = address; }
```

Отправляем запрос с невалидным адресом:

Bash

```
curl -s -X POST http://localhost:8080/api/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Иван","email":"ivan@example.com","age":25,
       "password":"secureP1","confirmPassword":"secureP1",
       "address":{"city":"","street":"","zipCode":"abc"}}'
```

JSON

```
{
  "errors": [
    {"field": "address.city", "message": "Город обязателен"},
    {"field": "address.street", "message": "Улица обязательна"},
    {"field": "address.zipCode", "message": "Индекс: 6 цифр"}
  ]
}
```

Spring показывает **полный путь** до невалидного поля: `address.city`.

> **⚠️ Антипаттерн: забытый `@Valid` на вложенном объекте**
> 
> Без `@Valid` проверится только `@NotNull` (объект не null), но поля `city`, `street`, `zipCode` **не будут проверены**. Пустые строки попадут в базу.

## 9. Обработка ошибок

**[Уровень: Middle]**

В зависимости от источника данных Spring бросает **разные исключения**. Нам нужны отдельные обработчики для каждого.

Определим единый формат ответа:

Java

```
package com.example.dto;

import java.time.LocalDateTime;
import java.util.List;

public class ValidationErrorResponse {

    private LocalDateTime timestamp;
    private int status;
    private String message;
    private List<FieldErrorDetail> errors;

    public ValidationErrorResponse(int status, String message,
                                   List<FieldErrorDetail> errors) {
        this.timestamp = LocalDateTime.now();
        this.status = status;
        this.message = message;
        this.errors = errors;
    }

    public record FieldErrorDetail(String field, String message) {}

    // Геттеры
    public LocalDateTime getTimestamp() { return timestamp; }
    public int getStatus() { return status; }
    public String getMessage() { return message; }
    public List<FieldErrorDetail> getErrors() { return errors; }
}
```

### 9.1. MethodArgumentNotValidException — ошибки @RequestBody

Бросается, когда `@Valid` на `@RequestBody` обнаруживает нарушения:

Java

```
package com.example.exception;

import com.example.dto.ValidationErrorResponse;
import com.example.dto.ValidationErrorResponse.FieldErrorDetail;
import jakarta.validation.ConstraintViolationException;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.util.List;

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ValidationErrorResponse> handleMethodArgumentNotValid(
            MethodArgumentNotValidException ex) {

        List<FieldErrorDetail> fieldErrors = ex.getBindingResult()
                .getFieldErrors()
                .stream()
                .map(fe -> new FieldErrorDetail(
                        fe.getField(), fe.getDefaultMessage()))
                .toList();

        return ResponseEntity.badRequest().body(
                new ValidationErrorResponse(400, "Ошибка валидации", fieldErrors));
    }
```

### 9.2. ConstraintViolationException — ошибки @PathVariable и @RequestParam

Бросается, когда `@Validated` на классе контроллера обнаруживает нарушения в аннотациях на `@PathVariable` или `@RequestParam`. Также бросается при валидации на уровне сервиса:

Java

```
    @ExceptionHandler(ConstraintViolationException.class)
    public ResponseEntity<ValidationErrorResponse> handleConstraintViolation(
            ConstraintViolationException ex) {

        List<FieldErrorDetail> fieldErrors = ex.getConstraintViolations()
                .stream()
                .map(cv -> {
                    String path = cv.getPropertyPath().toString();
                    String field = path.contains(".")
                            ? path.substring(path.lastIndexOf('.') + 1) : path;
                    return new FieldErrorDetail(field, cv.getMessage());
                })
                .toList();

        return ResponseEntity.badRequest().body(
                new ValidationErrorResponse(400, "Ошибка валидации параметров",
                        fieldErrors));
    }
```

### 9.3. Общий обработчик Exception

Последняя линия обороны — никогда не показывайте стектрейс клиенту:

Java

```
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ValidationErrorResponse> handleGeneral(Exception ex) {
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(
                new ValidationErrorResponse(500, "Внутренняя ошибка сервера",
                        List.of()));
    }
}
```

### 9.4. BindingResult — ручная обработка (альтернатива)

Если нужно обработать ошибки прямо в контроллере, добавьте `BindingResult` **сразу после** `@Valid`:

Java

```
@PostMapping("/v2")
public ResponseEntity<?> createV2(
        @RequestBody @Valid UserCreateRequest request,
        BindingResult result) {  // ← СРАЗУ после @Valid!
    if (result.hasErrors()) {
        // Ручная обработка — MethodArgumentNotValidException НЕ бросается
    }
    return ResponseEntity.status(HttpStatus.CREATED).body(userService.create(request));
}
```

Если `BindingResult` стоит не сразу после `@Valid`, Spring проигнорирует его и бросит исключение как обычно.

### 9.5. 💡 RFC 7807 Problem Details

Начиная со Spring Boot 3, появилась встроенная поддержка стандарта **RFC 7807** для формата ошибок API через класс `org.springframework.http.ProblemDetail`. Включается одной строкой:

properties

```
# application.properties
spring.mvc.problemdetails.enabled=true
```

Spring будет возвращать ошибки в стандартизированном формате. Для кастомизации можно использовать `ProblemDetail` напрямую в обработчиках вместо нашего `ValidationErrorResponse`. Это индустриальный стандарт, упрощающий интеграцию с клиентами.

## 10. Кастомные валидаторы

**[Уровень: Middle/Senior]**

Встроенных аннотаций не всегда хватает. Кастомный валидатор состоит из двух частей:

text

```
@PhoneNumber (аннотация)
    │
    │  @Constraint(validatedBy = PhoneNumberValidator.class)
    │
    └──→ PhoneNumberValidator
              implements ConstraintValidator<PhoneNumber, String>
                                              │            │
                                        тип аннотации   тип значения
```

### 10.1. @PhoneNumber — валидатор без зависимостей

**Аннотация:**

Java

```
package com.example.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = PhoneNumberValidator.class)
@Target({ElementType.FIELD, ElementType.PARAMETER})
@Retention(RetentionPolicy.RUNTIME)
public @interface PhoneNumber {

    String message() default "Невалидный телефон. Формат: +7XXXXXXXXXX";

    // Обязательные атрибуты Bean Validation:
    Class<?>[] groups() default {};

    // payload позволяет присвоить метаданные нарушению
    // (например, уровень серьёзности). Обычно остаётся пустым.
    Class<? extends Payload>[] payload() default {};
}
```

**Валидатор:**

Java

```
package com.example.validation;

import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

public class PhoneNumberValidator implements ConstraintValidator<PhoneNumber, String> {

    private static final String PHONE_PATTERN = "^\\+7\\d{10}$";

    @Override
    public void initialize(PhoneNumber annotation) {
        // Здесь можно прочитать параметры аннотации
    }

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null) {
            return true; // null проверяет @NotNull — принцип единственной ответственности
        }
        return value.matches(PHONE_PATTERN);
    }
}
```

Применение в `UserCreateRequest`:

Java

```
@PhoneNumber // наш кастомный валидатор
private String phone;
```

### 10.2. @UniqueEmail — валидатор с доступом к базе данных

Иногда валидатор должен обратиться к базе данных — например, проверить уникальность email. Это принципиально другой уровень: валидатор становится Spring-бином с инжектированными зависимостями. Hibernate Validator создаёт валидаторы через Spring, что делает это возможным:

Java

```
package com.example.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = UniqueEmailValidator.class)
@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
public @interface UniqueEmail {
    String message() default "Пользователь с таким email уже существует";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

Java

```
package com.example.validation;

import com.example.repository.UserRepository;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;
import org.springframework.stereotype.Component;

@Component // Spring управляет жизненным циклом — DI работает
public class UniqueEmailValidator implements ConstraintValidator<UniqueEmail, String> {

    private final UserRepository userRepository;

    public UniqueEmailValidator(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Override
    public boolean isValid(String email, ConstraintValidatorContext context) {
        if (email == null) return true;
        return !userRepository.existsByEmailIgnoreCase(email);
    }
}
```

> **💡 Важно знать:** между проверкой уникальности и записью в БД другой поток может вставить тот же email (race condition). Поэтому **всегда дублируйте** unique constraint в БД — `@Column(unique = true)`.

## 11. Cross-field валидация

**[Уровень: Senior]**

Встроенные аннотации работают на уровне одного поля. Для проверки связи между полями (`password == confirmPassword`) есть два подхода.

### 11.1. Простой способ — @AssertTrue

Java

```
@AssertTrue(message = "Пароли не совпадают")
public boolean isPasswordsMatch() {
    if (password == null || confirmPassword == null) return true;
    return password.equals(confirmPassword);
}
```

Просто и быстро, но есть проблемы: ошибка привязывается к `passwordsMatch` (по имени метода), а не к конкретному полю. И логику нельзя переиспользовать в другом DTO.

### 11.2. Полноценный способ — валидатор уровня класса

Когда проблемы `@AssertTrue` становятся критичны — нужна привязка ошибки к конкретному полю и переиспользуемость — создаём валидатор на уровне класса:

text

```
┌─────────────────────────────────────┐
│   UserCreateRequest                  │
│   password:        "securePass1"     │
│   confirmPassword: "differentPass"   │──→ @PasswordMatch сравнивает
└─────────────────────────────────────┘
         │ не совпадают
         ▼
ConstraintViolation → поле "confirmPassword"
```

**Аннотация:**

Java

```
package com.example.validation;

import jakarta.validation.Constraint;
import jakarta.validation.Payload;
import java.lang.annotation.*;

@Documented
@Constraint(validatedBy = PasswordMatchValidator.class)
@Target({ElementType.TYPE}) // ← ставится на КЛАСС
@Retention(RetentionPolicy.RUNTIME)
public @interface PasswordMatch {
    String message() default "Пароли не совпадают";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
```

**Валидатор:**

Java

```
package com.example.validation;

import com.example.dto.UserCreateRequest;
import jakarta.validation.ConstraintValidator;
import jakarta.validation.ConstraintValidatorContext;

public class PasswordMatchValidator
        implements ConstraintValidator<PasswordMatch, UserCreateRequest> {

    @Override
    public boolean isValid(UserCreateRequest request,
                           ConstraintValidatorContext context) {
        if (request.getPassword() == null || request.getConfirmPassword() == null) {
            return true; // @NotBlank проверит отдельно
        }

        boolean valid = request.getPassword().equals(request.getConfirmPassword());

        if (!valid) {
            // Привязываем ошибку к конкретному полю
            context.disableDefaultConstraintViolation();
            context.buildConstraintViolationWithTemplate("Пароли не совпадают")
                    .addPropertyNode("confirmPassword")
                    .addConstraintViolation();
        }
        return valid;
    }
}
```

Применение — аннотация на классе:

Java

```
@PasswordMatch // ← cross-field валидация
public class UserCreateRequest {
    // ...поля name, email, password, confirmPassword, address...
}
```

> **🛠️ Сделай сам:** создайте аннотацию `@DateRange` уровня класса, которая проверяет что `startDate < endDate` в DTO для создания события.

## 12. Группы валидации

**[Уровень: Senior]**

Один DTO для создания и обновления, но правила разные? Группы валидации решают это.

**Наглядная таблица правил:**

|Поле|Аннотация|`OnCreate`|`OnUpdate`|
|---|---|---|---|
|`id`|`@Null` / `@NotNull`|`@Null` — не нужен|`@NotNull` — обязателен|
|`name`|`@NotBlank`|✅ Проверяется|✅ Проверяется|
|`email`|`@NotBlank`|✅ Обязателен|❌ Не проверяется|
|`password`|`@NotBlank`|✅ Обязателен|❌ Не проверяется|

**Шаг 1 — интерфейсы-маркеры:**

Java

```
package com.example.validation;

import jakarta.validation.groups.Default;

// extends Default — чтобы аннотации без groups тоже работали!
public interface OnCreate extends Default {}
```

Java

```
package com.example.validation;

import jakarta.validation.groups.Default;

public interface OnUpdate extends Default {}
```

**Шаг 2 — аннотации с группами:**

Java

```
package com.example.dto;

import com.example.validation.OnCreate;
import com.example.validation.OnUpdate;
import jakarta.validation.constraints.*;

public class UserRequest {

    @Null(groups = OnCreate.class, message = "Id не нужен при создании")
    @NotNull(groups = OnUpdate.class, message = "Id обязателен при обновлении")
    private Long id;

    @NotBlank(message = "Имя обязательно") // без groups → Default → работает всегда
    @Size(min = 2, max = 100)
    private String name;

    @NotBlank(groups = OnCreate.class, message = "Email обязателен при регистрации")
    @Email(message = "Невалидный формат email")
    private String email;

    @NotBlank(groups = OnCreate.class, message = "Пароль обязателен")
    @Size(min = 8, max = 64)
    private String password;

    // Геттеры и сеттеры
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
    public String getPassword() { return password; }
    public void setPassword(String password) { this.password = password; }
}
```

**Шаг 3 — контроллер:**

Java

```
@PostMapping
@ResponseStatus(HttpStatus.CREATED)
public UserResponse create(
        @RequestBody @Validated(OnCreate.class) UserRequest request) {
    // Проверит: @Null(id), @NotBlank(name), @NotBlank(email), @NotBlank(password)
    return userService.create(request);
}

@PutMapping("/{id}")
public UserResponse update(@PathVariable Long id,
        @RequestBody @Validated(OnUpdate.class) UserRequest request) {
    // Проверит: @NotNull(id), @NotBlank(name)
    // НЕ проверит: email и password — у них groups = OnCreate
    return userService.update(id, request);
}
```

> **⚠️ Антипаттерн: группа без `extends Default`**
> 
> Если `OnCreate` не наследует `Default`, то `@Validated(OnCreate.class)` проверит **только** аннотации с `groups = OnCreate.class`. Аннотации без `groups` (как `@NotBlank` на `name`) будут **проигнорированы**. Это самая частая ошибка при работе с группами.

> **💡 Группы vs отдельные DTO:** группы добавляют сложность. Альтернатива — отдельные `UserCreateRequest` и `UserUpdateRequest`. Проще читать и поддерживать. Группы оправданы, когда DTO совпадают на 90% или операций больше двух.

> **🛠️ Сделай сам:** добавьте группу `OnPatch` для PATCH-операции, где ни одно поле не является обязательным. Как изменятся аннотации?

## 13. Валидация на уровне сервиса

**[Уровень: Senior]**

Сервис может вызываться не только из контроллера — но из Kafka-консьюмера, scheduler'а, другого сервиса. Валидация на уровне сервиса гарантирует проверку независимо от источника.

Java

```
package com.example.service;

import com.example.dto.UserCreateRequest;
import com.example.dto.UserResponse;
import jakarta.validation.Valid;
import jakarta.validation.constraints.Min;
import org.springframework.stereotype.Service;
import org.springframework.validation.annotation.Validated;

@Service
@Validated // ← включает AOP-прокси для валидации параметров
public class UserService {

    public UserResponse create(@Valid UserCreateRequest request) {
        // Если request невалиден → ConstraintViolationException ДО тела метода
        return new UserResponse(1L, request.getName(), request.getEmail());
    }

    public UserResponse findById(@Min(value = 1, message = "Id >= 1") Long id) {
        // Если id < 1 → ConstraintViolationException
        return new UserResponse(id, "User", "user@example.com");
    }
}
```

> **🔬 Под капотом**
> 
> `spring-boot-starter-validation` активирует `ValidationAutoConfiguration`, которая регистрирует `MethodValidationPostProcessor` как Spring Bean. Аннотация `@Validated` на классе сервиса помечает бин как кандидат для Method Validation — AOP-перехватчик начинает оборачивать вызовы его методов. Явный `@EnableMethodValidation` не требуется при использовании стартера в Spring Boot 3.x.
> 
> При нарушении бросается `ConstraintViolationException`, который перехватывается нашим `GlobalExceptionHandler` (раздел 9.2).

**Рекомендация:** контроллер валидирует **формат данных** (`@NotBlank`, `@Email`, `@Size`), сервис — **бизнес-правила** (уникальность, доступность, права).

## 16. Типичные ошибки

**[Уровень: Middle]**

**1. Забытый `spring-boot-starter-validation`** — аннотации молча игнорируются. Нет ошибки компиляции.

**2. `javax.validation` вместо `jakarta.validation`** — не компилируется в Spring Boot 3.x.

**3. `@NotBlank` на `Integer`** — `UnexpectedTypeException` в рантайме. Для чисел используйте `@NotNull @Min`.

**4. Забытый `@Valid` на вложенном объекте** — поля вложенного DTO не валидируются:

Java

```
// ❌ Поля AddressDto НЕ проверяются
@NotNull private AddressDto address;

// ✅ @Valid включает каскадную валидацию
@Valid @NotNull private AddressDto address;
```

**5. Забытый `@Validated` на классе контроллера** — `@Min` на `@PathVariable` молча игнорируется.

**6. `BindingResult` не сразу после `@Valid`** — Spring бросает исключение вместо заполнения result.

**7. Один обработчик вместо двух** — `ConstraintViolationException` от `@PathVariable` и сервисов не перехватывается. Нужны **оба** `@ExceptionHandler`.

**8. Группа без `extends Default`** — аннотации без `groups` не проверяются при `@Validated(OnCreate.class)`.

## 17. Итоги

### Сводная таблица

|Что валидируем|Аннотация|Исключение|
|---|---|---|
|`@RequestBody` (тело)|`@Valid` / `@Validated(Group)`|`MethodArgumentNotValidException`|
|`@PathVariable`|`@Min` + `@Validated` на классе|`ConstraintViolationException`|
|`@RequestParam`|`@NotBlank` + `@Validated` на классе|`ConstraintViolationException`|
|Вложенный объект|`@Valid` на поле DTO|Часть `MethodArgumentNotValidException`|
|Параметр сервиса|`@Valid` + `@Validated` на классе|`ConstraintViolationException`|

### Чеклист для code review

text

```
□  spring-boot-starter-validation в pom.xml
□  Импорты jakarta.validation (не javax)
□  @Valid на @RequestBody
□  @Validated на классе контроллера (если есть @PathVariable/@RequestParam)
□  @Valid на вложенных объектах в DTO
□  Группы наследуют Default
□  Кастомные валидаторы: isValid(null) → true
□  GlobalExceptionHandler обрабатывает ОБА исключения
```
