**Без продуманной обработки ошибок ваш API — чёрный ящик для клиента: вместо понятного «пользователь не найден» он получает стектрейс в 50 строк или, что ещё хуже, HTTP 200 с полем `"error"` в теле.** В этой статье мы разберём все механизмы Spring для обработки исключений — от `@ResponseStatus` до `ProblemDetail` (RFC 7807) — и пошагово соберём production-ready `GlobalExceptionHandler`, который превращает любое исключение в предсказуемый, безопасный и информативный JSON-ответ.

## 1. Что мы строим

В статье 6.7 мы добавили валидацию через `@Valid`. Но ответ на ошибку валидации выглядел так:

JSON

```
{
  "timestamp": "2024-12-15T10:30:00.000+00:00",
  "status": 400,
  "error": "Bad Request",
  "path": "/api/users"
}
```

Какое поле не прошло валидацию? Что исправить? Клиент не знает. А если в коде `NullPointerException` — клиент может получить 500-ю ошибку со стектрейсом. Мы это исправим.

**К концу статьи мы построим `GlobalExceptionHandler`** — единый компонент, который:

- Перехватывает **любое** исключение из любого контроллера.
- Возвращает **единый JSON-формат** с `traceId`, статусом, сообщением.
- Логирует ошибки с правильным уровнем (`ERROR` / `WARN` / `DEBUG`).
- Никогда не раскрывает стектрейс клиенту.

Мы будем строить его итеративно: `v1` (простой) → `v2` (финальный, production-ready).

## 2. Три проблемы без обработки ошибок

**[Уровень: Intern]**

### Проблема 1: стектрейс в ответе клиенту

Без настроенной обработки ошибок Spring Boot может вернуть:

JSON

```
{
  "timestamp": "2024-12-15T10:30:00.000+00:00",
  "status": 500,
  "error": "Internal Server Error",
  "trace": "java.lang.NullPointerException: Cannot invoke \"String.length()\"...\n\tat com.example.service.UserService.findById(UserService.java:42)\n\tat com.example.controller.UserController.getUser(UserController.java:28)\n\t... 45 more",
  "path": "/api/users/42"
}
```

Злоумышленник видит имена классов (`com.example.service.UserService`), структуру пакетов, номера строк, зависимости (`org.springframework`, `org.apache`). Этого достаточно, чтобы искать известные уязвимости.

### Проблема 2: HTTP 200 с ошибкой внутри

JSON

```
HTTP/1.1 200 OK

{
  "success": false,
  "error": "User not found"
}
```

HTTP-статус 200 означает «успех». Клиентские библиотеки (`axios`, `fetch`), прокси, мониторинг — все ориентируются на статус. Если все ответы 200, мониторинг покажет «0 ошибок», пока приложение горит.

### Проблема 3: разные форматы в разных endpoint'ах

JSON

```
// GET /api/users/42 — UserController
{ "error": "User not found", "code": 404 }

// GET /api/tasks/99 — TaskController
{ "message": "Task does not exist", "status": "NOT_FOUND" }

// POST /api/projects — ProjectController
{ "errors": [{"msg": "not found"}], "success": false }
```

Вот что приходится писать клиенту:

JavaScript

```
// ❌ Кошмар — три формата, три парсера
function getErrorMessage(response) {
    if (response.data.error) return response.data.error;
    if (response.data.message) return response.data.message;
    if (response.data.errors?.[0]?.msg) return response.data.errors[0].msg;
    return 'Unknown error';
}
```

> ⚠️ **Все три проблемы решаются одним компонентом** — `GlobalExceptionHandler`. К концу статьи каждый ответ об ошибке из вашего API будет иметь одинаковую структуру, правильный HTTP-статус и никакого стектрейса.

## 3. Классификация ошибок и HTTP-статусы

**[Уровень: Junior]**

Все ошибки REST API делятся по двум осям:

||Техническая|Бизнесовая|
|---|---|---|
|**Клиент (4xx)**|400 — невалидный JSON, отсутствует параметр|404 — не найден, 409 — дубликат, 422 — бизнес-правило|
|**Сервер (5xx)**|500 — NPE, баг в коде|502 — внешний сервис недоступен|

**4xx** — клиент может исправить запрос и повторить. **5xx** — проблема на сервере, клиент ничего не сделает.

### Таблица HTTP-статусов

|Статус|Название|Когда использовать|Пример в TaskTracker|
|---|---|---|---|
|400|Bad Request|Невалидный JSON, ошибки `@Valid`|Пустое имя пользователя|
|401|Unauthorized|Нет аутентификации|_(рассмотрим в теме Security)_|
|403|Forbidden|Нет прав доступа|_(рассмотрим в теме Security)_|
|404|Not Found|Ресурс не существует|`GET /api/users/999` — нет такого пользователя|
|405|Method Not Allowed|Неправильный HTTP-метод|`PATCH /api/users` — не поддерживается|
|409|Conflict|Дубликат уникального поля|Регистрация с существующим email|
|410|Gone|Ресурс удалён навсегда|_(редко используется в CRUD API)_|
|422|Unprocessable Entity|Нарушение бизнес-правила|Назначение задачи на неактивного пользователя|
|429|Too Many Requests|Rate limiting|Слишком частые запросы к API|
|500|Internal Server Error|Баг в коде|`NullPointerException`|
|502|Bad Gateway|Внешний сервис упал|Ошибка при вызове Email API|
|503|Service Unavailable|Сервис перегружен|Плановое обслуживание|

## 4. Как Spring обрабатывает исключения

**[Уровень: Junior]**

Когда контроллер выбрасывает исключение, Spring запускает цепочку `HandlerExceptionResolver`. Каждый резолвер пытается обработать исключение — как только один справился, цепочка прерывается:

text

```
  Исключение из Controller
         │
         ▼
  ┌──────────────────────────────────────────────────┐
  │  ExceptionHandlerExceptionResolver (приоритет 1) │ ← ОДИН резолвер
  │                                                   │
  │  Шаг A: ищет @ExceptionHandler в ЭТОМ контроллере │ ← локальный
  │          Найден? → обработка, СТОП                │
  │                                                   │
  │  Шаг B: ищет @ExceptionHandler в @ControllerAdvice│ ← глобальный
  │          Найден? → обработка, СТОП                │
  └──────────────────┬───────────────────────────────┘
                     │ не найден
                     ▼
  ┌──────────────────────────────────────────────────┐
  │  ResponseStatusExceptionResolver (приоритет 2)    │
  │                                                   │
  │  Исключение имеет @ResponseStatus?                │
  │  Или это ResponseStatusException?                 │
  │  Да → устанавливает HTTP-статус, СТОП             │
  └──────────────────┬───────────────────────────────┘
                     │ не обработано
                     ▼
  ┌──────────────────────────────────────────────────┐
  │  DefaultHandlerExceptionResolver (приоритет 3)    │
  │                                                   │
  │  Стандартное Spring MVC исключение?                │
  │  (MethodArgumentNotValid → 400,                   │
  │   HttpRequestMethodNotSupported → 405, ...)       │
  │  Да → маппит в HTTP-статус, СТОП                  │
  └──────────────────┬───────────────────────────────┘
                     │ ничто не обработало
                     ▼
  ┌──────────────────────────────────────────────────┐
  │  BasicErrorController (/error)                    │
  │  Spring Boot fallback — последний рубеж           │
  └──────────────────────────────────────────────────┘
```

> 🔬 **Под капотом:** Ключевой момент — `ExceptionHandlerExceptionResolver` это **один** резолвер, который проверяет сначала **локальные** `@ExceptionHandler` (в самом контроллере), затем **глобальные** (в `@ControllerAdvice`). Это не два разных уровня, а два шага внутри одного резолвера.

## 5. Простые подходы: @ResponseStatus и ResponseStatusException

**[Уровень: Junior]**

### @ResponseStatus — аннотация на исключении

Java

```
package com.example.tasktracker.exception;

import org.springframework.http.HttpStatus;
import org.springframework.web.bind.annotation.ResponseStatus;

@ResponseStatus(HttpStatus.NOT_FOUND)
public class UserNotFoundException extends RuntimeException {
    public UserNotFoundException(Long id) {
        super("User with id " + id + " not found");
    }
}
```

Spring автоматически вернёт 404, но **мы не контролируем тело ответа** — формат задаёт Spring Boot.

### ResponseStatusException — программный способ

Java

```
import org.springframework.http.HttpStatus;
import org.springframework.web.server.ResponseStatusException;

@GetMapping("/{id}")
public User getUser(@PathVariable Long id) {
    return userRepository.findById(id)
        .orElseThrow(() -> new ResponseStatusException(
            HttpStatus.NOT_FOUND, "User with id " + id + " not found"));
}
```

Удобно для прототипов: не нужен отдельный класс. Но у вас 15 endpoint'ов — и в каждом `throw new ResponseStatusException(...)`. Теперь нужно добавить поле `errorCode` в каждый ответ — 15 мест для исправления. А логирование? Ещё 15 мест.

### Сравнительная таблица подходов

|Подход|Простота|Гибкость|Единый формат|Когда использовать|
|---|---|---|---|---|
|`@ResponseStatus`|★★★|★☆☆|Нет|Учебные примеры|
|`ResponseStatusException`|★★★|★★☆|Нет|Прототипы, MVP|
|`@RestControllerAdvice`|★★☆|★★★|**Да**|Production API|
|`+ ResponseEntityExceptionHandler + ProblemDetail`|★★☆|★★★|**Да (стандарт)**|Public / стандартизированный API|

Для production нужна **кастомная иерархия исключений + единый `@RestControllerAdvice`**.

## 6. Иерархия кастомных исключений

**[Уровень: Middle]**

Спроектируем иерархию, в которой каждое исключение несёт смысл бизнес-домена:

text

```
RuntimeException
 └── ApplicationException (abstract)
      │   Поля: HttpStatus status, String errorCode
      │
      ├── NotFoundException (404 NOT_FOUND)
      │    ├── UserNotFoundException
      │    └── TaskNotFoundException
      │
      ├── ConflictException (409 CONFLICT)
      │    └── UserAlreadyExistsException
      │
      └── BusinessException (422 UNPROCESSABLE_ENTITY)
           └── TaskAssignmentException
```

### Базовый класс

Java

```
package com.example.tasktracker.exception;

import org.springframework.http.HttpStatus;

/**
 * Базовое исключение приложения.
 * Содержит HTTP-статус и код ошибки для маппинга в REST-ответ.
 */
public abstract class ApplicationException extends RuntimeException {

    private final HttpStatus status;
    private final String errorCode;

    protected ApplicationException(HttpStatus status, String errorCode, String message) {
        super(message);
        this.status = status;
        this.errorCode = errorCode;
    }

    protected ApplicationException(HttpStatus status, String errorCode,
                                   String message, Throwable cause) {
        super(message, cause);
        this.status = status;
        this.errorCode = errorCode;
    }

    public HttpStatus getStatus() {
        return status;
    }

    public String getErrorCode() {
        return errorCode;
    }
}
```

> 💡 **Важно знать:** Хранение `HttpStatus` в доменном исключении — осознанный компромисс. Это удобно (статус рядом с исключением), но создаёт зависимость на `spring-web`. Если ваши исключения используются вне web-контекста (batch-обработка, messaging), рассмотрите вынос маппинга статусов в `@ControllerAdvice`.

> 💡 **Важно знать:** Все наши исключения наследуют `RuntimeException` (через `ApplicationException`). Это важно для `@Transactional`: по умолчанию Spring откатывает транзакцию только при `RuntimeException` и `Error`. Checked exceptions транзакцию **не откатывают**, если явно не указать `@Transactional(rollbackFor = CheckedException.class)`. Наша иерархия с `RuntimeException` работает с `@Transactional` корректно «из коробки».

### Промежуточные и конкретные исключения

Java

```
package com.example.tasktracker.exception;

import org.springframework.http.HttpStatus;

public class NotFoundException extends ApplicationException {
    public NotFoundException(String message) {
        super(HttpStatus.NOT_FOUND, "NOT_FOUND", message);
    }
}

public class ConflictException extends ApplicationException {
    public ConflictException(String message) {
        super(HttpStatus.CONFLICT, "CONFLICT", message);
    }
}

public class BusinessException extends ApplicationException {
    public BusinessException(String message) {
        super(HttpStatus.UNPROCESSABLE_ENTITY, "BUSINESS_RULE_VIOLATION", message);
    }
}
```

Java

```
package com.example.tasktracker.exception;

public class UserNotFoundException extends NotFoundException {
    public UserNotFoundException(Long userId) {
        super("User with id " + userId + " not found");
    }
}

public class UserAlreadyExistsException extends ConflictException {
    public UserAlreadyExistsException(String email) {
        super("User with email '" + email + "' already exists");
    }
}

public class TaskNotFoundException extends NotFoundException {
    public TaskNotFoundException(Long taskId) {
        super("Task with id " + taskId + " not found");
    }
}

public class TaskAssignmentException extends BusinessException {
    public TaskAssignmentException(String message) {

```

## 8. GlobalExceptionHandler v1 — @RestControllerAdvice

**[Уровень: Middle]**

`@RestControllerAdvice` = `@ControllerAdvice` + `@ResponseBody`. Один класс ловит исключения из **всех** контроллеров. Начнём с простой версии:

Java

```
package com.example.tasktracker.exception;

import com.example.tasktracker.dto.ErrorResponse;
import jakarta.servlet.http.HttpServletRequest;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.time.Instant;

@RestControllerAdvice
public class GlobalExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // Бизнес-ошибки — вся наша иерархия
    @ExceptionHandler(ApplicationException.class)
    public ResponseEntity<ErrorResponse> handleApplicationException(
            ApplicationException ex, HttpServletRequest request) {

        log.warn("[{}] {}: {}", ex.getErrorCode(), request.getRequestURI(), ex.getMessage());

        ErrorResponse body = new ErrorResponse(
            getTraceId(), Instant.now(),
            ex.getStatus().value(), ex.getErrorCode(),
            ex.getMessage(), request.getRequestURI());

        return ResponseEntity.status(ex.getStatus()).body(body);
    }

    // Всё непредвиденное — 500
    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleAll(
            Exception ex, HttpServletRequest request) {

        log.error("Unhandled exception at {}: {}", request.getRequestURI(), ex.getMessage(), ex);

        ErrorResponse body = new ErrorResponse(
            getTraceId(), Instant.now(),
            500, "INTERNAL_ERROR",
            "An unexpected error occurred", request.getRequestURI());

        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(body);
    }

    private String getTraceId() {
        String traceId = MDC.get("traceId");
        return traceId != null ? traceId : "no-trace-id";
    }
}
```

Это работает для наших исключений. Но есть **проблема**: отправим невалидный JSON — Spring бросает `HttpMessageNotReadableException`. Наш catch-all `Exception.class` перехватит его и вернёт **500 вместо 400**. Клиентская ошибка превращается в серверную — неправильно.

## 9. ResponseEntityExceptionHandler — зачем наследоваться

**[Уровень: Middle/Senior]**

Spring содержит класс `ResponseEntityExceptionHandler`, в котором уже написаны обработчики для **~15 стандартных Spring MVC исключений**:

|Исключение|HTTP|Причина|
|---|---|---|
|`MethodArgumentNotValidException`|400|Ошибки `@Valid`|
|`HttpMessageNotReadableException`|400|Невалидный JSON|
|`HttpRequestMethodNotSupportedException`|405|`PATCH` вместо `POST`|
|`MissingServletRequestParameterException`|400|Нет обязательного query-параметра|
|`NoResourceFoundException`|404|URL не существует (Spring Boot 3.2+)|
|И ещё ~10 других|||

**Наследуя от него, мы получаем:**

1. Корректные статусы для всех стандартных Spring-исключений — они **не попадают** в наш catch-all `Exception.class`.
2. Возможность **переопределить** конкретный обработчик для кастомизации формата.
3. Единую точку — метод `handleExceptionInternal()`, через который проходят все стандартные обработчики.

> ⚠️ **Антипаттерн:** Нельзя в наследнике `ResponseEntityExceptionHandler` создать **новый** `@ExceptionHandler(MethodArgumentNotValidException.class)` — Spring обнаружит два обработчика для одного типа и бросит `IllegalStateException: Ambiguous @ExceptionHandler`. Нужно именно **переопределять** protected-метод `handleMethodArgumentNotValid`.

> 🛠️ **Сделай сам:** Перед тем как переходить к v2, проверь проблему v1 на практике: отправь `POST /api/users` с телом `{ invalid json }`. С текущим `GlobalExceptionHandler v1` ты получишь **500** вместо **400**. В v2 мы это исправим.

## 10. GlobalExceptionHandler v2 — финальная версия

**[Уровень: Middle/Senior]**

Наследуем от `ResponseEntityExceptionHandler` и переопределяем нужные методы:

Java

```
package com.example.tasktracker.exception;

import com.example.tasktracker.dto.ErrorResponse;
import com.example.tasktracker.dto.ErrorResponse.ValidationError;
import jakarta.servlet.http.HttpServletRequest;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.http.HttpHeaders;
import org.springframework.http.HttpStatus;
import org.springframework.http.HttpStatusCode;
import org.springframework.http.ResponseEntity;
import org.springframework.lang.NonNull;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;
import org.springframework.web.context.request.ServletWebRequest;
import org.springframework.web.context.request.WebRequest;
import org.springframework.web.servlet.mvc.method.annotation.ResponseEntityExceptionHandler;

import java.time.Instant;
import java.util.List;

@RestControllerAdvice
public class GlobalExceptionHandler extends ResponseEntityExceptionHandler {

    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    // ═══════════════════════════════════════════════════════════
    // 1. Бизнес-ошибки — наша иерархия ApplicationException
    // ═══════════════════════════════════════════════════════════

    @ExceptionHandler(ApplicationException.class)
    public ResponseEntity<ErrorResponse> handleApplicationException(
            ApplicationException ex, HttpServletRequest request) {

        HttpStatus status = ex.getStatus();
        logByStatus(status, ex.getErrorCode(), ex.getMessage(), request, ex);

        ErrorResponse body = new ErrorResponse(
            getTraceId(), Instant.now(),
            status.value(), ex.getErrorCode(),
            ex.getMessage(), request.getRequestURI());

        return ResponseEntity.status(status).body(body);
    }

    // ═══════════════════════════════════════════════════════════
    // 2. Ошибки валидации @Valid — переопределяем из базового класса
    // ═══════════════════════════════════════════════════════════

    @Override
    protected ResponseEntity<Object> handleMethodArgumentNotValid(
            @NonNull MethodArgumentNotValidException ex,
            @NonNull HttpHeaders headers,
            @NonNull HttpStatusCode status,
            @NonNull WebRequest request) {

        List<ValidationError> fieldErrors = ex.getBindingResult()
            .getFieldErrors().stream()
            .map(fe -> new ValidationError(
                fe.getField(), fe.getDefaultMessage(), fe.getRejectedValue()))
            .toList();

        log.warn("Validation failed at {}: {}", extractPath(request), fieldErrors);

        ErrorResponse body = new ErrorResponse(
            getTraceId(), Instant.now(),
            HttpStatus.BAD_REQUEST.value(), "VALIDATION_FAILED",
            "Validation failed", extractPath(request), fieldErrors);

        // Вызываем handleExceptionInternal — он корректно устанавливает заголовки
        return handleExceptionInternal(ex, body, headers, status, request);
    }

    // ═══════════════════════════════════════════════════════════
    // 3. Все стандартные Spring-исключения — единый формат
    //    Переопределяем handleExceptionInternal, через который
    //    проходят ВСЕ обработчики базового класса
    // ═══════════════════════════════════════════════════════════

    @Override
    protected ResponseEntity<Object> handleExceptionInternal(
            @NonNull Exception ex, Object body,
            @NonNull HttpHeaders headers,
            @NonNull HttpStatusCode statusCode,
            @NonNull WebRequest request) {

        // Если body уже задан (например, из handleMethodArgumentNotValid) — не перезаписываем
        if (body == null || body instanceof String) {
            HttpStatus status = HttpStatus.resolve(statusCode.value());
            String errorName = status != null ? status.getReasonPhrase() : "Error";

            body = new ErrorResponse(
                getTraceId(), Instant.now(),
                statusCode.value(), errorName.toUpperCase().replace(' ', '_'),
                ex.getMessage(), extractPath(request));

            log.warn("Spring MVC exception at {}: {} — {}",
                extractPath(request), ex.getClass().getSimpleName(), ex.getMessage());
        }

        return super.handleExceptionInternal(ex, body, headers, statusCode, request);
    }

    // ═══════════════════════════════════════════════════════════
    // 4. Catch-all — непредвиденные исключения → 500
    // ═══════════════════════════════════════════════════════════

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleAllUncaughtExceptions(
            Exception ex, HttpServletRequest request) {

        String traceId = getTraceId();

        // 500 — всегда ERROR с полным стектрейсом
        log.error("[traceId={}] Unhandled exception at {} {}: {}",
            traceId, request.getMethod(), request.getRequestURI(),
            ex.getMessage(), ex);

        ErrorResponse body = new ErrorResponse(
            traceId, Instant.now(),
            500, "INTERNAL_ERROR",
            "An unexpected error occurred. Please contact support with traceId: " + traceId,
            request.getRequestURI());

        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(body);
    }

    // ═══════════════════════════════════════════════════════════
    // Вспомогательные методы
    // ═══════════════════════════════════════════════════════════

    private void logByStatus(HttpStatus status, String errorCode,
                             String message, HttpServletRequest request, Exception ex) {
        String uri = request.getMethod() + " " + request.getRequestURI();
        if (status.is5xxServerError()) {
            log.error("[traceId={}] [{}] {} at {}", getTraceId(), errorCode, message, uri, ex);
        } else if (status == HttpStatus.NOT_FOUND) {
            log.debug("[{}] {} at {}", errorCode, message, uri);
        } else {
            log.warn("[{}] {} at {}", errorCode, message, uri);
        }
    }

    private String getTraceId() {
        String traceId = MDC.get("traceId");
        return traceId != null ? traceId : "no-trace-id";
    }

    private String extractPath(WebRequest request) {
        if (request instanceof ServletWebRequest swr) {
            return swr.getRequest().getRequestURI();
        }
        return "unknown";
    }
}
```

## 11. ProblemDetail и RFC 7807

**[Уровень: Senior]**

В предыдущем разделе мы создали свой `ErrorResponse`. Это работает, но это **наш** формат — каждый проект придумывает свой. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) (ранее RFC 7807) — индустриальный **стандарт** формата ошибок с пятью фиксированными полями:

|Поле|Описание|
|---|---|
|`type`|URI — идентификатор **типа** проблемы (ссылка на документацию)|
|`title`|Краткое описание типа (не конкретного случая)|
|`status`|HTTP-статус|
|`detail`|Описание **конкретного** случая|
|`instance`|URI запроса|

Spring 6.x поддерживает `ProblemDetail` «из коробки»:

Java

```
import org.springframework.http.HttpStatus;
import org.springframework.http.ProblemDetail;
import jakarta.servlet.http.HttpServletRequest;
import java.net.URI;
import java.time.Instant;

@ExceptionHandler(ApplicationException.class)
public ProblemDetail handleApplicationException(
        ApplicationException ex, HttpServletRequest request) {

    ProblemDetail problem = ProblemDetail.forStatusAndDetail(
        ex.getStatus(), ex.getMessage());

    problem.setTitle(ex.getErrorCode());
    problem.setType(URI.create("https://api.tasktracker.com/errors/" +
        ex.getErrorCode().toLowerCase()));
    problem.setInstance(URI.create(request.getRequestURI()));
    problem.setProperty("traceId", getTraceId());     // расширение
    problem.setProperty("timestamp", Instant.now());   // расширение

    return problem; // Content-Type: application/problem+json
}
```

JSON

```
{
  "type": "https://api.tasktracker.com/errors/not_found",
  "title": "NOT_FOUND",
  "status": 404,
  "detail": "User with id 42 not found",
  "instance": "/api/users/42",
  "traceId": "abc-123",
  "timestamp": "2024-12-15T10:30:00Z"
}
```

Включение для стандартных Spring-исключений:

properties

```
# application.properties
spring.mvc.problemdetails.enabled=true
```

> 💡 **Важно знать:** `spring.mvc.problemdetails.enabled=true` активирует внутренний Spring Boot `@ControllerAdvice`, который обрабатывает стандартные исключения с `ProblemDetail`. Если вы уже наследуете `ResponseEntityExceptionHandler` — ваш advice имеет приоритет, и это свойство практически не влияет. Оно полезно, если вы **не** наследуете `ResponseEntityExceptionHandler` и хотите стандартные ошибки в формате RFC 7807.

### Когда что выбирать

|Критерий|Кастомный `ErrorResponse`|`ProblemDetail` (RFC 7807)|
|---|---|---|
|Стандартизация|Свой формат|Индустриальный стандарт|
|Content-Type|`application/json`|`application/problem+json`|
|Расширяемость|Поля в record|`setProperty()`|
|Для нового публичного API|Допустимо|**Рекомендуется**|
|Для внутреннего API с legacy|**Проще**|Возможно избыточно|

В этой статье мы продолжаем использовать `ErrorResponse` — он нагляднее для обучения. Но для нового проекта рассмотрите `ProblemDetail`.

**Service-слой — граница трансляции.** Здесь технические исключения превращаются в доменные:

Java

```
package com.example.tasktracker.service;

import com.example.tasktracker.exception.TaskAssignmentException;
import com.example.tasktracker.exception.TaskNotFoundException;
import com.example.tasktracker.exception.UserAlreadyExistsException;
import com.example.tasktracker.exception.UserNotFoundException;
import com.example.tasktracker.model.Task;
import com.example.tasktracker.model.User;
import com.example.tasktracker.repository.TaskRepository;
import com.example.tasktracker.repository.UserRepository;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.dao.DataIntegrityViolationException;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class UserService {

    private static final Logger log = LoggerFactory.getLogger(UserService.class);
    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    public User findById(Long id) {
        // Техническое Optional.empty() → доменное исключение
        return userRepository.findById(id)
            .orElseThrow(() -> new UserNotFoundException(id));
    }

    @Transactional
    public User create(User user) {
        if (userRepository.existsByEmail(user.getEmail())) {
            throw new UserAlreadyExistsException(user.getEmail());
        }
        try {
            return userRepository.save(user);
        } catch (DataIntegrityViolationException ex) {
            // Race condition: другой поток создал такой же email
            // Логируем оригинальную причину — она теряется при трансляции
            log.warn("Data integrity violation: {}", ex.getMessage());
            throw new UserAlreadyExistsException(user.getEmail());
        }
    }
}
```

> ⚠️ **Антипаттерн:** Пробрасывание `DataIntegrityViolationException` в REST-ответ. Клиент увидит: `"could not execute statement; constraint [uk_users_email]"` — утечка структуры БД.

## 13. Логирование и traceId

**[Уровень: Senior]**

### Уровни логирования

|HTTP|Уровень|Стектрейс в логе|Почему|
|---|---|---|---|
|404|`DEBUG`|Нет|Обычная ситуация|
|400, 409, 422|`WARN`|Нет|Клиентская ошибка, может указывать на баг в клиенте|
|500, 502|`ERROR`|**Да**|Баг или сбой — нужна полная диагностика|

Это реализовано в методе `logByStatus()` нашего `GlobalExceptionHandler`.

### traceId через MDC

Чтобы `traceId` был доступен **во всех логах** одного запроса (не только в ответе), нужен фильтр:

Java

```
package com.example.tasktracker.filter;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.MDC;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.UUID;

/**
 * Генерирует traceId для каждого запроса.
 * Кладёт в MDC — доступен во всех логах этого запроса.
 * Добавляет в заголовок ответа — клиент может передать в поддержку.
 */
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class TraceIdFilter extends OncePerRequestFilter {

    private static final String TRACE_ID_HEADER = "X-Trace-Id";
    private static final String TRACE_ID_MDC_KEY = "traceId";

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {

        // Берём traceId из заголовка (если клиент передал) или генерируем новый
        String traceId = request.getHeader(TRACE_ID_HEADER);
        if (traceId == null || traceId.isBlank()) {
            traceId = UUID.randomUUID().toString();
        }

        MDC.put(TRACE_ID_MDC_KEY, traceId);
        response.setHeader(TRACE_ID_HEADER, traceId);

        try {
            filterChain.doFilter(request, response);
        } finally {
            MDC.clear(); // Обязательно очищаем — потоки переиспользуются!
        }
    }
}
```

Теперь в `logback-spring.xml` добавляем `traceId` в формат логов:

XML

```
<configuration>
    <appender name="CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%X{traceId:-no-trace}] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>
    <root level="INFO">
        <appender-ref ref="CONSOLE" />
    </root>
</configuration>
```

Логи становятся такими:

text

```
10:30:00.123 [a1b2c3d4-e5f6-7890] WARN  c.e.t.e.GlobalExceptionHandler - [NOT_FOUND] User with id 42 not found at GET /api/users/42
10:30:01.456 [f7g8h9i0-j1k2-3456] ERROR c.e.t.e.GlobalExceptionHandler - [traceId=f7g8h9i0-j1k2-3456] Unhandled exception at GET /api/users/1: DB connection lost
```

`GlobalExceptionHandler` берёт `traceId` из MDC через `MDC.get("traceId")` — **один и тот же** `traceId` в логе и в ответе клиенту.

> 💡 **Важно знать:** В production используй **Micrometer Tracing** (Spring Boot 3.x, замена Spring Cloud Sleuth) — он автоматически генерирует `traceId` и `spanId`, пробрасывает их между микросервисами, интегрируется с Zipkin/Jaeger. `UUID.randomUUID()` — учебный подход. Зависимость для production:
> 
> XML
> 
> ```
> <dependency>
>     <groupId>io.micrometer</groupId>
>     <artifactId>micrometer-tracing-bridge-otel</artifactId>
> </dependency>
> ```

> ⚠️ **Антипаттерн: логирование дважды.** Если `GlobalExceptionHandler` логирует исключение, service **не должен** логировать его ещё раз. Исключение: service логирует `WARN` при **трансформации** (catch `DataIntegrityViolation` → throw `UserAlreadyExistsException`) — чтобы сохранить оригинальный контекст.

## 14. BasicErrorController и /error endpoint

**[Уровень: Senior]**

Spring Boot регистрирует `BasicErrorController` на пути `/error`. Это **последний рубеж** — обрабатывает ошибки, которые **не попали** в `@ControllerAdvice`:

1. **Исключение в фильтре** — фильтры работают **до** `DispatcherServlet`, `@ControllerAdvice` до них не добирается.
2. **Ошибки после response commit** — ответ уже начал отправляться клиенту.

### Обработка 404 для несуществующих URL

В Spring Boot 3.2+ при обращении к несуществующему URL Spring бросает `NoResourceFoundException`, которое обрабатывается через `ResponseEntityExceptionHandler` автоматически. В более ранних версиях Spring Boot требовались специальные настройки, чтобы Spring выбрасывал `NoHandlerFoundException` вместо прямого перенаправления на `/error`:

properties

```
# Для Spring Boot < 3.2 — без этих настроек 404 обходит @ControllerAdvice:
# spring.mvc.throw-exception-if-no-handler-found=true
# spring.web.resources.add-mappings=false

# Почему нужны оба:
# throw-exception-if-no-handler-found=true — заставляет DispatcherServlet
#   бросать NoHandlerFoundException вместо sendError(404)
# add-mappings=false — отключает ResourceHttpRequestHandler,
#   который иначе перехватывает ВСЕ запросы и возвращает 404 сам,
#   до того как DispatcherServlet увидит что handler не найден
```

> 💡 **Важно знать:** Если вы используете Spring Boot 3.2+ (рекомендовано в этом курсе), `NoResourceFoundException` выбрасывается по умолчанию и попадает в `ResponseEntityExceptionHandler`. Настройки выше не нужны. Но если вы работаете с Spring Boot 3.0–3.1, добавьте обе строки — иначе обращение к несуществующему URL не попадёт в ваш `GlobalExceptionHandler`.

### Настройки application.properties

properties

```
# Не включать стектрейс в ответы — НИКОГДА в production
server.error.include-stacktrace=never
# Не раскрывать класс исключения
server.error.include-exception=false
# Включить сообщение об ошибке
server.error.include-message=always

# ProblemDetail (раскомментируйте, если используете ProblemDetail вместо ErrorResponse)
# spring.mvc.problemdetails.enabled=true
```

### Кастомизация через ErrorAttributes

Java

```
package com.example.tasktracker.config;

import org.springframework.boot.web.error.ErrorAttributeOptions;
import org.springframework.boot.web.servlet.error.DefaultErrorAttributes;
import org.springframework.stereotype.Component;
import org.springframework.web.context.request.WebRequest;

import java.time.Instant;
import java.util.Map;

import org.slf4j.MDC;

/**
 * Кастомизация /error endpoint.
 * Добавляет traceId, убирает опасные поля.
 */
@Component
public class CustomErrorAttributes extends DefaultErrorAttributes {

    @Override
    public Map<String, Object> getErrorAttributes(
            WebRequest webRequest, ErrorAttributeOptions options) {
        Map<String, Object> attrs = super.getErrorAttributes(webRequest, options);

        attrs.put("traceId", MDC.get("traceId"));
        attrs.put("timestamp", Instant.now().toString());
        attrs.remove("trace");
        attrs.remove("exception");

        return attrs;
    }
}
```

> 💡 **Важно знать:** В хорошо спроектированном REST API `BasicErrorController` срабатывает **редко**. Большинство ошибок ловит `GlobalExceptionHandler`. Но `BasicErrorController` — это страховочная сетка, и её тоже нужно настроить (убрать стектрейс, добавить `traceId`).

## 15. Тестирование обработки ошибок

**[Уровень: Senior]**

Каждый error-сценарий нужно покрыть тестом:

Java

```
package com.example.tasktracker.controller;

import com.example.tasktracker.exception.GlobalExceptionHandler;
import com.example.tasktracker.exception.UserAlreadyExistsException;
import com.example.tasktracker.exception.UserNotFoundException;
import com.example.tasktracker.service.UserService;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.context.annotation.Import;
import org.springframework.http.MediaType;
import org.springframework.test.web.servlet.MockMvc;

import static org.hamcrest.Matchers.*;
import static org.mockito.ArgumentMatchers.any;
import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(UserController.class)
@Import(GlobalExceptionHandler.class)
class UserControllerErrorHandlingTest {

    @Autowired
    private MockMvc mockMvc;

    @MockBean
    private UserService userService;

    @Test
    @DisplayName("GET /api/users/{id} — не найден → 404 с телом ErrorResponse")
    void getUser_notFound_returns404() throws Exception {
        when(userService.findById(42L)).thenThrow(new UserNotFoundException(42L));

        mockMvc.perform(get("/api/users/42")
                .accept(MediaType.APPLICATION_JSON))
            .andExpect(status().isNotFound())
            .andExpect(content().contentTypeCompatibleWith(MediaType.APPLICATION_JSON))
            .andExpect(jsonPath("$.status").value(404))
            .andExpect(jsonPath("$.error").value("NOT_FOUND"))
            .andExpect(jsonPath("$.message").value("User with id 42 not found"))
            .andExpect(jsonPath("$.path").value("/api/users/42"))
            .andExpect(jsonPath("$.traceId").exists());
    }

    @Test
    @DisplayName("POST /api/users — дубликат email → 409")
    void createUser_duplicate_returns409() throws Exception {
        when(userService.create(any())).thenThrow(
            new UserAlreadyExistsException("john@example.com"));

        mockMvc.perform(post("/api/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content("""
                    { "name": "John", "email": "john@example.com" }
                    """))
            .andExpect(status().isConflict())
            .andExpect(jsonPath("$.status").value(409))
            .andExpect(jsonPath("$.error").value("CONFLICT"));
    }

    @Test
    @DisplayName("500 — стектрейс НЕ утекает клиенту")
    void internalError_noStackTraceLeak() throws Exception {
        when(userService.findById(1L)).thenThrow(new RuntimeException("DB down"));

        mockMvc.perform(get("/api/users/1"))
            .andExpect(status().isInternalServerError())
            .andExpect(jsonPath("$.error").value("INTERNAL_ERROR"))
            .andExpect(jsonPath("$.traceId").exists())
            // Проверяем что опасные данные НЕ утекают
            .andExpect(jsonPath("$.trace").doesNotExist())
            .andExpect(jsonPath("$.exception").doesNotExist())
            // Сообщение обобщённое, без "DB down"
            .andExpect(jsonPath("$.message").value(
                containsString("unexpected error")));
    }

    @Test
    @DisplayName("POST /api/users — невалидный JSON → 400")
    void malformedJson_returns400() throws Exception {
        mockMvc.perform(post("/api/users")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{ invalid }"))
            .andExpect(status().isBadRequest())
            .andExpect(jsonPath("$.traceId").exists())
            .andExpect(jsonPath("$.status").value(400));
    }
}
```

> 🛠️ **Сделай сам:** Напиши тест `deleteUser_withActiveTasks_returns422()` — service бросает `BusinessException("Cannot delete user with active tasks")`, тест проверяет 422 и сообщение.

## 16. Типичные ошибки — чек-лист

**[Уровень: Middle]**

|#|Антипаттерн|Что делать вместо|
|---|---|---|
|1|`catch (Exception e) { return null; }` — глотание|Бросить доменное исключение|
|2|`ResponseEntity.ok(Map.of("error", ...))` — 200 с ошибкой|Правильный HTTP-статус|
|3|Разные форматы в разных контроллерах|Единый `GlobalExceptionHandler`|
|4|Стектрейс в ответе клиенту|`server.error.include-stacktrace=never`|
|5|`log.error()` без стектрейса для 500|`log.error("msg", ex)` — всегда с `ex`|
|6|Catch-all без `extends ResponseEntityExceptionHandler`|Наследоваться — иначе `@Valid` → 500|
|7|Новый `@ExceptionHandler(MethodArgumentNotValidException.class)` при наследовании от `ResponseEntityExceptionHandler`|**Переопределять** protected-метод|
|8|`DataIntegrityViolationException` в ответе|Транслировать в доменное исключение|

## 17. Проверь себя

### Вопросы

**[Intern]** Почему нельзя возвращать 200 OK при ошибке?

<details> <summary>Ответ</summary> HTTP-статус 200 означает «успех». Клиентские библиотеки, прокси, мониторинг ориентируются на статус. Если все ответы 200, мониторинг покажет 0 ошибок, а кеш может закешировать «успешный» ответ с ошибкой. </details>

**[Junior]** Какой HTTP-статус вернуть, если клиент пытается создать пользователя с email, который уже существует?

<details> <summary>Ответ</summary> 409 Conflict — конфликт при создании из-за дубликата уникального поля. </details>

**[Middle]** Почему `@ExceptionHandler` внутри контроллера имеет приоритет над `@RestControllerAdvice`?

<details> <summary>Ответ</summary> Потому что `ExceptionHandlerExceptionResolver` — это один резолвер, который сначала ищет обработчик в текущем контроллере (локальный), и только если не нашёл — ищет в `@ControllerAdvice` бинах (глобальный). </details>

**[Senior]** Почему нельзя создать `@ExceptionHandler(MethodArgumentNotValidException.class)` в наследнике `ResponseEntityExceptionHandler`?

<details> <summary>Ответ</summary> `ResponseEntityExceptionHandler` уже содержит `@ExceptionHandler`, объявленный на список стандартных исключений (включая `MethodArgumentNotValidException`). Два `@ExceptionHandler` для одного типа в одном бине вызовут `IllegalStateException: Ambiguous @ExceptionHandler`. Нужно переопределять protected-метод `handleMethodArgumentNotValid`. </details>

**[Senior]** Чем `ProblemDetail` (RFC 7807) лучше кастомного `ErrorResponse` DTO?

<details> <summary>Ответ</summary> ProblemDetail — индустриальный стандарт (RFC 9457, ранее 7807). Любой клиент, знающий стандарт, может обработать ошибки без документации. Content-Type `application/problem+json` — машиночитаемый маркер. Расширяется через `setProperty()`. Встроен в Spring 6.x. </details>
