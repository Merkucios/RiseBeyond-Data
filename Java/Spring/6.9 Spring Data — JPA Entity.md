> ## 🎯 Переломный момент
> 
> **До этой статьи** данные хранились в `HashMap` внутри сервиса — один перезапуск приложения, и все пользователи исчезали. **Теперь** мы подключаем реальную базу данных — это меняет всё.
> 
> Восемь статей мы строили контроллеры, DTO, валидацию, обработку ошибок. Не хватало одного — **persistence**: способности приложения помнить данные между запусками. JPA (Jakarta Persistence API) и Hibernate решают именно эту задачу, превращая Java-объекты в строки таблиц.
> 
> В этой статье мы создадим Entity-класс `User` с полным набором аннотаций, подключим H2 для разработки, настроим автоматический аудит и напишем тесты. Тот самый `User` из статей 6.6 (DTO) и 6.7 (валидация) — теперь с настоящей базой данных.

## 1. Что такое JPA и ORM

**[Уровень: Intern]**

### 1.1. Проблема: объекты ≠ таблицы

Восемь статей мы строили контроллеры, DTO, валидацию. Но данные хранились так:

Java

```
// Наша "база данных" из предыдущих статей 😅
@Service
public class UserService {
    // Данные живут только пока запущено приложение
    private final Map<Long, User> storage = new HashMap<>();
    private final AtomicLong idGenerator = new AtomicLong(1);
    // Перезапуск приложения → всё исчезает 💀
}
```

Теперь заменим `HashMap` на настоящую БД. Но есть фундаментальная проблема: Java и реляционные базы данных «думают» по-разному.

Java

```
// Как видит мир Java
public class User {
    private Long id;
    private String firstName;
    private Address address;      // Вложенный объект!
    private List<Order> orders;   // Коллекция объектов!
}
```

SQL

```
-- Как видит мир реляционной БД
CREATE TABLE users (
    id         BIGINT PRIMARY KEY,
    first_name VARCHAR(50)
    -- address?  Отдельная таблица? Встроенные колонки?
    -- orders?   Как хранить коллекцию в строке?
);
```

Этот конфликт называется **Object-Relational Impedance Mismatch**. Вот полная карта соответствий между двумя мирами:

text

```
┌──────────────────────────────────────────┬────────────────────────────────────┐
│            Java (OOP)                    │     БД (Реляционная модель)        │
├──────────────────────────────────────────┼────────────────────────────────────┤
│ Класс (User)                             │ Таблица (users)                    │
│ Поле (firstName: String)                 │ Колонка (first_name VARCHAR)        │
│ Объект (new User("John", "Doe"))         │ Строка (row / record)              │
│ Примитивный тип (String, Long, boolean)  │ Тип данных (VARCHAR, BIGINT, BOOL) │
│ Ссылка на объект (@ManyToOne User)       │ Внешний ключ (user_id FK)          │
│ Коллекция (@OneToMany List<Order>)       │ Связанная таблица + JOIN           │
│ Наследование (class Admin extends User)  │ ??? (нет прямого аналога)          │
│ Идентичность объекта (==)                │ Первичный ключ (PRIMARY KEY)       │
└──────────────────────────────────────────┴────────────────────────────────────┘
```

**ORM (Object-Relational Mapping)** — это технология-переводчик между двумя мирами. Ты описываешь маппинг через аннотации, а ORM автоматически генерирует SQL.

### 1.2. Три уровня стека: JPA, Hibernate, Spring Data JPA

Вместо абстрактных аналогий — конкретные роли каждого слоя:

text

```
┌────────────────────────────────────────────────────────────────────┐
│  Spring Data JPA  →  "Я создам Repository-реализацию за тебя"     │
│                                                                    │
│  Ты пишешь:  Optional<User> findByEmail(String email);            │
│  Spring делает: генерирует полную реализацию + SQL-запрос          │
│                                                                    │
│  Пакет: org.springframework.data.jpa                               │
├────────────────────────────────────────────────────────────────────┤
│  JPA (Jakarta Persistence API 3.x)  →  "Вот стандарт маппинга"    │
│                                                                    │
│  Спецификация (контракт): @Entity, @Id, @Column, EntityManager     │
│  Сама по себе НЕ работает — только описывает правила               │
│                                                                    │
│  Пакет: jakarta.persistence  ← ВАЖНО! Не javax.persistence!       │
├────────────────────────────────────────────────────────────────────┤
│  Hibernate ORM 6.x  →  "Я реально выполняю маппинг"               │
│                                                                    │
│  Реализация JPA: генерирует SQL, кэши, прокси, диалекты БД        │
│  Пакет: org.hibernate                                              │
├────────────────────────────────────────────────────────────────────┤
│  JDBC  →  низкоуровневый протокол связи с БД                       │
├────────────────────────────────────────────────────────────────────┤
│  PostgreSQL / H2 / MySQL  →  физическое хранилище данных           │
└────────────────────────────────────────────────────────────────────┘
```

> 💡 **Важно знать:** Spring Boot 3.x использует **`jakarta.persistence.*`** (Jakarta EE 10). Если видишь в проекте `javax.persistence.*` — это код под Spring Boot 2.x / Hibernate 5.x. В нашем цикле везде только `jakarta.persistence`.

## 2. Подключение и настройка

**[Уровень: Intern]**

### 2.1. Зависимости (pom.xml)

XML

```
<dependencies>
    <!-- Spring Data JPA: подтягивает Hibernate 6.x + Jakarta Persistence 3.x -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-data-jpa</artifactId>
    </dependency>

    <!-- H2: встроенная in-memory БД для разработки и тестов -->
    <dependency>
        <groupId>com.h2database</groupId>
        <artifactId>h2</artifactId>
        <scope>runtime</scope>
    </dependency>

    <!-- PostgreSQL: раскомментируй для production
    <dependency>
        <groupId>org.postgresql</groupId>
        <artifactId>postgresql</artifactId>
        <scope>runtime</scope>
    </dependency>
    -->

    <!-- Lombok: удобство, но с правилами для JPA (разберём в разделе 10) -->
    <dependency>
        <groupId>org.projectlombok</groupId>
        <artifactId>lombok</artifactId>
        <optional>true</optional>
    </dependency>

    <!-- Тесты -->
    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-test</artifactId>
        <scope>test</scope>
    </dependency>
</dependencies>
```

> 💡 **Важно знать:** `scope=runtime` означает, что драйвер БД нужен только при запуске, но не при компиляции. Наш Java-код зависит от JPA-интерфейсов (`jakarta.persistence`), а не от конкретного JDBC-драйвера — это правильная абстракция.

## 3. Первая @Entity

**[Уровень: Junior]**

### 3.1. Минимальная Entity

Java

```
package com.example.demo.entity;

import jakarta.persistence.Entity;           // ← jakarta, не javax!
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

// @Entity — маркер для Hibernate: этот класс маппится на таблицу в БД
@Entity
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String firstName;
    private String lastName;

    // JPA ОБЯЗАТЕЛЬНО требует конструктор без аргументов.
    // protected — достаточно (Hibernate создаёт подкласс-прокси)
    protected User() {
    }

    public User(String firstName, String lastName) {
        this.firstName = firstName;
        this.lastName = lastName;
    }

    // Геттеры и сеттеры
    public Long getId()                      { return id; }
    public String getFirstName()             { return firstName; }
    public void setFirstName(String fn)      { this.firstName = fn; }
    public String getLastName()              { return lastName; }
    public void setLastName(String ln)       { this.lastName = ln; }
}
```

При запуске Hibernate прочитает аннотации и выполнит:

SQL

```
-- DDL, автоматически сгенерированный Hibernate для H2
CREATE TABLE user (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY,
    first_name VARCHAR(255),
    last_name  VARCHAR(255),
    PRIMARY KEY (id)
);
```

> 🛠️ **Сделай сам — первый момент истины:**
> 
> 1. Создай класс `User` с `@Entity` и `@Id`
> 2. Добавь интерфейс: `public interface UserRepository extends JpaRepository<User, Long> {}`
> 3. Запусти приложение: `./mvnw spring-boot:run`
> 4. Открой `http://localhost:8080/h2-console`
>     - JDBC URL: `jdbc:h2:mem:devdb`
>     - Username: `sa`
>     - Password: _(пусто)_
> 5. Выполни `SELECT * FROM user` — увидишь пустую таблицу
> 6. Создай пользователя через `POST /users` (контроллер из статьи 6.5)
> 7. Обнови `SELECT` — увидишь сохранённую строку
> 
> **Данные больше не исчезают при перезапуске!** 🎉

### 3.2. Требования к Entity-классу и почему они именно такие

**[Уровень: Junior/Middle]**

|Требование|Причина|Что сломается без него|
|---|---|---|
|Аннотация `@Entity`|Маркер для Hibernate — без неё класс игнорируется при сканировании|Таблица не создаётся, Repository не работает|
|No-args конструктор (`public` или `protected`)|Hibernate создаёт объекты через `Class.newInstance()` при загрузке из БД|`InstantiationException` при чтении из БД|
|Класс **не `final`**|Hibernate создаёт прокси-подкласс для lazy loading|Lazy loading не работает, предупреждения `HHH000`|
|Методы **не `final`**|Прокси переопределяет геттеры, перехватывая вызовы|Lazy associations не инициализируются|
|Поле с `@Id`|Каждая Entity обязана иметь первичный ключ|`AnnotationException: No identifier specified`|
|Поля **не `final`**|Hibernate устанавливает значения через рефлексию при десериализации|Невозможно загрузить Entity из БД|
|Реализация `Serializable` _(рекомендуется)_|Требование JPA-спецификации; обязательно при использовании L2-кэша или кластеризации|Проблемы с distributed кэшем и составными ключами|

> 🔬 **Под капотом:** Hibernate создаёт **прокси-подкласс** твоей Entity — примерно `User$HibernateProxyXyz extends User`. Этот класс переопределяет все геттеры: при первом вызове он обращается к БД и загружает данные (lazy loading). Именно поэтому класс и методы не могут быть `final` — подкласс обязан их переопределить. `protected` конструктор достаточен: прокси-подкласс может вызвать конструктор родителя, а `private` — нет.

### 3.3. @Table — настройки таблицы

Java

```
package com.example.demo.entity;

import jakarta.persistence.Entity;
import jakarta.persistence.Index;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;

@Entity
@Table(
    name = "users",              // Имя таблицы (без @Table = имя класса lowercase)
    schema = "public",           // Схема БД (актуально для PostgreSQL)
    uniqueConstraints = {
        @UniqueConstraint(
            name = "uk_users_email",   // Имя constraint в DDL
            columnNames = {"email"}
        )
    },
    indexes = {
        @Index(
            name = "idx_users_last_name",
            columnList = "last_name"
        )
    }
)
public class User {
    // ...
}
```

> 💡 **Важно знать:** Spring Boot по умолчанию применяет `CamelCaseToUnderscoresNamingStrategy`. Класс `UserProfile` → таблица `user_profile`, поле `firstName` → колонка `first_name`. Явная аннотация `@Table(name = "users")` переопределяет это поведение.

### 3.4. @Id и @GeneratedValue — стратегии генерации ключа

**[Уровень: Junior/Middle]**

Java

```
package com.example.demo.entity;

import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.SequenceGenerator;

// Стратегия 1: IDENTITY — БД генерирует id (AUTO_INCREMENT / SERIAL)
// Подходит для H2 и MySQL. Простая, но не поддерживает batch insert.
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Java

```
// Стратегия 2: SEQUENCE — sequence-объект в БД (рекомендуется для PostgreSQL)
// Hibernate запрашивает пачку id заранее → поддерживает batch insert.
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")
@SequenceGenerator(
    name = "user_seq",
    sequenceName = "user_id_seq",   // Имя sequence в PostgreSQL
    allocationSize = 50             // Hibernate берёт 50 id за раз
)
private Long id;
```

Java

```
// Стратегия 3: UUID — генерация UUID (Hibernate 6.x+)
// Для распределённых систем, где id генерируется до сохранения в БД.
import java.util.UUID;

@Id
@GeneratedValue(strategy = GenerationType.UUID)
private UUID id;
```

|Стратегия|СУБД|Batch INSERT|Рекомендация|
|---|---|---|---|
|`IDENTITY`|MySQL, PostgreSQL (SERIAL), H2|❌ Нет|Простые проекты, MySQL, H2 в тестах|
|`SEQUENCE`|PostgreSQL, Oracle, H2|✅ Да|**PostgreSQL — рекомендуется**|
|`TABLE`|Любая|❌ Нет|Избегать (медленно, блокировки таблицы)|
|`AUTO`|Зависит от Hibernate|Зависит|Hibernate 6: выбирает SEQUENCE (не IDENTITY!)|
|`UUID`|Любая|✅ Да|Микросервисы, распределённые системы|

> 💡 **Важно знать (Senior+):** `IDENTITY` **полностью отключает Hibernate batch insert**. При этой стратегии БД назначает `id` в момент `INSERT`, а Hibernate должен немедленно прочитать `GENERATED_KEY` — значит, каждый `INSERT` выполняется отдельным запросом. `SEQUENCE` позволяет запросить `allocationSize` id заранее одним вызовом sequence, а потом вставить все строки одним batch'ем. На 10 000 записей разница в производительности достигает **5–10x**.

> 💡 **Важно знать:** в **Hibernate 6.x** стратегия `AUTO` по умолчанию выбирает `SEQUENCE` (не `IDENTITY`, как в Hibernate 5). Это может удивить разработчиков, мигрирующих со Spring Boot 2.x на 3.x. Для предсказуемости всегда указывай стратегию явно.

## 4. Маппинг колонок: @Column и типы данных

**[Уровень: Junior]**

### 4.1. @Column — детальное управление

Java

```
package com.example.demo.entity;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Lob;
import jakarta.persistence.Table;

import java.math.BigDecimal;
import java.time.LocalDateTime;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(
        name = "email",          // Явное имя колонки в БД
        nullable = false,        // DDL: NOT NULL (не проверяет на Java-уровне!)
        unique = true,           // DDL: UNIQUE constraint
        length = 150             // VARCHAR(150) вместо дефолтного VARCHAR(255)
    )
    private String email;

    @Column(
        name = "salary",
        precision = 10,          // Всего 10 значащих цифр
        scale = 2                // 2 знака после запятой → NUMERIC(10,2)
    )
    private BigDecimal salary;   // Для денег — ВСЕГДА BigDecimal, не double!

    @Lob
    @Column(name = "bio", columnDefinition = "TEXT")
    private String bio;          // Большой текст — TEXT вместо VARCHAR

    @Column(
        name = "created_at",
        nullable = false,
        updatable = false        // После INSERT значение никогда не обновляется через JPA
    )
    private LocalDateTime createdAt;
}
```

> 💡 **Важно знать:** `@Column(nullable = false)` влияет только на **DDL-генерацию** (`NOT NULL` в `CREATE TABLE`). Для проверки на Java-уровне до выполнения SQL используй `@NotNull` из Bean Validation (статья 6.7). Лучшая практика — ставить оба.

> ⚠️ **Антипаттерн:** никогда не используй `double`/`Double` для денежных сумм. Из-за ошибок округления IEEE 754 ты потеряешь копейки. Всегда `BigDecimal` с `@Column(precision = 10, scale = 2)`.

### 4.2. Маппинг типов Java → SQL

|Java тип|PostgreSQL|H2|Примечания|
|---|---|---|---|
|`String`|`VARCHAR(255)`|`VARCHAR(255)`|`@Column(length=N)` меняет размер|
|`String` + `@Lob`|`TEXT`|`CLOB`|Для больших текстов|
|`Integer` / `int`|`INTEGER`|`INTEGER`|`int` = `NOT NULL` (примитив)|
|`Long` / `long`|`BIGINT`|`BIGINT`|Для id и больших чисел|
|`Boolean` / `boolean`|`BOOLEAN`|`BOOLEAN`|`boolean` = `NOT NULL` (примитив)|
|`BigDecimal`|`NUMERIC(p,s)`|`NUMERIC(p,s)`|`@Column(precision=, scale=)`|
|`LocalDate`|`DATE`|`DATE`|Нативно с JPA 2.2+|
|`LocalDateTime`|`TIMESTAMP`|`TIMESTAMP`|Дата + время, без timezone|
|`Instant`|`TIMESTAMP WITH TIME ZONE`|`TIMESTAMP`|**Рекомендуется** для UTC|
|`UUID`|`UUID`|`UUID`|Hibernate 6 — нативный тип|
|`Enum`|`VARCHAR` или `INT`|`VARCHAR` или `INT`|`@Enumerated` — обязательна|

## 5. @Enumerated: маппинг перечислений

**[Уровень: Junior/Middle]**

### 5.1. Enum Role

Java

```
package com.example.demo.entity;

/**
 * Роли пользователя в системе.
 * Используется в User.role с @Enumerated(EnumType.STRING).
 */
public enum Role {
    USER,
    MODERATOR,
    ADMIN
}
```

### 5.2. EnumType.STRING — правильный способ

Java

```
package com.example.demo.entity;

import jakarta.persistence.Column;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;

// В классе User:

@Enumerated(EnumType.STRING)          // В БД хранится: "USER", "ADMIN", "MODERATOR"
@Column(name = "role", nullable = false, length = 20)
private Role role;
```

В таблице `users` будет читабельно:

text

```
id │ email              │ role
───┼────────────────────┼───────────
1  │ admin@example.com  │ ADMIN
2  │ user@example.com   │ USER
3  │ mod@example.com    │ MODERATOR
```

### 5.3. EnumType.ORDINAL — опасный антипаттерн

Java

```
// ❌ НИКОГДА НЕ ДЕЛАЙ ТАК
@Enumerated(EnumType.ORDINAL)  // В БД хранится: 0, 1, 2...
private Role role;
```

> ⚠️ **Антипаттерн: `EnumType.ORDINAL` — никогда не использовать!**
> 
> Java
> 
> ```
> // БЫЛО (данные в БД: USER=0, MODERATOR=1, ADMIN=2):
> public enum Role { USER, MODERATOR, ADMIN }
> 
> // ДОБАВИЛИ роль GUEST между USER и MODERATOR:
> public enum Role { USER, GUEST, MODERATOR, ADMIN }
> //                       ↑↑↑↑
> //  Теперь: USER=0, GUEST=1, MODERATOR=2, ADMIN=3
> //
> //  Все строки в БД со значением 1 были "MODERATOR" → стали "GUEST"
> //  Все строки со значением 2 были "ADMIN"     → стали "MODERATOR"
> //
> //  Данные повреждены ТИХО: без ошибок, без исключений.
> //  Пользователи с ролью ADMIN неожиданно стали MODERATOR.
> ```

### 5.4. AttributeConverter — профессиональный подход

**[Уровень: Senior+]**

`EnumType.STRING` хранит имя значения как есть (`"ADMIN"`). `AttributeConverter` позволяет хранить **любое кастомное значение** — например, компактные коды для экономии места или совместимости с легаси-схемой:

Java

```
package com.example.demo.entity;

import jakarta.persistence.AttributeConverter;
import jakarta.persistence.Converter;

/**
 * Конвертер: Role ↔ однобуквенный код в БД.
 * USER → "U", MODERATOR → "M", ADMIN → "A"
 *
 * autoApply = true: применяется автоматически ко всем полям типа Role.
 * При использовании конвертера убери @Enumerated с поля.
 */
@Converter(autoApply = true)
public class RoleConverter implements AttributeConverter<Role, String> {

    @Override
    public String convertToDatabaseColumn(Role role) {
        if (role == null) return null;
        // Используем switch-expression (Java 14+)
        return switch (role) {
            case USER      -> "U";
            case MODERATOR -> "M";
            case ADMIN     -> "A";
        };
    }

    @Override
    public Role convertToEntityAttribute(String code) {
        if (code == null) return null;
        return switch (code) {
            case "U" -> Role.USER;
            case "M" -> Role.MODERATOR;
            case "A" -> Role.ADMIN;
            default  -> throw new IllegalArgumentException(
                "Неизвестный код роли в БД: '" + code + "'"
            );
        };
    }
}
```

При использовании `@Converter(autoApply = true)` поле в Entity не требует `@Enumerated`:

Java

```
// С autoApply = true — конвертер применяется автоматически
@Column(name = "role", length = 1)
private Role role;  // В БД: "U", "M", "A"

// Без autoApply — указывай явно:
// @Convert(converter = RoleConverter.class)
// @Column(name = "role", length = 1)
// private Role role;
```

> 💡 **Важно знать:** `AttributeConverter` полезен не только для `Enum`. Его применяют для маппинга кастомных типов (`Money`, `PhoneNumber`), шифрования полей перед сохранением, и любых преобразований Java-тип ↔ SQL-тип, которые не покрывает стандартный маппинг Hibernate.

## 6. @Embedded и @Embeddable — Value Objects

**[Уровень: Middle]**

### 6.1. Зачем нужны Value Objects

В Domain-Driven Design (DDD) **Value Object** — объект без собственного идентификатора, чья идентичность определяется совокупностью значений полей. Адрес — классический пример: два адреса `{Пушкина, 10, Москва}` — это один и тот же адрес, независимо от того, что это два разных Java-объекта.

В JPA Value Object реализуется через `@Embeddable` + `@Embedded`. Поля встраиваемого объекта хранятся **в той же таблице**, что и основная Entity. Никакой отдельной таблицы `addresses` не создаётся.

### 6.2. @Embeddable — класс Address

Java

```
package com.example.demo.entity;

import jakarta.persistence.Column;
import jakarta.persistence.Embeddable;
import java.util.Objects;

@Embeddable   // ← Этот класс можно встраивать в другие Entity
public class Address {

    // Важно: у @Embeddable НЕТ поля @Id — у Value Object нет идентификатора
    @Column(name = "street", length = 200)
    private String street;

    @Column(name = "city", nullable = false, length = 100)
    private String city;

    @Column(name = "zip_code", length = 10)
    private String zipCode;

    @Column(name = "country", length = 3)
    private String country;

    // JPA-required: конструктор без аргументов
    protected Address() {
    }

    public Address(String street, String city, String zipCode, String country) {
        this.street  = street;
        this.city    = city;
        this.zipCode = zipCode;
        this.country = country;
    }

    // Value Object неизменяем: геттеры есть, сеттеров нет
    public String getStreet()  { return street; }
    public String getCity()    { return city; }
    public String getZipCode() { return zipCode; }
    public String getCountry() { return country; }

    // Value Object: равенство по значениям ВСЕХ полей
    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Address address = (Address) o;
        return Objects.equals(street,  address.street)
            && Objects.equals(city,    address.city)
            && Objects.equals(zipCode, address.zipCode)
            && Objects.equals(country, address.country);
    }

    @Override
    public int hashCode() {
        return Objects.hash(street, city, zipCode, country);
    }
}
```

### 6.3. @Embedded в Entity

Java

```
package com.example.demo.entity;

import jakarta.persistence.Embedded;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String firstName;

    @Embedded   // Поля Address встраиваются как колонки таблицы users
    private Address address;
}
```

Hibernate создаст **одну таблицу**, где поля `Address` становятся обычными колонками:

SQL

```
-- Результирующий DDL: одна таблица, не две!
CREATE TABLE users (
    id         BIGINT GENERATED BY DEFAULT AS IDENTITY,
    first_name VARCHAR(255),
    -- Поля из @Embeddable Address (встроены сюда напрямую):
    street     VARCHAR(200),
    city       VARCHAR(100) NOT NULL,
    zip_code   VARCHAR(10),
    country    VARCHAR(3),
    PRIMARY KEY (id)
    -- Никакой таблицы addresses!
);
```

### 6.4. @AttributeOverride — два Address в одной Entity

Если у `User` есть и домашний, и рабочий адрес — имена колонок конфликтуют. `@AttributeOverride` переопределяет имена колонок для каждого вхождения:

Java

```
package com.example.demo.entity;

import jakarta.persistence.AttributeOverride;
import jakarta.persistence.AttributeOverrides;
import jakarta.persistence.Column;
import jakarta.persistence.Embedded;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    // Домашний адрес — колонки из @Embeddable: street, city, zip_code, country
    @Embedded
    private Address homeAddress;

    // Рабочий адрес — колонки переименованы через @AttributeOverride
    @Embedded
    @AttributeOverrides({
        // name = "fieldName" — имя Java-поля в @Embeddable классе
        @AttributeOverride(name = "street",  column = @Column(name = "work_street")),
        @AttributeOverride(name = "city",    column = @Column(name = "work_city")),
        @AttributeOverride(name = "zipCode", column = @Column(name = "work_zip_code")),
        @AttributeOverride(name = "country", column = @Column(name = "work_country"))
    })
    private Address workAddress;
}
```

> 💡 **Важно знать:** в `@AttributeOverride` атрибут `name` — это **имя Java-поля** в `@Embeddable` классе (`"zipCode"`), а **не** имя колонки. Атрибут `column = @Column(name = "...")` задаёт новое имя колонки в физической таблице.

## 7. Жизненный цикл Entity

### 7.1. Базовый уровень: четыре состояния

**[Уровень: Junior/Middle]**

Каждый JPA-объект в любой момент времени находится в одном из четырёх состояний:

text

```
                   entityManager.persist()
   ┌────────────────────────────────────────────────┐
   │                                                ▼
┌──────────┐                              ┌──────────────────┐
│   NEW    │                              │    MANAGED       │
│(Transient)│                             │   (Persistent)   │◄─ findById()
└──────────┘                              └──────────────────┘◄─ JPQL query
 new User()                               Hibernate следит за    ◄─ merge()
 Объект создан,                           ВСЕМИ изменениями
 БД не знает                              (dirty checking)
                                               │         │
                                   remove()    │         │ detach()
                                               ▼         │ clear()
                                        ┌──────────┐     │ close()
                                        │ REMOVED  │     │
                                        └──────────┘     ▼
                                        Помечен на   ┌──────────┐
                                        удаление.    │ DETACHED │
                                        При flush → │          │
                                        DELETE в БД  └──────────┘
                                                     Имеет id, но
                                                     изменения НЕ
                                                     отслеживаются.
                                                     merge() → MANAGED
```

|Состояние|Что это|Dirty Checking|В Persistence Context|
|---|---|---|---|
|**NEW**|`new User()`, БД не знает об объекте|Нет|Нет|
|**MANAGED**|Привязан к `EntityManager`, все изменения отслеживаются|**Да**|**Да**|
|**DETACHED**|Был managed, `EntityManager` закрыт или вызван `detach()`|Нет|Нет|
|**REMOVED**|Помечен на удаление, при `flush()` → `DELETE`|Да|Да|

**Самое важное для практики — dirty checking:**

Java

```
package com.example.demo.service;

import com.example.demo.repository.UserRepository;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class UserService {

    private final UserRepository userRepository;

    public UserService(UserRepository userRepository) {
        this.userRepository = userRepository;
    }

    @Transactional // Открывает транзакцию и Persistence Context
    public void deactivateUser(Long id) {
        User user = userRepository.findById(id).orElseThrow();
        // user — MANAGED: Hibernate запомнил снимок его состояния

        user.setActive(false);
        // Hibernate обнаружил изменение через dirty checking

        // НЕ НУЖНО вызывать: userRepository.save(user);  ← лишний вызов!

    } // ← Конец @Transactional: Hibernate выполнит flush() → commit()
      //   → UPDATE users SET active = false WHERE id = ?
}
```

---

✅ **Чекпоинт:** пока объект MANAGED (внутри `@Transactional`), любые изменения полей автоматически попадают в БД. Повторный `save()` внутри транзакции — лишний вызов.

### 7.2. Под капотом: Persistence Context и First Level Cache

**[Уровень: Senior]**

> 🔬 **Под капотом**
> 
> **Persistence Context** — рабочая область Hibernate в рамках одной транзакции. Он хранит:
> 
> 1. Все MANAGED Entity (карта: id → объект)
> 2. **Снимки (snapshots)** — копии состояния каждой Entity в момент загрузки
> 
> При `flush()` (который вызывается перед `commit()`) Hibernate сравнивает текущее состояние каждого MANAGED объекта со снимком. Если поля изменились — генерирует `UPDATE` только для изменённых колонок. Это и есть **dirty checking**.
> 
> Persistence Context также является **First Level Cache (L1)**: если вызвать `findById(1L)` дважды в одной транзакции — второй вызов вернёт объект из памяти без SQL-запроса:
> 
> Java
> 
> ```
> @Transactional
> public void example(Long id) {
>     User u1 = repository.findById(id).orElseThrow(); // SQL: SELECT * FROM users WHERE id=?
>     User u2 = repository.findById(id).orElseThrow(); // Из L1-кэша, без SQL!
>     System.out.println(u1 == u2); // true — один и тот же объект в памяти!
> }
> ```
> 
> После закрытия `EntityManager` (конец транзакции) все MANAGED Entity становятся DETACHED. Изменения detached-объекта не попадут в БД без явного `merge()`.
> 
> Именно поэтому `spring.jpa.open-in-view=false` важен: OSIV держит `EntityManager` открытым вплоть до рендера HTTP-ответа, маскируя `LazyInitializationException` и провоцируя непредсказуемые запросы на уровне View.

## 8. Lifecycle Callbacks

**[Уровень: Middle]**

JPA позволяет выполнять произвольный код при событиях жизненного цикла Entity:

|Аннотация|Когда вызывается|Типичный use case|
|---|---|---|
|`@PrePersist`|До первого `INSERT`|Установить `createdAt`, сгенерировать slug|
|`@PostPersist`|После `INSERT` (id уже присвоен)|Логирование, отправка доменного события|
|`@PreUpdate`|До `UPDATE` изменённой MANAGED Entity|Обновить `updatedAt`|
|`@PostUpdate`|После `UPDATE`|Аудит изменений|
|`@PreRemove`|До `DELETE`|Проверки перед удалением|
|`@PostRemove`|После `DELETE`|Очистка связанных ресурсов|
|`@PostLoad`|После загрузки Entity из БД|Инициализация `@Transient` полей|

Java

```
package com.example.demo.entity;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.PostLoad;
import jakarta.persistence.PrePersist;
import jakarta.persistence.PreUpdate;
import jakarta.persistence.Table;
import jakarta.persistence.Transient;

import java.time.LocalDateTime;

@Entity
@Table(name = "users")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String firstName;
    private String lastName;

    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @Column(name = "updated_at")
    private LocalDateTime updatedAt;

    // @Transient — поле НЕ маппится ни на какую колонку в БД
    @Transient
    private String displayName;

    // ── Lifecycle Callbacks ───────────────────────────────────────

    @PrePersist
    protected void onCreate() {
        // Вызывается ОДИН РАЗ — перед первым INSERT
        this.createdAt = LocalDateTime.now();
        this.updatedAt = LocalDateTime.now();
    }

    @PreUpdate
    protected void onUpdate() {
        // Вызывается перед каждым UPDATE (только если Entity изменилась!)
        this.updatedAt = LocalDateTime.now();
    }

    @PostLoad
    protected void onLoad() {
        // Вызывается после загрузки из БД — удобно для вычисляемых полей
        this.displayName = firstName + " " + lastName;
    }

    // Конструкторы, геттеры, сеттеры...
    protected User() {}

    public Long getId()           { return id; }
    public String getFirstName()  { return firstName; }
    public void setFirstName(String v) { this.firstName = v; }
    public String getLastName()   { return lastName; }
    public void setLastName(String v)  { this.lastName = v; }
    public LocalDateTime getCreatedAt() { return createdAt; }
    public LocalDateTime getUpdatedAt() { return updatedAt; }
    public String getDisplayName()      { return displayName; }
}
```

> 💡 **Важно знать:** `@PreUpdate` вызывается **только** если Hibernate обнаружил хотя бы одно изменение через dirty checking. Если поля Entity не изменились — `UPDATE` не выполняется и `@PreUpdate` не вызывается.

## 9. Equals, hashCode и toString

**[Уровень: Middle/Senior]**

Это самая коварная тема в JPA. Неправильная реализация приводит к трудноуловимым багам в продакшене.

### 9.1. Три сценария, почему всё ломается

**Сценарий 1: объект «теряется» в `HashSet` после `save()`**

text

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│  User user = new User("John", "Doe");                                   │
│       └─► id = null                                                     │
│       └─► hashCode = Objects.hash(null) = 0   ← bucket[0]              │
│                                                                         │
│  Set<User> pendingUsers = new HashSet<>();                               │
│  pendingUsers.add(user);          // добавлен в bucket[0]               │
│  pendingUsers.contains(user);     // ✅ true                            │
│                                                                         │
│  repository.save(user);           // id теперь = 42!                   │
│       └─► hashCode = Objects.hash(42) = ???  ← другой bucket!          │
│                                                                         │
│  pendingUsers.contains(user);     // ❌ FALSE — объект «потерялся»!    │
│                                   // Ищем в bucket[???], он в bucket[0] │
└─────────────────────────────────────────────────────────────────────────┘
```

**Сценарий 2: `@Data` на Entity с двунаправленными связями → `StackOverflowError`**

text

```
user.toString()
  │
  └─► "User{id=1, orders=" + orders.toString()
                                     │
                                     └─► orders.get(0).toString()
                                                  │
                                                  └─► "Order{id=10, user=" + user.toString()
                                                                                   │
                                                                                   └─► "User{id=1, orders=" + ...
                                                                                                         │
                                                                                                         ↻ БЕСКОНЕЧНО

java.lang.StackOverflowError
```

**Сценарий 3: `@Data` и два новых объекта с `id = null` → некорректное равенство**

Java

```
// @Data генерирует equals по ВСЕМ полям, включая id
User user1 = new User("John", "Doe", "john@mail.com"); // id = null
User user2 = new User("John", "Doe", "john@mail.com"); // id = null

// user1.equals(user2) → true ← ЭТО РАЗНЫЕ ПОЛЬЗОВАТЕЛИ!
// При добавлении в Set они «склеятся» в один объект

Set<User> batch = new HashSet<>();
batch.add(user1);
batch.add(user2);
System.out.println(batch.size()); // 1 — вместо ожидаемых 2!
```

### 9.2. Правильная реализация: по id с константным hashCode

Java

```
package com.example.demo.entity;

import java.util.Objects;

// Фрагмент класса User

@Override
public boolean equals(Object o) {
    if (this == o) return true;
    // getClass() вместо instanceof — для корректной работы с Hibernate Proxy
    // (proxy — это подкласс User, instanceof вернул бы true даже для прокси)
    if (o == null || getClass() != o.getClass()) return false;
    User user = (User) o;
    // id == null → два NEW объекта НЕ равны (правильно: это разные сущности)
    // id != null → сравниваем по первичному ключу
    return id != null && id.equals(user.id);
}

@Override
public int hashCode() {
    // КОНСТАНТА — стабильна при переходе NEW (id=null) → MANAGED (id=42)
    // Без константного hashCode объект «потеряется» в HashSet после save()
    // Недостаток: O(n) поиск в HashMap вместо O(1) при большом числе объектов
    // На практике: коллекции Entity редко превышают тысячи элементов — приемлемо
    return getClass().hashCode();
}
```

### 9.3. Альтернатива: по Natural Key (business key)

Если у Entity есть уникальное неизменяемое бизнес-поле (email, ISBN, ИНН):

Java

```
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    User user = (User) o;
    return email != null && email.equals(user.email);
    // email — уникален, задаётся при создании объекта, не изменяется
}

@Override
public int hashCode() {
    return Objects.hash(email); // Стабилен: email задаётся до persist()
}
```

### 9.4. Безопасный toString

Java

```
@Override
public String toString() {
    // ✅ ВКЛЮЧАТЬ: id, String-поля, enum, примитивы
    // ❌ НЕ ВКЛЮЧАТЬ: @OneToMany коллекции, @ManyToMany, lazy @ManyToOne
    return "User{" +
           "id=" + id +
           ", email='" + email + '\'' +
           ", role=" + role +
           ", active=" + active +
           '}';
    // НИКОГДА: + ", orders=" + orders
    //   → вне транзакции: LazyInitializationException
    //   → внутри транзакции: N+1 запросов при каждом логировании
}
```

## 10. Lombok и JPA: правильный набор

**[Уровень: Middle]**

### 10.1. Почему @Data — антипаттерн для Entity

> ⚠️ **Антипаттерн: `@Data` на `@Entity` — никогда!**
> 
> `@Data` генерирует сразу:
> 
> - `equals`/`hashCode` по **всем** полям → `StackOverflowError` при двунаправленных связях (сценарий 2 из раздела 9.1)
> - `toString` со **всеми** полями → `LazyInitializationException` при логировании вне транзакции
> - `@RequiredArgsConstructor` → нет no-args конструктора → `InstantiationException` при загрузке из БД

### 10.2. Правильный набор аннотаций

Java

```
package com.example.demo.entity;

import jakarta.persistence.Column;
import jakarta.persistence.Embedded;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;
import lombok.AccessLevel;
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.EqualsAndHashCode;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import lombok.ToString;

@Entity
@Table(
    name = "users",
    uniqueConstraints = {
        @UniqueConstraint(name = "uk_users_email", columnNames = "email")
    }
)
@Getter                                                // Генерирует все геттеры
@Setter                                                // Генерирует все сеттеры
@NoArgsConstructor(access = AccessLevel.PROTECTED)     // JPA-required; protected = достаточно
@AllArgsConstructor                                    // Нужен для @Builder
@Builder                                               // Паттерн Builder для создания объектов
@ToString                                              // Добавь exclude для lazy-коллекций!
@EqualsAndHashCode(onlyExplicitlyIncluded = true)      // Только помеченные поля
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include   // Только id участвует в equals/hashCode
    private Long id;

    @Column(name = "first_name", nullable = false, length = 50)
    private String firstName;

    @Column(name = "last_name", nullable = false, length = 50)
    private String lastName;

    @Column(name = "email", nullable = false, unique = true, length = 150)
    private String email;

    @Column(name = "password_hash", nullable = false)
    private String passwordHash;

    @Enumerated(EnumType.STRING)
    @Column(name = "role", nullable = false, length = 20)
    private Role role;

    @Embedded
    private Address address;

    @Column(name = "active", nullable = false)
    @Builder.Default   // Значение по умолчанию при использовании @Builder
    private boolean active = true;
}
```

> 💡 **Важно знать:** `@Builder` создаёт конструктор со всеми параметрами и **удаляет** конструктор по умолчанию. Именно поэтому нужны **оба**: `@NoArgsConstructor` (для JPA) и `@AllArgsConstructor` (для `@Builder`). Если написать только `@Builder` без `@NoArgsConstructor` — получишь `InstantiationException` при загрузке Entity из БД.

|Аннотация|Безопасна для Entity?|Причина|
|---|---|---|
|`@Getter`|✅ Да|Просто геттеры — безопасно|
|`@Setter`|✅ Да|Просто сеттеры — безопасно|
|`@NoArgsConstructor(PROTECTED)`|✅ Да|JPA-required конструктор|
|`@AllArgsConstructor`|✅ Да|Для `@Builder`|
|`@Builder` (с `@NoArgsConstructor` + `@AllArgsConstructor`)|✅ Да|Без пары — нет no-args|
|`@ToString(exclude = {"orders"})`|✅ Да|Без `exclude` → `LazyInitializationException`|
|`@EqualsAndHashCode(onlyExplicitlyIncluded = true)`|✅ Да|Контролируемые поля|
|**`@Data`**|❌ **Никогда**|`StackOverflowError`, `LazyInitializationException`, нарушение контракта `equals`|
|`@Value`|❌ Нет|Делает класс и поля `final` → Hibernate не может создать прокси|
|`@RequiredArgsConstructor` (без `@NoArgsConstructor`)|❌ Нет|Нет no-args конструктора|

## 11. Spring Data Auditing

**[Уровень: Senior]**

Spring Data Auditing автоматически заполняет поля `createdAt` / `updatedAt` — без ручного `@PrePersist` / `@PreUpdate` в каждой Entity.

### 11.1. Конфигурационный класс

Java

### 11.2. BaseEntity — базовый класс с аудитом

Java

```
package com.example.demo.entity;

import jakarta.persistence.Column;
import jakarta.persistence.EntityListeners;
import jakarta.persistence.MappedSuperclass;
import lombok.Getter;
import lombok.Setter;
import org.springframework.data.annotation.CreatedDate;
import org.springframework.data.annotation.LastModifiedDate;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

import java.time.LocalDateTime;

@MappedSuperclass                                   // Не создаёт свою таблицу; поля наследуются
@EntityListeners(AuditingEntityListener.class)      // Spring Data заполняет аудит-поля
@Getter
@Setter
public abstract class BaseEntity {

    @CreatedDate                                    // Spring Data заполнит при persist()
    @Column(name = "created_at", nullable = false, updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate                               // Spring Data обновит при каждом update()
    @Column(name = "updated_at")
    private LocalDateTime updatedAt;
}
```

### 11.3. User extends BaseEntity

Java

```

## 12. ddl-auto: управление схемой

**[Уровень: Middle/Senior]**

|Значение|Что делает|Когда использовать|
|---|---|---|
|`create`|DROP ALL + CREATE (данные теряются!)|Только local dev|
|`create-drop`|Как `create` + DROP при shutdown|Тесты, демонстрации|
|`update`|Добавляет новые колонки/таблицы, НЕ удаляет старые|⚠️ Никогда в production|
|`validate`|Только проверяет соответствие Entity и схемы; ничего не меняет|✅ Production (с Flyway)|
|`none`|Hibernate не трогает схему|Production (ручной DDL)|

> ⚠️ **Антипаттерн: `ddl-auto=update` в production**
> 
> На первый взгляд удобно: добавил поле в Entity — колонка появилась в БД. Но:
> 
> - **Не удаляет** колонки при удалении полей из Entity → мусор в схеме навсегда
> - **Не переименовывает**: `name → fullName` создаст новую пустую колонку `full_name`, старая `name` останется с данными → данные потеряны для приложения
> - **Нет rollback**: если что-то пошло не так — откатить схему невозможно
> - **Нет code review**: изменения схемы не проходят ревью как обычный код
> - **Расхождение сред**: staging и production могут накопить разные схемы

> 💡 **Важно знать: правильный путь — Flyway или Liquibase**
> 
> text
> 
> ```
> src/main/resources/db/migration/
> ├── V1__create_users_table.sql      ← Создаём таблицу users
> ├── V2__add_address_columns.sql     ← Добавляем колонки Address
> └── V3__add_index_on_email.sql      ← Добавляем индекс по email
> ```
> 
> Каждый файл — версионированная SQL-миграция. Flyway выполняет их по порядку, отслеживает что уже применено, не позволяет изменить уже применённый файл. Это как Git для схемы базы данных.
> 
> **В статье 6.11** разберём управление схемой через Flyway: настройка CI/CD pipeline с автоматическими миграциями, откат изменений, baseline для существующих баз.

**Рекомендация по среде:**

text

```
Local dev  →  ddl-auto=create-drop + H2       (быстрая итерация)
CI / Tests →  ddl-auto=create-drop + H2       (изолированные тесты)
Staging    →  ddl-auto=validate   + Flyway    (идентично production)
Production →  ddl-auto=validate   + Flyway    (единственный правильный вариант)
```

## 13. Полная Entity: собираем всё вместе

**[Уровень: Junior/Middle]**

> 💡 **Связь с предыдущими статьями:** это тот же `User` из статей 6.6 (DTO и маппинг) и 6.7 (валидация). Теперь к нему добавились JPA-аннотации. `UserService` больше не хранит пользователей в `HashMap` — он использует `UserRepository` с настоящей БД.

Java

```
package com.example.demo.entity;

import jakarta.persistence.Column;
import jakarta.persistence.Embedded;
import jakarta.persistence.Entity;
import jakarta.persistence.EntityListeners;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.Index;
import jakarta.persistence.Table;
import jakarta.persistence.UniqueConstraint;
import jakarta.persistence.Version;
import lombok.AccessLevel;
import lombok.AllArgsConstructor;
import lombok.Builder;
import lombok.EqualsAndHashCode;
import lombok.Getter;
import lombok.NoArgsConstructor;
import lombok.Setter;
import lombok.ToString;
import org.springframework.data.jpa.domain.support.AuditingEntityListener;

@Entity
@Table(
    name = "users",
    uniqueConstraints = {
        @UniqueConstraint(name = "uk_users_email", columnNames = "email")
    },
    indexes = {
        @Index(name = "idx_users_last_name", columnList = "last_name")
    }
)
@EntityListeners(AuditingEntityListener.class)        // Включаем Spring Data Auditing
@Getter
@Setter
@NoArgsConstructor(access = AccessLevel.PROTECTED)    // JPA-required
@AllArgsConstructor                                   // Для @Builder
@Builder
@ToString                                             // Добавь exclude при появлении связей!
@EqualsAndHashCode(onlyExplicitlyIncluded = true)
public class User extends BaseEntity {                // createdAt, updatedAt из BaseEntity

    // ── Первичный ключ ─────────────────────────────────────────────
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    @EqualsAndHashCode.Include
    private Long id;

    // ── Основные поля ──────────────────────────────────────────────
    @Column(name = "first_name", nullable = false, length = 50)
    private String firstName;

    @Column(name = "last_name", nullable = false, length = 50)
    private String lastName;

    @Column(name = "email", nullable = false, unique = true, length = 150)
    private String email;

    @Column(name = "password_hash", nullable = false)
    private String passwordHash;

    // ── Enum (всегда STRING!) ──────────────────────────────────────
    @Enumerated(EnumType.STRING)
    @Column(name = "role", nullable = false, length = 20)
    private Role role;

    // ── Value Object (@Embedded) ───────────────────────────────────
    @Embedded                      // Поля Address → колонки таблицы users
    private Address address;

    // ── Флаг активности ───────────────────────────────────────────
    @Column(name = "active", nullable = false)
    @Builder.Default
    private boolean active = true;

    // ── Оптимистичная блокировка ───────────────────────────────────
    @Version                       // Hibernate инкрементирует при каждом UPDATE
    @Column(name = "version")
    private Long version;

    // createdAt, updatedAt — из BaseEntity, заполняются Spring Data Auditing
}
```

SQL

```

## 14. Тестирование Entity

**[Уровень: Senior]**

### 14.1. Что такое @DataJpaTest

`@DataJpaTest` — тест-слайс Spring Boot, который загружает только JPA-слой:

|Что загружает|Что НЕ загружает|
|---|---|
|`@Entity` классы|`@Service`, `@Component`|
|`@Repository` интерфейсы|`@Controller`, `@RestController`|
|`EntityManager`, `DataSource`|`@Configuration` (кроме JPA)|
|**H2 in-memory** (по умолчанию)|Внешние HTTP-запросы|
|Транзакция с **автоматическим rollback**|Kafka, Redis, etc.|

### 14.2. Полный тест UserRepository

Java

```
package com.example.demo.repository;

import com.example.demo.config.JpaAuditingConfig;
import com.example.demo.entity.Address;
import com.example.demo.entity.Role;
import com.example.demo.entity.User;
import jakarta.persistence.PersistenceException;
import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;
import org.springframework.context.annotation.Import;

import java.time.LocalDateTime;
import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

@DataJpaTest
@Import(JpaAuditingConfig.class)  // Явно импортируем: @DataJpaTest не сканирует @Configuration
class UserRepositoryTest {

    @Autowired
    private TestEntityManager entityManager;  // Обёртка над JPA EntityManager для тестов

    @Autowired
    private UserRepository userRepository;

    // ── Вспомогательный метод ──────────────────────────────────────

    private User buildUser(String email) {
        return User.builder()
                .firstName("John")
                .lastName("Doe")
                .email(email)
                .passwordHash("$2a$10$hashedPassword")
                .role(Role.USER)
                .address(new Address("123 Main St", "Austin", "78701", "US"))
                .build();
    }

    // ── Тест 1: persist и генерация id ────────────────────────────

    @Test
    @DisplayName("Должен сохранить User и сгенерировать id")
    void shouldPersistUserAndGenerateId() {
        // given
        User user = buildUser("john@example.com");

        // when
        User saved = entityManager.persistAndFlush(user);

        // then
        assertThat(saved.getId()).isNotNull().isPositive();
        assertThat(saved.getEmail()).isEqualTo("john@example.com");
        assertThat(saved.getRole()).isEqualTo(Role.USER);
        assertThat(saved.isActive()).isTrue();
    }

    // ── Тест 2: Spring Data Auditing ──────────────────────────────

    @Test
    @DisplayName("Spring Data Auditing должен заполнить createdAt автоматически")
    void shouldSetCreatedAtViaAuditing() {
        // given
        LocalDateTime before = LocalDateTime.now().minusSeconds(1);
        User user = buildUser("audit@example.com");

        // when
        entityManager.persistAndFlush(user);

        // then
        LocalDateTime after = LocalDateTime.now().plusSeconds(1);
        assertThat(user.getCreatedAt())
                .isNotNull()
                .isAfter(before)
                .isBefore(after);
        assertThat(user.getUpdatedAt())
                .isNotNull();
    }

    // ── Тест 3: unique constraint ─────────────────────────────────

    @Test
    @DisplayName("Должен выбросить исключение при дублировании email")
    void shouldFailOnDuplicateEmail() {
        // given — сохраняем первого пользователя
        entityManager.persistAndFlush(buildUser("duplicate@example.com"));

        // when/then — второй с тем же email → нарушение unique constraint
        assertThatThrownBy(() ->
                entityManager.persistAndFlush(buildUser("duplicate@example.com"))
        ).isInstanceOf(PersistenceException.class);
        // PersistenceException — базовый класс для constraint violation
        // DataIntegrityViolationException — Spring-обёртка, тоже допустима
    }

    // ── Тест 4: @Enumerated(STRING) ───────────────────────────────

    @Test
    @DisplayName("Role должна храниться в БД как строка (не число)")
    void shouldMapEnumAsString() {
        // given
        User user = buildUser("admin@example.com");
        user.setRole(Role.ADMIN);
        entityManager.persistAndFlush(user);

        // КЛЮЧЕВОЙ МОМЕНТ: clear() сбрасывает L1-кэш (First Level Cache)
        // Без этого findByEmail вернёт объект из памяти, не из H2!
        entityManager.clear();

        // when — загружаем из реальной БД
        User loaded = userRepository.findByEmail("admin@example.com").orElseThrow();

        // then
        assertThat(loaded.getRole()).isEqualTo(Role.ADMIN);

        // Дополнительно: проверяем физическое значение в БД через native SQL
        String dbValue = (String) entityManager.getEntityManager()
                .createNativeQuery("SELECT role FROM users WHERE email = ?1")
                .setParameter(1, "admin@example.com")
                .getSingleResult();
        assertThat(dbValue).isEqualTo("ADMIN"); // Строка, не число!
    }

    // ── Тест 5: @Embedded Address ─────────────────────────────────

    @Test
    @DisplayName("Должен сохранить и загрузить встроенный Address")
    void shouldPersistAndRetrieveEmbeddedAddress() {
        // given
        Address address = new Address("456 Oak Ave", "Portland", "97201", "US");
        User user = buildUser("portland@example.com");
        user.setAddress(address);

        entityManager.persistAndFlush(user);
        entityManager.clear(); // Сбрасываем L1-кэш перед загрузкой из H2

        // when
        User loaded = userRepository.findByEmail("portland@example.com").orElseThrow();

        // then
        assertThat(loaded.getAddress()).isNotNull();
        assertThat(loaded.getAddress().getCity()).isEqualTo("Portland");
        assertThat(loaded.getAddress().getZipCode()).isEqualTo("97201");
        assertThat(loaded.getAddress()).isEqualTo(address); // Value Object: equals по полям
    }

    // ── Тест 6: NOT NULL constraint ───────────────────────────────

    @Test
    @DisplayName("Должен выбросить исключение при null firstName")
    void shouldFailOnNullFirstName() {
        // given
        User user = User.builder()
                .firstName(null)       // @Column(nullable = false) → NOT NULL в DDL
                .lastName("Doe")
                .email("null@example.com")
                .passwordHash("hash")
                .role(Role.USER)
                .build();

        // when/then
        assertThatThrownBy(() -> entityManager.persistAndFlush(user))
                .isInstanceOf(PersistenceException.class);
    }

    // ── Тест 7: query method findByEmail ─────────────────────────

    @Test
    @DisplayName("Должен найти пользователя по email")
    void shouldFindByEmail() {
        // given
        entityManager.persistAndFlush(buildUser("findme@example.com"));

        // when
        Optional<User> found = userRepository.findByEmail("findme@example.com");

        // then
        assertThat(found).isPresent();
        assertThat(found.get().getFirstName()).isEqualTo("John");
    }

    @Test
    @DisplayName("Должен вернуть пустой Optional для несуществующего email")
    void shouldReturnEmptyForNonExistentEmail() {
        assertThat(userRepository.findByEmail("nobody@example.com")).isEmpty();
    }
}
```

> 💡 **Важно знать:** паттерн `persistAndFlush(entity)` → `entityManager.clear()` → `findBy...()` — ключевой приём в тестах маппинга. `persistAndFlush()` сохраняет данные в H2 и синхронизирует SQL. `clear()` сбрасывает L1-кэш, принудительно заставляя следующий `find` читать из реальной H2, а не из памяти. Без `clear()` тест проверяет кэш, а не маппинг.

## 15. Типичные ошибки

**[Уровень: Middle]**

|Ошибка|Симптом|Решение|
|---|---|---|
|Нет no-args конструктора|`InstantiationException` при загрузке из БД|Добавить `protected User() {}`|
|`final` класс Entity|Lazy loading не работает, предупреждения `HHH000`|Убрать `final` с класса и методов|
|`@Data` на Entity|`StackOverflowError`, `LazyInitializationException` при логировании|`@Getter @Setter @ToString(exclude=...) @EqualsAndHashCode(onlyExplicit...)`|
|`EnumType.ORDINAL`|Данные ломаются при добавлении значений в Enum|`EnumType.STRING`|
|`ddl-auto=update` в prod|Потеря данных при переименовании, мусорные колонки|`validate` + Flyway|
|`LazyInitializationException`|Обращение к lazy-коллекции вне транзакции|`JOIN FETCH`, `@EntityGraph`, маппинг в DTO внутри `@Transactional`|
|`@Column(nullable=false)` без `@NotNull`|`NULL` попадает в БД с ошибкой уровня СУБД|Добавить `@NotNull` из Bean Validation|
|`open-in-view=true` (default!)|N+1 запросов в View, утечка DB-соединений|`spring.jpa.open-in-view=false`|
|`@Builder` без `@NoArgsConstructor`|`InstantiationException` при загрузке из БД|Оба: `@NoArgsConstructor` + `@AllArgsConstructor` + `@Builder`|
|`javax.persistence.*` вместо `jakarta.persistence.*`|`ClassNotFoundException` при запуске|Заменить все импорты на `jakarta.persistence.*`|

### Практическое задание

Создай Entity `Product` с полным набором аннотаций:

text

```
Product:
├── id             (Long, IDENTITY)
├── name           (String, не null, длина до 200)
├── price          (BigDecimal, precision=10, scale=2)
├── category       (Enum: ELECTRONICS, CLOTHING, FOOD, BOOKS)
├── sku            (String, уникальный бизнес-ключ / natural key)
├── active         (boolean, default true)
├── createdAt      (через Spring Data Auditing)
├── updatedAt      (через Spring Data Auditing)
└── dimensions     (@Embedded):
    ├── widthCm    (Double)
    ├── heightCm   (Double)
    └── weightKg   (Double)
```

**Требования к реализации:**

1. `Category` — `@Enumerated(EnumType.STRING)`
2. `Dimensions` — отдельный `@Embeddable` класс с конструктором, геттерами и `equals`/`hashCode`
3. `equals`/`hashCode` для `Product` — по полю `sku` (natural key), `hashCode = Objects.hash(sku)`
4. Lombok: правильный набор без `@Data`
5. `Product` extends `BaseEntity` (для аудита)

**Требования к тестам (`@DataJpaTest`):**

1. Продукт сохраняется с корректным `createdAt` (через аудит)
2. Дублирование `sku` выбрасывает `PersistenceException`
3. `Category` хранится в БД как строка (проверить через native SQL: `SELECT category FROM products WHERE sku = ?`)
4. `Dimensions` корректно сохраняются и загружаются (с `entityManager.clear()` перед загрузкой)
